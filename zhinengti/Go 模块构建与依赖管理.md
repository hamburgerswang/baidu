Go 模块构建与依赖管理

# 一、历史：Go 依赖管理的变迁
Go 语言的依赖管理经历了几个重要的阶段，每一次变化都是为了解决上一代方案的痛点，最终目标是实现 **可重现的构建（Reproducible Builds）** 和 **版本精确控制**。

## 1.1 GOPATH 时代
在 Go 1.5 之前，Go 语言主要依赖 `GOPATH` 环境变量。

* **机制：** 所有 Go 项目的代码、依赖包和编译产物都存储在 `$GOPATH/src`、`$GOPATH/pkg` 和 `$GOPATH/bin` 目录下。
* **痛点：**
    * **无法锁定依赖版本 ：**
        * 所有的依赖都去 GOPATH/src 目录寻找
        * 每次拉取代码时获取到的都是 master 分支的最新代码
        * 在不同人的机器上使用的依赖库可能版本不一样

    * **依赖冲突：**
        * A项目 依赖 C v1.0 版本
        * B项目 依赖 C v2.0 版本
        * GOPATH 下的 C 只能有一个，这种情况无法解决

    * **菱形依赖**
        * 没有版本概念，当依赖同一个库的多个版本时，无法解决
            * app 依赖库 A, B
            * A 依赖 C v1.0 版本
            * B 依赖 C v2.0 版本
            * GOPATH 下的 C 只能有一个，这种情况无法解决




## 1.2 Vendor 机制
为了解决 GOPATH 的全局依赖问题，社区引入了 `vendor` 目录机制。在Go 1.5 以实验性功能引入，Go 1.6 正式开启。

* **机制：** 在项目根目录下创建一个 `vendor` 目录，将项目所需的所有依赖库的特定版本副本放在该目录下。
* **优先级：** `go build` 等命令会优先查找项目目录下的 `vendor` 文件夹中的包，如果找不到，才会去 `$GOPATH` 中寻找。
* **解决问题：**
    * 可复现构建
        * 由于依赖库存放在 vendor 目录，并提交到代码仓库中，所有人 clone 后的代码使用的是相同的依赖，所以可以构建出相同的包；

    * 依赖冲突问题
        * A 项目的 vendor 目录存放其依赖的 C v1.0 版本
        * B 项目的 vendor 目录存在其依赖的 C v2.0 版本

    * 摆脱了对依赖项目的实时依赖
        * 因为依赖的源码已经包含在 vendor 目录下，即使原项目被删库，依然不影响项目的编译运行；


* **痛点：**
    * **代码仓库膨胀：** 依赖包的完整副本被复制到每个项目中，导致项目仓库体积增大。
    * **生态化碎片：** Go 官方只提供了 vendor 机制，没有提供管理 vendor 目录的官方工具，社区出现大量三方工具，如：godep, govender, glide, gb 等，每个工具都有自己的元数据文件和工作流，导致社区生态碎片化；


## 1.3 dep 尝试
为了解决 vendor 工具链生态碎片化的问题，Go 官方团队在社区的号召下成立了一个委员会，启动一个官方的”实验性“项目，旨在为社区提供一个统一的依赖管理工具，这个项目的成果就是 dep;

### dep 的核心设计
引入了两个核心的元数据文件：

* **Gopkg.toml** 类似与 go.mod 是一个清单文件，有开发者手动维护。用来声明项目的直接依赖以及版本约束。

```toml
# Gopkg.toml 示例
[[constraint]]
name = "github.com/gin-gonic/gin"
version = "1.3.0"
```
* **Gopkg.lock** 这个是有 dep 工具自动生成的锁文件。会根据 Gopkg.toml 中的约束，计算出一个满足所有条件的、确切的依赖版本树（包含所有直接依赖和间接依赖），并将每个依赖的具体 `commit hash` 锁定下来

```toml
[[projects]]
name = "github.com/gin-gonic/gin"
version = "1.3.0"
revision="2312xxxxx"
packages=["."]
```
开发者将这两个文件提交到 Git 。当其他成员拉取代码后，只需要运行 `dep ensure` , dep 就会根据`Gopkg.lock` 文件，下载完全一致的依赖版本到 vendor 目录。

### dep 的优点和痛点
|**方面**|**优点(没有 lock 文件的情况)**|**痛点（Go 社区转向 MVS 的原因）**|
|-|-|-|
|**版本新旧**|始终使用依赖的最新特性和安全补丁，减少技术债务。|**易导致版本漂移 (Version Drift) **。如果依赖 C 后来发布了 1.6.0，下次构建时 `dep` 会自动升级到 1.6.0，可能破坏构建的可重现性。|
|**兼容性**|鼓励开发者使用最新 API，更容易发现依赖之间的兼容性问题。|**引入新的 Bug 风险大**。如果没有新的依赖约束，使用最新版会引入未经过您项目充分测试的新功能或 Bug。|
|**解决冲突**|冲突解决相对直观（总是选最高的）。|**“依赖地狱” (Dependency Hell) **难以解决，即当间接依赖链非常复杂时，很难找到一个同时满足所有最高约束的版本。|

### dep 没有成为最终方案的原因？
`dep` 在当时非常受欢迎，甚至被官方 Wiki 推荐。但最终，Go 核心团队（特别是 Go 语言负责人 Russ Cox）提出了完全不同的设计理念（即后来的 Go Modules），导致 `dep` 被弃用。

主要原因有两点：

#### A. 算法之争：SAT 求解器 vs MVS
* `dep`** (以及 Glide, npm, Cargo)** 使用的是 **SAT 求解器**。
    * **逻辑**：它会试图满足你在 `Gopkg.toml` 里写的所有约束，寻找一个“完美解”。
    * **缺点**：这是一个 NP-Hard 问题（计算复杂度极高）。随着依赖树变大，计算依赖关系会变得非常慢，甚至无解。而且它倾向于使用“符合要求的最新版”  **(最大版本选择)**，这有时会引入潜在的破坏性更新。

* **Go Modules** 使用的是 **MVS (Minimal Version Selection, 最小版本选择)**。
    * **逻辑**：不找最新版，而是找“能满足需求的**最老**版本”。
    * **优点**：算法极其简单、快速，且具有极高的确定性和稳定性（High Fidelity Builds）。


#### 示例：
假设：

* 项目 app 依赖模块 A,B
* A 依赖模块 C 的版本 >= 1.2.0
* B 依赖模块 C 的版本 >= 1.3.0
* C 的最新可用版本 1.5.0

|**工具**|**算法策略**|**结果选择**|**解释**|
|-|-|-|-|
|`dep`|最大版本选择| 1.5.0|它找到了满足 A 和 B 要求的**最新**可用版本。|
|`Go Modules`|最小版本选择 (MVS)|1.3.0|它找到了满足 A 和 B 要求的**最小**（最老）的版本。|

#### B. 摆脱 GOPATH 的决心
`dep` 虽然管理了依赖，但它依然默认你的项目是放在 `$GOPATH/src` 下的，它没有彻底解决 *必须在指定目录下写代码*  这个反人类的设定。而 Go Modules 的设计初衷之一就是彻底干掉 `$GOPATH` 对项目路径的限制。



###  dep 历史意义 
dep 的出现，统一了 Go 社区的依赖管理时间。它确立了 ”清单文件 + 锁文件“的模式，以及对语义化版本的强调，为后来了的 

`Go Modules`

 铺平了道路。

|**特性**|**dep**|**Go Modules**|
|-|-|-|
|**配置文件**|`Gopkg.toml`|`go.mod`|
|**锁定文件**|`Gopkg.lock`|`go.sum`|
|**代码存放**|`vendor/` 目录|`$GOPATH/pkg/mod` (全局缓存)|
|**版本选择算法**|**SAT Solver **(追求符合条件的最新版)|**MVS **(追求符合条件的最老版)|
|**项目位置**|在 `$GOPATH/src`下|任意位置|
|**现状**|已停止维护 (Archived)|官方标准|

##  1.4 Modules (模块)
Go 1.11 引入，并在 **Go 1.16+** 版本中成为默认且推荐的依赖管理方式。它彻底解决了之前方案的痛点。

* **机制：**
    * 项目不再必须放在 `$GOPATH` 下。
    * 每个项目都有一个 `go.mod` 文件来定义项目自身的模块路径和所有依赖库的精确版本。
    * 依赖包的缓存统一存放在 `$GOPATH/pkg/mod` 目录下，实现了全局缓存，解决了 `vendor` 的冗余问题。
    * 同一个模块支持多个版本同时存在， 在 mod 目录下命名为 `<moduleName>@<version>`
