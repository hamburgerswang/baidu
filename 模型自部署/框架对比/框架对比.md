## 1. Qwen3.5-4B 任务拆分（关注完整耗时）
|目标 QPS|vLLM 完整耗时 P50 / P99 (s)|SGLang 完整耗时 P50 / P99 (s)|
|-|-|-|
|1|0.73 / 2.33|**0.50 / 1.33**|
|4|0.77 / 2.41|**0.64 / 1.65**|
|8|1.33 / 5.16|**0.76 / 2.13**|
|10|1.94 / 7.45|**0.96 / 2.54**|
|12|2.06 / 6.98|**1.22 / 4.10**|
|15|3.83 / 10.88|**1.95 / 6.10**|

* QPS 在 1 到 15 之间，SGLang 的完整耗时 P50 比 vLLM 低 30% 到 50%，P99 低 40% 到 65%。
* QPS 20 时 SGLang 崩了：在途请求从 32 涨到 298，说明请求在持续堆积。这一档 vLLM 虽然也变慢，但在途请求稳定在约 100，没有崩。
* 按"完整耗时 P99 ≤ 3s"算，单卡容量是 SGLang 约 10 QPS，vLLM 约 4 QPS。



## 2. Qwen3-14B 首句（关注首 Token 和首句）
|目标 QPS|vLLM 首 Token P50 / P99|SGLang 首 Token P50 / P99|vLLM 首句 P50 / P99|SGLang 首句 P50 / P99|
|-|-|-|-|-|
|1|0.20 / **0.25**|**0.19** / 0.80|0.39 / **0.70**|**0.33** / 0.81|
|4|0.21 / **0.27**|**0.20** / 0.37|**0.42 / 0.76**|0.49 / 0.93|
|8|0.22 / **0.28**|**0.21** / 0.57|**0.44 / 0.84**|0.64 / 2.30|
|12|0.23 / **0.27**|**0.22** / 0.74|**0.43 / 0.85**|0.81 / 2.09|
|15|0.23 / **0.31**|**0.22** / 0.74|**0.48 / 0.89**|0.86 / 2.61|
|20|0.25 / **0.35**|0.26 / 0.88|**0.46 / 0.92**|1.38 / 3.51|
|30|**0.29 / 0.49**|1.64 / 2.99|**0.63 / 1.26**|2.69 / 4.59|

* 首 Token 的 P50 两边基本相同，QPS ≤ 15 时 SGLang 快约 10ms。但 vLLM 的 P99 始终在 0.25 到 0.35s，SGLang 在 0.4 到 0.9s，vLLM 的长尾稳定得多。
* 首句差距更大。按"首句 P99 ≤ 1s"算，vLLM 到 QPS 20 都达标（0.92s），SGLang 只撑到 QPS 4（0.93s），QPS 8 就升到 2.3s。**单卡容量 vLLM 约是 SGLang 的 5 倍。**
* 原因在生成阶段：同一档 QPS 下，SGLang 的完整耗时和在途请求数都明显更高。QPS 20 时 SGLang 的在途请求是 194，vLLM 是 59。生成慢导致请求在系统里停留更久，首句也跟着被拖慢。
* 稳定性：vLLM 7017 个请求零失败；SGLang 有 3 次连接断开，分别是 `Connection reset` 1 次、`Server disconnected` 2 次。

## 3. 最终结论
|场景|选型|理由|
|-|-|-|
|**Qwen3-14B 首句**|**vLLM**|首 Token 和首句的 P99 全程稳定，满足首句 P99 ≤ 1s 的单卡容量约 20 QPS，SGLang 约 4 QPS，并且零失败|
|**Qwen3.5-4B 任务拆分**|**默认用 vLLM；低流量下 SGLang 可以作为优化方向**|SGLang 在 QPS ≤ 15 时完整耗时约低一半，但 QPS 20 会崩，而且有少量断连。要切到 SGLang，需要先查清崩溃原因，并按单卡约 10 QPS 规划实例数，同时加上限流|
|**团队统一框架**|**vLLM**|两个场景里 vLLM 在高负载下都更稳。现有 Go 服务、启动脚本和监控都是基于 vLLM 建的，切换还有额外的运维成本|

## 4. 结论的局限和后续
**SGLang 的 decode 在负载下变慢**

* 压测工具不直接算 TPOT（每个输出 token 的耗时），我用 14B 重测数据估算了一下：(完整耗时 P50 − 首 Token P50) ÷ (平均输出 token − 1)。

|目标 QPS|vLLM TPOT|SGLang TPOT|vLLM 首 Token P50|SGLang 首 Token P50|
|-|-|-|-|-|
|1|41 ms|47 ms|0.20 s|0.19 s|
|8|50 ms|85 ms|0.22 s|0.21 s|
|15|54 ms|128 ms|0.23 s|0.22 s|
|20|58 ms|211 ms|0.25 s|0.26 s|

* **首 Token 的 P50 两边几乎相同。** 说明 SGLang 接收新请求、做 prefill 的速度没有问题，低负载下甚至略快。
* **TPOT 差距随负载拉大。** QPS 从 1 升到 20，vLLM 的 TPOT 只从 41ms 涨到 58ms；SGLang 从 47ms 涨到 211ms，高了约 4.5 倍。
* **首句和完整耗时差，是 decode 慢造成的。** 首句要等前面十几个 token 生成出来，每个 token 都慢，首句就跟着慢。请求生成得慢，在系统里停留的时间就长，所以 QPS 20 时 SGLang 的在途请求是 194，vLLM 只有 59。
