# hey 压测：常见问题与解答

> 配套文档：[hey 你好 "压测"](hey你好“压测”.md)
> 整理方式：按「基础认知 → 参数用法 → 结果解读 → 压测方法 → 局限与替代 → 文档勘误」六类组织，共 36 问。

## 速查：最容易被问到的 8 个点

| 问题 | 一句话答案 |
|:---|:---|
| `-n` 和 `-c` 什么关系 | n 是总请求数，c 是同时进行的数量，c 不能大于 n |
| QPS 是并发数吗 | 不是。QPS ≈ 并发数 ÷ 平均延迟 |
| `-q` 限的是全局还是单 worker | 每个 worker，总 QPS 上限 ≈ q × c |
| 能带 Bearer Token 吗 | 能，用 `-H "Authorization: Bearer <token>"` |
| 能压 WebSocket 吗 | 不能，hey 只做 HTTP/1.1 和 HTTP/2 |
| 能测首 token 延迟吗 | 不能，hey 读完整响应体才计时 |
| 结果可信吗 | 取决于压测机是否为瓶颈，单机压测机容易被自身限制 |
| 和 k6 怎么选 | 临时快速验证用 hey，需要脚本化/复杂场景用 k6 |

## 一、基础认知

### Q1. hey 是什么？和 ab、JMeter、wrk、k6 怎么选？
**答：**
- hey 是 Go 写的命令行 HTTP 压测工具，特点是轻量、单命令、并发高（goroutine）、报告直观（含 P90/P99 和直方图）。
- 选型可以按场景：

| 场景 | 推荐 |
|:---|:---|
| 临时验证某个接口能不能扛住 | hey |
| 只压最简单的 GET，机器上装了 Apache | ab 也能用，但功能和协议都落后 |
| 大型压测、需要图形界面、团队协作、分布式 | JMeter |
| 要在 Linux 上把单机压到极限 | wrk / wrk2 |
| 需要脚本编排（登录、动态参数、多接口串联）、要进 CI | k6（或 Locust） |

- 结论：hey 的定位是「开发自测 + 快速验证」，不是「专业压测平台」。

### Q2. hey 是哪个公司/谁写的？还能维护吗？
**答：**
- 作者 Jaana Dogan（前 Google，现 AWS），项目原名 boom，因重名改叫 hey，托管在 github.com/rakyll/hey，MIT 协议。
- 项目较早，更新节奏慢，但功能稳定、代码简单，日常接口压测足够用；遇到需要复杂场景时换 k6 更合适。

### Q3. hey 支持 HTTP/2 吗？怎么开？
**答：**
- 支持，加 `-h2` 参数。默认走 HTTP/1.1。
- 注意：走 HTTP/2 通常要求 HTTPS + ALPN 协商，用 `https://` 地址测试更贴近真实；HTTP 明文（h2c）支持视服务端而定。

### Q4. hey 能压 WebSocket 吗？
**答：**
- 不能。hey 只发 HTTP 请求、读完响应就结束，不解析 WebSocket 帧，也就测不了握手之后的消息收发和长连接。
- 要压 WebSocket，用 `websocat`、k6 的 WebSocket 模块，或自己写脚本。
- 文档 1.1 节写的「支持 HTTP/HTTPS 以及 WebSocket」，WebSocket 这句不准确，对外讲解时建议改掉。

### Q5. hey 能压 HTTPS 和自签名证书的接口吗？
**答：**
- 能压 HTTPS。但自签名证书会校验失败，hey 本身没有跳过证书校验的参数（如 `-k`）。
- 临时方案：把证书加到系统信任链，或通过本地反向代理（如 Nginx）用 HTTP 转发到目标。

### Q6. hey 会是「压测机先扛不住」吗？怎么判断？
**答：**
- 会。hey 单进程、单机，压测机自身的 CPU、网卡、文件描述符、端口都可能成为瓶颈。
- 判断方法：
  - 压测运行时看压测机的 CPU 是否打满、网卡带宽是否接近上限。
  - 客户端出现大量 `dial tcp ... cannot assign requested address`，是本地端口耗尽。
  - 服务端 CPU 很低但 QPS 上不去，说明瓶颈在压测侧。
- 缓解：调大 `ulimit -n`、用 `-disable-keepalive` 对比结果、换多台机器分别压。

## 二、参数与用法

### Q7. `-n` 和 `-c` 到底是什么关系？
**答：**
- `-n` 是总请求数（默认 200），`-c` 是并发 worker 数（默认 50）。
- 执行方式：起 c 个 worker，每个循环发请求，直到总数达到 n。
- `-c` 不能大于 `-n`，否则 hey 直接报错。
- 例：`-n 1000 -c 100` ≈ 每个 worker 发 10 个；`-n 200 -c 30` ≈ 每个 worker 发 6~7 个。
- 注意不是「n × c」的请求量，这一点最容易误解。

### Q8. `-n` 和 `-z` 同时写会怎样？
**答：**
- `-z` 优先，`-n` 被忽略。到时间就停，不管发了多少个请求。
- 例：`hey -z 30s -n 100000` 实际压 30 秒，请求数取决于这 30 秒能发多少。
- 用途：想看「稳态吞吐」用 `-z`；想跑固定样本量、便于对比用 `-n`。

### Q9. `-q` 限的是总 QPS 还是每个 worker 的 QPS？
**答：**
- **每个 worker**。这是最容易踩的坑。
- `-c 50 -q 10` 的总 QPS 上限约 50 × 10 = 500，不是 10。
- 想精确控制总 QPS，要把 `-q` 换算成「目标 QPS ÷ 并发数」。

### Q10. 为什么 POST 请求会报错？`-d` 和 `-m` 必须一起用吗？
**答：**
- hey 对 POST/PUT 这类方法要求有请求体，不带 `-d` 或 `-D` 会报错。
- 正确写法：`hey -m POST -d '{"a":1}' -H "Content-Type: application/json" <url>`。
- 另外要注意 Content-Type：hey 有 `-T` 参数指定（默认 text/html），也可以直接用 `-H "Content-Type: ..."`。

### Q11. `-d` 和 `-D` 有什么区别？
**答：**
- `-d`：请求体直接写在命令行里，适合短 JSON。
- `-D`：从文件读取请求体，适合长 JSON、XML、或者需要版本管理的 payload。
- 请求体里有大量引号、中文、换行时，用 `-D` 避免 shell 转义问题。

### Q12. 多个 `-H` 怎么用？重复的 header 会怎样？
**答：**
- 每个 `-H` 加一个 header，可以重复多个：
  `-H "Content-Type: application/json" -H "App-Version: 1.0.0" -H "X-Trace-Id: test"`。
- 同名 header 写两次，实际发出时可能是覆盖或合并，取决于底层实现，不要依赖这个行为。
- header 里含空格、逗号、中文时，一定用双引号包住。

### Q13. 要带 Bearer Token 怎么压？
**答：**
```bash
hey -n 200 -c 30 -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/user/getInfo
```
- 建议把 token 放环境变量，避免写进 shell 历史。
- 注意 token 有效期：压测时间长、token 中途过期，会突然大量 401。
- 不要和 `-a`（Basic 认证）同时用，两者都会设置 Authorization 头。

### Q14. 要带 Cookie / Session 怎么压？
**答：**
- 直接把 Cookie 当普通 header 带：
  `-H "Cookie: SESSION=abc123; uid=1001"`。
- 适合固定会话的压测。如果要压「不同用户各自登录」的场景，hey 做不到（不能每个请求用不同 token），需要 k6 这类脚本化工具。

### Q15. 请求体里中文会不会乱码？
**答：**
- 命令行走 `-d '{"name":"测试"}'` 时，注意 shell 编码（UTF-8）和 `Content-Type` 带上 `charset=utf-8`。
- 更稳妥的做法：把请求体写进文件用 `-D`，文件保存为 UTF-8。

### Q16. 怎么通过代理压测？
**答：**
- `-x "127.0.0.1:8080"` 指定 HTTP 代理。
- 用途：测试环境必须走代理、或者要模拟特定出口 IP。
- 代理本身会成为瓶颈，压测机到代理的链路也要一并观察。

### Q17. 文档没写，但很有用的参数有哪些？
**答：**

| 参数|作用|典型场景|
|:---|:---|:---|
| `-T`|指定 Content-Type|POST 表单/JSON 不想写完整 -H 时|
| `-A`|指定 Accept 头|模拟浏览器的内容协商|
| `-host`|覆盖请求的 Host 头|同一个 IP 压不同域名（灰度/多租户）|
| `-disable-keepalive`|禁用连接复用，每次新建连接|对比「建连开销」对性能的影响|
| `-disable-redirects`|不跟随 301/302|避免重定向让结果失真|
| `-disable-compression`|不请求压缩|想看压缩前后的传输差异|

### Q18. hey 支持动态参数（比如每次请求不同的 ID）吗？
**答：**
- 官方版本不支持，所有请求打同一个 URL。文档里的「示例 6 动态 URL」用的是社区 fork 的扩展语法 `{{(2-9)(1-9)}}`，不是原生能力，用之前要确认版本。
- 需要动态参数、链路编排、登录态，用 k6、Locust、JMeter。

## 三、结果解读

### Q19. QPS 是怎么算出来的？为什么和并发数对不上？
**答：**
- hey 不「测」QPS，而是算出来的：`QPS = 请求总数 ÷ Total`。
- 三者的关系（Little 定律）：`并发数 ≈ QPS × 平均延迟`。
- 所以 `-c 100` 不代表 QPS 是 100 或 100×某数。举例：平均延迟 0.45 秒、QPS 54.85，则实际只有约 25 个请求在同时处理——剩下的 worker 在等响应。
- 想提 QPS，要么降延迟，要么加并发；加并发到一定程度后 QPS 不再涨，说明到了服务端瓶颈。

### Q20. Average 和 P90 差很多，说明什么？
**答：**
- 说明存在长尾：多数请求很快，少数请求特别慢。
- 常见原因：GC 停顿、锁竞争、连接池排队、下游偶发超时、慢 SQL、冷缓存。
- 优化长尾通常比优化平均值更有效，因为用户感知的「卡」主要来自长尾。

### Q21. 直方图里为什么有几档是 [0]？
**答：**
- hey 把「最快」到「最慢」之间自动等分成若干档，某些档没有请求就会显示 0。
- 比如最慢请求 1.20 秒，但绝大多数请求集中在 0.3 秒附近，右侧几档自然是 0。
- 出现 0 不代表压测异常，只是分布形状的体现。

### Q22. Details 里 `resp wait` 和 `resp read` 有什么区别？
**答：**
- `DNS+dialup`：DNS 解析加建连（含 TLS 握手）耗时。
- `DNS-lookup`：只有 DNS 解析的耗时。
- `req write`：写出请求体的耗时。
- `resp wait`：发出请求到收到响应第一个字节的时间，**基本等于服务端处理时间**，是最能反映接口逻辑快慢的指标。
- `resp read`：读取响应体的耗时，反映响应体大小和网络传输。
- 判断瓶颈：`resp wait` 高 → 服务端慢（逻辑、DB、下游）；`resp read` 高 → 响应体大或带宽受限；`DNS+dialup` 高 → 连接开销大，可以对比 `-disable-keepalive`。

### Q23. 出现 429、502、503、504 分别说明什么？
**答：**

|状态码|含义|压测中的常见原因|
|:---|:---|:---|
|429|被限流|网关/接口限流阈值太低，压测流量超过配额|
|502|网关收到上游的错误响应|上游服务崩溃、端口没起、连接被拒|
|503|服务不可用|上游过载被摘除、健康检查失败|
|504|网关超时|上游处理超过网关超时时间|

- 出现这些先确认：是接口本身的问题，还是压测强度超出了环境该承受的量。压测环境限流阈值通常要单独放开。

### Q24. `Error distribution` 是什么意思？
**答：**
- 有非预期响应（连接失败、超时、非 2xx）时，hey 会额外打印错误分布，按错误类型计数。
- 常见条目：`dial tcp: connect: connection refused`（服务没起/端口错）、`timeout`（`-t` 到期）、`EOF`（连接被对端关闭）。
- 排查顺序：先看是不是地址写错、服务没起，再看是不是压太狠把服务压挂了。

### Q25. `-o result.csv` 导出的内容是什么？
**答：**
- 逐条请求的明细（每行一个请求），不是汇总报告。
- 常见列：响应时间、状态码、耗时等，可以用 Excel 透视、算分位数、画分布。
- 适合事后分析，但文件会比较大（请求数越多越大）。

### Q26. 为什么两次压测结果差很多？
**答：**
- 常见原因：
  - 缓存冷热：第一次压缓存全空，第二次命中缓存，延迟差几倍。
  - 服务端刚启动，JIT/连接池/热数据未就绪。
  - 压测机自身负载不同（同时在跑别的程序）。
  - 网络环境波动、其他人在共用测试环境。
- 建议：每次压测前预热一轮（先跑 `-n 100` 丢弃结果），正式的至少跑 3 次取中位数。

## 四、压测方法与落地

### Q27. 并发数应该设多少？
**答：**
- 不要拍脑袋。先估线上峰值：`并发 ≈ 峰值 QPS × 平均响应时间`。
- 例：线上峰值 500 QPS、平均响应 50ms，同时处理约 25 个请求，压测就从 25~50 并发起步。
- 然后阶梯加：50 → 100 → 200 → 400，观察 QPS 和 P99 的拐点。

### Q28. hey 能做阶梯加压吗？
**答：**
- 不能，hey 一次运行只有一个并发数。
- 两种做法：
  - 手动跑多轮：`for c in 50 100 200 400; do hey -n 5000 -c $c <url>; done`，把结果记下来画曲线。
  - 换工具：k6 有 `stages` 直接描述阶梯加压，wrk2 可以固定速率。

### Q29. 压测环境要注意什么？
**答：**
- 数据和线上量级接近，至少保证索引、缓存、数据分布不差太多，否则测出来的数字没参考价值。
- 隔离：不要压在共享测试环境上，别人同时在用会互相干扰。
- 依赖：数据库、Redis、下游服务要一起观察，否则瓶颈会被误判在应用层。
- 限流：确认网关、接口的限流阈值，压测前临时放开，否则测的是限流不是性能。
- 日志：压测时把 DEBUG 日志关掉，否则日志 IO 会严重拖慢服务。

### Q30. 压测结果怎么和监控对照？
**答：**
- 压测同时看服务端的：CPU、内存、GC 次数和停顿、线程/协程数、连接池使用率、DB 慢查询、Redis 延迟、下游接口耗时。
- 对照方法：客户端 P99 突然抬升的时间点，服务端哪个指标同时异常，基本就是瓶颈所在。
- 只看客户端报告很难定位根因，必须配合服务端指标。

### Q31. 压测发现 QPS 上不去，怎么定位？
**答：**
- 按这条链路排查：
  1. 压测机是否到瓶颈（CPU、端口、带宽）。
  2. `resp wait` 是否偏高（服务端处理慢）。
  3. 服务端 CPU 是否打满；没打满但 QPS 上不去 → 大概率卡在 IO 或锁。
  4. 连接池、协程池、DB 连接数是否打满（排队）。
  5. 下游依赖（DB、Redis、第三方接口）耗时是否上升。
  6. 是否有全局锁、同步写日志、序列化等单点开销。
- 工具配合：pprof（Go）、arthas（Java）、慢查询日志、APM。

### Q32. 压测怎么进 CI/CD？
**答：**
- 基本做法：部署到预发环境后自动跑一轮固定场景的 hey，把 QPS、P99 与基线比对，超出阈值就失败。
- 注意：
  - 场景要稳定（固定 `-n`、固定数据），否则结果不可比。
  - 要预热，去掉首轮冷启动的影响。
  - 机器资源要有保障，CI 机和压测机争抢 CPU 会让结果抖动。
  - 门禁阈值要留足噪声空间（比如允许 15% 波动），否则会频繁误报。

### Q33. hey 适合做容量评估吗？
**答：**
- 可以做一个粗略参考，但不够严谨。
- 局限：单机、不能分布式、不能模拟真实流量模型（不同接口比例、用户思考时间）、不能动态参数。
- 正式容量评估建议用 k6 / JMeter 做场景化压测，配合全链路压测平台。

## 五、局限与替代

### Q34. hey 测不了什么？什么情况下必须换工具？
**答：**

| 测不了 | 替代方案 |
|:---|:---|
| 动态参数、多接口串联、登录态 | k6、Locust、JMeter |
| 每个请求不同 token / 用户 | k6 |
| WebSocket、SSE 长连接的帧级交互 | k6（WS 模块）、websocat、自研脚本 |
| 首 token 延迟（TTFT）、流式分块延迟 | llmperf、genai-perf、k6 自定义脚本 |
| 分布式压测（多机发压） | JMeter 分布式、k6 云、内部压测平台 |
| 阶梯加压、峰值保持、浪涌 | k6 stages、JMeter 线程组 |
| 结果持久化和趋势对比 | 压测平台，hey 只能导 CSV 自己分析 |

### Q35. 什么时候从 hey 升级到 k6？
**答：**
- 出现下面任意一条就该考虑：
  - 需要「先登录拿 token，再压业务接口」。
  - 需要按比例混合多个接口（浏览 70%、下单 20%、支付 10%）。
  - 需要阶梯加压、浪涌、长时间稳定性测试。
  - 需要把压测做成规范化的脚本进 CI，并输出结构化指标。
- k6 用 JS 写脚本，成本不高，迁移很快。

## 六、文档勘误与易错点

> 这几条是对外讲解时最容易被追问的地方，建议提前准备。

### Q36. 文档里有几处需要修正或补充说明？
**答：**

| 位置|现文档表述|建议修正|
|:---|:---|:---|
|1.1 核心特性|「兼容 HTTP、HTTPS 以及 WebSocket 协议」|hey 不支持 WebSocket，只支持 HTTP/1.1 和 HTTP/2|
|3.1 参数表|`-q` 描述为「限制每个并发 worker 的 QPS」|描述正确，但读者常误以为是全局 QPS，需强调总 QPS ≈ q × c|
|3.1 参数表|未提 `-c` 不能大于 `-n`|补一句，否则新手容易踩坑|

## 附：最常用命令速查

```bash
# 快速验证能否扛住
hey -n 1000 -c 100 http://host/api/hello

# 按时长压、看稳态
hey -z 60s -c 50 http://host/api/hello

# POST JSON
hey -n 500 -c 50 -m POST -H "Content-Type: application/json" -d '{"id":1}' http://host/api/submit

# 带 Bearer Token
hey -n 500 -c 50 -H "Authorization: Bearer $TOKEN" http://host/api/user/info

# 带 Basic 认证
hey -n 200 -c 30 -a "admin:123456" http://host/api/admin/getInfo

# 限速 + 导出明细
hey -c 50 -z 60s -q 10 -o ./result.csv http://host/api/hello

# HTTP/2
hey -n 1000 -c 100 -h2 https://host/api/hello

# 对比建连开销
hey -n 1000 -c 100 -disable-keepalive http://host/api/hello
```
