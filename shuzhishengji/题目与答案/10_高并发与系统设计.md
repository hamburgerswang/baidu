# 10 高并发与系统设计（50 题）（题目与答案）

## 基础概念

### 1. 【高频】QPS、TPS、RT、并发数之间是什么关系？
**答案：**
- QPS：每秒处理的请求数。TPS：每秒处理的事务数（一个事务可能包含多个请求）。RT：单个请求的响应时间。并发数：系统中同时在处理的请求数。
- 关系（Little 定律）：并发数 = QPS × 平均 RT。例如 QPS 为 1000、平均 RT 为 50ms，则系统中同时约有 50 个请求在处理。
- 推论：在并发能力（线程数、连接数）固定的情况下，RT 越高，能达到的 QPS 越低。所以降低 RT 是提升吞吐的重要手段。
- 关注分位数：平均 RT 会掩盖长尾，要看 P99、P999。

### 2. 【高频】高并发系统设计的通用手段有哪些？
**答案：**
- 扩展：无状态服务水平扩展；数据层读写分离、分库分表。
- 缓存：多级缓存（本地缓存、Redis、CDN），减少对数据库的访问。
- 异步：消息队列解耦和削峰，非核心逻辑异步处理。
- 池化和复用：连接池、协程池、对象池。
- 批量：批量读写，减少网络往返和数据库访问次数。
- 保护：限流、熔断、降级、超时、隔离（舱壁模式）。
- 数据优化：索引、冷热分离、预计算、冗余字段。
- 就近：CDN、多机房部署。

### 3. 【高频】缓存、异步、削峰、限流、降级、熔断分别解决什么问题？
**答案：**
- 缓存：读多写少的场景下，降低读请求的延迟和对数据库的压力。
- 异步：把不需要立即完成的操作（发通知、打点、落库）移出主链路，降低响应时间，并解耦服务。
- 削峰：用消息队列或排队缓冲突发流量，后端按自己的处理能力匀速消费，防止被打垮。
- 限流：控制进入系统的流量不超过容量上限，保护系统；超出的请求拒绝或排队。
- 降级：系统压力大或依赖出故障时，关闭或简化非核心功能，保证核心功能可用。
- 熔断：依赖持续出错或变慢时，暂时停止调用它、快速失败，防止故障扩散（雪崩），并给依赖恢复的时间。

### 4. 垂直扩展和水平扩展怎么选？
**答案：**
- 垂直扩展：升级单机配置（CPU、内存、磁盘）。简单，不需要改架构；但有硬件上限，成本增长快，单点风险依然存在。
- 水平扩展：增加机器数量。理论上可以无限扩展，有容错能力；但需要服务无状态化，数据层需要分片，系统复杂度更高。
- 选择：
  - 先垂直扩展解决短期问题（成本低、见效快）。
  - 长期增长和高可用要求必须依靠水平扩展。
  - 无状态服务优先水平扩展；有状态的存储（数据库）先垂直扩展加读写分离，再考虑分片。

### 5. 【专家】有状态服务怎么做水平扩展？
**答案：**
- 状态外置：把会话、缓存等状态移到 Redis、数据库等外部存储，服务本身变成无状态，就能直接水平扩展。这是首选方案。
- 状态分片：状态必须保存在本地时（如长连接、内存计算、游戏房间），按 key（用户 ID、房间 ID）做一致性哈希，路由到固定的节点；扩缩容时只迁移部分 key。
- 会话粘性：负载均衡按用户把请求固定到某个节点，实现简单，但节点故障时状态会丢失。
- 状态复制：主从复制或基于共识协议（Raft）的多副本，保证节点故障时状态不丢。
- 扩缩容的过程：需要做状态迁移（先复制、再切换路由、最后清理），迁移期间要处理好双写或请求转发。
- 例子：实时数字人的资源路数和预热实例，就是一种需要专门调度和管理的有状态资源。

### 6. 【高频】什么是 C10K 问题？epoll 的原理是什么？
**答案：**
- C10K：单机同时处理一万个并发连接的问题。传统的"一个连接一个线程"模型下，线程的内存开销和上下文切换开销会让系统撑不住。
- 解决思路：I/O 多路复用，用少量线程管理大量连接，只处理就绪的连接。
- select 和 poll：每次调用都要把全部 fd 拷贝到内核，并线性扫描所有 fd，连接越多越慢；select 还有 1024 个 fd 的上限。
- epoll：
  - epoll_create 在内核中创建一个事件表（红黑树管理注册的 fd）。
  - epoll_ctl 注册或修改 fd，只需注册一次。
  - fd 就绪时，内核通过回调把它放进就绪链表；epoll_wait 只返回就绪的 fd，复杂度与总连接数无关。
  - 支持水平触发（LT）和边缘触发（ET）。
- Go 的 netpoller 底层就是基于 epoll（Linux 上），让 goroutine 能以同步的写法实现高并发网络 I/O。

### 7. 同步、异步、阻塞、非阻塞的区别是什么？
**答案：**
- 阻塞和非阻塞：描述调用方在等待结果时的状态。阻塞调用会让线程挂起，直到结果返回；非阻塞调用立即返回（可能是"尚未就绪"），线程可以去做别的事。
- 同步和异步：描述结果怎么通知调用方。同步是调用方自己等待或主动查询结果；异步是被调用方完成后通过回调、事件、消息通知调用方。
- 组合：
  - 同步阻塞：普通的 read。
  - 同步非阻塞：轮询或 I/O 多路复用（epoll 本身仍然是同步的，就绪后由用户自己读取数据）。
  - 异步非阻塞：Linux 的 io_uring、Windows 的 IOCP，内核完成读写后再通知。
- Go 的 goroutine：在代码层面看起来是同步阻塞的写法，底层由运行时用非阻塞 I/O 加 netpoller 实现，阻塞的只是 goroutine，不是线程。

### 8. 零拷贝（sendfile、mmap）的原理是什么？
**答案：**
- 传统的文件发送：磁盘 → 内核缓冲区 → 用户缓冲区（read）→ socket 缓冲区（write）→ 网卡。共 4 次拷贝（其中 2 次是 CPU 拷贝）、4 次用户态和内核态的切换。
- mmap：把文件映射到用户进程的地址空间，省去了内核缓冲区到用户缓冲区的拷贝，但仍需要从内核缓冲区拷贝到 socket 缓冲区。
- sendfile：数据直接在内核中从文件缓冲区传到 socket，不经过用户态。如果网卡支持 SG-DMA（分散聚集 DMA），连 socket 缓冲区的拷贝也能省掉，只剩 DMA 拷贝，实现真正的零 CPU 拷贝。
- 应用：Kafka 发送消息给消费者时使用 sendfile；Nginx 发送静态文件时开启 sendfile。
- 适合：数据不需要在用户态处理、直接转发的场景。

## 限流熔断

### 9. 【高频】常见的限流算法（计数器、滑动窗口、漏桶、令牌桶）有什么区别？
**答案：**
- 固定窗口计数器：每个时间窗口（如 1 秒）内计数，超过阈值就拒绝。实现最简单；缺点是窗口边界处可能出现两倍流量（前一个窗口的末尾和后一个窗口的开头各来一波）。
- 滑动窗口：把窗口切成多个小格，或者记录每个请求的时间戳（用 Redis 的 ZSET），统计最近一个完整窗口内的请求数。更平滑，解决了边界问题，但占用内存更多。
- 漏桶：请求进入一个队列，以固定的速率流出处理。输出非常平滑，但无法应对突发流量（突发的请求只能排队或被丢弃）。
- 令牌桶：以固定速率往桶中放令牌，请求拿到令牌才能通过，桶有容量上限。平均速率受控，同时允许一定程度的突发（桶中积累的令牌），是最常用的方案（Go 的 golang.org/x/time/rate 就是令牌桶）。
- 选择：保护下游、要求匀速处理时用漏桶；接口限流、允许突发时用令牌桶。

### 10. 【高频】分布式限流怎么实现？用 Redis 怎么做？
**答案：**
- 为什么需要：单机限流只能限制单个实例；多实例部署时需要集群维度的总量控制，比如对某个用户、某个 API Key 的全局限流。
- Redis 固定窗口：`INCR key` 加 `EXPIRE`（key 中带上窗口编号），超过阈值就拒绝。
- Redis 滑动窗口：用 ZSET，以时间戳作为 score；每次请求先 `ZREMRANGEBYSCORE` 删除窗口外的记录，再 `ZCARD` 计数，未超过阈值就 `ZADD`。要用 Lua 脚本保证这几步是原子的。
- Redis 令牌桶：在 Hash 中保存当前令牌数和上次填充的时间，Lua 脚本中根据时间差计算应补充的令牌，再扣减。
- 注意：
  - 每个请求都要访问一次 Redis，延迟增加，Redis 也可能成为瓶颈。
  - Redis 不可用时要有降级策略（放行或退回到单机限流）。
  - 热点 key 要分片。
- 也可以用 Sentinel 集群限流、网关自带的限流能力。

### 11. 【专家】单机限流和集群限流怎么配合？热点 key 限流怎么做？
**答案：**
- 配合：
  - 单机限流保护每个实例自身不被打垮（按实例容量设置），零网络开销，作为第一道防线。
  - 集群限流控制全局的配额（按用户、按租户、按 API 设置总量）。
  - 请求先过单机限流，再过集群限流。
  - 另一种做法：把集群总配额按实例数平均分到单机（实例数变化时需要动态调整），可以避免每次请求都访问 Redis，但精度较低。
- 热点 key 限流：
  - 问题：针对某个热门参数（如热门商品 ID、热门 Agent）的请求特别多，按接口整体限流无法保护它，按 key 限流又会造成 Redis 上的热点。
  - 做法：
    - 在本地先统计参数的访问频率（滑动窗口加 LRU），识别出热点参数后单独限流（Sentinel 的热点参数限流就是这样做的）。
    - 集群场景下，热点 key 的计数在本地预先聚合，再批量同步到 Redis，或者把一个 key 拆成多个子 key 分散压力。
- 动态配置：限流阈值放在配置中心，支持实时调整。

### 12. 熔断器的三种状态是什么？Hystrix、Sentinel 的原理是什么？
**答案：**
- 三种状态：
  - 关闭（Closed）：正常调用，同时统计错误率或慢调用的比例。
  - 打开（Open）：比例超过阈值后打开，所有请求直接快速失败（走降级逻辑），持续一个冷却时间。
  - 半开（Half-Open）：冷却时间结束后放少量请求试探，成功就回到关闭，失败就回到打开。
- Hystrix：
  - 用滑动窗口统计请求的成功、失败、超时；错误率超过阈值且请求数达到最小值时触发熔断。
  - 用线程池或信号量做资源隔离（舱壁模式），防止一个依赖占满全部线程。
  - 已经停止维护。
- Sentinel（阿里）：
  - 以资源为中心，基于滑动窗口实时统计。
  - 支持流量控制（QPS、并发线程数、热点参数）、熔断降级（慢调用比例、异常比例、异常数）、系统自适应保护。
  - 规则可以动态配置，有控制台。
- Go 生态中可以使用 sentinel-golang、gobreaker 等。

### 13. 服务降级有哪些方式？降级开关怎么设计？
**答案：**
- 降级方式：
  - 功能降级：关闭非核心功能（推荐、追问、个性化）。
  - 数据降级：返回缓存的或默认的数据；返回简化版本的数据。
  - 流程降级：同步改成异步，写操作暂存到队列。
  - 读降级：只读缓存，不回源数据库。
  - 写降级：只写缓存，异步同步到数据库。
  - 依赖降级：调用失败时使用兜底逻辑或兜底文案。
- 开关设计：
  - 放在配置中心，支持实时生效，不需要重启或发版。
  - 按功能点、接口、用户群设置粒度。
  - 可以手动打开，也可以由熔断、监控指标自动触发。
  - 打开开关要记录日志、发通知，方便追溯。
  - 提前梳理降级预案：哪些功能可以降级、降级后的表现、对业务的影响，并定期演练。

### 14. 【专家】自适应限流（根据 CPU、RT 动态调整）怎么实现？
**答案：**
- 背景：固定的限流阈值需要人工根据压测结果设置，系统的处理能力会随依赖状态、机器负载变化，固定阈值要么过严浪费容量，要么过松保护不住。
- 思路：根据系统当前的实际状态动态计算允许的并发数或 QPS。
- BBR 风格的算法（如 Kratos 和 sentinel-golang 中的实现）：
  - 实时统计最近窗口内的最大通过 QPS（maxPass）和最小 RT（minRT），估算系统容量为 maxPass × minRT。
  - 当 CPU 使用率超过阈值（如 80%），且当前在途请求数超过估算的容量时，拒绝新请求。
- 基于排队论或 Little 定律的思路：在途请求数持续上升而吞吐不再增加，说明系统已经饱和，此时减小并发上限。
- 类似 TCP 拥塞控制的方式（如 Netflix 的 concurrency-limits）：根据 RT 的变化动态增减并发上限，RT 升高就减小，RT 稳定就缓慢增大。
- 注意：要有一个保底的固定上限；算法参数需要压测调优；拒绝的请求要能快速返回。

## 缓存

### 15. 【高频】缓存和数据库的一致性怎么保证？先更新库还是先删缓存？
**答案：**
- 推荐做法（Cache-Aside）：先更新数据库，再删除缓存（而不是更新缓存）。
- 为什么删除而不是更新：并发更新时，更新缓存的顺序可能和更新数据库的顺序不一致，导致缓存中留下旧值；删除后由下一次读请求回源加载，更简单、可靠。
- 为什么不先删缓存：先删缓存、还没更新数据库时，另一个读请求回源读到旧值并写回缓存，缓存中就是脏数据，而且会一直保持到过期，窗口期较长。
- 先更新数据库再删缓存也有极端情况：读请求在更新之前读到旧值，在删缓存之后才写回缓存，概率很低。
- 兜底：
  - 缓存设置过期时间，保证最终一致。
  - 删除缓存失败时重试（用消息队列，或订阅 binlog 异步删除）。
  - 对一致性要求很高的数据，不走缓存，直接读主库。
- 强一致需要分布式锁或其他代价较高的方案，一般业务接受最终一致。

### 16. 【高频】延迟双删是什么？有什么问题？
**答案：**
- 做法：先删除缓存，再更新数据库，等待一段时间（如几百毫秒）后再删除一次缓存。
- 目的：第二次删除用来清掉在"更新数据库期间"被其他读请求写回缓存的旧值；在主从架构中，也能清掉从库延迟期间读到的旧值。
- 问题：
  - 等待多长时间难以确定：要大于"一次读请求回源并写回缓存的耗时"或主从延迟，只能凭经验估计。
  - 等待会增加写请求的耗时（可以把第二次删除改为异步执行）。
  - 第二次删除也可能失败，需要重试机制。
  - 在等待窗口内仍然可能读到旧数据。
- 实践：更常用的是"先更新数据库再删缓存，加上通过消息队列或 binlog 异步重试删除"。

### 17. 【专家】基于 binlog 订阅（Canal）更新缓存的方案是怎样的？
**答案：**
- 架构：业务只写数据库 → Canal 伪装成 MySQL 的从库，订阅 binlog → 解析出行变更事件 → 发送到消息队列 → 缓存同步服务消费事件，删除或更新对应的缓存。
- 优点：
  - 业务代码和缓存维护解耦，业务不需要关心缓存。
  - 不会遗漏更新（任何写入数据库的路径都会产生 binlog，包括手工修复数据）。
  - 天然可以重试（消息消费失败可以重新消费）。
  - 同一行数据的变更按顺序处理（按主键分区）。
- 注意：
  - 有一定的延迟（通常是秒级以内），属于最终一致。
  - 需要保证消息队列按主键有序，否则可能乱序覆盖。
  - 链路变长，要监控同步延迟和积压。
  - 需要处理全量初始化和 Canal 自身的高可用。
- 同样的架构也可以用来同步搜索索引（ES）、数仓。

### 18. 【高频】多级缓存（本地缓存 + Redis）怎么设计？本地缓存怎么失效？
**答案：**
- 结构：请求先查进程内的本地缓存，未命中再查 Redis，再未命中就回源数据库，然后逐级回填。
- 本地缓存：
  - 访问延迟是纳秒到微秒级，能扛住超高频的读。
  - 适合热点数据、变化少的配置。
  - 容量有限，要设置上限和淘汰策略（LRU 或 LFU；Go 中可以用 freecache、ristretto、bigcache）。
  - 每个实例各自一份，存在不一致的问题。
- 失效方式：
  - 短 TTL（如几秒到几分钟），容忍短期不一致。
  - 主动通知：数据变更时通过消息（Redis Pub/Sub、MQ）广播，各实例删除对应的本地缓存。
  - 版本号：在 Redis 中存版本号，本地缓存定期比对。
- 防击穿：回源时用 singleflight 合并相同 key 的并发请求。
- 适用：Agent 配置、热门商品等读多写少、能容忍短暂不一致的数据。

### 19. 热点数据怎么发现？热点 key 怎么处理？
**答案：**
- 发现：
  - 提前预知：活动、明星、爆款，可以提前人工标记和预热。
  - 实时探测：客户端或代理层统计 key 的访问频率（滑动窗口加 TopK 算法，如 HeavyKeeper），超过阈值就判定为热点；Redis 的 `--hotkeys`（需要 LFU 淘汰策略）或者 monitor 采样；云 Redis 的热 key 分析功能。
- 处理：
  - 本地缓存：把热点 key 缓存到各实例的本地，大部分读不再访问 Redis（最有效）。
  - 拆分 key：把一个热 key 复制成多份（key_1 到 key_N），读的时候随机选一份，分散到不同的分片；写的时候要更新全部副本。
  - 读写分离：增加 Redis 的只读副本。
  - 限流：对热点参数单独限流。
- 热点写（如计数器）：本地聚合后批量写入，或者拆分成多个子计数器，读取时求和。

### 20. Cache-Aside、Read-Through、Write-Through、Write-Behind 有什么区别？
**答案：**
- Cache-Aside（旁路缓存）：由应用自己管理缓存。读时先查缓存，未命中就查数据库再回填；写时先更新数据库，再删除缓存。最常用，灵活。
- Read-Through：应用只和缓存交互，缓存未命中时由缓存层自己去数据库加载。应用代码更简单，但需要缓存组件支持加载逻辑。
- Write-Through：写操作经过缓存层，缓存层同步写数据库和缓存，两者都成功才返回。一致性较好，但写延迟高。
- Write-Behind（Write-Back）：写操作只写缓存，由缓存层异步批量写回数据库。写性能最好，能合并多次写；但缓存故障时可能丢数据，一致性弱。适合计数、点赞这类可以容忍少量丢失的高频写场景。
- 业务开发中最常用的是 Cache-Aside；高频计数类场景常用 Write-Behind 的思路（Redis 计数后定期落库）。

## 存储与数据

### 21. 【高频】数据库读写分离的原理是什么？主从延迟怎么处理？
**答案：**
- 原理：主库处理写请求，通过 binlog 复制到一个或多个从库，从库承担读请求，从而扩展读能力。路由由中间件（如 ProxySQL、DBProxy）或应用层的数据源配置完成。
- 主从延迟的影响：刚写入的数据马上去从库读，可能读不到或读到旧值（如注册后立即查询个人信息）。
- 处理方式：
  - 关键的读请求强制走主库：写完之后的一段时间内，同一个用户的读请求走主库；或者对一致性要求高的接口一律读主库。
  - 写后读的数据直接使用写入时的结果，不再查询。
  - 先读从库，读不到再读主库（适合"数据不存在"可以判定的场景）。
  - 业务上容忍延迟：通过界面提示"处理中"。
  - 降低延迟：从库并行复制、避免大事务、提升从库的配置。
- 监控主从延迟，超过阈值时把从库摘除出读流量。

### 22. 【高频】什么时候需要分库分表？分片键怎么选？
**答案：**
- 什么时候需要：
  - 单表数据量过大（经验值为千万行级别，或者数据大小达到几十 GB），索引变深、查询变慢、DDL 困难。
  - 单库的写入 QPS、连接数、存储空间达到瓶颈。
  - 优先考虑其他手段：优化 SQL 和索引、读写分离、冷热分离（归档历史数据）。确实不够时再分片，因为分片带来的复杂度很高。
- 分库和分表的区别：分表解决单表过大的问题；分库解决单库性能和容量的问题。
- 分片键的选择：
  - 是最常用的查询条件，让绝大多数查询只落在一个分片上（如按 uid 分片，"查询某个用户的数据"只访问一个分片）。
  - 数据分布均匀，避免热点。
  - 值不会改变。
- 分片算法：哈希取模（分布均匀，但扩容时需要迁移数据）；范围分片（适合按时间查询，但容易产生热点）；一致性哈希。
- 可举例：对话记录表按 uid 对 2048 取模分成 2048 张表。

### 23. 【专家】分库分表后跨分片查询、分页、排序怎么处理？
**答案：**
- 跨分片查询：
  - 尽量避免：通过分片键的设计让查询落在单个分片上。
  - 非分片键查询：建立映射表（如"订单号到 uid"），先查映射表定位分片；或者把数据同步到 ES 或数仓，用于检索和统计分析。
- 分页和排序：
  - 全局分页：每个分片都取前 (offset + limit) 条，在内存中汇总排序后再截取。页码越深代价越大。
  - 优化：使用游标分页（基于上一页最后一条的排序值，每个分片只取 limit 条）；禁止跳页，只允许"下一页"；或者交给 ES 处理。
- 聚合：每个分片分别计算 count、sum，再汇总；avg 要用 sum 除以 count 计算，不能直接对各分片的 avg 求平均。
- JOIN：避免跨分片 JOIN。可以冗余字段、在应用层分两次查询、把小表做成广播表（每个分片都有一份），或者让关联的表使用相同的分片键（如订单和订单明细都按 uid 分片）。
- 分布式事务：尽量让一个事务内的数据在同一个分片；否则使用最终一致性方案。

### 24. 【专家】不停机数据迁移（双写、校验、切流）怎么做？
**答案：**
- 适用场景：分库分表、更换数据库（如迁到 GaiaDB）、修改表结构。
- 步骤：
  1. 全量迁移：用工具（DTS 或自研脚本）把历史数据拷贝到新库。
  2. 增量同步：订阅 binlog 实时同步，或者在应用层开启双写（以旧库为主，同时写新库，新库写失败只记录日志、不影响主流程）。
  3. 数据校验：对比新旧库的行数、按主键范围的校验和、抽样全字段比对，修复差异，持续一段时间（如 7 天）。
  4. 灰度切读：按比例把读流量切到新库，对比新旧库的结果。
  5. 切写：改为以新库为主写入，旧库作为备份继续写入，以便回滚。
  6. 观察稳定后，下线旧库的写入和数据。
- 关键点：
  - 每一步都可以回滚。
  - 双写的顺序和失败处理要设计好。
  - 迁移期间防止数据冲突（如自增 ID 冲突，可以改用全局 ID）。
  - 切换时尽量选择低峰期。
- 可举例：646 init 表的治理方案是迁移到 GaiaDB，按 uid 分表，双写 7 天后切换。

### 25. 冷热数据分离怎么设计？
**答案：**
- 划分依据：按时间（最近 N 个月为热数据）、按访问频率、按业务状态（已完成的订单为冷数据）。
- 存储分层：
  - 热数据：在线数据库加缓存，追求低延迟。
  - 温数据：普通存储或只读副本。
  - 冷数据：低成本存储，如对象存储、HDFS/AFS、列式数仓，压缩存储。
- 迁移：定时任务把达到条件的数据从热库导出到冷存储，校验后从热库删除。
- 访问冷数据：
  - 业务上提供单独的历史查询入口（允许较慢）。
  - 查询时按条件路由：时间范围落在冷数据区间的，去冷存储查询。
  - 或者冷数据只用于离线分析和审计，不提供在线查询。
- 收益：热库的数据量变小，查询和备份更快，成本更低。

### 26. 【高频】海量历史数据怎么归档和清理？删除大表数据有什么风险？
**答案：**
- 风险：
  - 一条 SQL 删除大量数据会产生大事务：长时间持有锁，阻塞其他写入；产生大量 undo 和 binlog；主从延迟剧增；中途失败回滚的代价更大。
  - 可能把 IO 和 CPU 打满，影响线上业务。
  - 删除后表空间不会自动缩小（InnoDB 只把空间标记为可复用）。
- 正确做法：
  1. 先归档：导出到冷存储，校验行数和内容。
  2. 分批删除：按主键范围小批量删除（如每次几千行），批次之间休眠，在低峰期执行，监控主从延迟。
  3. 按分区表存储的数据，直接 DROP PARTITION，速度最快。
  4. 需要清空整张表时，用 TRUNCATE 或"建新表、切换、删除旧表"，比 DELETE 快得多。
  5. 删除后释放表空间（OPTIMIZE TABLE 或在线重建表），注意对线上的影响。
- 流程：和 DBA 确认方案、准备回滚手段、通过 DMS 等平台提交变更。
- 可举例：智能体对话数据有 2048 张分表，约 20T。先冷备到 AFS 并抽样校验，再按 0-1023、1024-2047 两段生成删除 SQL，通过 DMS 分批执行；shendeng 库清理 thread_record 表后，存储占用从约 80% 降到约 61%。

## 系统设计题

### 27. 【高频】设计一个短链接系统。
**答案：**
- 需求和量级：长链接转短链接，访问短链接时 302 跳转；读远多于写（如读写比 100:1）；可以支持自定义短码、过期时间、访问统计。
- 生成短码：
  - 发号器生成全局唯一 ID（数据库号段模式或雪花算法），转成 62 进制。7 位 62 进制可以表示约 3.5 万亿个链接。
  - 或者对长链接做哈希取前几位，需要处理冲突（加盐重试）。
  - 发号器生成的连续 ID 容易被遍历，可以对 ID 做混淆。
- 存储：短码到长链接的映射存在 KV 存储或 MySQL（短码为主键）；同一个长链接是否复用已有短码，按需求决定（需要额外建一个长链接哈希的索引）。
- 读链路：Redis 缓存热门短码，加上本地缓存；不存在的短码用布隆过滤器拦截，防止穿透。
- 跳转：301 是永久重定向，浏览器会缓存，减轻服务端压力，但统计不到访问；302 每次都经过服务端，可以统计。
- 统计：访问日志异步发送到消息队列，再写入数仓。
- 扩展：防止被滥用（恶意链接检测）、多机房部署。

### 28. 【高频】设计一个秒杀系统。
**答案：**
- 特点：瞬时流量极高、库存极少、绝对不能超卖、大部分请求最终都会失败。
- 分层过滤，把流量拦在越前面越好：
  - 前端：活动页静态化放 CDN；按钮防重复点击；倒计时以服务端时间为准；验证码或答题，把流量打散。
  - 网关：限流、黑名单、按用户限频。
  - 资格校验：活动状态、用户资格，提前把数据缓存起来。
- 扣库存：
  - 库存预加载到 Redis，用 Lua 脚本原子地"检查库存、扣减、记录用户已购买"（同时防止一人多买）。
  - 也可以拆成多个库存分片，分散热点。
  - 本地内存先做一次过滤：库存已经售罄后，直接返回失败。
- 下单：扣库存成功后发送消息到队列，异步创建订单，削峰；用户端轮询下单结果。
- 数据库：最终以数据库为准，用 `UPDATE ... SET stock = stock - 1 WHERE stock > 0` 兜底防止超卖；订单表对（用户、活动）建唯一索引，防止重复下单。
- 其他：支付超时自动取消订单并回补库存；对账；活动前压测和预热；秒杀服务独立部署，防止影响其他业务。

### 29. 【高频】设计一个分布式 ID 生成器（雪花算法的时钟回拨问题怎么处理）。
**答案：**
- 要求：全局唯一、趋势递增（便于 B+ 树索引写入）、高性能、高可用；有时还要求 ID 不能被猜出连续的规律。
- 方案：
  - UUID：不需要中心节点；但太长、无序，作为 InnoDB 主键会导致页分裂，性能差。
  - 数据库号段模式（如美团 Leaf-segment）：每次从数据库领取一个号段（如 1000 个），在内存中分配；用双 buffer 提前加载下一个号段。性能高，ID 趋势递增。
  - 雪花算法：64 位 = 1 位符号位 + 41 位毫秒时间戳（约可用 69 年）+ 10 位机器 ID + 12 位序列号（每毫秒 4096 个）。不依赖存储，性能极高。
- 时钟回拨的处理：
  - 回拨幅度很小时（几毫秒），等待时钟追上后再生成。
  - 回拨较大时，拒绝服务并告警，或者切换到备用的机器 ID 位。
  - 启动时校验当前时间是否大于上次生成 ID 的时间（持久化保存）。
  - 关闭 NTP 的跳变式校时，改成平滑调整。
- 机器 ID 的分配：用 ZooKeeper、etcd 或数据库注册分配，防止重复。

### 30. 设计一个排行榜系统。
**答案：**
- 实时排行榜：Redis ZSET，member 为用户 ID，score 为分数。
  - ZINCRBY 更新分数。
  - ZREVRANGE 获取前 N 名。
  - ZREVRANK 获取某个用户的排名。
  - 复杂度都是 O(log N)。
- 分数相同时按时间先后排序：把 score 编码为"分数 × 一个大数 + (最大时间戳 - 达成时间)"，让先达成的排在前面（要注意 double 的精度上限，整数部分约 2^53）。
- 超大规模（亿级用户）：
  - 只对前 N 名精确排名（维护前 N 名的 ZSET）。
  - 其他用户按分数段分桶计数，估算排名。
  - 或者按分片维护多个 ZSET，查询前 N 名时汇总。
- 周期性的榜单（日榜、周榜）：key 中带上日期，到期删除；按天的数据可以用 ZUNIONSTORE 合并成周榜。
- 持久化：分数变更异步写入数据库，Redis 丢失数据时可以重建。

### 31. 【高频】设计一个 feed 流（推模式、拉模式、推拉结合）。
**答案：**
- 推模式（写扩散）：用户发帖时，把帖子 ID 写入所有粉丝的收件箱（timeline）。读的时候直接读自己的收件箱，非常快；但大 V 有上千万粉丝时，一次发帖要写上千万次，写入压力和存储都很大，而且有延迟。
- 拉模式（读扩散）：用户读取时，拉取所有关注对象的最新帖子，合并排序。写入简单；但关注的人多时读取慢，难以做缓存。
- 推拉结合：
  - 普通用户发帖用推模式。
  - 大 V 发帖不推送，粉丝读取时再拉取大 V 的最新帖子，和自己收件箱中的内容合并。
  - 只给活跃粉丝推送，不活跃的粉丝在登录时再拉取补齐。
- 存储：收件箱用 Redis ZSET（score 为时间）只保留最近的 N 条，更早的数据回源数据库；帖子内容单独存储，收件箱中只存 ID。
- 分页：用游标（时间或 ID）分页，不要用 offset。
- 推荐类 feed（如抖音）是另一套架构：召回、排序、重排。

### 32. 设计一个点赞/计数系统。
**答案：**
- 需求：点赞和取消点赞、查询点赞数、查询"我是否点过赞"、点赞列表；写入 QPS 高、读取 QPS 更高，计数可以短暂不准确，但不能出现明显的错误。
- 点赞关系：（用户 ID，对象 ID）存在数据库中，建唯一索引防止重复点赞；Redis 中用 Set 或 Bitmap 加速"是否点过赞"的判断（大量对象时注意内存）。
- 计数：
  - Redis INCR 和 DECR 实时计数。
  - 异步批量落库：定时把增量合并后写入数据库，而不是每次点赞都更新数据库（热门内容的点赞会造成行锁竞争）。
  - 热门对象的计数拆分成多个子 key，读取时求和。
- 一致性：以关系表为准，定期校准计数（重新统计后修正）。
- 防刷：限频，识别异常行为。
- 写入链路：点赞事件发送到消息队列，消费方负责落库和计数，削峰并支持重试。

### 33. 【专家】设计一个 IM 即时通讯系统（消息有序、可靠、已读未读）。
**答案：**
- 架构：
  - 接入层：长连接网关（WebSocket 或 TCP），维护连接，记录用户在哪台网关上（路由表存在 Redis 中）。
  - 逻辑层：消息服务、会话服务、群组服务。
  - 存储层：消息存储（按会话分区）、离线消息、会话列表。
  - 推送：在线用户直接推送，离线用户走厂商通道。
- 有序：
  - 每个会话维护单调递增的序号（seq，由会话内的发号器生成，如 Redis INCR）。
  - 消息按会话 ID 路由到同一个处理队列。
  - 客户端按 seq 排序和展示，发现 seq 不连续时主动拉取补齐。
- 可靠（不丢、不重）：
  - 客户端发送时带上客户端消息 ID，服务端按它去重，保证幂等。
  - 服务端落库后返回 ACK，客户端没收到 ACK 就重发。
  - 下行推送也要求客户端 ACK，没收到 ACK 就重推。
  - 客户端重新上线后，根据自己已收到的最大 seq 拉取离线消息。
- 已读未读：
  - 单聊：记录每个用户在每个会话中的已读 seq，未读数 = 最新 seq - 已读 seq。
  - 群聊：每个成员记录已读位置；"消息被哪些人读过"的列表在大群中开销很大，可以只对小群提供，或者只展示已读人数。
- 大群：推送时写扩散的成本很高，改为读扩散（消息只存一份，成员按 seq 拉取）。
- 其他：多端同步、消息撤回、存储的冷热分离。

### 34. 设计一个延迟任务/定时任务调度系统。
**答案：**
- 需求：任务在指定时间执行（订单超时取消、定时提醒），或按 cron 周期执行；任务量大；执行不重复、不遗漏；支持重试和监控。
- 延迟任务的实现：
  - Redis ZSET：score 为执行时间，调度线程定期用 ZRANGEBYSCORE 取出到期的任务，用 Lua 原子地"取出并删除"，防止多个实例重复获取。
  - 时间轮：内存中的时间轮（如 Kafka 的分层时间轮），精度高、效率高，但需要持久化和故障恢复。
  - 消息队列的延迟消息：RocketMQ 支持延迟级别或任意时间的延迟消息；RabbitMQ 用 TTL 加死信队列实现。
  - 数据库扫描：任务表中有执行时间字段并建索引，定时扫描到期的任务。简单可靠，适合量不大的场景。
- 定时（cron）任务：分布式调度框架（如 XXL-JOB、ElasticJob），或公司内部的定时平台。由调度中心触发，执行器执行；按分片并行处理；用分布式锁或调度中心保证同一时刻只执行一次。
- 可靠性：任务执行要幂等；失败重试；执行记录和告警；执行超时检测。
- 可举例：对话数据冷备部署成 vs-timer 的 CRON-BATCH 任务，每天 01:45 执行，按分表区间拆成多个子任务并发执行。

### 35. 【专家】设计一个支持千万级用户的"最近使用"列表服务。
**答案：**
- 需求：记录用户最近使用过的对象（智能体、数字人），按最近使用时间倒序展示，带上最近一次的使用信息（如最后一条 query），首屏要快，支持翻页，数据保留一段时间（如 12 个月）。
- 写入：在使用行为发生的地方（对话接口）把事件异步发送到消息队列，由消费方写入存储，不阻塞主流程；过滤无效事件（如默认引导产生的空 query）。
- 存储：
  - Redis ZSET：key 为用户 ID，member 为对象 ID，score 为时间戳；用 ZREMRANGEBYRANK 只保留最近的 N 条（如 16 条），控制内存；详情（最近一条 query 等）存在单独的 String 或 Hash 中；设置过期时间。
  - MySQL：保存全量的使用记录，（uid，对象 ID）唯一，按 uid 加时间建索引，支持深度翻页和 Redis 数据丢失后的恢复。
- 读取：首屏读 Redis，未命中时回源 MySQL 并回写 Redis；翻页直接查 MySQL（游标分页）；读出后过滤掉已下线、已删除、不可见的对象。
- 职责划分：存储服务只负责记录和返回 ID 列表加基础信息，封面、视频等展示信息由分发侧组装。
- 容量估算：单条约 0.2KB，每个用户最多 16 条，约 3.2KB；按日活或峰值 PV 估算 Redis 内存和 MySQL 行数。
- 可举例：数字人"最近使用"接口按单日峰值 30 万 PV 预估，Redis 约 0.9GB，MySQL 约 3000 万行；QPS 峰值约 5，耗时 150ms；PC 首页"最近使用智能体"也采用了 Redis 加 MySQL 回源回填的方案。

### 39. 【专家】设计一个大模型推理服务网关（排队、优先级、流式、计费）。
**答案：**
- 和普通 API 网关的区别：单个请求耗时长（秒级到分钟级）；流式输出；成本以 token 计算；后端 GPU 资源稀缺、昂贵，容量有限。
- 接入：统一的 API（兼容 OpenAI 格式），流式使用 SSE，按调用方鉴权，统一管理模型和供应商的密钥。
- 排队和优先级：
  - 后端容量按并发数（或 KV Cache 容量）而不是 QPS 衡量。
  - 超出容量的请求进入优先级队列（在线交互的请求优先于离线批量任务，付费用户优先），设置排队超时。
  - 按租户做公平调度，防止一个租户占满资源。
- 路由：按模型、区域、负载、延迟选择后端实例或供应商；前缀感知路由（相同前缀的请求路由到同一个实例，提高 KV Cache 命中率）；熔断和降级。
- 流式：透传 SSE 不做缓冲；客户端断开时取消后端的生成；处理超时和心跳。
- 计费：从响应中读取输入 token、输出 token、缓存 token，按调用方实时累计；配额和预算控制；异步落库、对账。
- 可观测：首 token 延迟、每 token 延迟、排队时间、各模型的错误率和吞吐、GPU 利用率。

### 42. 【专家】设计一个视频生产任务调度平台（多阶段、可重试、可观测）。
**答案：**

  - 阶段级别的自动重试：区分可重试和不可重试的错误，有次数上限。

  - 重试时保留原始的失败信息。
- 可观测：每个任务的阶段时间线；各阶段的耗时分布、成功率、积压量；失败告警和群通知；可用率等统计数据。
- 扩展：新的生产方案（如长底板循环方案跳过衔接视频的生成和质检）通过任务类型字段区分流程，复用状态枚举，不影响存量链路。

## 性能与容量

### 43. 【高频】压测怎么做？压测指标看什么？
**答案：**
- 准备：
  - 明确目标（预期的 QPS、延迟要求）。
  - 压测环境尽量接近线上（配置、数据量），或者在线上做隔离的全链路压测（流量染色，压测数据写入影子库表）。
  - 构造接近真实分布的请求数据。
  - 下游依赖要么一起压测，要么 mock 掉。
- 执行：从低到高逐步加压（阶梯式），找到拐点（继续加压 QPS 不再上升、延迟急剧增大的点）；稳定性压测要持续较长时间（观察内存泄漏）；还可以做突发流量测试。
- 工具：wrk、hey、ab、JMeter、Locust、k6。
- 指标：
  - 吞吐：QPS、TPS。
  - 延迟：P50、P95、P99、最大值。
  - 错误率。
  - 资源：CPU、内存、GC、协程数、连接数、数据库和 Redis 的负载。
- 分析：用 pprof 等工具定位瓶颈，优化后再次压测验证。
- 可举例：agent-mount 优化用 hey（100 个请求，并发 10）压测，配合 pprof 查看协程、内存分配、堆、阻塞、锁的情况；平均耗时从 3.23s 降到 0.197s，Requests/sec 从 3.09 提升到 50.6。

### 44. 【高频】线上接口突然变慢，排查思路是什么？
**答案：**
- 先止损：判断影响面；如果有刚上线的变更，优先回滚；扩容、限流、降级非核心功能。
- 确定范围：所有接口都慢还是个别接口慢？所有实例都慢还是个别实例？从什么时候开始的？和变更、流量变化、依赖的告警在时间上是否吻合？
- 逐层排查：
  - 流量：QPS 是否突增，是否有异常请求（刷量、超大请求）。
  - 自身：CPU、内存、GC、协程数、连接池是否打满、锁竞争（用 pprof）。
  - 下游：用 trace 查看是哪个依赖变慢了（数据库慢查询、Redis 延迟、第三方接口、模型服务）。
  - 基础设施：网络、磁盘、宿主机、容器资源限制。
- 定位根因并修复，最后复盘：补充监控、告警和预案。

### 45. CPU 飙高、内存泄漏怎么排查？
**答案：**
- CPU 飙高：
  - 用 top 确认是哪个进程。
  - Go 程序：用 `go tool pprof http://host/debug/pprof/profile?seconds=30` 采集 CPU profile，看火焰图中的热点函数。常见原因有死循环、大量序列化和反序列化、正则表达式、频繁的内存分配导致 GC 占用高、锁的自旋。
  - 其他语言：Java 用 jstack 加 top -H 找到占用高的线程。
- 内存泄漏：
  - 观察内存是否持续增长、不回落。
  - Go 程序：对比两个时间点的 heap profile（`-base` 参数）找出增长的部分；查看 goroutine profile，确认协程数是否持续增长（goroutine 泄漏是最常见的原因）。
  - 常见原因：goroutine 阻塞在 channel 上无法退出；没有上限的缓存或 map；没有正确取消的 Ticker、timer；切片引用了大数组导致整个数组无法回收；连接或响应体没有关闭。
- 预防：常态化开启 pprof 端点（做好鉴权）；监控协程数、内存、GC 频率。

### 46. 【专家】容量规划怎么做？怎么根据业务增长预估机器、存储、带宽？
**答案：**
- 输入：业务预期（DAU 增长、活动带来的峰值倍数），历史数据（日均和峰值 QPS 的比例、每个用户的请求量、每条数据的大小）。
- 计算：
  - 计算资源：峰值 QPS 除以单实例经过压测验证的安全 QPS（按 60% 到 70% 的水位计算），再乘以冗余系数（N+1、机房容灾），得到实例数。
  - 存储：每天新增的数据量乘以保留天数，乘以副本数，再乘以索引和碎片的系数，同时考虑冷热分层。
  - 带宽：峰值 QPS 乘以平均响应大小（加上请求大小），乘以安全系数。
  - 缓存：热数据量乘以单条数据的内存开销（包括数据结构本身的开销）。
- 依赖：下游（数据库、Redis、模型配额）的容量也要同步评估，系统的整体容量取决于最弱的那个环节。
- 验证：通过全链路压测验证，定期复核（如每个季度），活动前专门做一次评估。
- 可举例：数字人"最近使用"接口预估 Redis 约 0.9GB、MySQL 约 3000 万行；对话数据按 20T 的规模规划冷备方案。

### 47. 长尾延迟（P99）高怎么优化？请求对冲（hedged request）是什么？
**答案：**
- 常见原因：GC 停顿、个别慢实例、慢查询、锁竞争、排队、网络抖动、缓存未命中回源、一个请求依赖多个下游时的"木桶效应"。
- 优化：
  - 找出慢的请求，用 trace 分析它们的共同点。
  - 减少 GC（减少内存分配、对象池）。
  - 剔除慢实例（基于延迟的负载均衡）。
  - 设置合理的超时并快速失败。
  - 预热缓存，避免冷启动。
  - 减少串行依赖，改为并行。
- 请求对冲：
  - 第一个请求在一定时间（如 P95 延迟）内还没有返回时，再向另一个副本发送同样的请求，取最先返回的结果，取消另一个。
  - 只增加少量额外负载（约 5%），就能显著降低 P99。
  - 只适用于幂等的读请求；要限制对冲的比例，防止在系统整体变慢时放大流量。
- 参考 Google 的《The Tail at Scale》。

### 48. 连接池大小怎么设置？
**答案：**
- 不是越大越好：连接太多会增加数据库的上下文切换和内存开销，实例数量多时，总连接数（实例数乘以每个实例的连接池大小）可能超过数据库的上限。
- 估算：所需连接数 ≈ QPS × 平均每次查询的耗时（Little 定律），再留一些余量。例如 QPS 为 1000、平均查询耗时 5ms，大约只需要 5 个连接，留余量后设置为 10 到 20 个即可。
- Go 的 database/sql 参数：
  - SetMaxOpenConns：最大连接数，必须设置，防止打爆数据库。
  - SetMaxIdleConns：空闲连接数，设置得接近最大连接数可以减少频繁建连。
  - SetConnMaxLifetime：连接的最长存活时间，要小于数据库和中间设备的超时时间。
  - SetConnMaxIdleTime：空闲连接的最长保留时间。
- 观察指标：等待连接的次数和时长（db.Stats() 中的 WaitCount、WaitDuration），据此调整。
- 类似地，HTTP 客户端要设置 MaxIdleConnsPerHost（默认只有 2，高并发时会频繁建连）。

### 49. 【专家】大促/大型活动（如春节活动）前要做哪些准备？
**答案：**
- 容量评估：根据活动预期的峰值流量，评估每个环节的容量（服务、数据库、缓存、消息队列、第三方服务、模型配额），找出瓶颈后扩容或优化。
- 全链路压测：按预期峰值的 1.5 到 2 倍压测，验证容量和降级预案的效果。
- 预案：
  - 限流阈值的配置。
  - 降级开关（关闭哪些非核心功能、各自的触发条件）。
  - 熔断配置。
  - 应急方案（扩容流程、回滚流程、切换机房）。
  - 预案要提前演练。
- 预热：缓存预热、实例预热（数字人或 Agent 实例提前部署好）、CDN 预热、提前建好数据库连接。
- 变更管控：活动前后一段时间内封网，禁止非必要的变更。
- 监控和值班：活动专属大盘、关键指标告警、值班安排和沟通渠道。
- 活动后：复盘，回收扩容的资源。
- 可举例：CNY 活动的数字人"最近使用"接口，上线前做了容量预估。

### 50. 【专家】如何衡量一个系统的高可用程度？异地多活怎么设计？
**答案：**
- 衡量：
  - 可用性 = 正常服务的时间除以总时间，或者成功请求数除以总请求数。
  - 99.9% 对应每年约 8.76 小时的不可用时间；99.99% 约 52.6 分钟。
  - 还要看 MTTR（平均恢复时间）、MTBF（平均故障间隔）、RTO（故障后恢复服务需要的时间）、RPO（故障时最多丢失多长时间的数据）。
- 提升可用性的手段：消除单点、冗余部署、故障隔离、快速发现和恢复（监控、自动切换）、变更管控（灰度、回滚）。
- 异地多活：
  - 单元化：按用户（如 uid 取模）把流量和数据划分到不同的单元（机房），每个单元能独立完成该用户的全部业务，实现单元内闭环。
  - 数据同步：单元之间双向同步数据（防止循环复制、处理冲突）；全局数据（如配置、库存）由中心单元写入，同步到其他单元。
  - 流量调度：入口按路由规则分配单元；某个单元故障时，把它的流量切到其他单元。
  - 难点：
    - 数据冲突：同一条数据只允许在它所属的单元写入。
    - 同步延迟导致切换时可能丢失少量数据。
    - 强一致的业务难以做到多活。
    - 成本高。
- 根据业务的重要性选择：同城双活、两地三中心或异地多活。
