# 01 LLM 基础（40 题）（题目与答案）

标记：【高频】常被问到；【专家】考察深度，专家职级重点准备。

### 1. 【高频】Transformer 的整体结构是什么？Encoder、Decoder 分别做什么？
**答案：**
- 由 Encoder 和 Decoder 两部分堆叠组成，每层包含多头注意力、前馈网络（FFN）、残差连接和 LayerNorm。
- Encoder：对输入做双向自注意力，得到每个 token 的上下文表示，适合理解类任务（如 BERT）。
- Decoder：带因果掩码（causal mask）的自注意力，只能看到前面的 token，逐个生成；原始结构里还有 cross-attention 读取 Encoder 输出（如 T5、翻译模型）。
- 现在的大模型（GPT、LLaMA、文心）基本是 Decoder-only。

### 2. 【高频】Self-Attention 的计算过程是什么？为什么要除以 √d_k？
**答案：**
- 输入 X 分别乘 W_Q、W_K、W_V 得到 Q、K、V；计算 `softmax(QKᵀ/√d_k)·V`。
- QKᵀ 表示每个 token 对其他 token 的相关度，softmax 后作为权重对 V 加权求和。
- 除以 √d_k：Q·K 的方差随维度 d_k 线性增长，数值过大会让 softmax 进入饱和区，梯度接近 0；缩放后方差稳定在 1 左右，训练更稳定。
- 复杂度是 O(n²·d)，n 为序列长度，这是长上下文昂贵的根源。

### 3. Multi-Head Attention 的作用是什么？头数怎么影响效果和计算量？
**答案：**
- 把 d_model 拆成 h 个头，每个头在不同子空间学习不同的关注模式（语法、指代、位置等），最后拼接再线性变换。
- 总计算量和单头基本相同（每头维度是 d_model/h），只是表达更丰富。
- 头数太少表达能力受限；太多则单头维度过小，效果反而下降。常见配置是每头 64 或 128 维。

### 4. 【专家】MHA、MQA、GQA 的区别是什么？对推理显存和速度有什么影响？
**答案：**
- MHA：每个头都有独立的 K、V。
- MQA：所有头共享一组 K、V，KV Cache 缩小到 1/h，推理快，但效果有损失。
- GQA：把头分成 g 组，每组共享 K、V，是两者的折中（LLaMA2-70B、LLaMA3 采用）。
- 推理的 decode 阶段主要受显存带宽限制，KV Cache 越小，能支持的并发和上下文越长，速度越快。
- 取舍：GQA 在效果接近 MHA 的前提下，把 KV Cache 降到 g/h。

### 5. 位置编码有哪些方案？绝对位置编码、RoPE、ALiBi 各有什么特点？
**答案：**
- 注意力本身不感知顺序，需要位置编码。
- 绝对位置编码：正弦或可学习向量加到输入上，实现简单，但很难外推到训练时没见过的长度。
- RoPE：把位置信息以旋转的方式乘到 Q、K 上，使注意力分数只依赖相对位置，是目前主流（LLaMA、Qwen）。
- ALiBi：不加位置向量，而是在注意力分数上按距离加线性惩罚，外推能力较好。

### 6. 【专家】RoPE 为什么能做长度外推？NTK-aware、YaRN 等外推方法的思路是什么？
**答案：**
- RoPE 本身外推能力有限：超出训练长度时，高频维度上会出现没训练过的旋转角度，效果下降。
- 位置插值（PI）：把新位置线性压缩到训练范围内，代价是相邻位置分辨率降低，通常需要少量微调。
- NTK-aware：调大 RoPE 的底数 base，高频维度基本不变、低频维度被插值，兼顾局部精度和远距离。
- YaRN：按频率分段处理，再加注意力温度修正，用少量长文本微调就能把上下文扩展数倍。
- 工程上通常是"改 RoPE 参数 + 少量长文本继续训练"。

### 7. Decoder-only 架构为什么成为大模型主流？
**答案：**
- 训练目标统一（预测下一个 token），可以直接用海量无标注文本，规模化最简单。
- 因果注意力天然适合生成，也能通过 Prompt 完成理解类任务。
- 推理时可以复用 KV Cache，工程实现简单。
- 实验上在相同算力下，Decoder-only 的 zero-shot 和 few-shot 泛化表现更好。

### 8. 【高频】什么是 KV Cache？为什么能加速推理？它的显存占用怎么估算？
**答案：**
- 自回归生成时，前面 token 的 K、V 不会变化，缓存下来，每步只需计算新 token 的 Q、K、V，避免重复计算。
- 显存估算：`2（K 和 V）× 层数 × KV 头数 × 每头维度 × 序列长度 × batch × 每个元素字节数`。
- 例：一个 32 层、32 个 KV 头、每头 128 维的模型，用 FP16 时每个 token 约 0.5MB；4K 上下文约 2GB。
- 优化方向：GQA/MQA、KV 量化（INT8/FP8）、PagedAttention、前缀缓存复用。

### 9. 【专家】PagedAttention（vLLM）解决了什么问题？原理是什么？
**答案：**
- 问题：传统实现按最大长度为每个请求预分配连续的 KV 显存，实际生成长度不确定，造成大量内部碎片和浪费，并发上不去。
- 原理：借鉴操作系统的虚拟内存分页，把 KV Cache 切成固定大小的块（block），通过块表把逻辑位置映射到物理块，按需分配。
- 收益：显存利用率接近满载，同样显存可以承载更多并发请求；还能在多个请求间共享相同前缀的块（如同一个 System Prompt、并行采样）。
- 代价：注意力计算要按块表做非连续访存，需要专门的 kernel。

### 10. 【专家】Prefill 和 Decode 两个阶段的计算特点有什么不同？为什么要分开优化？
**答案：**
- Prefill：一次性处理整段输入，矩阵乘法规模大，属于计算密集型，决定首 token 延迟。
- Decode：每步只生成一个 token，要读取全部权重和 KV Cache，属于访存密集型，决定每 token 延迟。
- 两者混在同一批次时会互相干扰：长 Prompt 的 prefill 会拖慢其他请求的 decode。
- 优化手段：Chunked Prefill（把长 prefill 切块和 decode 混排）、PD 分离（prefill 和 decode 放在不同机器上，分别扩容）。

### 11. 【高频】首 token 延迟（TTFT）和每 token 延迟（TPOT）分别受什么因素影响？怎么优化？
**答案：**
- TTFT：受输入长度、排队时间、prefill 算力、前面的检索和工具调用耗时影响。优化手段有缩短 Prompt、前缀缓存（Prompt Caching）、减少串行前置步骤、扩容降低排队。
- TPOT：受模型大小、显存带宽、batch 大小、KV Cache 长度影响。优化手段有量化、GQA、投机解码、合适的并发数。
- Agent 场景：用户感知的"首 token"还包含意图识别、RAG、工具调用等前置耗时，往往比模型本身更大，要做全链路拆解。

### 12. Continuous Batching 和静态 Batching 的区别是什么？
**答案：**
- 静态 Batching：一批请求一起开始，必须等最长的那条生成完才释放，短请求空等，GPU 利用率低。
- Continuous Batching：以每个 decode 步为粒度调度，有请求结束就立即换入新请求。
- 效果：吞吐通常能提升数倍，平均延迟也下降，是 vLLM、TGI 等推理框架的标配。

### 13. 【专家】投机解码（Speculative Decoding）的原理是什么？什么场景收益大？
**答案：**
- 用一个小的草稿模型（或 Medusa 多头、EAGLE 等方法）快速猜出接下来 k 个 token，再用大模型一次前向并行验证。
- 被接受的 token 直接输出，第一个不一致的位置用大模型的结果替换；数学上保证输出分布和只用大模型一致。
- 收益取决于接受率：输出可预测性高的场景（代码补全、模板化回复、改写）效果好；高温度的创意写作收益小。
- 代价：多部署一个草稿模型，batch 很大时收益会下降。

### 14. 【高频】Temperature、Top-k、Top-p 分别是什么？怎么影响输出？
**答案：**
- Temperature：把 logits 除以 T 再 softmax。T 越小分布越尖锐，输出越确定；T 越大越随机。
- Top-k：只在概率最高的 k 个 token 中采样。
- Top-p（核采样）：只在累计概率达到 p 的最小 token 集合中采样，候选数量会随分布自适应。
- 实践：结构化输出、工具调用、分类用低温度（0 到 0.3）；创意写作用较高温度。通常调 Temperature 和 Top-p 其中一个即可。

### 15. Greedy、Beam Search、采样解码各适合什么场景？
**答案：**
- Greedy：每步取概率最大的 token，确定性强，但容易重复、内容平淡。
- Beam Search：保留多条候选序列，适合翻译、摘要这类有标准答案的任务；用于开放式对话时输出容易趋同、变得无聊。
- 采样解码：配合 Temperature 和 Top-p，适合对话和创作，是大模型对话的主流方式。

### 16. 重复惩罚（repetition penalty）、频率惩罚、存在惩罚有什么区别？
**答案：**
- 重复惩罚：对已经出现过的 token 的 logits 按系数缩放（如除以 1.1），不管出现了几次。
- 频率惩罚：按 token 已出现的次数线性扣分，出现越多扣得越多。
- 存在惩罚：只要出现过就固定扣一次分，用来鼓励模型引入新话题。
- 惩罚过大会导致模型回避必要的重复词（如专有名词、代码变量名），需要按任务调整。

### 17. 【高频】Tokenizer 有哪些方案（BPE、WordPiece、SentencePiece）？中文 token 计费为什么更贵？
**答案：**
- BPE：从字符开始反复合并出现频率最高的相邻对，GPT 系列使用（byte-level BPE 可以覆盖任意字符）。
- WordPiece：合并标准是提升语言模型似然，BERT 使用。
- SentencePiece：直接在原始文本上训练，不依赖空格分词，支持 BPE 和 Unigram，适合中文等无空格语言。
- 中文更贵：如果词表里中文词条少，一个汉字可能被拆成多个 byte token；同样语义的中文比英文 token 数更多。中文优化过的模型（如文心、Qwen）一个 token 大约对应 1 到 2 个汉字。

### 18. 上下文窗口长度受什么限制？长上下文模型就不需要 RAG 了吗？
**答案：**
- 限制因素：注意力计算量随长度平方增长；KV Cache 显存随长度线性增长；训练时的长度和位置编码外推能力。
- 仍然需要 RAG：知识库往往远超任何上下文窗口；全量塞入成本高、延迟大；长上下文中间部分的信息容易被忽略；RAG 更容易做权限控制、实时更新和引用溯源。
- 实践：长上下文和 RAG 结合，用 RAG 粗召回，用长上下文容纳更多候选和整篇文档。

### 19. 【专家】Lost in the Middle 现象是什么？对 Prompt 和 RAG 设计有什么启发？
**答案：**
- 现象：关键信息放在长上下文的开头或结尾时模型利用得好，放在中间时效果明显下降，表现为 U 形曲线。
- 对 Prompt：关键指令放在开头的 System Prompt，或在结尾再重申一次；不要把重要约束埋在大段材料中间。
- 对 RAG：控制 top-k，不要无脑多塞；rerank 后把最相关的片段放在首尾；对片段做去重和压缩。
- 新模型有所改善，但在自己的业务上仍应实测。

### 20. 【高频】预训练、SFT、RLHF 三个阶段分别做什么？
**答案：**
- 预训练：在海量文本上做下一个 token 预测，学到语言能力和世界知识，得到基座模型。
- SFT（监督微调）：用高质量的"指令-回答"数据训练，让模型学会遵循指令和对话格式。
- RLHF/偏好对齐：用人类偏好数据让模型更有用、更安全、更符合人类期望，减少有害和无用回答。
- 三个阶段的数据量依次大幅减少，数据质量要求依次升高。

### 21. RLHF 中奖励模型怎么训练？PPO 的大致流程是什么？
**答案：**
- 奖励模型：对同一个 Prompt 采样多个回答，由人工排序；用成对排序损失训练，使优选回答得分更高。
- PPO 流程：策略模型生成回答，奖励模型打分，再加上与参考模型的 KL 惩罚（防止偏离太远），然后用 PPO 更新策略。
- 训练时需要同时运行策略模型、参考模型、奖励模型、价值模型四个模型，工程复杂、成本高、训练不稳定。

### 22. 【专家】DPO 和 PPO 的区别是什么？GRPO 有什么特点？
**答案：**
- DPO：直接用偏好对（好回答和差回答）构造损失函数，不需要单独训练奖励模型，也不需要强化学习采样，训练像 SFT 一样稳定、成本低；缺点是依赖离线偏好数据，探索能力弱。
- PPO：在线采样加奖励模型，上限更高，但复杂且不稳定。
- GRPO（DeepSeek 提出）：对同一个 Prompt 采样一组回答，用组内的相对得分作为优势，去掉了价值模型，省显存；适合数学、代码这类可以用规则判定对错的任务，是 DeepSeek-R1 推理能力训练的关键。

### 23. 【高频】LoRA 的原理是什么？rank 怎么选？QLoRA 又做了什么？
**答案：**
- 原理：冻结原始权重 W，旁路加一个低秩分解 ΔW = B·A（r 远小于 d），只训练 A 和 B，可训练参数通常只有原模型的千分之几到百分之几。
- rank 选择：常用 8 到 64。任务简单、数据少时 r 取小值；任务复杂、和原能力差距大时取大值；另有缩放系数 alpha 配合使用。
- 推理时可以把 B·A 合并回 W，不增加延迟；也可以在同一个基座上热切换多个 LoRA。
- QLoRA：基座用 4-bit NF4 量化后冻结，LoRA 部分仍用 16 位训练，再配合分页优化器，让单卡也能微调大模型。

### 24. 全参微调、LoRA、Prompt Tuning、P-Tuning 怎么选型？
**答案：**
- 全参微调：效果上限最高，但显存和存储成本大，容易灾难性遗忘；适合数据多、有充足算力、需要深度改变模型能力的场景。
- LoRA：效果接近全参，成本低，可以多任务热插拔，是目前的默认选择。
- Prompt Tuning / P-Tuning：只训练少量虚拟 token 的嵌入，参数最少，但在小模型上效果不稳定，现在用得较少。
- 选型顺序：先用 Prompt 和 RAG 能否解决；不行再考虑 LoRA；最后才是全参。

### 25. 【高频】什么时候应该微调，什么时候用 RAG 或 Prompt 就够了？
**答案：**
- 缺知识（企业文档、实时信息）：用 RAG。知识会变化，需要引用和权限控制，微调做不到。
- 缺格式和风格（固定输出结构、话术风格）：先用 Prompt 和 few-shot，不稳定再微调。
- 缺能力（特定领域推理、专有任务）或需要降本（用小模型替代大模型）：用微调或蒸馏。
- 判断依据：Prompt 迭代后效果到顶、有足够高质量数据（通常上千条）、调用量大到成本敏感时，才值得微调。

### 26. 微调数据怎么构造？数据量、质量、多样性哪个更重要？
**答案：**
- 来源：线上真实日志筛选、人工标注、用强模型生成后人工审核、从 badcase 中修正。
- 质量最重要：少量高质量数据（几千条）通常胜过大量噪声数据；错误标注会被模型学进去。
- 多样性其次：要覆盖意图、句式、难度和边界情况，否则模型会过拟合到少数模式。
- 实践：去重、清洗、留出评测集；混入一部分通用数据，防止通用能力下降。

### 27. 灾难性遗忘是什么？微调时怎么缓解？
**答案：**
- 现象：在新任务上微调后，模型原有的通用能力（对话、推理、其他任务）明显下降。
- 缓解手段：
  - 用 LoRA 等参数高效方法，保留原始权重不动。
  - 混入通用数据或原始指令数据一起训练。
  - 降低学习率、减少训练轮数。
  - 在通用评测集上持续监控回归。

### 28. 【高频】模型量化（INT8、INT4、GPTQ、AWQ）的原理和精度损失怎么权衡？
**答案：**
- 原理：把 FP16 的权重（或激活）映射到低比特整数，减少显存占用和访存量，加快 decode。
- INT8：精度损失通常很小，可以放心用。INT4：显存约为 FP16 的四分之一，有一定精度损失，大模型比小模型更能承受。
- GPTQ：基于二阶信息逐层量化，最小化输出误差。AWQ：识别对激活影响大的少量重要权重并保护它们，效果和速度都较好。
- 权衡：上线前在业务评测集上对比量化前后的效果；对精度敏感的任务（数学、代码、结构化输出）要格外验证。

### 29. 模型蒸馏的原理是什么？在 Agent 场景怎么用小模型替代大模型？
**答案：**
- 原理：用大模型（教师）的输出或概率分布作为监督信号训练小模型（学生），让小模型以更低成本逼近大模型效果。
- Agent 中的用法：把意图识别、路由、工具参数抽取、query 改写、追问生成等高频、窄任务的环节，用大模型批量生成标注数据，再训练小模型替代。
- 收益：延迟和成本大幅下降，适合 QPS 高的环节。
- 注意：建立评测集，持续对比小模型和大模型的效果，设置回退到大模型的兜底。

### 30. MoE 架构的原理是什么？推理时有什么挑战？
**答案：**
- 原理：把 FFN 替换成多个专家网络，由路由器为每个 token 选择 top-k 个专家（如 8 选 2），总参数量很大，但每个 token 实际计算的参数少。
- 优点：在相同计算量下获得更大的模型容量（如 Mixtral、DeepSeek-V3）。
- 推理挑战：所有专家都要常驻显存，总显存需求大；专家负载不均衡；多卡部署需要专家并行，存在大量跨卡通信；小 batch 时效率不高。

### 31. 【高频】大模型幻觉产生的原因有哪些？工程上怎么缓解？
**答案：**
- 原因：训练数据中有错误或过时信息；模型的训练目标是生成"看起来合理"的文本，而不是"正确"的文本；知识没有覆盖到；解码时的随机性。
- 工程缓解：
  - 用 RAG 提供可靠资料，要求基于资料回答并带引用。
  - 在 Prompt 中允许模型回答"不知道"。
  - 降低温度。
  - 对关键事实做后置校验（规则、检索比对、第二个模型复核）。
  - 能用工具获取的数据（价格、时间、计算）一律调用工具，不让模型凭记忆回答。

### 32. 推理模型（如 o1、DeepSeek-R1）和普通指令模型在使用上有什么区别？
**答案：**
- 推理模型在给出答案前会进行较长的内部思考，擅长数学、代码、多步推理和规划。
- 使用区别：
  - Prompt 更简洁，直接说清目标和约束，不需要写"一步步思考"，few-shot 有时反而有害。
  - 延迟高、输出 token 多、成本高。
  - 不适合简单问答和对延迟敏感的实时场景。
- Agent 中常见做法：规划、复杂决策环节用推理模型，执行和对话环节用普通模型。

### 33. 【专家】思维链（CoT）为什么能提升推理能力？对延迟和成本有什么影响？
**答案：**
- 原因：模型每生成一个 token 只能做固定量的计算；把中间步骤写出来，相当于给复杂问题分配了更多计算步骤，每步只需解决一个简单子问题，前面写出的中间结果也可以作为后续推理的依据。
- 影响：输出 token 成倍增加，延迟和成本随之上升；对简单任务没有收益，甚至可能"想多了"出错。
- 工程取舍：
  - 只对复杂任务开启 CoT；简单任务直接回答。
  - 思考内容可以不展示给用户，或折叠展示。
  - 用路由按问题难度选择模型和是否推理。
  - 对高频任务，可以把带 CoT 的输出蒸馏给小模型。

### 34. 结构化输出（JSON Mode、约束解码）是怎么实现的？
**答案：**
- Prompt 约束：在 Prompt 中给出 schema 和示例，让模型按格式输出。实现最简单，但不能保证 100% 合法。
- JSON Mode / Structured Outputs：服务端在解码时限制只能生成符合 JSON 语法或指定 JSON Schema 的 token。
- 后置处理：解析失败时尝试修复（补括号、去掉 markdown 代码块），或者带上错误信息让模型重试。
- 生产建议：优先使用供应商的原生结构化输出能力，同时保留校验和重试兜底。

### 35. 【专家】Grammar-constrained decoding 的原理是什么？和后置校验重试相比有什么优劣？
**答案：**
- 原理：把 JSON Schema 或正则、上下文无关文法编译成状态机；每一步解码时根据当前状态计算哪些 token 合法，把不合法 token 的 logits 置为负无穷（如 Outlines、XGrammar、llama.cpp 的 GBNF）。
- 优势：保证格式 100% 合法，不需要重试，节省延迟和成本。
- 劣势：
  - 需要能控制推理引擎，调用闭源 API 时做不到。
  - 文法复杂时每步都有额外计算开销。
  - 强制格式可能干扰模型推理，导致内容质量下降。
  - 只保证格式合法，不保证语义正确（字段值仍可能是错的）。
- 后置校验重试：通用、实现简单，但失败时延迟翻倍。实践中两者常一起用：约束解码保格式，后置校验保语义。

### 36. Embedding 模型和生成模型的训练目标有什么不同？
**答案：**
- 生成模型：目标是预测下一个 token，学习的是生成文本的概率分布。
- Embedding 模型：目标是把语义相近的文本映射到向量空间中相近的位置，通常用对比学习（如 InfoNCE）训练，即拉近正样本对（query 和相关文档）、推远负样本。
- 训练关键：难负样本挖掘、大 batch、指令前缀（区分 query 和文档）。
- 生成模型的隐藏层可以直接拿来当 embedding，但效果通常不如专门训练的 embedding 模型。

### 37. 多模态大模型（图文）一般怎么把图像接入语言模型？
**答案：**
- 常见结构：视觉编码器（如 ViT、CLIP）、投影层（MLP 或 Q-Former）、语言模型三部分。
- 图像切成 patch 后编码成向量，通过投影层映射到语言模型的词向量空间，当作"图像 token"和文本拼接在一起输入。
- 训练分两阶段：先对齐（训练投影层，让图像特征能被语言模型理解），再做指令微调（学会看图回答问题）。
- 工程注意：高分辨率图片会产生大量图像 token，要控制分辨率或切图策略，以控制成本和延迟。

### 38. 【高频】如何评估一个大模型在你业务上的效果？
**答案：**
- 构建业务评测集：从线上真实 query 中抽样，覆盖主要意图和难例，并持续加入 badcase。
- 定义指标：准确率、满意度、格式合规率、badcase 率、延迟、成本，按业务目标选取。
- 评估方式：能用规则判定的用自动化评估；开放式回答用 LLM-as-a-Judge，再用人工抽样校准；关键结论以人工评估为准。
- 上线验证：离线评估通过后，再用 AB 实验看线上指标。
- 可举例：资源型智能体追问优化，用 150 条追问人工评估，badcase 率从 20% 降到 4.67%。

### 39. 私有化部署大模型需要考虑哪些问题（显存、吞吐、并发、成本）？
**答案：**
- 显存：模型权重（参数量乘以每参数字节数）加 KV Cache 加运行时开销，要按最大并发和上下文长度预留。
- 吞吐和延迟：选择推理框架（vLLM、TensorRT-LLM、SGLang），配置 batch、并行方式（TP/PP），根据 TTFT 和 TPOT 目标调优。
- 量化：在效果可接受的前提下降低显存和成本。
- 运维：模型版本管理、灰度发布、监控（GPU 利用率、排队长度、延迟）、弹性扩缩容、故障切换。
- 成本：比较自建 GPU 和调用 API 的单位成本；调用量小时 API 往往更划算。
- 合规：数据不出域、日志脱敏、模型许可证（license）。

### 40. 【专家】给定 QPS 和平均输入输出长度，怎么估算需要多少张 GPU？
**答案：**
- 第一步，确定单卡（或单个模型实例）能承载的容量：在目标 TTFT 和 TPOT 约束下压测，得到单实例最大并发数 C，以及吞吐（输出 token/s）。
- 第二步，按 Little 定律算所需并发：单请求耗时 T ≈ TTFT + 输出长度 × TPOT；系统中同时在处理的请求数 ≈ QPS × T。
- 第三步，所需实例数 ≈ QPS × T / C，再乘以 1.3 到 1.5 的冗余系数（应对峰值和故障）。实例数乘以每个实例的 GPU 数，就是总卡数。
- 示例：QPS=10，每请求平均 5 秒，则同时约有 50 个请求；若单实例在延迟达标时支持 16 个并发，需要约 4 个实例，加冗余取 5 到 6 个。
- 注意：输入越长 prefill 越重，输出越长 decode 占用越久；理论估算只能作参考，最终以压测数据为准。
