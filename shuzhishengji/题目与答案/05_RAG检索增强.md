# 05 RAG 检索增强生成（50 题）（题目与答案）

### 1. 【高频】RAG 的完整流程是什么？离线和在线分别做什么？
**答案：**
- 离线（建索引）：文档接入 → 解析（pdf、docx、网页转文本）→ 清洗 → 切分成 chunk → 生成 embedding → 写入向量库，同时建立关键词索引，保存元数据（来源、权限、时间）。
- 在线（问答）：query 理解和改写 → 检索（向量加关键词）→ 过滤（权限、时间）→ 融合排序 → rerank → 选出 top-k 拼接进 Prompt → 模型生成答案并带引用 → 后处理（引用校验、内容审核）。
- 配套：评估、badcase 闭环、索引增量更新。

### 2. 【高频】RAG 解决了大模型的哪些问题？又带来了哪些新问题？
**答案：**
- 解决的问题：
  - 知识过时（可以实时更新知识库）。
  - 缺少私有知识（企业文档）。
  - 幻觉（基于资料回答，可以溯源）。
  - 权限控制（按用户过滤可见文档）。
  - 比微调成本低。
- 新问题：
  - 检索不准时，模型会被错误资料误导。
  - 链路变长，延迟增加。
  - 切分、索引、评估的工程复杂度。
  - 上下文变长，成本增加。
  - 多跳推理、全局汇总类问题（如"总结所有文档"）效果差。
  - 文档中的注入风险。

### 3. 【高频】文档切分（Chunking）有哪些策略？chunk 大小和重叠怎么定？
**答案：**
- 策略：
  - 固定长度切分：按 token 数，最简单。
  - 递归切分：按段落 → 句子 → 字符逐级切分，尽量保持语义完整。
  - 按文档结构切分：按标题、章节、表格。
  - 语义切分：按相邻句子的 embedding 相似度变化处切开。
- 大小：常用 256 到 1024 个 token。太小则上下文不完整、语义残缺；太大则包含的噪声多，embedding 被稀释，占用上下文多。FAQ、短问答用小 chunk，说明书、长文用大 chunk。
- 重叠：通常是 chunk 大小的 10% 到 20%，防止关键信息恰好被切断。
- 最终以评测集上的召回率为准，做几组参数对比实验。

### 4. 【专家】语义切分、按结构切分（标题层级）、父子 chunk 各有什么优劣？
**答案：**
- 语义切分：切分点在语义边界上，chunk 内容更连贯；但需要计算 embedding，成本高，chunk 长度不均匀，阈值难以调整。
- 按结构切分：利用标题层级、段落、列表，符合作者的组织方式，还可以把标题路径作为元数据加到 chunk 上，提升检索效果；依赖文档格式规范，扫描件和排版混乱的文档效果差。
- 父子 chunk：用小 chunk（子）做检索，精度高；命中后返回它所在的大 chunk（父）或整节内容给模型，上下文完整。兼顾检索精度和上下文完整性；代价是存储结构更复杂，上下文占用更多。
- 实践：先按结构切分，过长的部分再递归切分，配合父子 chunk 召回；每个 chunk 前面加上文档标题和章节路径。

### 5. 表格、图片、公式等非文本内容怎么入库？
**答案：**
- 表格：
  - 小表格整体转成 markdown 或 HTML 作为一个 chunk，保留表头。
  - 大表格按行分组切分，每组都带上表头。
  - 可以再用模型生成一段表格摘要，单独索引。
- 图片：用 OCR 提取文字；用多模态模型生成图片描述（caption）后索引文本；或者用多模态 embedding（如 CLIP）直接对图片建索引。命中后可以把原图交给多模态模型。
- 公式：转成 LaTeX 文本保存。
- 都要保留与原文位置的关联，方便引用和展示原图。

### 6. PDF 解析有哪些难点？版面分析、OCR 怎么选型？
**答案：**
- 难点：
  - 多栏排版导致阅读顺序错乱。
  - 页眉、页脚、页码混入正文。
  - 跨页的表格和段落。
  - 扫描件没有文本层。
  - 公式、图表、复杂表格（合并单元格）。
  - 加密或字体编码问题导致乱码。
- 选型：
  - 有文本层的规范文档：直接提取文本（如 PyMuPDF、pdfplumber），速度快。
  - 复杂版面：使用版面分析模型（识别标题、段落、表格、图片区域）加阅读顺序恢复，如开源的 MinerU、Marker，或云服务的文档解析能力。
  - 扫描件：OCR（如 PaddleOCR），表格单独做表格结构识别。
  - 多模态大模型直接把页面转成 markdown：效果好，但成本高、速度慢，适合高价值文档。
- 按文档的价值和类型路由到不同的解析方案。

### 7. 【高频】Embedding 模型怎么选？中文场景有哪些常用模型？
**答案：**
- 选型依据：
  - 在自己业务数据上的检索效果（最重要；公开榜单如 MTEB/C-MTEB 只作参考）。
  - 支持的最大输入长度、向量维度（影响存储和速度）。
  - 多语言能力、推理成本、是否可以私有化部署。
- 中文常用：BGE 系列（如 bge-m3，支持多语言、长文本、稠密加稀疏检索）、GTE 系列、各云厂商的 embedding 服务（如百度千帆、通义）。
- 注意：
  - query 和文档要用同一个模型。
  - 有些模型要求在 query 前加指令前缀。
  - 换模型需要重建全部索引。

### 8. Embedding 的维度高低对效果和成本有什么影响？
**答案：**
- 维度高：表达能力强，但存储（维度乘以 4 字节乘以向量数）、内存、检索计算量都随之增加。
- 维度低：成本低、检索快，但可能损失精度。
- 收益递减：超过一定维度后，效果提升有限。
- 降维手段：支持 Matryoshka（套娃）表示的模型可以直接截断前 N 维使用；也可以用量化（PQ、二值化）压缩存储。
- 估算示例：1 亿个 1024 维的 float32 向量，约需 400GB 原始存储，还不算索引开销。

### 9. 【高频】向量检索为什么要用 ANN？精确检索有什么问题？
**答案：**
- 精确检索（暴力计算）：query 要和每个向量计算距离，复杂度是 O(N·d)，数据量到百万、千万级时延迟和 CPU 开销无法接受。
- ANN（近似最近邻）：用索引结构牺牲少量召回率，换取数量级的速度提升，查询复杂度接近对数级。
- 衡量：召回率（和精确结果的重合度）、延迟、QPS、内存占用，通过索引参数在它们之间权衡。
- 数据量小（几万条以内）时，暴力检索就够用了，而且结果精确。

### 10. 【高频】HNSW 的原理是什么？M、efConstruction、efSearch 怎么调？
**答案：**
- 原理：多层的近邻图（借鉴跳表）。上层节点少、边跨度大，用于快速定位到大致区域；下层节点多、连接密，用于精细搜索。查询时从顶层入口开始贪心搜索，逐层向下。
- M：每个节点的最大连接数。越大召回越高，但内存占用和建索引时间增加，常用 16 到 64。
- efConstruction：建索引时的候选队列大小。越大图的质量越好，召回越高，但建索引越慢，常用 100 到 500。
- efSearch（ef）：查询时的候选队列大小，必须大于等于 top-k。越大召回越高，但查询越慢，是线上最常调的参数，可以按请求动态设置。
- 特点：召回高、速度快；缺点是内存占用大（全部在内存中），删除操作不友好。

### 11. IVF、PQ、IVF-PQ 的原理是什么？和 HNSW 怎么选？
**答案：**
- IVF：先用 k-means 把向量聚成 nlist 个簇，查询时只搜索离 query 最近的 nprobe 个簇。nprobe 越大召回越高、速度越慢。
- PQ（乘积量化）：把向量切成 m 段，每段用码本中的编号表示，大幅压缩存储（可以压缩几十倍），用查表近似计算距离，会损失精度。
- IVF-PQ：两者结合，先用 IVF 粗筛，簇内用 PQ 压缩后的向量计算距离，适合超大规模、内存有限的场景。
- 选择：
  - 内存充足、追求高召回和低延迟：HNSW。
  - 数据规模极大、内存受限：IVF-PQ（或 IVF-SQ8），通常加 rerank 弥补精度。
  - 需要频繁全量重建的批量场景：IVF 建索引更快。

### 12. 【专家】DiskANN 解决了什么问题？什么场景适合用？
**答案：**
- 问题：HNSW 需要把全部向量和图放在内存中，十亿级数据的内存成本过高。
- 原理：基于 Vamana 图算法构建图索引存放在 SSD 上；内存中只保留 PQ 压缩后的向量，用于在搜索时快速估算距离、引导路径；只对少量候选点从磁盘读取原始向量做精确计算。通过控制访问磁盘的次数，在 SSD 上实现毫秒级查询。
- 适合：数据量很大（亿级到十亿级）、对成本敏感、可以接受比纯内存方案稍高的延迟。
- Milvus 等向量库都支持 DiskANN 索引。

### 13. 【高频】向量数据库怎么选型（Milvus、Elasticsearch、pgvector、Faiss）？
**答案：**
- Faiss：是一个库，不是数据库。性能好、索引类型全，但没有持久化、分布式、过滤、增删改等能力，适合嵌入到自己的服务中，或离线批量计算。
- Milvus：专门的分布式向量数据库，支持多种索引、标量过滤、多租户（partition）、水平扩展，适合千万到十亿级的专门向量检索场景；运维组件较多。
- Elasticsearch：已经在用 ES 做全文检索时，可以直接用它的向量能力，天然支持混合检索；大规模时向量检索的性能和资源效率不如专门的向量库。
- pgvector：PostgreSQL 的扩展，数据和业务表放在一起，支持事务和 SQL 关联查询，适合百万级以内、追求架构简单的场景。
- 选型维度：数据规模、QPS 和延迟要求、是否需要混合检索和复杂过滤、团队现有技术栈、运维成本。

### 14. 【专家】Milvus 的架构是什么样的？数据写入、索引构建、查询的流程分别是什么？
**答案：**
- 架构：存储和计算分离，分为四层。
  - 接入层（Proxy）：接收请求、校验、路由。
  - 协调层（Coordinator）：管理元数据、调度数据和索引任务。
  - 执行节点：DataNode 负责写入、QueryNode 负责查询、IndexNode 负责建索引。
  - 存储层：etcd 存元数据，消息队列（Pulsar 或 Kafka）作为日志，对象存储（MinIO、S3）存数据和索引文件。
- 写入：数据进入消息队列的通道（每个分片对应一个虚拟通道）；DataNode 消费后在内存中形成"增长中的段"；达到阈值后封存（seal）成段，写入对象存储。
- 索引构建：段封存后，由 IndexNode 为其构建索引，存到对象存储。
- 查询：QueryNode 加载已封存段的索引；同时订阅消息队列，处理增长中的段（暴力搜索）；Proxy 汇总各节点的结果后返回 top-k。
- 一致性级别可以配置（强一致、有界过期、会话一致、最终一致），用来权衡新写入数据的可见性和延迟。

### 15. 向量库中的标量过滤（metadata filter）怎么做？前过滤和后过滤有什么区别？
**答案：**
- 用途：按租户、权限、时间、类别等条件过滤，如 `tenant_id = x AND date > y`。
- 后过滤：先做向量检索取出 top-k，再按条件过滤。实现简单，但过滤条件很严格时，结果可能远少于 k 条，甚至为空。
- 前过滤：先按条件筛选出候选集，再在候选集中做向量检索，结果数量有保证；但在图索引中，过滤掉大量节点会让图的连通性变差，影响召回和速度。
- 向量库的做法：在搜索过程中用位图跳过不满足条件的点；过滤后剩余数据很少时自动退化为暴力搜索。
- 设计建议：高频的过滤维度（如租户）用 partition 或分区键做物理隔离，比运行时过滤更高效。

### 16. 【高频】混合检索（向量 + BM25）怎么做？结果怎么融合（RRF、加权）？
**答案：**
- 原因：向量检索擅长语义相似，但对专有名词、型号、编号、精确短语不敏感；BM25 擅长精确词匹配，两者互补。
- 做法：同一个 query 并行走向量检索和关键词检索，各取 top-N，然后融合。
- RRF（倒数排名融合）：`score = Σ 1/(k + rank_i)`，k 一般取 60。只看排名，不需要统一分数的尺度，简单稳健，是常用的默认方案。
- 加权融合：分别归一化两路分数后加权求和，可以调权重，但对分数分布敏感，需要调参。
- 融合后通常再经过 rerank 精排。
- 也可以使用稀疏向量（如 SPLADE、bge-m3 的稀疏输出）代替 BM25，统一在向量库中完成混合检索。

### 17. 【高频】Rerank 的作用是什么？Cross-Encoder 和 Bi-Encoder 的区别是什么？
**答案：**
- 作用：召回阶段追求"不漏"，取几十到上百条候选；rerank 阶段用更精确但更慢的模型重新打分，选出最相关的 top-k 交给大模型。对最终效果的提升通常很明显。
- Bi-Encoder（双塔）：query 和文档分别编码成向量，计算相似度。文档向量可以离线预先计算，检索快，适合召回；但 query 和文档之间没有交互，精度有限。
- Cross-Encoder：把 query 和文档拼在一起输入模型，直接输出相关性分数。两者充分交互，精度高；但每对都要计算一次，无法预先计算，只适合对少量候选做精排。
- 常用：bge-reranker 系列、各云厂商的 rerank 服务；也可以用大模型做 listwise 排序（成本更高）。

### 18. Rerank 延迟太高怎么办？
**答案：**
- 减少候选数：召回的结果先去重、粗过滤，只对 top 20 到 50 条做 rerank。
- 截断文本：rerank 时只用 chunk 的前若干个 token。
- 换更小的 rerank 模型，或者蒸馏、量化。
- 批量推理，用 GPU 部署；在多个实例上并行。
- 缓存：相同 query 和文档对的分数可以缓存。
- 分级：简单问题或高置信度的召回结果跳过 rerank。
- 设置超时降级：rerank 超时时直接使用融合后的排序结果。

### 19. 【高频】Query 改写有哪些方法（HyDE、多 query、子问题分解）？
**答案：**
- 指代消解和补全：结合对话历史，把不完整的问题改写成独立、完整的问题（多轮对话中最常用、收益最大）。
- 多 query：让模型从不同角度生成 3 到 5 个改写后的 query，分别检索后合并，提升召回率。
- HyDE：先让模型生成一个"假设的答案"，用这个答案的 embedding 去检索。原理是"答案和文档"比"问题和文档"更相似；缺点是假设答案中的错误会把检索带偏，并增加一次模型调用。
- 子问题分解：复杂问题拆成多个子问题，分别检索后综合，适合多跳问题。
- Step-back：先生成一个更抽象、更概括的问题，检索背景知识。
- 关键词抽取和同义词扩展：用于关键词检索。
- 注意：每次改写都增加延迟，可以用小模型完成，或者按问题类型选择是否改写。

### 20. 多轮对话中，用户的指代（"它多少钱"）怎么在检索前补全？
**答案：**
- 把最近几轮对话和当前问题交给模型（可以用小模型），要求改写成一个不依赖上下文、能独立理解的问题，如"它多少钱"改写为"iPhone 16 Pro 256G 的价格是多少"。
- Prompt 要点：
  - 只补全指代和省略的内容，不改变原意，不回答问题。
  - 当前问题已经完整时原样输出。
  - 话题切换时，不要错误地引入历史中的实体。
- 用改写后的问题做检索；生成答案时仍然使用原始的对话上下文。
- 评估：构造多轮对话样本，检查改写的正确率。

### 21. 【专家】召回率和准确率冲突时怎么取舍？top-k 怎么定？
**答案：**
- 分阶段解决冲突：召回阶段偏重召回率（取 top 50 到 100，多路召回），精排阶段偏重准确率（rerank 后取 top 3 到 10），避免在一个阶段内同时兼顾两者。
- top-k 的取舍：
  - 太小：答案所在的 chunk 可能没有被带进上下文。
  - 太大：噪声增加，模型容易被干扰（lost in the middle），成本和延迟也增加。
- 确定方法：
  - 在评测集上画出召回率随 k 变化的曲线，找到拐点。
  - 结合答案准确率做实验。
  - 也可以用 rerank 分数阈值动态截断（低于阈值的不要），而不是固定 k。
- 按问题类型区分：事实类问题 k 取小值；汇总类、多跳问题 k 取大值。

### 22. 【高频】检索结果怎么组装进 Prompt？顺序和格式有什么讲究？
**答案：**
- 格式：每个 chunk 用编号和标签包裹，带上来源元数据（文档标题、章节、时间、链接），方便模型引用，如 `[1] 标题：xxx\n内容：xxx`。
- 顺序：最相关的放在开头或结尾（考虑 lost in the middle 现象）；同一文档中相邻的 chunk 合并后按原文顺序排列，保持连贯。
- 去重和压缩：去掉重复内容；必要时只保留与问题相关的句子。
- 指令：要求只根据资料回答，注明引用编号，资料不足时说明。
- 资料和指令分开放置，资料放在标签内，声明它是数据而不是指令（防注入）。

### 23. 检索内容超过上下文长度时怎么办？
**答案：**
- 精简：减小 top-k，提高 rerank 阈值；去重；合并相邻的 chunk。
- 压缩：
  - 用小模型对每个 chunk 抽取与问题相关的句子（上下文压缩）。
  - 先对检索结果做摘要。
  - 使用 LLMLingua 这类 Prompt 压缩方法。
- 分治：Map-Reduce，分批让模型基于部分资料回答，再汇总；或者 Refine，逐批迭代完善答案。
- 换模型：使用长上下文模型（注意成本）。
- 按 token 预算分配：System Prompt、对话历史、检索结果分别设置上限。

### 24. 【高频】如何让回答带上引用出处？怎么校验引用的真实性？
**答案：**
- 生成：资料中给每个 chunk 编号，要求模型在每句话或每个观点后标注引用编号，如 [1][3]；也可以要求结构化输出（答案文本加引用列表）。
- 展示：前端把编号渲染成可点击的来源链接，定位到原文段落。
- 校验：
  - 编号必须在本次提供的资料范围内，否则删除。
  - 语义校验：用 NLI 模型或小模型判断被引用的 chunk 是否支持这句话，不支持的标记或删除。
  - 抽样人工审核。
- 指标：引用的准确率（引用的资料确实支持该说法）和覆盖率（需要引用的观点都有引用）。

### 25. 【高频】RAG 效果不好，你怎么系统地排查（切分、召回、排序、生成哪一环出问题）？
**答案：**
- 先收集 badcase，对每个 case 标注正确答案在知识库中的位置，然后逐环节检查：
  1. 知识库里有没有答案：没有就是知识缺失，需要补充文档。
  2. 解析和切分：答案所在的内容是否被正确解析（表格乱码、内容丢失）？是否被切断在两个 chunk 中？
  3. 召回：包含答案的 chunk 是否出现在召回的 top-N 中？没有出现就是召回问题，考虑 query 改写、混合检索、更换 embedding 模型、调整 chunk 大小。
  4. 排序：召回了但 rerank 后没有进入 top-k，就是排序问题。
  5. 生成：资料已经在上下文中但答案仍然错误，就是生成问题，考虑 Prompt、资料格式、模型能力。
- 按环节统计各类问题的占比，优先解决占比最大的问题。
- 搭建工具：能看到每个 badcase 的完整链路（改写后的 query、召回结果、分数、最终 Prompt）。

### 26. 【专家】RAG 的评估指标有哪些？RAGAS 中 faithfulness、answer relevancy、context precision/recall 分别是什么？
**答案：**
- 检索指标：Recall@k、MRR、NDCG、Hit Rate，需要标注每个问题的相关文档。
- RAGAS 指标（大多用大模型自动计算）：
  - faithfulness（忠实度）：答案中的论断能被检索到的上下文支持的比例，衡量幻觉。
  - answer relevancy（答案相关性）：答案是否切题，是否回答了用户的问题。
  - context precision（上下文精确率）：检索出的上下文中相关内容的比例，以及相关内容是否排在前面。
  - context recall（上下文召回率）：标准答案中的信息有多少能在检索到的上下文中找到（需要标准答案）。
- 端到端：答案正确率（人工或大模型对比标准答案）、用户满意度、拒答率。
- 注意：用大模型自动评估要和人工评估做一致性校准。

### 27. 怎么构造 RAG 的评测集？没有标注数据时怎么办？
**答案：**
- 有线上日志时：抽样真实用户问题，人工标注答案和来源文档，覆盖高频问题、长尾问题、无答案问题、多跳问题。
- 没有标注数据时：
  - 用大模型基于文档自动生成"问题、答案、来源"三元组，再人工抽检筛选。
  - 让业务专家写一批核心问题。
  - 上线后持续把 badcase 加入评测集。
- 要求：
  - 分布贴近真实情况；包含"知识库中没有答案"的问题，用来测试拒答能力。
  - 评测集和优化过程隔离，防止过拟合。
  - 规模：几百条起步，按类别分层。

### 28. 【高频】知识库更新后，向量索引怎么增量更新？删除文档怎么处理？
**答案：**
- 以文档为单位管理：每个 chunk 记录 doc_id、版本号、内容哈希。
- 更新：文档变化时重新解析和切分，对比 chunk 的哈希；只对新增和变化的 chunk 重新计算 embedding 并写入，删除失效的 chunk（也可以整篇文档删除后重新写入，实现简单）。
- 删除：按 doc_id 删除所有 chunk。向量库一般是先标记删除，后台合并时（compaction）物理删除；HNSW 删除过多会影响图质量，需要定期重建。
- 一致性：先写入新版本，再删除旧版本，避免更新期间检索不到内容；用版本号保证只检索最新版本。
- 触发方式：文档系统的变更事件（消息队列）驱动，加上定期全量校对兜底。
- 更换 embedding 模型时必须全量重建，可以新建一套索引，构建完成后切换。

### 29. 大规模知识库（上亿 chunk）的存储和检索怎么设计？
**答案：**
- 分片：按租户或业务分 collection 和 partition，再在内部水平分片；查询时尽量路由到少数分片。
- 索引：内存成本高时使用 IVF-PQ、DiskANN 或标量量化；热数据用 HNSW。
- 分层检索：先用元数据或类别缩小范围，再做向量检索。
- 存储分离：向量库只存向量和必要的元数据，原文存放在 KV 存储或对象存储中，命中后再取原文。
- 写入：批量写入，建索引放在后台异步进行，避免影响在线查询。
- 容量估算：向量的原始存储量加索引开销、副本数、QPS 对应的节点数，都要提前规划。
- 监控：召回率（定期抽样与精确检索结果对比）、延迟、内存使用。

### 30. 【专家】多租户知识库怎么做数据隔离？每个租户一个 collection 还是用 partition/过滤？
**答案：**
- 每个租户一个 collection：隔离最彻底，可以单独配置索引和资源，删除方便；但租户很多（上万个）时，collection 数量过多，元数据和资源开销大，小租户浪费资源。
- partition 或分区键：同一个 collection 内按租户划分分区，查询时指定分区，物理上隔离、检索效率高；需要关注数量上限（不同向量库版本限制不同，需要确认）。
- 标量过滤：所有租户共用一个 collection，查询时带 tenant_id 过滤条件。最灵活、资源利用率高，但依赖每次查询都正确带上过滤条件，代码出错就会泄露数据；大租户和小租户混在一起时，过滤性能会受影响。
- 常用方案：大租户使用独立的 collection；大量中小租户共享 collection，使用分区键。
- 安全：tenant_id 由服务端根据身份强制注入，不信任请求中传入的值。

### 31. 知识库权限控制怎么做（不同用户能看到不同文档）？
**答案：**
- 入库时，每个 chunk 带上权限元数据：所属文档、可见的部门、用户组、密级，从文档系统同步。
- 检索时，服务端根据当前用户身份计算可以访问的权限集合，作为过滤条件注入（前过滤），保证无权限的内容不会出现在召回结果中，更不会进入 Prompt。
- 权限变化：文档权限修改后，及时更新对应 chunk 的元数据。
- 权限组合复杂（大量单独授权）时：先检索，再调用权限服务批量校验（后过滤），同时放大召回数量。
- 审计：记录每次回答引用了哪些文档。
- 原则：不能依赖 Prompt 让模型"不要透露某些内容"，必须在检索层就过滤掉。

### 32. GraphRAG 的原理是什么？和普通 RAG 相比适合什么问题？
**答案：**
- 原理（以微软 GraphRAG 为例）：
  - 用大模型从文档中抽取实体和关系，构建知识图谱。
  - 对图做社区检测（如 Leiden 算法），为每个社区生成多层次的摘要。
  - 查询时，局部问题从相关实体出发，沿关系扩展取得上下文；全局问题基于社区摘要做 Map-Reduce 汇总。
- 适合：
  - 需要全局理解的问题（如"这些文档的主要主题有哪些"）。
  - 多跳关系推理（"A 的合作方的竞争对手是谁"）。
  - 实体关系密集的领域（金融、医疗、情报）。
- 缺点：建图需要大量调用大模型，成本高；更新困难；简单的事实问题效果不一定比普通 RAG 好。

### 33. 【专家】知识图谱怎么从非结构化文本自动构建？实体对齐怎么做？
**答案：**
- 构建流程：
  1. 文本切分。
  2. 实体识别：用大模型或 NER 模型抽取实体（人、组织、产品等）及其类型。
  3. 关系抽取：抽取实体之间的关系三元组（头实体、关系、尾实体），可以预先定义 schema 约束关系类型，提高一致性。
  4. 属性抽取。
  5. 写入图数据库（如 Neo4j、NebulaGraph），保留每个三元组的来源 chunk，用于溯源。
- 实体对齐（消歧和合并）：
  - 规范化名称（大小写、简称、别名词典）。
  - 用名称和描述的 embedding 计算相似度，召回候选的重复实体。
  - 结合上下文属性（类型、关联实体）判断是否为同一实体，可以让大模型做最终判断。
  - 合并后维护别名列表。
- 质量控制：抽样评估抽取的准确率；对低置信度的三元组标记，或交给人工审核。

### 34. 多模态 RAG（图片、音频、视频检索）怎么做？
**答案：**
- 方案一，统一转成文本：图片做 OCR 加生成描述，音频做语音识别转文本，视频抽关键帧加字幕加语音识别；之后按文本 RAG 处理。实现简单、成熟，但会丢失视觉细节。
- 方案二，多模态 embedding：用 CLIP 这类模型，把图片和文本映射到同一个向量空间，可以用文本搜图、以图搜图。
- 方案三，直接对文档页面截图做 embedding（如 ColPali），检索到页面图片后交给多模态大模型回答，适合版面复杂的文档。
- 视频：按时间切片，每个片段带上时间戳，命中后返回对应的时间点。
- 结果分模态融合排序，生成时把图片等原始内容交给多模态模型。
- 可举例：智能体对话打点中记录了多模态检索结果（图片、音频、视频、文本），用于分析各模态的触发情况。

### 35. 【高频】什么问题应该走 RAG，什么问题应该直接回答？怎么判断要不要检索？
**答案：**
- 需要检索：涉及私有知识、实时信息、具体事实和数据、需要引用来源的问题。
- 不需要检索：闲聊、通用常识、创作、改写、翻译、数学计算、对上一轮内容的追问（上下文中已有信息）。
- 判断方式：
  - 规则：按 Agent 配置（是否挂载了知识库）、关键词判断。
  - 分类模型或大模型判断是否需要检索（输出 yes/no，或同时输出检索 query）。
  - 让模型通过工具调用自主决定是否检索（Agentic RAG）。
- 权衡：判断错误时，漏检索可能导致幻觉，多检索会增加延迟和噪声。高风险领域倾向于多检索。

### 36. 【专家】Self-RAG、CRAG（纠错式 RAG）的思路是什么？
**答案：**
- Self-RAG：训练模型输出特殊的反思 token，用来判断：是否需要检索；检索到的段落是否相关；生成的内容是否被段落支持；回答是否有用。生成时根据这些判断决定是否检索、选择哪些段落、是否重新生成。核心是让模型自己评估检索和生成的质量。
- CRAG：增加一个轻量的检索评估器，给检索结果打分：
  - 正确：对文档做提炼（去噪）后使用。
  - 错误：丢弃检索结果，改用网页搜索。
  - 不确定：两者结合。
  - 核心是检索质量差时的自动纠正机制。
- 工程借鉴：不必训练专门的模型，可以用 Prompt 或小模型实现"检索结果相关性判断"和"答案是否有依据"的检查，不通过时触发重新检索或拒答。

### 37. 结构化数据（数据库）和非结构化文档怎么统一检索？
**答案：**
- 路由：先判断问题类型。统计、筛选、聚合类问题（"上个月销售额"）走 Text2SQL 或 API 查询；概念、说明类问题走文档 RAG；混合问题拆开分别处理后汇总。
- 统一索引：把结构化数据的关键记录转成文本描述，一起建索引（适合商品、FAQ 这类数据量不大的情况）；同时保留结构化字段，用于过滤。
- 用 Agent 统一编排：把"文档检索"和"数据查询"都作为工具，由模型决定调用哪个，可以多次调用后综合回答。
- 回答中注明数据来源和统计时间。

### 38. FAQ 类问答用 RAG 还是 QA 对精确匹配？怎么结合？
**答案：**
- QA 对匹配：用户问题和标准问题（及其相似问法）匹配，命中后直接返回审核过的标准答案。准确、可控、快，适合高频、对答案要求严格的问题（政策、价格、流程）。
- RAG：覆盖长尾问题，能综合多个文档回答，但答案不可控。
- 结合方式：
  - 先做 FAQ 检索，相似度高于阈值时直接返回标准答案（或交给模型改写语气）。
  - 低于阈值时走 RAG。
  - 也可以把相似度中等的 FAQ 作为高优先级资料放入 RAG 上下文。
- 运营：把 RAG 中的高频问题沉淀成 FAQ。

### 39. Embedding 模型需要微调吗？怎么用业务数据微调？
**答案：**
- 需要微调的情况：领域专业性强（医疗、法律、内部术语），通用模型的召回率不达标；业务对"相关"有特殊定义。
- 数据：构造（query、正样本文档）对，来源包括点击日志、人工标注、用大模型根据文档生成问题。负样本要包含难负样本（相似但不相关的文档，用当前模型检索出的排名靠前的错误结果）。
- 方法：基于开源模型用对比学习（InfoNCE）微调，batch 中其他样本自然作为负样本；可以用 sentence-transformers、FlagEmbedding 等工具。
- 评估：在独立的测试集上对比微调前后的 Recall@k，同时检查通用能力是否退化。
- 代价：微调后要全量重建索引。

### 40. 【高频】RAG 链路的延迟主要在哪？怎么优化？
**答案：**
- 延迟分布：query 改写（一次模型调用）、embedding、向量检索加关键词检索、rerank、大模型生成（prefill 随上下文变长而增加，再加上生成时间）。通常改写、rerank 和生成占大头。
- 优化：
  - 并行：多路召回并行；改写和部分检索并行。
  - 减少模型调用：用小模型改写；简单问题跳过改写和 rerank。
  - 缩短上下文：减小 top-k、压缩资料，加快 prefill。
  - 缓存：query embedding、检索结果、语义缓存。
  - 索引参数：调整 efSearch，在召回率和速度之间取得平衡。
  - 流式输出：首 token 尽快返回。
- 监控各环节的 P50 和 P99 耗时，有针对性地优化。

### 41. 检索结果能做缓存吗？语义缓存怎么实现？
**答案：**
- 精确缓存：对规范化后的 query 加知识库版本加权限范围计算哈希作为 key，缓存检索结果或最终答案。实现简单，但只有完全相同的问题才能命中。
- 语义缓存：
  - 把历史 query 的 embedding 和对应答案存入向量索引（或 Redis 的向量能力）。
  - 新 query 先做向量检索，相似度高于阈值时直接返回缓存的答案（如 GPTCache 的思路）。
- 失效：知识库更新时，按版本号或相关文档失效对应的缓存；设置 TTL。
- 隔离：缓存 key 必须包含租户和权限范围，防止不同用户串用答案。
- 适合：重复率高的 FAQ 类问题；不适合个性化、时效性强的问题。

### 42. 【专家】语义缓存的相似度阈值怎么定？误命中怎么处理？
**答案：**
- 误命中的危害：语义相近但答案不同的问题（"北京明天天气"和"上海明天天气"，"如何开通"和"如何取消"）会返回错误答案，比不命中更糟糕。
- 确定阈值：
  - 构造标注集：问题对加上"答案是否可以共用"的标签。
  - 画出不同阈值下的命中率和误命中率曲线，按业务能容忍的误命中率选阈值，通常要设置得较高。
- 降低误命中：
  - 实体校验：命中后对比两个问题中的关键实体（地点、时间、产品），不一致就不使用缓存。
  - 先用 embedding 召回候选，再用 rerank 或小模型判断"两个问题是否等价"。
  - 按领域使用不同的阈值。
- 处理：允许用户反馈"答案不对"后失效对应的缓存；监控缓存命中后的差评率。

### 43. 长文档问答用 RAG 还是长上下文模型？怎么权衡成本？
**答案：**
- 长上下文模型：把整篇文档放入上下文，能理解全文结构、跨章节的关联，适合总结、全局分析、文档较短（几万 token）的情况。缺点是每次提问都要处理全文，成本和延迟高，中间部分的信息可能被忽略。
- RAG：只放入相关片段，成本低、速度快；适合针对具体事实反复提问的场景，但不擅长全局性问题。
- 权衡：
  - 单次分析、文档不长：用长上下文。
  - 同一篇文档被频繁提问：用 RAG，或者用长上下文加 Prompt Caching（文档放在固定前缀中，后续提问命中缓存，大幅降低成本）。
  - 超长文档：RAG 加分章节摘要。
- 估算：每次请求的 token 数乘以单价乘以调用量，再对比两种方案的效果评测结果后决定。

### 44. 资源类内容（影视、小说、音乐）的检索有什么特殊之处？
**答案：**
- 实体为主：用户大多搜索作品名、演员、作者、歌手，需要实体识别和精确匹配；名称有别名、简称、错别字、谐音，要做别名库和纠错。
- 结构化属性多：类型、题材、年代、地区、评分，常常需要按属性过滤和推荐（"类似《三体》的科幻小说"）。
- 版本多：同名作品（翻拍、不同年份）、同一作品的多个版本需要区分。
- 时效和热度：新作品要及时入库，排序要考虑热度。
- 合规：涉及版权，不能引导盗版和网盘下载。
- 对话策略：用户要的是推荐，而不是对作品内容提问，追问应引导到同类型、同题材、同作者的推荐。
- 可举例：资源型智能体追问优化中，用专用模板禁止对剧情和人物提问、禁止引导网盘下载，追问 badcase 率从 20% 降到 4.67%。

### 45. 【高频】Elasticsearch 的倒排索引原理是什么？BM25 怎么计算？
**答案：**
- 倒排索引：文档经过分词后，建立"词项到包含该词项的文档列表"的映射（posting list，记录文档 ID、词频、位置）。查询时取出各个词项的文档列表做交集或并集，再计算相关性。词典用 FST 压缩存储，文档列表用压缩编码。
- BM25：对查询中的每个词项累加 `IDF × (tf × (k1+1)) / (tf + k1 × (1 - b + b × 文档长度/平均长度))`。
  - IDF：词越稀有，权重越高。
  - tf：词频，有饱和效应，词频越高收益增长越慢（k1 一般为 1.2）。
  - b：文档长度归一化（一般为 0.75），长文档会被适当降权。
- 中文要选择合适的分词器（如 IK、jieba），并维护业务词典，否则效果很差。

### 46. ES 分片数、副本数怎么规划？深分页有什么问题？
**答案：**
- 分片：主分片数在建索引时确定，之后不能直接修改（只能重建索引或 split）。单个分片一般控制在 10 到 50GB；分片过多会增加集群元数据和查询合并的开销，分片过少则无法水平扩展。按数据量和增长预期来估算。
- 副本：提供高可用和读扩展，一般设为 1；读多时可以增加；写入多时副本会增加写入开销。
- 时间序列数据：按时间滚动建索引，配合生命周期管理（ILM）做冷热分层。
- 深分页：`from + size` 方式下，每个分片都要取出 from+size 条数据，再在协调节点汇总排序，翻页越深开销越大（默认 from+size 不能超过 10000）。
- 解决：用 search_after（基于上一页最后一条的排序值游标翻页）；导出数据用 scroll 或 PIT（时间点）。

### 47. 向量检索的召回结果如何去重和多样化（MMR）？
**答案：**
- 去重：同一文档相邻或高度重叠的 chunk 合并；内容哈希完全相同的直接去掉；embedding 相似度非常高的只保留一个。
- MMR（最大边际相关性）：逐个挑选结果，每次选择"与 query 相关度高，同时与已选结果相似度低"的候选，分数为 `λ × sim(q, d) - (1 - λ) × max sim(d, 已选)`。λ 越大越看重相关性，越小越看重多样性。
- 适用：问题需要多角度信息、召回结果被同一文档或同一观点占据时。
- 其他做法：限制每个文档最多贡献 N 个 chunk。

### 48. 【专家】RAG 系统上线后怎么持续优化？badcase 怎么闭环？
**答案：**
- 收集：用户反馈（点踩、改写重问、转人工）、低置信度回答、拒答记录、抽样评估结果。
- 定位：用全链路 trace 判断问题出在哪个环节（知识缺失、解析、召回、排序、生成）。
- 分类修复：
  - 知识缺失：补充文档、沉淀 FAQ。
  - 解析和切分问题：调整对应文档类型的解析策略。
  - 召回问题：query 改写、同义词、调整混合检索权重、微调 embedding。
  - 生成问题：修改 Prompt、更换模型。
- 回归：修复后加入评测集，每次变更都运行回归，防止退化。
- 节奏：定期（如每周）复盘 badcase 的分布和指标趋势；监控线上满意度、拒答率、引用准确率。

### 49. 时效性强的知识（新闻、价格）怎么在 RAG 中处理？
**答案：**
- 数据层：实时或高频增量入库；每个 chunk 带发布时间和失效时间元数据；过期数据自动下线。
- 检索层：问题带有时间意图（"最新""今天"）时，按时间过滤或在排序中加入时间衰减。
- 实时数据不放进 RAG：价格、库存、天气这类每分每秒都在变化的数据，通过工具调用实时接口获取。
- 生成层：Prompt 中注入当前日期；回答时注明信息的时间；不同来源时间不一致时，以最新的为准并说明。
- 缓存的 TTL 要短。

### 50. 【专家】设计一个企业级知识库问答系统，从文档接入到在线问答的完整架构是什么？
**答案：**
- 接入层：对接多种数据源（文档系统、Wiki、网盘、数据库、工单）的连接器，支持全量同步和基于事件的增量同步；同步文档的权限信息。
- 处理层（异步流水线，消息队列驱动）：解析（按类型路由，支持 OCR 和版面分析）→ 清洗 → 结构化切分（父子 chunk）→ embedding → 写入向量库和全文索引；原文和元数据写入数据库和对象存储；有任务状态管理和失败重试。
- 检索层：query 理解（改写、意图、是否需要检索）→ 混合召回 → 权限过滤（服务端强制注入）→ rerank → 上下文组装。
- 生成层：模型网关（多模型、降级）、Prompt 模板版本管理、引用标注、流式输出、内容审核。
- 应用层：问答界面、引用跳转、反馈按钮、多轮对话。
- 运营和评估：评测集、自动评估、badcase 平台、知识缺口分析、使用数据看板。
- 非功能要求：多租户隔离、审计日志、索引容量规划、检索链路的 P99 延迟监控、降级预案（检索服务故障时返回提示或只用 FAQ）。
