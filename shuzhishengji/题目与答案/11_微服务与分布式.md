# 11 微服务与分布式（45 题）（题目与答案）

## 微服务

### 1. 【高频】微服务和单体架构各有什么优缺点？服务怎么拆分？
**答案：**
- 单体架构：
  - 优点：开发、测试、部署简单；模块之间是本地调用，性能好；事务容易保证。
  - 缺点：代码库越来越大，难以维护；一处改动就要整体发布；无法按模块单独扩容；技术栈被绑定；一个模块出问题可能拖垮整个系统。
- 微服务：
  - 优点：按业务独立开发、部署、扩容；故障隔离；团队自治；可以按需选择技术栈。
  - 缺点：分布式带来的复杂性（网络调用、分布式事务、数据一致性）；运维和监控成本高；排查问题困难；接口的协调成本。
- 拆分原则：
  - 按业务领域（DDD 的限界上下文）拆分，高内聚、低耦合。
  - 每个服务拥有自己的数据，不共享数据库。
  - 考虑团队结构（康威定律）。
  - 按变更频率和扩展需求拆分（如把高频变化的挂载服务、对话服务独立出来）。
  - 不要拆得过细：先粗粒度拆分，需要时再进一步拆。

### 2. 【高频】服务注册与发现的原理是什么？Consul、etcd、Nacos、BNS 怎么选？
**答案：**
- 原理：
  - 服务实例启动时，把自己的地址和元数据注册到注册中心，并定期发送心跳（或者由注册中心做健康检查）；实例下线或心跳超时后被移除。
  - 调用方从注册中心获取服务的实例列表（订阅变更、本地缓存），再通过负载均衡选择一个实例调用。
- 选型：
  - etcd：基于 Raft，强一致（CP），是 k8s 的基础组件；适合 Go 生态和 k8s 环境，常配合 gRPC 使用。
  - Consul：内置健康检查、多数据中心、KV 存储、服务网格，开箱即用。
  - Nacos：阿里开源，同时提供注册中心和配置中心，支持 AP 和 CP 两种模式，在 Java 和 Spring Cloud 生态中常用。
  - BNS：百度内部的名字服务，通过服务名解析出实例列表，内部服务一般统一使用。
- 选择依据：团队现有的技术栈、一致性要求（注册中心通常更看重可用性，AP 更合适）、运维成本、公司内部规范。

### 3. 客户端负载均衡和服务端负载均衡的区别是什么？
**答案：**
- 服务端负载均衡：调用方请求一个统一的入口（如 Nginx、LVS、云负载均衡），由它把请求分发到后端实例。调用方不需要知道后端的实例，实现简单；但多了一跳网络，负载均衡器本身可能成为瓶颈或单点。
- 客户端负载均衡：调用方从注册中心获取实例列表，自己选择实例直接调用（如 gRPC 内置的负载均衡、各种 RPC 框架）。少了一跳，性能好，可以做更智能的策略（基于延迟、基于连接数）；但每个客户端都要实现负载均衡逻辑，而且依赖注册中心。
- 服务网格：负载均衡逻辑放在 Sidecar 中，对业务代码透明。
- 实践：对外流量使用服务端负载均衡（网关）；内部服务之间的调用常用客户端负载均衡或 Service Mesh。

### 4. 【高频】常见负载均衡算法（轮询、加权、最少连接、一致性哈希）有哪些？
**答案：**
- 轮询：按顺序依次分配，简单、均匀，适合实例配置相同的情况。
- 加权轮询：按权重分配，配置高的机器分到更多请求。Nginx 使用平滑加权轮询，避免集中分配到同一个实例。
- 随机和加权随机：实现简单，请求量大时接近均匀。
- 最少连接（最少活跃请求）：分给当前处理中请求最少的实例，能适应请求耗时差异大的情况（如大模型请求）。
- 基于响应时间：分给最近响应最快的实例（如 P2C 算法：随机选两个实例，再选负载较低的那个）。
- 一致性哈希：相同的 key（用户 ID、会话 ID）总是路由到同一个实例，适合有本地状态或缓存的场景（如会话粘性、提高缓存或 KV Cache 的命中率）；加入虚拟节点可以让分布更均匀。
- 选择：普通无状态服务用加权轮询或 P2C；耗时差异大的长请求用最少连接；需要状态亲和的用一致性哈希。

### 5. 【高频】gRPC 的原理是什么？和 HTTP/JSON 相比有什么优劣？
**答案：**
- 原理：
  - 基于 HTTP/2 传输，用 Protobuf 定义接口（IDL）和序列化数据，通过代码生成工具生成客户端和服务端的代码。
  - 支持四种调用模式：一元调用、服务端流、客户端流、双向流。
  - HTTP/2 的多路复用让一条连接可以同时承载多个请求。
- 优势：
  - 二进制序列化，体积小、编解码快。
  - 强类型的接口契约，有代码生成，跨语言调用方便。
  - 原生支持流式调用。
  - 内置超时（deadline）、元数据（metadata）、拦截器等机制。
- 劣势：
  - 可读性差，调试不如 JSON 方便（需要专门的工具）。
  - 浏览器不能直接调用（需要 gRPC-Web 或网关转换）。
  - 负载均衡需要特殊处理：长连接上的 HTTP/2 多路复用，会让 L4 负载均衡失效，需要客户端负载均衡或 L7 代理。
- 选择：内部服务之间的高性能调用用 gRPC；对外开放的 API、前端调用用 HTTP/JSON。

### 6. Protobuf 的编码原理是什么？字段兼容性怎么保证？
**答案：**
- 编码：
  - 每个字段编码为"tag 加值"，tag 由字段编号和类型（wire type）组成；不传字段名，所以体积小。
  - 整数使用 Varint 变长编码，小的数字只占 1 个字节；负数用 sint 类型（ZigZag 编码）更高效。
  - 字符串和嵌套消息使用"长度前缀加内容"。
  - 没有设置的字段（proto3 中默认值）不会被编码。
- 兼容性规则：
  - 字段编号一旦使用就不能改动或复用；删除字段后用 reserved 保留它的编号和名称。
  - 新增字段使用新编号；旧代码解析时会忽略不认识的字段（向前兼容），新代码读取旧数据时，新增字段为默认值（向后兼容）。
  - 不要修改已有字段的类型（少数兼容的类型除外，如 int32、int64、uint32 之间，但要注意截断）。
  - 字段名可以改（因为编码中不包含名称），但会影响 JSON 映射。
- proto3 中区分"没有设置"和"值为默认值"：使用 optional 关键字或包装类型（wrappers）。

### 7. HTTP/2 的多路复用解决了什么问题？队头阻塞还存在吗？
**答案：**
- HTTP/1.1 的问题：一条连接同一时间只能处理一个请求（pipelining 很少使用），所以浏览器要开多条连接（每个域名约 6 条）；而且请求头是重复的文本，开销大。
- HTTP/2 的改进：
  - 二进制分帧，在一条 TCP 连接上通过多个流（stream）并发传输多个请求和响应，帧可以交错发送，解决了 HTTP 层的队头阻塞。
  - HPACK 头部压缩。
  - 流的优先级、服务端推送（已基本废弃）。
- 仍然存在 TCP 层的队头阻塞：所有的流共用一条 TCP 连接，一旦丢包，TCP 要等重传完成才能把后续数据交给上层，所有流都会被阻塞。在丢包率高的网络中，表现甚至可能不如 HTTP/1.1 的多连接。
- HTTP/3 基于 QUIC（UDP），每个流独立处理丢包，彻底解决了队头阻塞，还支持 0-RTT 建连和连接迁移（切换网络时不断开）。

### 8. 【高频】服务间调用超时怎么设置？超时传递（deadline propagation）是什么？
**答案：**
- 设置超时：
  - 每个下游调用都必须设置超时，没有超时的调用一旦下游卡住，会耗尽调用方的资源（协程、连接）。
  - 超时时间参考下游的 P99 延迟再加一些余量；不要一律设置成很大的值。
  - 区分连接超时和读写超时。
- 超时传递：
  - 问题：入口的总预算是 1 秒，但每一层服务都各自设置了 1 秒超时，入口已经超时返回了，下游还在继续执行，白白浪费资源。
  - 做法：把剩余的截止时间（deadline）随请求一起传递（gRPC 会自动在 metadata 中传递；Go 中用 context.WithTimeout 和 ctx 在调用链中传递）。下游根据剩余时间决定是否还要执行，或者设置更短的超时；剩余时间不够时直接放弃。
- 重试和超时的配合：重试的总耗时也不能超过上游的预算。

### 9. 【专家】重试风暴是怎么产生的？怎么避免（重试预算、退避、只在一层重试）？
**答案：**
- 产生原因：
  - 下游变慢或出现故障时，调用方大量重试，请求量成倍增加，下游更加不堪重负，形成恶性循环。
  - 多层服务都各自重试时，次数相乘：每层重试 3 次，一共 3 层，最底层的服务会收到 3 的 3 次方，即 27 倍的请求。
- 避免方法：
  - 只在一层重试：一般只在最靠近故障点的那一层，或者最上层重试，其他层不重试，直接把错误返回给上游。
  - 重试预算：限制重试请求占总请求的比例（如不超过 10%），超过就不再重试（gRPC 有 retry throttling 机制）。
  - 指数退避加随机抖动，避免大量请求同时重试。
  - 只对可以重试的错误重试（超时、503），不对 4xx 重试。
  - 配合熔断：下游持续失败时直接熔断，停止重试。
  - 下游返回明确的信号（如 429 加 Retry-After），调用方遵照执行。
  - 重试的请求必须是幂等的。

### 10. 服务网格（Service Mesh、Istio）是什么？Sidecar 有什么代价？
**答案：**
- 服务网格：把服务间通信的治理能力（服务发现、负载均衡、熔断、重试、超时、mTLS 加密、可观测）从业务代码中剥离出来，放到基础设施层。
- 架构：
  - 数据面：每个服务实例旁边部署一个 Sidecar 代理（如 Envoy），拦截所有进出流量。
  - 控制面：Istio 的 istiod，负责下发配置、证书。
- 好处：业务代码不需要集成各种 SDK；多语言统一治理；策略可以集中配置和动态生效；默认开启 mTLS。
- Sidecar 的代价：
  - 每次调用多经过两跳代理，增加延迟（通常是毫秒级以内）。
  - 每个 Pod 额外占用 CPU 和内存。
  - 运维复杂度高，排查问题时多了一层。
  - Sidecar 的升级和注入管理。
- 演进：Ambient Mesh（没有 Sidecar，在节点级处理）、基于 eBPF 的方案，用来降低代价。

### 11. API 网关的职责有哪些？
**答案：**
- 统一入口：对外暴露统一的域名和接口，隐藏内部服务的拆分。
- 路由：按路径、域名、header 转发到后端服务，支持灰度和 AB 分流。
- 安全：鉴权（token、AK/SK、OAuth）、防重放、IP 黑白名单、WAF、防刷。
- 流量治理：限流、熔断、超时、重试、负载均衡。
- 协议转换：HTTP 转 gRPC，处理 WebSocket、SSE 这类长连接。
- 请求和响应处理：参数校验、header 改写、跨域处理、压缩、响应聚合（BFF）。
- 可观测：访问日志、监控指标、生成并透传 trace_id。
- 注意：网关只做通用的横切功能，不要承载业务逻辑。

### 12. 【高频】接口版本管理和向后兼容怎么做？
**答案：**
- 版本标识：在 URL 中（/v1/、/v2/）、header 中，或者参数中标明版本；不兼容的变更必须升级版本号。
- 向后兼容的规则：
  - 只新增，不删除、不修改：新增可选的请求参数，并设置合理的默认值；响应中只新增字段。
  - 不改变已有字段的类型和含义；枚举值只增加，调用方要能处理不认识的枚举值。
  - 错误码保持稳定。
- 新老版本并存：新版本上线后，旧版本继续保留，给调用方留出迁移时间；统计旧版本的流量，推动调用方升级，到期后下线（下线前要先拒绝并通知）。
- 契约测试：用接口契约（OpenAPI、Protobuf）做兼容性检查，CI 中自动检测是否有不兼容的变更。
- 可举例：mount 接口新增 message_id、log_id、content_id 等可选参数，不传时保持原有行为；646 的老协议请求导致 panic 后，直接拒绝老协议流量。

### 13. 【专家】跨多个服务的需求，上线顺序怎么确定？怎么避免上线依赖导致故障？
**答案：**
- 确定顺序：
  - 画出依赖关系：谁调用谁、新字段由谁产生、由谁消费。
  - 原则是被依赖的一方先上线（提供方先于调用方），新字段的消费方要能兼容"字段不存在"的情况。
  - 数据库变更先于代码上线（先加字段，代码再读写），删除字段则反过来（代码先停止使用，再删除字段）。
- 避免故障：
  - 每个服务都要向前和向后兼容：新代码在依赖方还没上线时也能正常运行（新参数可选、新功能用开关控制）。
  - 功能开关：所有服务的代码都上线后，再统一打开开关，把"代码发布"和"功能生效"分开。
  - 每一步都可以单独回滚，回滚不会破坏其他服务。
  - 写进上线文档：顺序、负责人、验证方法、回滚方案，按 checklist 逐步执行。
- 可举例：
  - RFQ 线索链路改动 5 个服务，按 704 → 676 → 722 → 646 的顺序发布，704 必须先上线，因为下游会开始传递新字段。
  - 对客 PaaS 按架构后端 → pipeline 后端 → pipeline 前端 → paas 的顺序上线；pipeline 后端如果晚于 paas 上线，对外接口的调用会失败。

### 14. 配置中心怎么做到配置热更新？
**答案：**
- 推送通知：客户端用长轮询（如 Apollo、Nacos）或长连接监听配置变更；服务端在配置变化时立即响应，客户端再拉取最新的配置。
- 客户端更新：拉取到新配置后，原子地替换内存中的配置对象（Go 中可以用 atomic.Value 存储配置指针，读取时不加锁），并触发注册的回调（如重建连接池、更新限流阈值）。
- 本地缓存：配置写入本地文件，配置中心不可用时用本地缓存启动，保证可用性。
- 校验：新配置先校验格式和取值范围，校验失败就继续使用旧配置，并告警。
- 灰度：先推送给部分实例，观察无误后再全量。
- 注意：不是所有配置都能热更新（如监听端口），这类配置需要重启生效，要在文档中说明。

### 15. 服务的健康检查和优雅退出怎么做？
**答案：**
- 健康检查：
  - 存活检查（liveness）：进程是否还活着、是否卡死，失败则重启实例。
  - 就绪检查（readiness）：是否可以接收流量（依赖是否就绪、缓存是否已经预热），失败则从负载均衡中摘除，但不重启。
  - 检查逻辑要轻量；不要把下游依赖的状态放进存活检查中，否则下游一出故障，所有实例都会被重启。
- 优雅退出：
  1. 收到 SIGTERM 信号后，先把就绪检查标记为失败，或者从注册中心注销，停止接收新流量。
  2. 等待负载均衡和注册中心生效（几秒钟）。
  3. 调用 `http.Server.Shutdown(ctx)`，等待处理中的请求完成（设置最长等待时间）。
  4. 停止后台的 Worker（停止拉取新任务，完成当前的任务，或者把任务放回队列）。
  5. 关闭数据库、消息队列等连接，刷新日志。
- 长连接（SSE、WebSocket）：要通知客户端重连，或者等待连接结束，设置强制关闭的时间。

### 16. 【高频】链路追踪的原理是什么？traceId 和 spanId 怎么生成和传递？
**答案：**
- 原理（参考 Google Dapper）：
  - 一次请求经过的所有服务共用一个 traceId。
  - 每个操作单元是一个 span，有自己的 spanId，并记录父 spanId，由此组成一棵调用树。
  - span 记录开始和结束时间、服务名、操作名、标签、错误信息，异步上报到收集端，再进行存储和展示。
- 生成：
  - traceId 在入口处生成（随机的 128 位，或者带时间和机器信息），全局唯一。
  - spanId 在每个 span 创建时生成（随机 64 位）。
  - 如果上游已经传来了 trace 上下文，就沿用上游的 traceId，把上游的 spanId 作为父 spanId。
- 传递：
  - 跨进程：通过 HTTP 头（W3C 的 traceparent，或 B3 格式）、RPC 的 metadata、消息队列的消息头。
  - 进程内：通过 context 传递。
  - 由框架和中间件自动注入和提取，不依赖业务代码手动传递。
- 采样：通过控制采样率来平衡开销和覆盖度。

## 分布式理论

### 17. 【高频】CAP 定理是什么？BASE 理论是什么？
**答案：**
- CAP：一个分布式系统不可能同时满足以下三点：
  - 一致性（C）：所有节点在同一时刻看到的数据相同。
  - 可用性（A）：每个请求都能在合理时间内得到非错误的响应。
  - 分区容错性（P）：网络分区（节点之间无法通信）时，系统仍能继续运行。
- 网络分区在分布式系统中无法避免，所以 P 必须保证，实际上是在发生分区时于 C 和 A 之间做选择：
  - CP：发生分区时，拒绝部分请求以保证一致性（如 etcd、ZooKeeper、HBase）。
  - AP：发生分区时，继续提供服务，允许数据暂时不一致（如 Cassandra、Eureka、DNS）。
- BASE：AP 方向的实践原则。
  - 基本可用（Basically Available）：出现故障时允许损失部分功能或性能。
  - 软状态（Soft state）：允许存在中间状态。
  - 最终一致（Eventually consistent）：经过一段时间后，数据最终会达成一致。
- 互联网业务大多选择 BASE 加最终一致；涉及金额、库存的核心数据才追求强一致。

### 18. 【高频】Raft 协议的选主、日志复制流程是什么？
**答案：**
- 角色：Leader（领导者）、Follower（跟随者）、Candidate（候选者）。时间被划分为任期（term），每个任期最多只有一个 Leader。
- 选主：
  - Follower 在选举超时时间（随机 150 到 300ms，随机是为了避免同时发起选举）内没有收到 Leader 的心跳，就把任期加一，变成 Candidate，投票给自己，并向其他节点请求投票。
  - 其他节点在同一个任期内只投一票，并且只投给日志至少和自己一样新的候选者。
  - 获得多数票的候选者成为 Leader，开始定期发送心跳。
  - 选票被瓜分时，超时后重新发起选举。
- 日志复制：
  - 客户端的写请求只发给 Leader；Leader 追加日志条目，并行发送给 Follower（AppendEntries）。
  - 多数节点写入成功后，这条日志就被提交，Leader 把它应用到状态机，然后返回给客户端。
  - Leader 在后续的心跳中告诉 Follower 已提交的位置，Follower 再应用。
  - 发现日志不一致时，Leader 从后往前找到一致的位置，用自己的日志覆盖 Follower 的日志。
- 安全性：只有拥有全部已提交日志的节点才能当选为 Leader，所以已提交的数据不会丢失。

### 19. 【专家】Raft 和 Paxos 的区别是什么？脑裂怎么避免？
**答案：**
- Paxos：
  - Basic Paxos 只对单个值达成共识，分为 Prepare 和 Accept 两个阶段，由 Proposer、Acceptor、Learner 三种角色参与。
  - Multi-Paxos 通过选出一个稳定的 Leader 来优化，但论文中对工程实现的描述较少，难以理解和实现，各家的实现差异很大。
- Raft：
  - 以可理解性为设计目标，把问题拆分成选主、日志复制、安全性三个子问题。
  - 强 Leader（日志只从 Leader 流向 Follower）、日志连续（不允许空洞）。
  - 工程实现成熟（etcd、TiKV、Consul）。
  - 能力上和 Multi-Paxos 基本等价，但约束更多（日志必须按顺序提交），灵活性稍差。
- 脑裂（同时出现两个 Leader）的避免：
  - 多数派机制：成为 Leader 必须获得超过半数的票，网络分区后最多只有一个分区拥有多数节点，少数派的分区无法选出新 Leader，也无法提交写入。
  - 任期号：旧 Leader 恢复后，发现更高的任期号会立即退位成 Follower，它的请求也会被拒绝。
  - 读请求的一致性：用 ReadIndex 或租约（lease）机制，防止旧 Leader 返回过期的数据（使用租约机制时依赖时钟的准确性）。
  - 节点数取奇数（3 或 5 个）。

### 20. 一致性哈希的原理是什么？虚拟节点有什么作用？
**答案：**
- 普通哈希取模的问题：节点数量变化时（从 N 变成 N+1），几乎所有 key 的映射都会改变，导致大规模的数据迁移或缓存失效。
- 一致性哈希：
  - 把哈希值空间组织成一个环（0 到 2^32-1），节点按自身的哈希值放在环上。
  - key 也按哈希值落在环上，顺时针找到的第一个节点就是它所属的节点。
  - 增加或删除一个节点时，只影响它和相邻节点之间那一段的 key，迁移量约为 1/N。
- 虚拟节点：
  - 节点少的时候，在环上的分布不均匀，导致数据倾斜。
  - 让每个物理节点在环上对应多个虚拟节点（如 100 到 200 个），分布就更均匀。
  - 节点下线时，它的负载会分散到多个节点上，而不是全部压到相邻的一个节点。
  - 还可以按机器的性能设置不同数量的虚拟节点，实现加权。
- 应用：分布式缓存的分片、负载均衡的会话粘性、分布式存储。

### 21. Gossip 协议的原理和适用场景是什么？
**答案：**
- 原理：每个节点周期性地随机选择几个其他节点，交换自己知道的信息（节点状态、元数据），信息像流言一样在集群中扩散，经过 O(log N) 轮后传遍整个集群。
- 方式：推（push）、拉（pull）、推拉结合；用版本号或时间戳解决冲突，旧信息不会覆盖新信息。
- 特点：
  - 去中心化，没有单点。
  - 容错性好：部分节点故障或网络不稳定时仍然能够传播。
  - 扩展性好：每个节点的通信开销固定。
  - 缺点：最终一致，收敛需要时间；存在冗余消息。
- 适用场景：集群成员管理和故障检测（Consul 使用的 Serf、Cassandra、Redis Cluster 节点之间的状态同步）、元数据传播。不适合强一致的场景。

### 22. 【专家】线性一致性、顺序一致性、最终一致性有什么区别？
**答案：**
- 线性一致性（Linearizability，最强）：
  - 所有操作看起来像在一个单一副本上按某个全局顺序依次执行，并且这个顺序符合真实时间：一个操作完成后，之后开始的所有操作都能看到它的结果。
  - 实现代价高（需要共识协议，读写都要经过 Leader 确认），如 etcd 的线性一致读。
- 顺序一致性（Sequential Consistency）：
  - 所有进程看到的操作顺序相同，而且每个进程自己的操作顺序保持不变，但不要求符合真实时间（一个操作完成后，其他进程可能暂时还看不到它）。
- 因果一致性：只保证有因果关系的操作按顺序被看到，并发的操作可以按不同顺序被看到。
- 最终一致性（最弱）：没有新的写入时，经过一段时间后所有副本会达到一致；在这之前可能读到旧的值，不同客户端看到的顺序也可能不同。
- 会话级的保证（介于两者之间，工程中常用）：读己之写（自己写入的数据自己一定能读到）、单调读（不会读到比之前更旧的数据）。
- 选择：根据业务对一致性的需求，选择满足要求的最弱级别，以换取性能和可用性。

## 分布式事务

### 23. 【高频】分布式事务有哪些方案（2PC、3PC、TCC、Saga、本地消息表、事务消息）？
**答案：**
- 强一致：
  - 2PC（两阶段提交）：协调者先让所有参与者准备（prepare），全部成功后再统一提交（commit），否则统一回滚。如数据库的 XA 事务、Seata 的 AT 模式（基于类似 2PC 的思想）。
  - 3PC：在 2PC 的基础上增加 CanCommit 阶段和超时机制，减少阻塞，但仍然无法完全解决一致性问题，实际使用很少。
- 最终一致（业务中更常用）：
  - TCC：业务层实现 Try（预留资源）、Confirm（确认）、Cancel（取消）三个接口。性能好、侵入性强。
  - Saga：长事务拆成一系列本地事务，每一步都有对应的补偿操作，失败时按相反顺序执行补偿。适合流程长、跨多个服务的业务。
  - 本地消息表：业务数据和消息在同一个本地事务中写入，再由后台任务投递消息，下游消费后执行自己的事务。
  - 事务消息（如 RocketMQ）：先发送半消息，执行本地事务，再根据结果提交或回滚消息；MQ 会回查事务状态。
  - 最大努力通知加对账：适合跨公司的场景（如支付回调）。
- 选择：能避免分布式事务就避免（调整服务边界、让数据在同一个库）；需要时优先选择最终一致的方案。

### 24. 【高频】2PC 有什么问题？
**答案：**
- 同步阻塞：在准备和提交阶段，所有参与者都持有锁、等待协调者的指令，资源被长时间锁住，性能差。
- 协调者单点：协调者在发出准备请求后宕机，参与者会一直阻塞，不知道应该提交还是回滚。
- 数据不一致：提交阶段，如果只有部分参与者收到了 commit（网络问题或协调者中途宕机），就会出现一部分提交、另一部分没有提交的情况。
- 极端情况：协调者和某个参与者在提交阶段同时宕机，事务的最终状态无法确定。
- 性能：多次网络往返，加上长时间持有锁，无法满足高并发的需求。
- 所以在互联网高并发的场景中很少直接使用 XA 事务，多采用最终一致性方案。

### 25. 【专家】TCC 的空回滚、悬挂、幂等问题怎么处理？
**答案：**
- 幂等：网络重试会导致 Confirm 或 Cancel 被重复调用。处理方式是用事务控制表记录每个分支事务的状态（全局事务 ID 加分支 ID），已经执行过的直接返回成功。
- 空回滚：Try 请求因为网络原因没有到达参与者，但协调者超时后发起了 Cancel，参与者在没有执行过 Try 的情况下收到了 Cancel。处理方式：Cancel 执行时先查询事务控制表，发现没有 Try 的记录，就插入一条"已回滚"的记录，直接返回成功，不执行回滚逻辑。
- 悬挂：Cancel（空回滚）先执行完，迟到的 Try 才到达，执行后预留了资源，但再也不会有 Confirm 或 Cancel，资源被永久占用。处理方式：Try 执行前检查事务控制表，如果已经有"已回滚"的记录，就拒绝执行 Try。
- 实现：事务控制表以（全局事务 ID，分支 ID）为唯一键，状态包括已尝试、已确认、已取消，在业务操作的同一个本地事务中更新。Seata 的 TCC 模式已经内置了这套机制。

### 26. Saga 模式的补偿怎么设计？
**答案：**
- 每个正向操作 Ti 都设计一个对应的补偿操作 Ci，在语义上撤销 Ti 的效果（如创建订单对应取消订单，扣减库存对应回补库存，扣款对应退款）。
- 补偿操作的要求：
  - 幂等：可能被重复执行。
  - 可交换：补偿可能比正向操作先到达，要能处理（类似 TCC 的空回滚）。
  - 一定要能执行成功，失败时持续重试，最终交给人工处理。
- 编排方式：
  - 协同式（choreography）：各服务通过事件驱动，一个服务完成后发布事件，下一个服务订阅后执行。去中心化，但流程不直观，难以追踪。
  - 编排式（orchestration）：由中心的编排器（状态机）依次调用各服务，失败时按相反顺序调用补偿。流程清晰，容易监控，更常用。
- 注意隔离性：Saga 没有隔离性，中间状态对外可见（如订单已创建但还没有付款）。可以通过语义锁（状态字段标记为"处理中"）、业务上的约束来处理。
- 无法补偿的操作（如已经发出的短信），要放在流程的最后执行。

### 27. 【高频】本地消息表方案的流程是什么？
**答案：**
1. 业务服务在同一个本地事务中，同时写入业务数据和一条消息记录（状态为待发送），利用本地事务保证两者要么都成功，要么都失败。
2. 事务提交后，立即尝试把消息投递到 MQ（或直接调用下游）；投递成功后，把消息状态改为已发送。
3. 后台定时任务扫描超时仍未发送成功的消息，重新投递，有最大重试次数，超过后告警。
4. 下游服务消费消息，执行自己的本地事务；必须保证幂等（按消息 ID 去重），因为消息可能被重复投递。
5. 如果需要，下游处理完后回调或发送确认消息。
- 优点：实现简单，不依赖 MQ 的事务特性，可靠性高。
- 缺点：业务库中多了一张消息表；有定时扫描的开销；最终一致有一定延迟。

### 28. 【专家】跨系统的订单状态如何最终一致？对账和定时巡检怎么设计？
**答案：**
- 设计原则：
  - 每种状态都有唯一的权威数据源：订单系统拥有订单状态，支付系统拥有支付状态，制作系统拥有制作状态。其他系统只保存引用，或者保存一份可以重新计算的副本。
  - 状态变更通过事件或回调通知相关方，处理过程要幂等，状态只能单向推进。
- 实时链路：回调和消息（可能丢失、可能乱序）。乱序的处理方式：带上版本号或时间戳，只接受比当前状态更新的变更。
- 兜底一，定时巡检（reconcile）：定期扫描处于中间状态时间过长的订单，主动查询各个子系统的最新状态，重新计算订单状态并修复；无法自动修复的告警交给人工处理。
- 兜底二，对账：按天（或按小时）对比两个系统的数据（如订单数据和支付流水），比较数量、金额、状态，生成差异报告，再按规则自动修复或人工处理。
- 可举例：对客 PaaS 交付中，审核状态实时聚合，形象和声音状态以各自的源表为准；交付 stage 只在三处显式推进，并有 RecomputeDelivery 定时巡检兜底；部署是否完成以 agent/info 的 warmup_num 为准。

## 分布式锁与幂等

### 29. 【高频】分布式锁有哪些实现方式？各有什么问题？
**答案：**
- 数据库：
  - 用唯一索引插入一条记录表示加锁，删除记录表示解锁；或者用 `SELECT ... FOR UPDATE` 行锁。
  - 简单，不需要额外组件；但性能差，加锁的进程崩溃后没有自动释放的机制（需要额外设置过期时间并清理），不适合高并发。
- Redis：
  - `SET key value NX PX 过期时间`。
  - 性能高，有过期时间自动释放。
  - 问题：锁过期了但业务还没执行完；主从异步复制，主节点宕机时锁可能丢失；需要防止误删别人的锁。
- ZooKeeper：
  - 创建临时顺序节点，序号最小的获得锁，其他节点监听前一个节点。
  - 客户端会话断开时临时节点自动删除，锁可靠，而且是公平锁。
  - 性能比 Redis 低，需要维护 ZooKeeper 集群。
- etcd：基于租约（lease）加事务（比较版本号），强一致，有自动续约，适合 Go 和 k8s 生态。
- 选择：大多数业务（防止并发重复执行、轮询分配）用 Redis 就够了；对正确性要求极高时，用 etcd 或 ZooKeeper，再加上 fencing token。

### 30. 【高频】Redis 分布式锁怎么实现？锁过期但业务没执行完怎么办？
**答案：**
- 加锁：`SET lock_key 唯一值 NX PX 30000`，唯一值使用请求 ID 或 UUID，用来标识锁的持有者。
- 解锁：用 Lua 脚本原子地执行"判断值是否等于自己的唯一值，相等才删除"，防止误删其他持有者的锁（比如自己的锁已经过期，被别人获取了）：
```lua
if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) else return 0 end
```
- 锁过期但业务没执行完：
  - 看门狗续期：加锁成功后，启动后台协程，定期（如每过期时间的三分之一）检查自己是否还持有锁，持有就延长过期时间；业务结束或进程退出后停止续期（Redisson 的 watchdog 就是这样实现的）。
  - 根据业务的最长耗时设置足够长的过期时间。
  - 在业务的关键写入步骤中再次校验（fencing token、乐观锁），防止锁失效后两个持有者同时写入。
- 可重入：用 Hash 记录持有者和重入次数。
- 获取锁失败：可以自旋重试（带退避），也可以直接返回失败。

### 31. 【专家】Redlock 的争议是什么？fencing token 是什么？
**答案：**
- Redlock：
  - 部署 N 个（如 5 个）独立的 Redis 主节点，客户端依次向它们申请加锁。
  - 在锁的有效期内，在多数节点（大于等于 3 个）上加锁成功，才算获得锁。
  - 目的是解决单个 Redis 主从切换时锁丢失的问题。
- 争议（Martin Kleppmann 的批评）：
  - 依赖时钟：如果某个节点的时钟发生跳变，锁会提前过期，从而出现两个客户端同时持有锁的情况。
  - 进程停顿：客户端获得锁后发生长时间的 GC 停顿，停顿期间锁过期，被其他客户端获取；它恢复后仍然以为自己持有锁，继续写入。任何基于过期时间的锁都无法避免这个问题。
  - 结论：如果是为了效率（避免重复执行，偶尔失败也可以接受），用单个 Redis 就够了；如果是为了正确性，Redlock 也不够，需要 fencing token。
- fencing token：
  - 每次获取锁时，锁服务返回一个单调递增的令牌号。
  - 客户端写入存储时带上这个令牌号，存储服务只接受比已经见过的令牌号更大的写入，拒绝旧令牌的写入。
  - 这样，即使旧的持有者在锁过期后恢复并继续写入，它的写入也会被拒绝。
  - ZooKeeper 节点的 zxid、etcd 的 revision 可以作为 fencing token。

### 32. 基于 etcd/ZooKeeper 的分布式锁和 Redis 锁有什么区别？
**答案：**
- 一致性：
  - etcd 和 ZooKeeper 基于共识协议（Raft、ZAB），写入要经过多数节点确认，节点宕机也不会丢锁。
  - Redis 主从是异步复制的，主节点宕机后切换到从节点，锁可能丢失。
- 锁的释放：
  - etcd 和 ZooKeeper 把锁和客户端的会话或租约绑定，客户端崩溃或网络断开后，锁会自动释放，并且有续约机制（etcd 的 KeepAlive）。
  - Redis 依靠过期时间，需要自己实现续期。
- 等待机制：
  - etcd 和 ZooKeeper 可以监听（watch）前一个节点的删除事件，按顺序获取锁，是公平锁，不需要轮询。
  - Redis 一般需要自旋重试。
- 防护：etcd 和 ZooKeeper 天然提供单调递增的版本号，可以用作 fencing token。
- 性能：Redis 的性能更高、延迟更低；etcd 和 ZooKeeper 写入要经过共识，吞吐较低，不适合高频的加锁场景。
- 选择：对正确性要求高、加锁频率低（如选主、关键任务的互斥）用 etcd 或 ZooKeeper；高频、对少量重复可以容忍的场景用 Redis。

### 33. 【高频】接口幂等怎么设计？幂等 key 怎么选？
**答案：**
- 幂等：同一个请求执行一次和执行多次的效果相同。网络重试、用户重复点击、消息重复投递都需要幂等保证。
- 常见方案：
  - 唯一索引：业务唯一键（如订单号，或者用户 ID 加活动 ID）建唯一索引，重复插入会失败，捕获这个错误后返回已有的结果。
  - Token 机制：客户端先获取一个一次性 token，提交时带上，服务端用 Redis 的 `SET NX` 或 `DEL` 操作的返回值判断 token 是否已被使用。
  - 状态机加条件更新：`UPDATE ... SET status=已支付 WHERE id=? AND status=待支付`，状态只能单向流转，重复请求影响的行数为 0。
  - 乐观锁：使用版本号。
  - 去重表：记录已经处理过的请求 ID。
- 幂等 key 的选择：
  - 要能唯一标识"同一个业务操作"：客户端生成的请求 ID，或者业务唯一键（订单号、支付流水号、消息 ID、回调事件 ID）。
  - 不能用时间戳这类每次都不同的值。
  - 要考虑 key 的作用范围（如同一个用户的同一个操作）和保留时间。
- 返回结果：重复请求应该返回第一次请求的结果，而不是报错。

### 34. 消息重复消费怎么保证幂等？
**答案：**
- 原因：MQ 一般只能保证"至少一次"投递。消费成功了但提交 offset（或 ACK）失败、消费者发生 rebalance、生产者重发，都会导致消息被重复消费。
- 方法：
  - 业务天然幂等：如"把状态设置为 X"、按主键覆盖写入。
  - 唯一约束：用消息中的业务唯一键或消息 ID 作为唯一索引插入，重复插入会失败，直接跳过。
  - 去重记录：在消费的本地事务中，同时写入"已处理的消息 ID"（数据库），或者处理前用 Redis 的 SET NX 判断（要注意 Redis 和数据库之间的一致性问题，最好放在数据库的同一个事务中）。
  - 条件更新：状态机只能单向推进，旧消息不会覆盖新状态（带版本号）。
- 注意：去重记录要设置保留时间，并且要比消息可能重复的时间窗口更长。

## 消息队列

### 35. 【高频】为什么要用消息队列？会带来哪些问题？
**答案：**
- 作用：
  - 异步：把非核心步骤（通知、打点、写入统计数据）移出主链路，降低响应时间。
  - 解耦：生产者不需要知道有哪些消费者，新增消费者不用修改生产者。
  - 削峰：突发流量先进入队列，消费者按自己的能力匀速处理。
  - 广播：一条消息被多个系统消费。
  - 顺序和缓冲：日志收集、数据同步（binlog 发送到 MQ 再分发到下游）。
- 带来的问题：
  - 系统复杂度增加：MQ 本身的高可用、运维。
  - 消息丢失、重复消费、乱序。
  - 消息积压。
  - 一致性：异步带来数据延迟，需要最终一致性方案。
  - 排查链路变长。
- 可举例：数字人"最近使用"的写入链路，由 646 通过 bigpipe 发出事件，697 订阅后写入 Redis 和 MySQL，使用行为的记录不阻塞对话主流程。

### 36. 【高频】Kafka 为什么吞吐高？分区、副本、ISR 是什么？
**答案：**
- 吞吐高的原因：
  - 顺序写磁盘（追加写日志），并利用操作系统的页缓存。
  - 零拷贝（sendfile）发送数据给消费者。
  - 批量发送和批量压缩。
  - 分区并行：一个 topic 分成多个分区，分布在不同的 broker 上，并行读写。
  - 消费者按 offset 拉取，broker 不需要维护每条消息的消费状态。
- 分区（partition）：topic 的物理分片，每个分区是一个有序的、只能追加的日志。分区是并行和扩展的单位，消息只在分区内有序。
- 副本（replica）：每个分区有多个副本，分布在不同的 broker 上，其中一个是 Leader，负责读写，其他是 Follower，从 Leader 同步数据。
- ISR（In-Sync Replicas）：和 Leader 保持同步的副本集合。Follower 落后太多（超过 replica.lag.time.max.ms）就被移出 ISR。Leader 故障时，只从 ISR 中选举新的 Leader，以保证不丢失已提交的数据。
- HW（高水位）：ISR 中所有副本都已经同步到的位置，消费者只能读取到 HW 之前的消息。

### 37. 【高频】Kafka 如何保证消息不丢失？
**答案：**
- 生产者端：
  - acks=all（-1）：消息被 ISR 中所有副本写入后才算成功。
  - 设置重试次数（retries），开启幂等（enable.idempotence=true）防止重试导致重复。
  - 使用带回调的发送，处理发送失败的情况；不要发出去就不管了。
- broker 端：
  - replication.factor 大于等于 3。
  - min.insync.replicas 大于等于 2：ISR 中的副本数不足时拒绝写入，防止只写入一个副本。
  - unclean.leader.election.enable=false：禁止从不在 ISR 中的副本选出 Leader（否则会丢数据）。
- 消费者端：
  - 关闭自动提交 offset，处理成功之后再手动提交（先提交再处理，处理失败就会丢消息）。
  - 处理失败时重试，或者发送到死信队列。
- 代价：可靠性越高，延迟越高、吞吐越低，需要根据业务权衡（日志类数据可以使用 acks=1）。

### 38. 【高频】消息的顺序性怎么保证？
**答案：**
- Kafka 只保证分区内有序，所以需要顺序的消息要发送到同一个分区：用业务 key（订单 ID、用户 ID、会话 ID）作为消息的 key，按 key 哈希分区，同一个 key 的消息会进入同一个分区。
- 生产者：
  - 开启幂等，并且 max.in.flight.requests.per.connection 不超过 5，这样重试也不会打乱顺序（老版本的 Kafka 需要设置为 1）。
  - 同一个 key 的消息由同一个生产者按顺序发送。
- 消费者：
  - 一个分区同时只被一个消费者消费。
  - 消费者内部如果用多协程并行处理，要按 key 把消息分配到固定的协程（按 key 哈希到内存队列），否则会打乱顺序。
- 全局有序：只能使用一个分区，吞吐很低，一般不推荐。
- 业务层兜底：消息中带上版本号或序号，消费者丢弃旧版本的消息，或者检测到乱序时暂存，等待前面的消息。

### 39. 【高频】消息积压怎么处理？
**答案：**
- 先定位原因：
  - 消费者变慢了：下游变慢、处理逻辑有问题、消费者报错后不断重试。
  - 生产量突增。
  - 消费者实例挂了，或者频繁 rebalance。
- 应急处理：
  - 修复消费者的问题（下游故障就先降级或熔断）。
  - 扩容消费者：增加消费者实例数，但不能超过分区数（多出的消费者会空闲）。
  - 分区数不够时，临时新建一个分区更多的 topic，写一个转发程序把积压的消息快速转发过去，再用大量消费者并行处理。
  - 在消费者内部提高并发：批量拉取、批量写入下游、按 key 分配到多个协程并行处理（注意顺序要求）。
  - 非核心的消息可以先跳过（记录 offset，之后再补处理）。
- 预防：
  - 监控消费延迟（lag）并告警。
  - 根据峰值规划分区数和消费能力。
  - 消费逻辑要轻量，耗时的操作异步处理。

### 40. Kafka 的消费者组和 rebalance 是什么？rebalance 有什么问题？
**答案：**
- 消费者组：同一个组内的消费者共同消费一个 topic，每个分区只分配给组内的一个消费者，实现负载均衡；不同的组之间互不影响，各自消费全部消息（实现广播）。
- rebalance：组内成员或分区发生变化时（消费者加入或离开、心跳超时、处理时间超过 max.poll.interval.ms、分区数增加），由协调者重新分配分区和消费者的对应关系。
- 问题：
  - 传统的 rebalance（eager 协议）期间，整个组都要停止消费（stop the world），造成消费中断和延迟抖动。
  - rebalance 前已经处理但还没提交 offset 的消息，会被重复消费。
  - 频繁的 rebalance（如处理耗时太长被误判为宕机）会形成恶性循环。
- 优化：
  - 合理设置 session.timeout.ms、heartbeat.interval.ms、max.poll.interval.ms；减小 max.poll.records，让单批的处理耗时可控。
  - 使用增量协作式 rebalance（CooperativeStickyAssignor），只迁移需要变动的分区。
  - 静态成员（group.instance.id），实例重启时不触发 rebalance。
  - 消费逻辑要幂等，以应对重复消费。

### 41. 【专家】Kafka 的 Exactly-Once 语义是怎么实现的？
**答案：**
- 三个组成部分：
  - 幂等生产者：每个生产者有一个 PID，每个分区的每条消息都带有递增的序列号；broker 按（PID，分区，序列号）去重，生产者重试时不会重复写入。但只能保证单个会话、单个分区内不重复。
  - 事务：生产者设置 transactional.id，可以把"写入多个分区的消息，加上提交消费者的 offset"放进同一个原子事务中，要么全部可见，要么全部不可见。由事务协调者和事务日志实现两阶段提交，并在分区中写入事务标记。
  - 消费者设置 isolation.level=read_committed：只读取已经提交的事务消息，跳过已中止的事务消息。
- 适用范围：只在 Kafka 内部的"读取、处理、写回 Kafka"链路中（如 Kafka Streams、Flink 的 Kafka 连接器）实现端到端的 exactly-once。
- 局限：消费消息后写入外部系统（数据库、调用接口）时，Kafka 的事务管不到外部系统。这种情况仍然需要"至少一次加消费端幂等"，或者把 offset 和业务数据放在同一个数据库事务中保存。
- 代价：事务会增加延迟、降低吞吐。

### 42. RocketMQ 和 Kafka 有什么区别？事务消息怎么用？
**答案：**
- 区别：
  - 定位：Kafka 主要面向大数据和日志场景，吞吐量极高；RocketMQ 主要面向业务消息，功能更丰富。
  - 功能：RocketMQ 原生支持事务消息、延迟消息（5.x 版本支持任意时间的延迟）、消息过滤（tag）、消息重试和死信队列、按 key 查询消息；Kafka 的这些功能大多需要自己实现。
  - 存储：Kafka 每个分区一个文件，分区多时随机 IO 增加，性能下降；RocketMQ 所有消息写入同一个 CommitLog，再建立 ConsumeQueue 索引，topic 和队列很多时性能更稳定。
  - 生态：Kafka 在流处理（Flink、Spark）生态中的集成更好。
- 事务消息的流程：
  1. 生产者发送半消息（对消费者不可见）。
  2. 执行本地事务。
  3. 根据本地事务的结果，向 broker 提交（消息变为可见）或回滚（删除消息）。
  4. 如果第 3 步没有完成（生产者宕机），broker 会定期回查生产者的本地事务状态，再决定提交还是回滚。生产者要实现回查接口（根据业务 ID 查询本地事务是否成功）。
- 适用：本地数据库操作和发送消息需要保持一致的场景（如下单后通知库存服务）。

### 43. 延迟消息怎么实现？
**答案：**
- MQ 原生支持：
  - RocketMQ 4.x 提供固定的延迟级别（1s、5s、10s、30s、1m ...），5.x 支持任意时间的延迟。
  - RabbitMQ 用消息 TTL 加死信交换机实现：消息在一个没有消费者的队列中过期后，被转发到死信队列，再被消费；也可以使用延迟插件。
  - Kafka 原生不支持延迟消息。
- 自己实现：
  - Redis ZSET：score 为投递时间，定时任务取出到期的消息再投递到普通队列（用 Lua 保证取出并删除是原子的）。
  - 时间轮：在内存中实现，精度高、效率高，但需要持久化和故障恢复。
  - 数据库表加定时扫描：可靠，实现简单，适合量不大的场景。
  - 分级延迟 topic：按延迟时长分成多个 topic，消费者检查到时间才处理，没到时间就等待或重新投递。
- 典型场景：订单超时取消、延迟重试、定时提醒。

### 44. 死信队列的作用是什么？
**答案：**
- 定义：多次重试后仍然消费失败的消息（或者过期、被拒绝的消息），被转移到一个专门的队列，即死信队列。
- 作用：
  - 隔离"毒消息"：防止一条始终处理失败的消息无限重试，阻塞后续消息的消费（特别是在需要保证顺序的场景）。
  - 保留问题数据：方便排查，修复问题后再重新投递处理，消息不会丢失。
  - 用作延迟队列（RabbitMQ 的 TTL 加死信）。
- 实践：
  - 设置合理的最大重试次数和退避间隔。
  - 消息进入死信队列时告警。
  - 死信消息中保留失败原因和原始的元数据。
  - 提供重新投递的工具。
  - 定期清理或处理死信消息。

### 45. 【专家】用 MQ 做异步双写（Redis + MySQL）时，怎么保证两边数据一致？
**答案：**
- 明确以谁为准：通常以 MySQL 为权威数据源，Redis 是缓存或加速层；Redis 中的数据丢失或错误时，都可以从 MySQL 重建。
- 写入顺序和失败处理：
  - 消费者先写 MySQL（用唯一键加 upsert 保证幂等），成功后再写 Redis；Redis 写入失败时重试，重试后仍然失败就删除对应的 Redis key（下次读取时回源 MySQL 加载），而不是让 Redis 保留旧数据。
  - 只有两边都处理成功后才提交 offset；失败的消息重试，超过次数进入死信队列。
- 乱序：同一个用户的消息按 key 路由到同一个分区，保证顺序；数据带上时间戳，Redis 中用"时间更新才覆盖"的条件写入（例如 ZSET 的 ZADD GT 选项，只在分数更大时更新）。
- 读取兜底：Redis 未命中时回源 MySQL 并回填，所以即使 Redis 数据丢失也能自动恢复。
- 校准：定期抽样对比两边的数据，以 MySQL 为准修复 Redis；Redis 设置过期时间，避免错误数据长期存在。
- 可举例：数字人"最近使用"由 697 订阅 bigpipe 后双写 Redis（ZSET 只保留 16 条，过期时间 12 个月）和 MySQL；首屏读取时 Redis 未命中就回源 MySQL 并回写。
