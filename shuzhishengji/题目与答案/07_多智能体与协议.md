# 07 多智能体协作与协议（25 题）（题目与答案）

### 1. 【高频】为什么需要多智能体？单 Agent 解决不了什么问题？
**答案：**
- 单 Agent 的瓶颈：
  - 工具和职责太多时，Prompt 过长，选错工具的概率上升。
  - 长任务中上下文膨胀，注意力被稀释。
  - 无法并行处理。
  - 一个 Prompt 很难同时兼顾多种专业角色。
- 多智能体的价值：
  - 分工：每个 Agent 专注一个领域，Prompt 和工具集更小，效果更好。
  - 上下文隔离：子任务的中间过程不污染主上下文。
  - 并行：独立的子任务同时执行，缩短总耗时。
  - 互相校验：生成和审查由不同 Agent 负责，减少错误。
  - 组织复用：不同团队开发的 Agent 可以协作（跨组织调用）。
- 注意：多智能体会显著增加成本和复杂度，单 Agent 能解决的问题优先用单 Agent。

### 2. 【高频】多智能体有哪些协作模式（主从/Supervisor、流水线、辩论、群聊）？
**答案：**
- Supervisor（主从）：一个主 Agent 负责理解任务、分派给子 Agent、汇总结果。结构清晰、可控，是最常用的模式；缺点是主 Agent 可能成为瓶颈。
- 层级式：Supervisor 下面还有 Supervisor，适合大型复杂任务。
- 流水线（顺序）：多个 Agent 按固定顺序依次处理，如调研、写作、审核。流程稳定，适合步骤明确的任务。
- 辩论：多个 Agent 从不同立场讨论，再由裁判汇总，用于提升推理质量和减少偏见。成本高。
- 群聊（共享对话）：多个 Agent 在同一个对话中发言，由调度器决定下一个发言者（如 AutoGen 的 GroupChat），灵活，但容易失控。
- 交接（Handoff）：当前 Agent 把对话控制权转交给更合适的 Agent（如 OpenAI Agents SDK 的 handoff），适合客服分流。

### 3. 【专家】Supervisor 模式下，主 Agent 怎么决定把任务派给哪个子 Agent？
**答案：**
- 把子 Agent 当成工具：每个子 Agent 有名称、能力描述、输入参数，主 Agent 通过工具调用来派发任务，由模型根据描述选择。这是最常用的实现方式。
- 规则加模型混合：确定性的意图用规则路由；模糊的交给模型判断。
- 能力注册表：子 Agent 数量多时，先根据任务检索候选的子 Agent（类似工具检索），再由模型选择。
- 派发时要给出清晰的任务描述：目标、背景、约束、期望的输出格式。
- 结果处理：主 Agent 检查子 Agent 的结果是否满足要求，不满足时重新派发或换一个子 Agent。
- 评估：统计派发的准确率，即是否派给了正确的子 Agent。

### 4. 多智能体之间的消息格式怎么设计？
**答案：**
- 结构化消息，包括：
  - 消息 ID、会话或任务 ID、发送方、接收方、消息类型（任务请求、结果、状态更新、错误、澄清问题）。
  - 内容：任务描述或结果，用文本加结构化数据。
  - 附件或产物：文件、链接、数据。
  - 元数据：时间、优先级、截止时间、trace_id。
- 区分"给人看的自然语言"和"给程序处理的结构化字段"。
- 任务结果中包含完成状态（成功、失败、部分完成）和置信度，方便主 Agent 判断。
- 可以参考 A2A 协议中 Task、Message、Part、Artifact 的设计，便于和外部 Agent 互通。

### 5. 【高频】多智能体系统怎么避免互相"踢皮球"或无限对话？
**答案：**
- 明确职责边界：每个 Agent 的描述中写清楚负责什么、不负责什么。
- 设置终止条件：最大轮数、最大交接次数、总 token 和时间预算；达到上限后强制由主 Agent 汇总结束。
- 检测循环：同一个任务在两个 Agent 之间来回转交超过 N 次，就判定为踢皮球，交给主 Agent 或人工处理。
- 由一个明确的负责者对最终结果负责（如 Supervisor），其他 Agent 只返回结果，不能无限转交。
- 群聊模式中，由调度器（而不是 Agent 自己）决定下一个发言者，并设置结束判断。

### 6. AutoGen、CrewAI、MetaGPT 的设计思路分别是什么？
**答案：**
- AutoGen（微软）：以"可对话的 Agent"为核心，多个 Agent 通过消息对话协作；支持群聊和发言者选择、人类代理参与、代码执行。灵活，适合研究和实验。新版本改为事件驱动的架构。
- CrewAI：用角色（role）、目标（goal）、背景（backstory）定义 Agent，用 Task 定义任务，组成 Crew，按顺序或层级流程执行。上手简单，概念贴近团队协作。
- MetaGPT：模拟软件公司，产品经理、架构师、工程师、测试等角色按 SOP（标准作业流程）协作，Agent 之间通过结构化的文档（需求文档、设计文档）交接。强调用 SOP 约束协作，减少自由对话带来的混乱。
- 共同点：都在探索用角色分工加协作流程提升复杂任务的完成质量。

### 7. 【专家】多智能体系统的成本和延迟通常是单 Agent 的数倍，怎么判断值不值得？
**答案：**
- 先用单 Agent 做基线：在评测集上测出单 Agent 的成功率、成本、延迟。
- 再测多智能体方案：同样的评测集，对比成功率提升多少、成本和延迟增加多少。
- 判断标准：
  - 任务价值高、单 Agent 成功率明显不足（如复杂调研、编程），可以接受更高的成本。
  - 高频、简单、对延迟敏感的任务（对话问答），通常不值得。
  - 并行能否抵消一部分延迟。
- 降低成本：子 Agent 使用小模型；只在必要时启用多智能体（按任务复杂度路由）；减少 Agent 之间的往返次数。
- 用"每成功完成一个任务的成本"衡量，而不是只看单次调用成本。

### 8. 【高频】A2A（Agent2Agent）协议是什么？解决什么问题？
**答案：**
- 是 Google 在 2025 年 4 月发布的开放协议（后来捐给 Linux 基金会），用于不同厂商、不同框架开发的 Agent 之间互相发现和协作。
- 解决的问题：企业中有大量由不同团队、不同技术栈构建的 Agent，它们之间缺乏统一的通信方式，每次对接都要定制开发。
- 设计：基于 HTTP、JSON-RPC、SSE 等现有标准；Agent 可以作为不透明的黑盒协作，不需要暴露内部的工具、记忆和实现；支持长时间运行的任务、流式更新和推送通知；支持多模态内容。
- 定位：MCP 解决"Agent 怎么使用工具和数据"，A2A 解决"Agent 怎么和其他 Agent 协作"。

### 9. A2A 中 Agent Card、Task、Message、Artifact 分别是什么？
**答案：**
- Agent Card：Agent 的"名片"，一个 JSON 文档（通常放在 `/.well-known/agent.json` 这类公开路径下），描述名称、能力（skills）、服务地址、支持的输入输出模态、认证方式。用于发现和选择 Agent。
- Task：一次协作的工作单元，有唯一 ID 和生命周期状态（如 submitted、working、input-required、completed、failed、canceled），支持长时间运行。
- Message：客户端和远端 Agent 之间的一轮通信（角色为 user 或 agent），由多个 Part 组成（文本、文件、结构化数据）。
- Artifact：任务产出的结果（文档、图片、数据），也由 Part 组成，可以流式返回。
- 交互方式：同步请求、SSE 流式更新、长任务的推送通知（webhook）。

### 10. 【高频】A2A 和 MCP 的区别和关系是什么？
**答案：**
- MCP：连接 Agent（或 LLM 应用）和工具、数据源。工具是被动的、能力确定的，调用后立即返回结果，属于"纵向"集成。
- A2A：连接 Agent 和 Agent。对方是自主的智能体，会自己推理、可能需要多轮交互、可能长时间运行，对外隐藏内部实现，属于"横向"协作。
- 关系：两者互补，不是竞争关系。一个 Agent 内部用 MCP 调用工具，对外用 A2A 和其他 Agent 协作。
- 边界有时模糊：一个简单的 Agent 也可以包装成 MCP 工具；选择哪种取决于对方是否需要自主决策、多轮交互和长任务管理。

### 11. 【专家】ANP（Agent Network Protocol）的设计思路是什么？去中心化身份（DID）在其中起什么作用？
**答案：**
- ANP 的目标：成为"智能体互联网"的通信协议，让开放网络上任意的 Agent 能够互相发现、认证和通信，不依赖某个中心化平台。
- 三层结构：
  - 身份与加密通信层：基于 W3C DID（去中心化标识符），实现身份认证和端到端加密。
  - 元协议层：Agent 之间可以协商使用什么协议来通信（甚至由模型动态协商生成协议）。
  - 应用协议层：用 Agent 描述文档（基于 JSON-LD 等语义网标准）描述能力，支持发现。
- DID 的作用：
  - 每个 Agent 有自己可验证的身份（如 did:wba 方法，基于 Web 域名托管 DID 文档），不需要在每个平台单独注册账号。
  - 对方可以用 DID 文档中的公钥验证签名，确认身份。
  - 是跨平台、跨组织建立信任的基础。
- 和 A2A 的区别：A2A 偏企业内部和受信任的伙伴之间，依赖现有的认证体系；ANP 更强调开放网络中的去中心化和身份自主。

### 12. 跨组织的 Agent 互相调用，身份认证和信任怎么建立？
**答案：**
- 身份认证：
  - 组织之间：OAuth 2.0 客户端凭证、mTLS 双向证书、API Key 加签名。
  - 开放网络：DID 加数字签名。
  - Agent Card 中声明支持的认证方式。
- 授权：最小权限原则，按 scope 授权可以调用的能力；需要代表用户操作时，用户要明确授权（委托授权，如 OAuth 授权码流程）。
- 信任：
  - 白名单和准入审核：只和经过审核的 Agent 合作。
  - 签名校验：消息和结果带签名，防止篡改。
  - 信誉和评分：根据历史调用质量评估。
- 安全：把外部 Agent 返回的内容当作不可信输入（防注入）；敏感数据不传给外部 Agent，或者先脱敏；完整审计日志。
- 合同和计费：约定 SLA、数据使用范围、费用。

### 13. 多 Agent 并行执行时，共享状态怎么保证一致性？
**答案：**
- 优先避免共享写入：每个 Agent 写自己独立的输出区域，由主 Agent 统一合并，从设计上消除冲突。
- 必须共享时：
  - 乐观锁或版本号：写入时校验版本，冲突就重试或合并。
  - 分布式锁：对关键资源加锁（注意锁的超时）。
  - 单写者原则：某一类状态只允许一个 Agent 修改。
  - 事件溯源：状态的每次变更都记录为事件，按顺序回放，便于追溯。
- 状态合并：类似 LangGraph 的 reducer，为每个字段定义合并规则（列表追加、取最新值、取最大值）。
- 外部资源（数据库、文件）的并发写入要做幂等和冲突检测。

### 14. 【专家】多人（多用户）与多个数字人同时对话，调度策略怎么设计？
**答案：**
- 场景：一个房间里有多个用户和多个数字人（或智能体），需要决定每条消息由谁回复、是否回复、谁先回复。
- 调度要素：
  - 意图和领域匹配：根据 query 的领域和每个数字人的人设、专长，选择最合适的回复者。
  - 指名优先：用户明确 @ 了某个数字人，就由它回复。
  - 上下文连贯：正在和某个用户对话的数字人优先继续回复。
  - 是否需要回复：闲聊、用户之间的对话，数字人可以不插话。
  - 多个数字人都可以回复时：选一个主回复者，其他数字人按需补充，避免同时抢答。
- 实现：调度器可以用大模型输出结构化决策（回复者 ID、是否回复、顺序），输入包括 query、领域、主智能体 ID、历史上下文。
- 统计和评估：记录调度结果，用于离线分析和优化。
- 可举例：多人对话调度数据需求中，定义了调度命中统计口径，明细字段包括 query、主智能体 app_id、query 领域、历史上下文和调度结果，并产出了 Sugar 报表。

### 15. 多人对话中，如何决定由哪个 Agent 回复、是否需要回复？
**答案：**
- 是否回复：
  - 用户 @ 了某个 Agent，或问题明确指向 Agent，需要回复。
  - 用户之间闲聊、表示附和（"哈哈""好的"），一般不回复。
  - 可以训练分类器或用大模型判断"是否需要 Agent 介入"。
- 由谁回复：
  - 显式指定优先。
  - 其次按话题和 Agent 专长的匹配度。
  - 再考虑对话的连续性（上一轮是谁在回答）。
  - 负载和频率控制：避免同一个 Agent 刷屏，也避免冷落其他 Agent。
- 回复顺序：多个 Agent 都需要回复时，安排先后顺序，后回复的 Agent 能看到前面的回复，避免内容重复。
- 兜底：判断不出来时，由主 Agent 回复，或者提问澄清。

### 16. 调度命中率怎么统计？用 query 维度还是 session 维度？
**答案：**
- query 维度：以每条用户 query 为单位，计算"命中多人调度的 query 数 / 总 query 数"。粒度细，能反映调度策略在单次决策上的表现，便于定位具体的 badcase。
- session 维度：以会话为单位，计算"出现过多人调度的会话数 / 总会话数"。反映功能的覆盖面和使用情况，但一个会话中有多少次调度、调度是否准确，都看不出来。
- 选择：评估调度策略时用 query 维度；评估功能渗透率时用 session 维度。两者口径不同，不能混用，在报表中要写清楚。
- 可举例：多人调度数据需求中，最终确定以 query 为维度计算命中多人调度的比例，去掉了 session 维度的口径，因为目标是评估调度策略本身。

### 17. 【高频】多智能体系统怎么调试？怎么定位是哪个 Agent 出了问题？
**答案：**
- 全链路 trace：每个 Agent 的每一步（模型调用、工具调用、消息收发）都记录为一个 span，用同一个 trace_id 串起来，在可视化平台上能看到完整的调用树和时间线。
- 记录每个 Agent 的输入、输出、决策理由，方便判断是"主 Agent 派错了任务"还是"子 Agent 执行出错"。
- 逐层排查：先看最终结果哪里错了，沿着调用链往回找第一个出错的环节。
- 单独测试：为每个子 Agent 建立独立的评测集，单独评估；用固定的输入回放，复现问题。
- 统计：各 Agent 的失败率、耗时、重试次数，找出薄弱环节。

### 18. 子 Agent 失败时，主 Agent 怎么处理（重试、换 Agent、降级）？
**答案：**
- 按失败类型处理：
  - 临时性错误（超时、限流）：带退避重试。
  - 任务描述不清导致结果不符合要求：主 Agent 补充信息后重新派发。
  - 子 Agent 能力不足：换一个能力相近的 Agent，或者拆成更小的任务。
- 降级：
  - 非关键的子任务失败，主 Agent 基于已有结果继续，并在最终回答中说明缺失的部分。
  - 关键子任务失败，终止并告知用户，或转人工。
- 限制重试次数和总时长，避免级联放大。
- 子 Agent 要返回明确的失败原因，而不是空结果或含糊的文字，方便主 Agent 判断。

### 19. 多智能体的任务结果怎么汇总，避免信息冲突？
**答案：**
- 结构化输出：子 Agent 按统一的格式返回结果（结论、依据、来源、置信度），便于合并。
- 合并规则：
  - 去重：合并相同的结论。
  - 冲突处理：比较来源的可信度和时间；按置信度加权；必要时派出第三个 Agent 核实；无法判断时在结果中如实列出分歧。
- 由主 Agent（或专门的汇总 Agent）负责最终整合，并在 Prompt 中要求"发现矛盾时明确指出，不要强行统一"。
- 保留每条结论的来源，可以追溯是哪个 Agent 给出的。

### 20. 【专家】用 k8s 控制器（reconcile）模式管理 Agent 任务，有什么好处？
**答案：**
- reconcile 模式：声明"期望状态"，控制器不断观察"实际状态"，计算两者的差异，执行动作让实际状态逼近期望状态；循环执行，具有幂等性。
- 应用到 Agent 任务：
  - 任务的目标（如"交付一个部署好的数字人"）记录为期望状态。
  - 控制器定期检查各子任务（审核、制作、部署）的实际状态，推进到下一步。
  - 中途失败或被中断，下一次循环会自动从当前状态继续，而不是从头开始。
- 好处：
  - 天然具备容错和自愈能力，进程重启后能恢复。
  - 幂等：重复执行不会产生副作用。
  - 状态驱动，逻辑清晰，便于观察和排查。
  - 适合长时间运行、依赖外部异步系统的任务。
- 可举例：对客 PaaS 的交付状态由 status_query、回调、缩容三处显式推进，另外有 RecomputeDelivery 定时任务做兜底巡检，思路与 reconcile 一致。

### 21. 多 Agent 系统中，工具和权限怎么按角色隔离？
**答案：**
- 每个 Agent 只注册它的职责需要的工具，即最小工具集。如调研 Agent 只有搜索和阅读工具，执行 Agent 才有写入工具。
- 权限分级：只读、低风险写入、高风险写入；高风险操作只允许特定的 Agent 执行，并且需要人工确认。
- 凭证隔离：不同的 Agent 使用不同的凭证或服务账号，权限范围不同；不把凭证暴露在上下文中。
- 数据隔离：Agent 只能访问它被授权的数据范围（按租户、按用户）。
- 防止权限借用：低权限的 Agent 不能通过请求高权限的 Agent 代为执行，从而绕过限制，派发任务时也要校验原始请求者的权限。
- 审计：记录每个 Agent 的每一次工具调用。

### 22. 【高频】多智能体系统的评估和单 Agent 评估有什么不同？
**答案：**
- 端到端评估：最终任务的成功率、质量、成本、延迟，和单 Agent 相同，但还要和单 Agent 基线做对比，证明多智能体方案值得。
- 组件评估：
  - 每个子 Agent 单独评估。
  - 调度和派发的准确率：任务是否派给了正确的 Agent。
- 协作过程评估：
  - 交互轮数、冗余通信、踢皮球的比例。
  - 信息在传递中是否丢失或被曲解。
  - 冲突的处理是否正确。
- 归因：任务失败时，判断是哪个 Agent 或哪个环节导致的。
- 成本：总 token 消耗和单 Agent 的对比，按"每成功完成一个任务的成本"计算。

### 23. Agent 市场 / Agent 商店怎么做发现、计费和质量控制？
**答案：**
- 发现：
  - 分类、标签、搜索（关键词加语义）。
  - 个性化推荐、热门榜单、"最近使用"入口。
  - 程序调用方可以通过能力描述（Agent Card）自动发现。
- 计费：按调用次数、按 token、订阅制、免费加增值；平台和开发者分成；有调用记录和对账；设置配额和限流。
- 质量控制：
  - 上架审核：内容安全、功能测试、合规。
  - 运行监控：成功率、延迟、用户评分、投诉。
  - 低质量的 Agent 降低排序、警告或下架。
  - 状态同步：已下线的 Agent 不能再被分发和访问，同时要保证已上线的 Agent 状态正确（例如已上线却跳转到下线页的问题）。
- 安全：第三方 Agent 运行在受控环境中，权限受限；用户数据的使用要经过授权。

### 24. 人类在多 Agent 协作中扮演什么角色？什么时候需要人工介入？
**答案：**
- 角色：
  - 目标设定者：定义任务和验收标准。
  - 审批者：批准高风险操作。
  - 纠错者：在 Agent 卡住或出错时修正方向。
  - 协作者：负责 Agent 做不好的部分（判断、创意、对外沟通）。
- 需要人工介入的时机：
  - 高风险、不可逆的操作（付款、删除、对外发布）。
  - 低置信度的决策，或者多个 Agent 结论冲突无法自动解决。
  - 任务多次失败、超出预算。
  - 涉及合规、伦理的判断。
  - 质检场景中，机器质检不确定的结果交给人工复核。
- 设计：在流程中预留中断点；向人展示简洁的摘要和选项；人的决策要能回传给 Agent 继续执行。

### 25. 【专家】设计一个支持 A2A 的 Agent 网关，需要考虑哪些功能？
**答案：**
- 注册与发现：管理内部和外部 Agent 的 Agent Card，提供目录和搜索；健康检查；版本管理。
- 协议适配：对外提供标准的 A2A 接口（JSON-RPC、SSE、推送通知），对内适配各团队已有的 Agent 协议；支持和 MCP 的互相转换。
- 安全：
  - 认证（OAuth、mTLS、API Key），对调用方和被调用方都做身份校验。
  - 按 skill 粒度授权。
  - 请求和响应的内容审核、注入检测、敏感数据脱敏。
- 流量治理：限流、熔断、超时、重试、负载均衡、灰度路由。
- 任务管理：长任务的状态存储、断线重连、推送通知的可靠投递（重试、签名）。
- 可观测：全链路 trace、调用日志、成功率和延迟监控。
- 计费与审计：按调用方和 Agent 统计用量，记录完整的审计日志。
