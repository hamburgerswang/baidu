# 06 记忆与上下文工程（30 题）（题目与答案）

### 1. 【高频】Agent 的短期记忆和长期记忆分别是什么？怎么实现？
**答案：**
- 短期记忆：当前会话内的信息，包括对话历史、工具调用结果、中间状态，直接放在上下文窗口中。实现上是按 session 存储消息列表，每轮取最近的若干轮拼进 Prompt，过长时截断或摘要。
- 长期记忆：跨会话保留的信息，包括用户偏好、事实（"我是素食者"）、历史任务经验。实现上是从对话中抽取记忆，存入向量库、KV 存储或图数据库；新对话时按相关性检索出来注入上下文。
- 还有程序性记忆：Agent 的技能、规则、工作流，通常体现在 Prompt 和工具中。

### 2. 【高频】对话历史太长时怎么处理（滑动窗口、摘要、检索）？
**答案：**
- 滑动窗口：只保留最近 N 轮或最近 N 个 token。简单，但较早的重要信息会丢失。
- 摘要：把较早的历史压缩成摘要，加上最近几轮原文。能保留要点，但摘要本身有信息损失，而且需要额外调用模型。
- 检索：把历史消息存成可检索的单元，根据当前问题检索相关的历史片段。适合很长的会话，但可能检索不到。
- 组合使用：System Prompt、长期记忆、历史摘要、相关历史片段、最近几轮原文，按 token 预算分配。
- 处理时要保证消息序列合法：工具调用和对应的结果成对保留，角色交替。

### 3. 【专家】什么是上下文工程（Context Engineering）？和 Prompt 工程有什么区别？
**答案：**
- Prompt 工程：关注怎么写指令，即措辞、结构、示例。
- 上下文工程：关注每一次模型调用时，放进上下文窗口的全部信息应该是什么、以什么形式和顺序放入。包括指令、对话历史、记忆、检索结果、工具定义和工具结果、任务状态。
- 核心问题：在有限的窗口和成本约束下，让模型拿到完成当前步骤所需的、正确且足够的信息，同时噪声最少。
- 手段：检索与选择、压缩与摘要、结构化组织、隔离（子 Agent 使用独立上下文）、外部化（存到文件系统，用时再取）、提高缓存命中。
- 对 Agent 来说，上下文工程往往比 Prompt 措辞对效果的影响更大。

### 4. 【专家】Manus 分享的上下文工程经验有哪些（KV Cache 命中、工具遮蔽、文件系统作为记忆等）？
**答案：**
- 围绕 KV Cache 设计：Agent 的输入远长于输出，KV Cache 命中率是影响延迟和成本最关键的指标。要保持 Prompt 前缀稳定（不在开头放时间戳）、上下文只追加不修改、序列化方式确定（如 JSON 的 key 顺序固定）。
- 工具遮蔽而不是删除：动态增删工具定义会破坏缓存，还会让模型困惑（历史中引用了已不存在的工具）。应保持工具定义不变，在解码时用约束（logits mask）限制当前可选的工具。
- 文件系统作为上下文：大的观察结果（网页、文件内容）写入文件，上下文中只保留路径等引用，需要时再读取。压缩要做到可恢复。
- 用复述维持注意力：长任务中不断更新 todo.md，把目标和进度放到上下文末尾，防止目标漂移。
- 保留错误：失败的动作和报错信息留在上下文中，让模型从错误中学习，不要隐藏。
- 避免 few-shot 陷阱：上下文中大量相似的动作记录会让模型机械模仿，要在格式和措辞上引入少量变化。

### 5. 为什么要尽量保持 Prompt 前缀稳定？时间戳放在 System Prompt 开头有什么问题？
**答案：**
- 原因：Prompt Caching 和推理引擎的前缀缓存只能复用"从开头起完全相同"的部分。前缀稳定时，重复的 System Prompt 和工具定义不需要重新计算，首 token 延迟和费用都会大幅下降。
- 时间戳的问题：精确到秒的时间戳放在开头，每次请求的第一段就不同，后面所有内容都无法命中缓存，相当于缓存完全失效。
- 改进：
  - 时间放到 Prompt 后部，靠近用户消息的位置。
  - 降低精度，只精确到日期，让同一天的请求前缀相同。
  - 用户相关的变量同样放在后面。

### 6. 【高频】上下文中的工具结果要不要全部保留？怎么压缩？
**答案：**
- 不必全部原样保留：工具结果常常是上下文膨胀的主要原因（网页、搜索结果、文件内容）。
- 压缩方式：
  - 生成时就精简：工具只返回需要的字段。
  - 随时间衰减：最近几步的结果保留原文，较早的替换为摘要或"结果已省略，可重新获取"的引用。
  - 外部化：原文存入文件或缓存，上下文中保留路径和关键结论。
- 注意：
  - 工具调用和对应结果必须成对保留，不能只删结果，否则会破坏消息格式。
  - 压缩会影响缓存，尽量在固定时机批量压缩，而不是每轮都改写历史。

### 7. 上下文压缩（compaction）怎么做才不丢关键信息？
**答案：**
- 触发：上下文接近阈值（如窗口的 70% 到 80%）时触发，而不是每轮都压缩。
- 明确摘要必须保留的信息：用户的原始目标和约束、已做出的决定、当前进度和待办事项、关键数据（ID、路径、数字）、遇到的错误和已尝试过的方法。
- 最近几轮对话和关键工具结果保留原文，不压缩。
- 可恢复：被压缩的原始内容存到外部，需要时可以重新读取。
- 验证：用评测集对比压缩前后的任务成功率，检查压缩后模型是否重复做已经做过的事。

### 8. 【专家】用"文件系统/外部存储"作为 Agent 的扩展记忆，是怎么做的？
**答案：**
- 给 Agent 提供文件读写工具（或 KV、数据库工具），让它主动把信息写入外部存储：大的观察结果（网页正文、搜索结果、代码文件）、中间产物（笔记、草稿、计划）、任务状态（todo 列表、进度）。
- 上下文中只保留引用（文件路径、摘要），需要时 Agent 自己调用工具读取。
- 好处：上下文不再随任务长度无限增长；信息可持久化，跨步骤、跨会话复用；压缩时不会真正丢失信息。
- 要求：模型要知道什么时候该去查；文件组织清晰（命名规范、索引文件）；多用户场景做好存储隔离和权限控制。
- 例子：Claude Code 用项目说明文件和待办列表维持长期上下文；Manus 用 todo.md 和工作目录。

### 9. 情景记忆（episodic）和语义记忆（semantic）有什么区别？
**答案：**
- 情景记忆：具体发生过的事件和经历，带有时间和上下文，如"上周二用户让我订了去上海的机票，选了靠窗座位"。适合回顾历史、复用过去的成功经验。
- 语义记忆：从经历中提炼出来的、和具体事件无关的事实与知识，如"用户偏好靠窗座位""用户住在北京"。适合个性化和快速注入。
- 关系：语义记忆通常由多次情景记忆总结而来。
- 实现：情景记忆按时间存储完整事件或摘要；语义记忆以结构化的事实或画像形式存储，支持更新和去重。

### 10. 【高频】用户长期记忆（偏好、事实）怎么抽取、存储和更新？
**答案：**
- 抽取：
  - 对话结束后（或每隔若干轮）异步调用模型，从对话中抽取值得长期记住的信息，输出结构化的事实列表（类型、内容、置信度、来源对话）。
  - 只抽取稳定、有用的信息，过滤掉一次性的、临时的内容。
  - 也支持用户明确说"记住……"时立即写入。
- 存储：结构化字段（城市、语言等）存入 KV 或数据库；自由文本的事实存入向量库，方便语义检索。每条记忆带时间戳和来源。
- 更新：写入前检索相似的已有记忆，由模型判断是新增、更新、合并还是删除（如 Mem0 的 ADD/UPDATE/DELETE/NOOP 思路）。
- 使用：新对话时按当前话题检索相关记忆，注入上下文。

### 11. 【专家】记忆冲突（新旧事实矛盾）怎么处理？遗忘机制怎么设计？
**答案：**
- 冲突检测：写入新记忆时，检索语义相近的旧记忆，由模型判断是否矛盾，如"住在北京"和"刚搬到上海"。
- 冲突解决：
  - 默认以最新的、用户明确表达的信息为准，旧记忆标记为过期（保留历史版本，而不是直接删除）。
  - 置信度低时不覆盖，等待更多证据，或者向用户确认。
  - 区分临时状态（"这周在出差"）和长期事实。
- 遗忘机制：
  - 时间衰减：长期未被使用、时间久远的记忆降低权重或归档。
  - 访问频率：经常被使用的记忆强化。
  - 容量上限：超过上限时淘汰低价值的记忆。
  - 用户主动删除。
  - 合规：到期自动清理。
- 检索打分时综合相关性、新近度和重要性（参考斯坦福 Generative Agents 的做法）。

### 12. MemoryBank、MemGPT（Letta）的设计思路是什么？
**答案：**
- MemoryBank：
  - 存储对话记录、每日事件摘要、全局的用户画像。
  - 检索时按相关性召回。
  - 借鉴艾宾浩斯遗忘曲线：记忆强度随时间衰减，被回忆（检索使用）时强化，模拟人类的记忆和遗忘过程。
- MemGPT（现在叫 Letta）：
  - 借鉴操作系统的分层内存管理：上下文窗口相当于主存，外部存储相当于磁盘。
  - 主存分为核心记忆（可编辑的用户和人设信息块）和最近消息；外部存储分为对话历史（召回存储）和归档存储。
  - 模型通过函数调用自己管理记忆：读写核心记忆、搜索和写入归档、在上下文快满时把内容换出到外部。
  - 核心思想是让 Agent 自主管理自己的上下文。

### 13. A-Mem、RMM 等记忆框架有什么创新点？
**答案：**
- A-Mem（Agentic Memory，2025）：
  - 借鉴 Zettelkasten 卡片笔记法，每条记忆是一张"笔记"，包含内容、关键词、标签、上下文描述和 embedding。
  - 新记忆写入时，自动和已有的相关记忆建立链接。
  - 新记忆还会触发对相关旧记忆的描述进行更新（记忆演化），形成不断自我组织的知识网络。
- RMM（Reflective Memory Management，2025）：
  - 前瞻反思：按话题对对话进行多粒度的总结（话语、轮次、会话层级），形成结构化的记忆。
  - 回顾反思：根据模型在生成回答时实际引用了哪些检索到的记忆，在线调整检索器（用强化学习思路优化 rerank），让检索越用越准。
- 共同趋势：记忆不再是静态存储，而是可以组织、演化、根据使用反馈优化。

### 14. 【专家】知识图谱式记忆（如 AriGraph）和向量记忆相比有什么优势？
**答案：**
- AriGraph 的思路：Agent 在环境中探索时，把观察到的信息构建成记忆图。图中同时包含语义记忆（实体和关系三元组）和情景记忆（具体的观察事件，并与相关实体相连）。检索时，先找到相关实体，再沿关系扩展，同时取出关联的情景。
- 相比向量记忆的优势：
  - 能表达实体之间的结构化关系，支持多跳推理（"钥匙在哪个房间，那个房间在哪"）。
  - 事实更新更精确：修改某条关系即可，而不是新旧文本片段同时存在并相互矛盾。
  - 可解释，能看到推理路径。
- 劣势：构建依赖抽取质量，成本高；对模糊的、非结构化的信息（情绪、风格偏好）表达不如向量自然。
- 实践：图谱和向量混合使用，图谱存关键实体和关系，向量存自由文本。

### 15. 记忆检索的触发时机：每轮都检索还是按需检索？
**答案：**
- 每轮都检索：实现简单，不会遗漏；但增加每轮的延迟和成本，无关的记忆还会干扰回答。
- 按需检索：
  - 由模型通过工具决定是否查询记忆。
  - 或者用轻量的判断（意图分类、关键词）决定是否检索。
  - 节省资源，但可能该检索时没有检索。
- 折中：
  - 会话开始时检索一次核心画像，作为常驻上下文。
  - 之后话题变化或检测到需要个性化信息时，再检索相关记忆。
  - 设置相关度阈值，低于阈值的记忆不注入。
- 用 AB 实验评估个性化带来的收益和延迟成本。

### 16. 【高频】多轮对话中，消息序列不合法（如连续两条 user）会导致什么问题？怎么预防？
**答案：**
- 影响：
  - 很多模型接口要求 user 和 assistant 交替出现，工具调用后必须紧跟对应的工具结果；不合法时会直接报错，或者在内部重试、降级，导致延迟增加。
  - 即使接口不报错，模型对上下文的理解也会出错。
- 常见原因：
  - 上一轮生成失败或被打断，只保存了用户消息。
  - 并发写入导致顺序错乱。
  - 截断历史时把成对的工具调用和结果拆开了。
- 预防：
  - 写入时以"轮"为单位保存，回复成功后才落库（或者把失败的轮次标记为无效）。
  - 读取历史时校验并修复：过滤没有回复的 user 消息、合并连续的同角色消息、丢弃不完整的工具调用对。
- 可举例：排查数字人首 token 耗时长的问题时，trace 中发现 op_prompter 报"preRole: user, nowRole: user"的消息序列错误，根因是历史中有 user 输入但没有 assistant 回复；在 ai-agent-core 查询历史时过滤掉这类记录后修复。

### 17. 对话历史存储用什么数据库？表结构怎么设计？
**答案：**
- 选型：
  - MySQL（或 GaiaDB 这类兼容 MySQL 的分布式数据库）：支持按会话查询、事务、运维成熟，最常用；数据量大时按 uid 或 session 分表。
  - 写入量和数据量极大时，可以使用 HBase、宽表存储或 MongoDB。
  - 最近的历史可以用 Redis 缓存。
- 表结构：
  - 主键 id；uid、app_id（Agent）、session_id（thread_id）、message_id。
  - 角色、内容（文本或 JSON，包括工具调用）、状态（成功、失败、被打断）、模型、token 数、创建时间。
  - 索引：(session_id, create_time) 用于按会话拉取历史；(uid, app_id, update_time) 用于"最近使用"类查询。
- 分表：按 uid 取模分表（如 2048 张），保证同一用户的数据在同一张表。
- 生命周期：冷热分离、归档和删除的策略要在设计时就考虑。

### 18. 【高频】海量对话历史（几十 T）怎么做冷热分离和归档？
**答案：**
- 分层：近期数据（如最近 1 年）留在在线库；更早的数据导出到低成本存储（对象存储、AFS/HDFS）；在线库中删除后释放空间。
- 冷备流程：
  1. 按分表和时间范围导出（CSV 或 Parquet），可以用 DTS，也可以自己写备份任务（按分表区间分段、并发、限速）。
  2. 写入归档存储，按表名和日期组织目录。
  3. 抽样校验：文件大小、首尾记录的 id 和时间、行数与源表对比。
  4. 确认无误后，再分批删除在线数据。
  5. 最后释放表空间（删除数据不会自动缩小表文件）。
- 安全：删除前和 DBA 确认；分批执行，控制对线上的影响；保留回滚手段（冷备文件可以恢复）。
- 可举例：3 个 GaiaDB 集群、2 类对话表各 2048 张分表、约 20T 数据。用自研的 Go 备份任务按分表区间导出到 AFS（每日定时批任务、分段并发），抽样校验后通过 DMS 分批删除（厂内对话删到 2024-01-01，第三方删到 2025-01-01），最后做了表空间释放。

### 19. 对话历史的数据安全和合规删除怎么做？
**答案：**
- 访问控制：只有授权的服务和人员可以访问；查询要有审计；敏感字段加密存储；导出和下载要审批。
- 脱敏：日志和分析数据中，手机号、身份证等敏感信息需要脱敏。
- 保留期限：按合规要求设定保留时长，到期自动删除或匿名化（包括备份和归档中的数据）。
- 用户删除权：用户删除会话或注销账号时，删除在线库、缓存、索引（如果对话被用于记忆或检索）中的数据，归档数据也要能定位到并删除。
- 第三方 Agent：对话数据的归属和使用范围要在协议中约定。
- 删除操作要有记录，可以证明已经执行。

### 20. 跨会话（session）的记忆怎么关联？用户未登录时怎么办？
**答案：**
- 已登录：以用户 ID 为主键关联所有会话；长期记忆和"最近使用"记录都挂在用户 ID 下。
- 未登录：
  - 用设备 ID 或匿名 cookie ID 作为临时身份，关联同一设备上的会话。
  - 用户登录后，把匿名身份下的数据合并到用户 ID 下（需要用户知情）。
  - 匿名数据的保留时间短，个性化程度低。
  - 未登录且无法识别的请求，不写入长期记忆。
- 注意：
  - 不同 Agent 之间的记忆是否共享，要按产品设计和授权决定。
  - 未登录用户的数据（如 uid 为 0 的记录）不要大量写入数据库，否则会产生大量无效数据，需要额外的清理成本。
- 可举例：646 init 接口在 q2c 场景下产生大量 uid==0 的数据入库，靠定时脚本清理；治理方案是 uid==0 的 init 请求不入库。

### 21. 【专家】多 Agent 之间怎么共享记忆？共享记忆和私有记忆怎么隔离？
**答案：**
- 分层：
  - 全局共享记忆：用户画像、通用事实，所有 Agent 可读。
  - 团队或任务共享记忆：同一个任务中多个 Agent 共用的工作区，如黑板（blackboard）、共享状态。
  - 私有记忆：每个 Agent 自己的中间推理、专有数据。
- 实现：
  - 记忆按命名空间存储，如 user/、task/{id}/、agent/{id}/。
  - 每个 Agent 有读写权限配置。
  - 共享记忆的写入有来源标记和版本，便于追溯和处理冲突。
- 一致性：并发写同一份共享状态时，使用乐观锁或版本号；或者规定只能由主 Agent 写入，子 Agent 只读。
- 隐私：用户授权某个 Agent 使用的数据，不能被其他 Agent 读取；第三方 Agent 默认不能访问平台的全局记忆。

### 22. 记忆的隐私问题：用户要求"忘记我"时怎么做？
**答案：**
- 提供入口：用户可以查看 Agent 记住了什么，单条删除或全部清空；对话中说"忘掉这件事"也能触发删除。
- 删除范围：长期记忆库（向量库、KV、图数据库）、相关的缓存、摘要中包含的信息、基于这些信息生成的画像。必要时还包括对话历史本身。
- 实现：每条记忆记录来源（哪个会话、哪条消息），便于连带删除；向量库按 ID 删除后要确认已经物理清理。
- 已经用于训练模型的数据很难删除，所以用户数据用于训练前要有明确的授权，或者做好匿名化。
- 合规：符合《个人信息保护法》等法规要求，删除请求要在规定时间内完成并留下记录。

### 23. 摘要式记忆会产生信息失真吗？怎么评估记忆质量？
**答案：**
- 会：
  - 摘要可能遗漏关键细节（数字、条件）。
  - 可能曲解用户的原意。
  - 可能混入模型自己的推测（幻觉）。
  - 多次摘要的摘要，失真会累积。
- 降低失真：
  - 关键信息用结构化字段保存，不依赖自由文本摘要。
  - 保留原文引用，可以回溯。
  - 摘要时要求只记录用户明确说过的内容。
  - 避免对摘要反复做摘要。
- 评估：
  - 准确性：抽样对比记忆和原始对话，判断是否忠实。
  - 有用性：记忆被检索使用后，回答是否更好（AB 实验）。
  - 召回率：构造"需要用到某条历史信息"的问题集（如 LoCoMo、LongMemEval 这类长期记忆评测），测试能否答对。
  - 时效性：过期信息是否被正确更新。

### 24. 【高频】system prompt、历史、检索结果、工具结果怎么分配有限的 token 预算？
**答案：**
- 先确定总预算：模型的上下文上限，减去预留的输出长度，再考虑成本和延迟目标。
- 按优先级分配：
  1. System Prompt 和工具定义：固定且必须保留。尽量精简，放在最前面，便于命中缓存。
  2. 当前用户问题：必须完整保留。
  3. 最近几轮对话：保证对话连贯。
  4. 检索结果和工具结果：按相关性排序后截取，设置上限。
  5. 较早的历史：以摘要形式放入。
  6. 长期记忆：只放与当前问题相关的少量条目。
- 实现：用 tokenizer 精确计算；为每一块设置上限，超出时按规则截断或压缩；各部分的实际占比打到日志中，用于后续调优。
- 动态调整：问答类任务给检索结果更多空间；多轮闲聊给历史更多空间。

### 25. 子 Agent（sub-agent）的上下文为什么要隔离？结果怎么回传给主 Agent？
**答案：**
- 隔离的原因：
  - 子任务（如调研、搜索大量文件）会产生大量中间内容，全部放进主 Agent 的上下文会挤占窗口、稀释注意力、增加成本。
  - 子 Agent 专注于自己的子任务，上下文干净，效果更好。
  - 多个子 Agent 可以并行执行，互不干扰。
- 回传：
  - 子 Agent 完成后，只返回结构化的结论：结果摘要、关键数据、引用来源、是否成功、未解决的问题。
  - 中间过程不回传，可以存到外部，需要时查看。
  - 主 Agent 在派发任务时，要明确告诉子 Agent 需要返回什么格式和内容。
- 代价：子 Agent 看不到主 Agent 的全部上下文，任务描述必须写清楚背景和要求，否则会做偏。

### 26. 长任务 Agent（运行几小时）如何管理上下文？
**答案：**
- 外部化任务状态：计划、todo 列表、已完成步骤和产出存到文件或数据库中，每一步开始时读取最新的状态，而不是依赖完整的对话历史。
- 定期压缩：按阶段做摘要（compaction），保留目标、决策、进度、遇到的问题。
- 子任务隔离：把独立的子任务交给子 Agent，主 Agent 只保留子任务的结论。
- 用复述维持目标：把当前目标和待办事项放在上下文末尾，防止长任务中目标漂移。
- 检查点：状态持久化，支持中断后恢复，不需要重新执行已完成的部分。
- 预算控制：设置总 token 和时间上限，阶段性汇报进度。

### 27. 【专家】如何衡量上下文管理策略对效果和成本的影响？
**答案：**
- 效果指标：任务成功率、答案准确率（评测集）、长对话中引用早期信息的正确率、重复劳动的比例（压缩后又去重新获取已有的信息）、用户满意度。
- 成本和性能指标：每次请求的平均输入 token 数、KV Cache 或 Prompt Cache 命中率、首 token 延迟、单任务总成本。
- 方法：
  - 离线：在同一个评测集上，对比不同策略（滑动窗口、摘要、检索、不同的阈值）。
  - 线上：AB 实验。
  - 记录每次请求上下文各部分的 token 构成，分析哪部分占比最大、收益最小。
- 目标：找到在效果不下降的前提下成本最低的策略，即帕累托最优点。

### 28. 多模态内容（图片、文件）在上下文中怎么表示才省 token？
**答案：**
- 图片：
  - 按任务需要选择分辨率（很多模型的图片 token 数和分辨率相关），不需要细节时降低分辨率。
  - 只在需要看图的那一轮放入原图，之后的轮次替换成文字描述或引用。
  - 多张相似的图片只放关键的几张。
- 文件：
  - 转成文本或 markdown 后，按需检索相关片段，而不是全文放入。
  - 大文件先放摘要和目录，需要时再读取具体部分。
- 视频和音频：转写成文字，按时间戳切片，按需取用。
- 通用：上下文中用引用 ID 代替重复出现的大块内容。

### 29. 对话中的"状态"（如表单填写进度）放在上下文里还是放在外部存储？
**答案：**
- 放在外部存储（以它为准），上下文中只放当前状态的快照：
  - 状态是业务数据，需要准确、可查询、可以被其他服务使用（如线索表单的提交状态决定是否继续召回表单）。
  - 依赖模型从历史中推断状态，容易出错；历史被压缩或截断后，状态就丢了。
- 做法：
  - 用结构化的状态对象（已填写的字段、待填写的字段、步骤）存在会话存储（Redis 或数据库）中。
  - 每轮把最新状态以简洁的格式注入上下文。
  - 模型通过工具或结构化输出更新状态，由程序校验后写入。
- 好处：可以中断后恢复，可以跨端继续，可以做统计。

### 30. 【专家】设计一个支持千万用户的 Agent 记忆服务，你会怎么设计存储、检索和更新？
**答案：**
- 数据模型：每条记忆包含 user_id、namespace（全局、某个 Agent）、类型（事实、偏好、事件）、内容、embedding、重要性、来源（会话、消息）、创建和更新时间、状态（有效、过期、已删除）。
- 存储：
  - 结构化画像字段：KV 存储或 MySQL，按 user_id 分片。
  - 自由文本记忆：向量库，按 user_id 分区（partition key），检索时只在该用户的范围内搜索，量小、速度快。
  - 热点用户的画像放在 Redis 缓存中。
  - 原始对话归档到对象存储。
- 写入（异步）：对话结束后发送消息到队列 → 抽取服务批量调用模型抽取记忆 → 检索已有记忆做去重和冲突判断 → 写入。不阻塞在线对话链路。
- 读取（在线）：会话开始时加载核心画像（走缓存）；每轮按需检索 top-k 相关记忆，设置超时（例如超过 50ms 就跳过），失败不影响主流程。
- 更新和遗忘：按新近度、重要性、访问频率打分；定期合并相似的记忆、归档低价值的记忆；用户删除时同步清理所有存储。
- 容量估算：千万用户 × 人均 N 条记忆 × 每条的大小（文本加向量），得出向量库的规模和分片数。
- 治理：加密、访问审计、按 Agent 授权、合规删除、记忆质量抽样评估。
