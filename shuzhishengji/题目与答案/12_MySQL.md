# 12 MySQL（50 题）（题目与答案）

以下默认基于 MySQL 8.0 InnoDB。

## 索引

### 1. 【高频】InnoDB 为什么用 B+ 树做索引？和 B 树、哈希、红黑树相比有什么优势？
**答案：**
- 磁盘访问的特点：IO 以页（InnoDB 默认 16KB）为单位，随机 IO 的代价很高，所以索引结构要尽量减少磁盘访问的次数。
- B+ 树：
  - 非叶子节点只存键和指针，一个节点能存上千个键，树非常矮胖（三到四层就能存上千万行），一次查询只需要很少的 IO。
  - 所有数据都在叶子节点，叶子节点之间用双向链表相连，范围查询和排序只需要顺序遍历。
  - 每次查询都要走到叶子节点，查询性能稳定。
- 对比：
  - B 树：非叶子节点也存数据，单个节点能放的键更少，树更高；范围查询需要中序遍历，跨越多层。
  - 哈希：等值查询是 O(1)，但不支持范围查询、排序、最左前缀匹配，还有哈希冲突。InnoDB 只有内部自动构建的自适应哈希索引。
  - 红黑树和 AVL 树：每个节点只有两个分支，树太高（百万数据约 20 层），IO 次数过多。

### 2. 【高频】聚簇索引和二级索引的区别是什么？什么是回表？
**答案：**
- 聚簇索引（主键索引）：叶子节点存储的是整行数据，表数据本身就按主键组织成一棵 B+ 树，每张表只有一个。没有定义主键时，InnoDB 会选择第一个非空的唯一索引，再没有就使用隐藏的 row_id。
- 二级索引（普通索引）：叶子节点存储的是索引列的值加主键值。
- 回表：通过二级索引找到主键值后，再到聚簇索引中查出整行数据，多了一次 B+ 树的查找。
- 影响：
  - 回表的次数多时（命中的行很多），随机 IO 多，优化器可能放弃使用索引，改为全表扫描。
  - 主键越长，每个二级索引占用的空间就越大，所以主键应该尽量短。

### 3. 【高频】覆盖索引、索引下推（ICP）是什么？
**答案：**
- 覆盖索引：查询需要的所有列都在某个二级索引中（索引列加主键），可以直接从索引中返回结果，不需要回表。EXPLAIN 的 Extra 列显示 `Using index`。常见的优化手段是为高频查询建立包含所需字段的联合索引。
- 索引下推（Index Condition Pushdown，MySQL 5.6 引入）：
  - 使用联合索引时，对于索引中包含但因为不满足最左前缀而无法用于定位的列，在存储引擎层先用这些列过滤，再回表。
  - 例如索引 (name, age)，查询 `name LIKE '张%' AND age = 20`：没有 ICP 时，所有 name 匹配的记录都要回表，再由 Server 层判断 age；有了 ICP，在索引中就先过滤 age，减少回表次数。
  - EXPLAIN 的 Extra 列显示 `Using index condition`。

### 4. 【高频】联合索引的最左前缀原则是什么？`a=1 and b>2 and c=3` 能用到哪些列？
**答案：**
- 最左前缀：联合索引 (a, b, c) 按 a 排序，a 相同的按 b 排序，再按 c 排序。查询只有从最左列开始、连续地使用索引列，才能用索引定位。
  - 可以使用：a；a、b；a、b、c。
  - 只用 b、c 时，无法用索引定位（可以使用 MySQL 8.0 的 index skip scan 特性，但有使用条件）。
- `a=1 AND b>2 AND c=3`：
  - a 是等值条件，可以使用；b 是范围条件，可以使用。
  - 但在 b 的范围内，c 不是有序的，所以 c 无法用于定位，只能在索引中过滤（借助索引下推），这条查询的 key_len 只覆盖 a、b 两列。
- 改进：如果这种查询很频繁，把索引建成 (a, c, b)，等值条件的列放在前面，范围条件的列放在最后。
- 注意：
  - WHERE 中条件的书写顺序不影响索引的使用，优化器会自动调整。
  - `>=`、`BETWEEN`、`LIKE 'x%'` 在某些情况下后面的列还能继续使用，要以 EXPLAIN 的结果为准。

### 5. 【高频】哪些情况会导致索引失效？
**答案：**
- 对索引列做运算或使用函数：`WHERE DATE(create_time) = ...`、`WHERE id + 1 = 10`。应改写为范围条件，或者使用 MySQL 8.0 的函数索引。
- 隐式类型转换：字符串类型的列用数字比较（`phone = 138...`），相当于对列使用了函数；字符集不同的列做关联也会出现这个问题。
- 模糊查询以 % 开头：`LIKE '%abc'`。
- 联合索引不满足最左前缀。
- OR 两边的条件中有一个没有索引（可以把查询拆成 UNION）。
- 使用 `!=`、`NOT IN`、`IS NOT NULL` 时，过滤性差，优化器往往会选择全表扫描。
- 优化器判断全表扫描的代价更低：要回表的行太多（区分度低的列，如性别），或者统计信息不准确。
- ORDER BY 的排序方向和索引不一致（MySQL 8.0 支持降序索引）。
- 以 EXPLAIN 的结果为准，不要死记规则。

### 6. 主键用自增 ID 还是 UUID？为什么？
**答案：**
- 推荐使用自增 ID，或者趋势递增的分布式 ID（如雪花算法）。
- 自增 ID 的优点：
  - 新数据总是追加到 B+ 树的最右边，页的填充率高，很少发生页分裂。
  - 占用空间小（BIGINT 是 8 字节），二级索引也更小。
  - 插入性能好。
- UUID 的问题：
  - 无序，插入位置随机，导致频繁的页分裂、页面碎片和随机 IO，插入性能下降明显。
  - 占 36 字节的字符串（或 16 字节的二进制），让主键和所有二级索引都变大。
- 自增 ID 的注意点：
  - 对外暴露会泄露业务量，也容易被遍历（对外使用另外一个业务 ID）。
  - 分库分表时需要全局 ID。
  - 高并发插入时，自增锁可能有竞争（innodb_autoinc_lock_mode=2 可以缓解）。
- 必须使用 UUID 时，用有序的 UUID（UUIDv7，或者 MySQL 的 `UUID_TO_BIN(uuid, 1)` 交换时间位），并用二进制存储。

### 7. 【专家】一棵 B+ 树大概能存多少行数据？高度一般是几？
**答案：**
- 估算（页大小 16KB）：
  - 非叶子节点：主键为 BIGINT（8 字节），加上页指针（6 字节），每个条目约 14 字节，一页大约能存 16384 / 14 ≈ 1170 个条目。
  - 叶子节点：假设一行数据约 1KB，一页大约能存 16 行。
  - 高度为 2：1170 × 16 ≈ 1.87 万行。
  - 高度为 3：1170 × 1170 × 16 ≈ 2190 万行。
  - 高度为 4：大约是 250 亿行的量级。
- 结论：千万级数据的表，B+ 树的高度一般是 3 层；根节点和上层节点通常常驻在 Buffer Pool 中，一次查询实际只需要 1 到 2 次磁盘 IO。
- 行越宽，叶子节点能存的行越少，高度就越高；这也是"单表行数达到千万级时考虑拆分"这条经验的来源，但不是硬性规定，还要看行宽、查询模式和硬件。

### 8. 前缀索引怎么用？有什么缺点？
**答案：**
- 用法：对长字符串列只索引前 N 个字符：`ALTER TABLE t ADD INDEX idx_email(email(10))`。减少索引占用的空间，提高单页能存放的键数。
- 选择长度：计算区分度 `COUNT(DISTINCT LEFT(col, N)) / COUNT(*)`，选择区分度接近全列区分度的最小 N。
- 缺点：
  - 无法使用覆盖索引（索引中只有前缀，必须回表获取完整的值来判断）。
  - 不能用于 ORDER BY 和 GROUP BY。
  - 前缀区分度低时（如 URL 都以 https://www 开头），效果很差。可以把字符串反转后再建前缀索引，或者额外存一列哈希值并对它建索引。

### 9. 【高频】`WHERE IN` 里放多少个值比较合适？太多会怎样？
**答案：**
- 没有固定的标准，一般建议控制在几百到一千个以内，具体以压测和 EXPLAIN 的结果为准。
- 值太多的问题：
  - SQL 语句变得很长，解析和网络传输的开销增大，可能超过 max_allowed_packet 的限制。
  - 优化器估算行数时，IN 的值数量超过 eq_range_index_dive_limit（默认 200）后，就从逐个精确估算（index dive）改为用统计信息粗略估算，可能选错执行计划。
  - 一次返回大量数据，占用内存和网络，单次查询耗时变长。
- 做法：
  - 分批查询，每批几百个值，多批可以并发执行（控制并发数）。
  - 对 IN 中的值先去重。
  - 确认 IN 的列上有索引。
- 和 N+1 查询相比：一次 IN 批量查询远好于循环逐条查询。
- 可举例：agent-mount 把"每个挂载项起一个协程查库"改成 WHERE IN 批量查询后，平均耗时从 3.124s 降到 98ms。对于挂载数量特别多的智能体，还需要考虑分批查询。

### 10. 【专家】优化器为什么有时选错索引？怎么处理（analyze、force index）？
**答案：**
- 原因：
  - 优化器基于代价模型做选择，代价依赖统计信息（索引的基数 cardinality、表的行数）。统计信息是通过采样估算的，大量增删数据后可能不准确。
  - 估算回表的代价：认为回表的行数太多，于是选择了全表扫描或其他索引。
  - ORDER BY 加 LIMIT 的场景：优化器倾向于选择排序字段上的索引来避免排序，但实际上需要扫描大量数据才能凑够 LIMIT 的行数。
  - 数据分布不均匀（数据倾斜），统计信息中的平均值无法反映实际情况。
- 处理：
  - 用 `ANALYZE TABLE` 重新收集统计信息；调整采样的页数（innodb_stats_persistent_sample_pages）。
  - 用 `FORCE INDEX` 或 `USE INDEX` 强制使用某个索引（会让代码和索引名耦合，要谨慎使用）。
  - 改写 SQL，引导优化器（如调整 ORDER BY）。
  - 新建更合适的索引，或删除容易误导优化器的索引。
  - MySQL 8.0 可以使用直方图（`ANALYZE TABLE ... UPDATE HISTOGRAM`），为数据分布不均匀的列提供分布信息；也可以用优化器提示（hint）。
- 用 EXPLAIN 和 optimizer_trace 查看优化器的估算和选择过程。

## 事务与锁

### 11. 【高频】事务的 ACID 分别靠什么实现？
**答案：**
- 原子性（Atomicity）：靠 undo log。事务失败或回滚时，根据 undo log 撤销已经做出的修改。
- 一致性（Consistency）：是事务的最终目标，由其他三个特性加上数据库约束（主键、外键、唯一键）和应用逻辑共同保证。
- 隔离性（Isolation）：靠锁（行锁、间隙锁、临键锁）和 MVCC（ReadView 加 undo 版本链）。
- 持久性（Durability）：靠 redo log。WAL（先写日志）机制，事务提交时 redo log 先落盘，即使宕机也能通过 redo log 恢复已提交的数据；配合 doublewrite buffer 防止页写入一半造成的损坏。

### 12. 【高频】四种隔离级别分别解决了什么问题？MySQL 默认是哪个？
**答案：**
- 读未提交（Read Uncommitted）：可以读到其他事务还没有提交的修改，会出现脏读。
- 读已提交（Read Committed，RC）：只能读到已经提交的数据，解决了脏读；但同一个事务中两次读取的结果可能不同（不可重复读）。Oracle、PostgreSQL 默认使用 RC。
- 可重复读（Repeatable Read，RR）：同一个事务中多次读取的结果一致，解决了不可重复读。MySQL InnoDB 默认是 RR，并通过 MVCC 加临键锁在很大程度上避免了幻读。
- 串行化（Serializable）：事务完全串行执行，读操作也要加锁，解决了所有问题，但并发性能最差。
- 实践：很多互联网公司把 MySQL 改为 RC 级别，因为 RC 的间隙锁更少，死锁更少，并发性能更好；这时 binlog 要使用 row 格式。

### 13. 【高频】MVCC 的原理是什么？ReadView、undo log 怎么配合？
**答案：**
- 目的：读写互不阻塞。普通的 SELECT（快照读）不加锁，读取数据的某个历史版本。
- 实现：
  - 每行数据有隐藏列：trx_id（最后修改这一行的事务 ID）、roll_pointer（指向 undo log 中的上一个版本）。多次修改形成一条版本链。
  - ReadView：事务做快照读时生成的"可见性视图"，记录了当时的活跃事务列表（m_ids）、最小的活跃事务 ID（min_trx_id）、下一个将要分配的事务 ID（max_trx_id）、当前事务自己的 ID（creator_trx_id）。
- 可见性判断（沿版本链从最新的版本往前找）：
  - 版本的 trx_id 等于自己的事务 ID：可见。
  - 小于 min_trx_id：说明生成 ReadView 时已经提交，可见。
  - 大于等于 max_trx_id：说明是生成 ReadView 之后才开始的事务，不可见。
  - 在两者之间：如果在 m_ids 中（生成 ReadView 时还没提交），不可见；否则可见。
  - 不可见就沿着 roll_pointer 找上一个版本继续判断。
- RC 和 RR 的区别：RC 每次 SELECT 都生成新的 ReadView；RR 只在事务中第一次 SELECT 时生成，之后一直复用，所以能保证可重复读。
- undo log 的版本在没有任何 ReadView 还需要它时，由 purge 线程清理；长事务会让 undo log 无法清理而不断膨胀。

### 14. 【高频】RR 级别下怎么解决幻读？快照读和当前读有什么区别？
**答案：**
- 快照读：普通的 SELECT，读取 MVCC 的历史版本，不加锁。在 RR 级别下，整个事务使用同一个 ReadView，其他事务新插入的行对它不可见，所以快照读不会出现幻读。
- 当前读：`SELECT ... FOR UPDATE`、`SELECT ... LOCK IN SHARE MODE`（8.0 中是 FOR SHARE）、UPDATE、DELETE、INSERT，读取的是最新的已提交版本，并且要加锁。
- 当前读用临键锁（Next-Key Lock，即行锁加间隙锁）锁住扫描到的记录和记录之间的间隙，阻止其他事务在这个范围内插入新的行，从而避免幻读。
- 仍然可能出现幻读的情况：
  - 事务先做快照读，期间其他事务插入了一行并提交，本事务再对这一行做当前读或更新（如 UPDATE 所有行），然后再快照读，就能看到这行新数据（因为这行的 trx_id 变成了自己的）。
  - 所以说 RR 级别在很大程度上避免了幻读，但并不是完全杜绝。

### 15. 【高频】行锁、间隙锁、临键锁（Next-Key Lock）分别是什么？
**答案：**
- 行锁（Record Lock）：锁住索引上的某一条记录。InnoDB 的行锁加在索引上；如果查询没有用到索引，会扫描并锁住所有扫描到的记录，效果接近锁表。
- 间隙锁（Gap Lock）：锁住两条索引记录之间的间隙（开区间），防止其他事务往这个间隙中插入数据。间隙锁之间互不冲突（多个事务可以同时持有同一个间隙的间隙锁），只和插入意向锁冲突。只在 RR 级别下使用。
- 临键锁（Next-Key Lock）：行锁加上它前面的间隙锁，是一个左开右闭的区间，是 RR 级别下加锁的基本单位。
- 优化规则：
  - 唯一索引的等值查询，命中记录时，临键锁退化为行锁。
  - 等值查询没有命中记录时，退化为间隙锁。
- 插入意向锁：插入数据前在间隙上加的锁，多个插入意向锁之间不冲突（插入的位置不同就可以并发插入），但会和间隙锁冲突。

### 16. 【专家】一条 `UPDATE ... WHERE` 语句会加哪些锁？没有索引时会怎样？
**答案：**
- 先加表级的意向排他锁（IX），再在扫描到的索引记录上加行级的排他锁。具体加什么锁，取决于隔离级别、WHERE 条件使用的索引类型以及是否命中记录（以 RR 级别为例）：
  - 主键或唯一索引的等值条件，并且命中记录：只对这一行加行锁（X）。
  - 唯一索引的等值条件，没有命中记录：在对应的间隙上加间隙锁。
  - 普通二级索引的等值条件：在二级索引上对命中的记录加临键锁，并且在下一条不满足条件的记录前的间隙上加间隙锁；同时对聚簇索引中对应的行加行锁。
  - 范围条件：对扫描到的范围加临键锁。
- 没有索引（全表扫描）时：
  - RR 级别下，会对扫描到的每一条记录都加临键锁，相当于锁住了全表，其他事务的更新和插入都会被阻塞。
  - RC 级别下，扫描过程中会对不满足条件的记录及时释放锁（semi-consistent read），影响较小，但扫描期间仍然会加锁。
- 所以 UPDATE 和 DELETE 的 WHERE 条件必须使用索引；执行前用 EXPLAIN 确认；大批量更新要分批执行。
- 排查锁的情况：查询 `performance_schema.data_locks`。

### 17. 【高频】死锁是怎么产生的？怎么排查和避免？
**答案：**
- 产生原因：两个或多个事务互相持有对方需要的锁，形成循环等待。常见的情况：
  - 两个事务以相反的顺序更新相同的两行数据。
  - 间隙锁导致的死锁：两个事务都持有同一个间隙的间隙锁（间隙锁之间互不冲突），然后都要在这个间隙中插入数据（插入意向锁和对方的间隙锁冲突）。
  - 唯一键冲突时会加共享锁，并发插入相同的值也可能导致死锁。
- InnoDB 的处理：开启了死锁检测（innodb_deadlock_detect），发现死锁后回滚代价较小的事务，被回滚的事务收到 1213 错误；没有检测到的锁等待在 innodb_lock_wait_timeout 后超时。
- 排查：
  - `SHOW ENGINE INNODB STATUS` 查看最近一次死锁的详情（两个事务各自持有和等待的锁、对应的 SQL）。
  - 开启 innodb_print_all_deadlocks，把所有死锁记录到错误日志。
  - 结合 data_locks 表和业务代码分析。
- 避免：
  - 不同的事务以相同的顺序访问资源（如按主键排序后再更新）。
  - 缩短事务，减少锁的持有时间；大事务拆分。
  - WHERE 条件使用合适的索引，减少锁定的范围。
  - 考虑使用 RC 隔离级别，减少间隙锁。
  - 业务层捕获死锁错误后重试。

### 18. 意向锁的作用是什么？
**答案：**
- 意向锁是表级锁，分为意向共享锁（IS）和意向排他锁（IX）。事务在给某一行加行锁之前，要先给这张表加上对应的意向锁。
- 作用：让表级锁和行级锁能够快速判断是否冲突。
  - 如果没有意向锁，一个事务想对整张表加表锁（如 `LOCK TABLES ... WRITE`，或者某些 DDL）时，必须逐行检查是否有行被锁住，效率极低。
  - 有了意向锁，只需要检查表上是否存在意向锁就能判断是否冲突。
- 兼容性：意向锁之间互相兼容（IS 和 IX 可以共存，多个事务可以同时锁定不同的行）；意向锁只和表级的共享锁、排他锁冲突，例如 IX 和表级的 S 锁冲突。
- 意向锁由 InnoDB 自动添加，不需要用户手动操作。

### 19. 【高频】乐观锁和悲观锁怎么实现？各适合什么场景？
**答案：**
- 悲观锁：认为冲突经常发生，操作数据之前先加锁。
  - 实现：`SELECT ... FOR UPDATE` 锁住行，在同一个事务中处理完再提交。
  - 适合：写冲突频繁、冲突的代价很高的场景（如热门数据的扣减、余额变更）。
  - 缺点：锁会阻塞其他事务，并发度低，可能出现死锁，事务必须保持简短。
- 乐观锁：认为冲突很少发生，不加锁，在更新时检查数据是否被别人修改过。
  - 实现：用版本号字段，`UPDATE t SET ..., version = version + 1 WHERE id = ? AND version = ?`，影响行数为 0 说明有冲突，需要重试或报错；或者用条件更新，如 `UPDATE stock SET num = num - 1 WHERE id = ? AND num > 0`。
  - 适合：读多写少、冲突概率低的场景。
  - 缺点：冲突频繁时大量重试，浪费资源。
- 状态机的条件更新（`WHERE status = 待处理`）本质上也是乐观锁，常用于防止重复处理任务（如 Worker 抢任务）。

### 20. 【专家】并发插入导致主键冲突或唯一键冲突，怎么处理？`INSERT ... ON DUPLICATE KEY UPDATE` 有什么坑？
**答案：**
- 常见原因：
  - 并发的"先查询是否存在，不存在再插入"，存在检查和插入之间的竞态（check-then-act）。
  - 应用层自己生成的主键（如由时间戳、随机数拼接）发生碰撞。
  - 重复的请求（没有做幂等）。
- 处理方式：
  - 依靠唯一索引兜底：直接插入，捕获 1062（重复键）错误后，按业务需要选择忽略、查询已有记录返回，或者更新。
  - 使用 `INSERT ... ON DUPLICATE KEY UPDATE`（存在就更新）、`INSERT IGNORE`（存在就忽略）。
  - 并发很高时，用分布式锁或队列把对同一个 key 的写入串行化。
  - 主键使用可靠的分布式 ID，不要用时间戳之类的值拼接。
- ON DUPLICATE KEY UPDATE 的坑：
  - 加锁范围更大：冲突时会对相关记录加临键锁，在高并发下容易产生死锁。
  - 表上有多个唯一索引时，可能和非预期的那条记录冲突，结果难以预测。
  - 自增主键：即使最终执行的是更新，自增值也会被消耗，导致 ID 不连续、增长过快。
  - 影响行数的含义：插入返回 1，更新返回 2，值没有变化返回 0，代码判断时要注意。
  - binlog 为 statement 格式时，主从数据可能不一致（要使用 row 格式）。
- 可举例：平台上部分质检任务无法显示，原因是并发插入时数据库主键冲突。

## 日志与存储

### 21. 【高频】redo log、undo log、binlog 分别是什么？有什么区别？
**答案：**
- redo log（InnoDB 引擎层）：
  - 物理日志，记录"某个数据页的某个位置做了什么修改"。
  - 用于崩溃恢复，保证持久性。
  - 采用 WAL（先写日志）：修改先写入 redo log，数据页的刷盘延后进行。
  - 文件大小固定，循环写入；已经刷盘的数据页对应的日志空间可以被覆盖。
- undo log（InnoDB 引擎层）：
  - 逻辑日志，记录修改前的旧值（插入对应删除，更新记录旧值）。
  - 用于事务回滚（原子性）和 MVCC（提供历史版本）。
- binlog（Server 层，所有存储引擎都有）：
  - 逻辑日志，记录 SQL 语句或行的变更。
  - 追加写入，写满一个文件后切换到新文件，不会覆盖。
  - 用于主从复制、按时间点恢复数据、数据订阅（如 Canal）。
- 区别：redo log 用于崩溃恢复，不能用于复制和按时间点恢复；binlog 用于复制和恢复，但不能保证崩溃安全。两者通过两阶段提交保持一致。

### 22. 【高频】两阶段提交是什么？为什么需要？
**答案：**
- 问题：redo log 和 binlog 是两个独立的日志，如果一个写成功、另一个没写成功时发生宕机，就会出现主库（按 redo log 恢复）和从库或备份（按 binlog 恢复）的数据不一致。
- 流程：
  1. prepare 阶段：写 redo log，并把状态标记为 prepare。
  2. 写 binlog。
  3. commit 阶段：把 redo log 的状态改为 commit。
- 崩溃恢复时的判断：
  - redo log 是 commit 状态：直接提交。
  - redo log 是 prepare 状态：检查对应的 binlog 是否完整（通过 XID 关联）。binlog 完整就提交，不完整就回滚。
  - 这样就保证了 redo log 和 binlog 的一致。
- 性能：组提交（group commit）把多个事务的刷盘操作合并，减少 fsync 的次数。
- 配置：sync_binlog=1 加 innodb_flush_log_at_trx_commit=1（俗称"双 1"）可以保证不丢数据。

### 23. binlog 的三种格式（statement、row、mixed）有什么区别？
**答案：**
- statement：记录原始的 SQL 语句。日志量小；但遇到不确定的函数（NOW()、UUID()、带 LIMIT 但没有 ORDER BY 的 UPDATE）时，在从库上执行的结果可能不同，造成主从不一致。
- row：记录每一行修改前后的值。准确可靠，主从一致；可以用来做数据订阅（Canal）和闪回恢复。缺点是日志量大，例如一条 UPDATE 影响了一百万行，就会产生一百万条行记录。
- mixed：默认使用 statement，遇到可能不安全的语句时自动切换为 row。
- 推荐使用 row（MySQL 5.7.7 之后是默认值），可以配合 binlog_row_image=MINIMAL 减少日志量。
- 大批量修改数据时要注意 binlog 的体积和主从延迟，应该分批执行。

### 24. 【专家】redo log 刷盘策略（innodb_flush_log_at_trx_commit）怎么配？
**答案：**
- 取值：
  - 1（默认，最安全）：每次事务提交时，把 redo log 写入操作系统并调用 fsync 刷到磁盘。宕机或断电都不会丢失已提交的事务；但每次提交都要 fsync，性能最低。
  - 2：每次提交时写入操作系统的页缓存（不 fsync），后台线程每秒执行一次 fsync。MySQL 进程崩溃不会丢数据（数据已经在操作系统缓存中）；但操作系统崩溃或断电时，可能丢失约 1 秒的数据。
  - 0：每秒写入并刷盘一次，提交时不做操作。MySQL 进程崩溃也可能丢失约 1 秒的数据。性能最高、最不安全。
- 配合 sync_binlog：等于 1 时每次提交都刷盘 binlog；等于 N 时每 N 次提交刷盘一次。
- 选择：
  - 核心业务（交易、资金）：使用"双 1"配置。
  - 可以容忍少量丢失的场景（日志类数据、可以重建的数据、批量导入）：可以设置为 2 或 0，提高写入性能。
  - 组提交和 SSD 可以减小"双 1"对性能的影响。

### 25. Buffer Pool 的作用是什么？LRU 怎么改进的？
**答案：**
- 作用：InnoDB 在内存中缓存数据页和索引页，读写都先操作 Buffer Pool，减少磁盘 IO。被修改过的页（脏页）由后台线程异步刷回磁盘。一般把机器内存的 50% 到 80% 分配给 Buffer Pool。
- 普通 LRU 的问题：
  - 预读的页可能根本不会被访问，却挤掉了热数据。
  - 全表扫描或大范围查询，一次性读入大量只会访问一次的页，把整个热数据区冲刷掉（缓存污染）。
- InnoDB 的改进：
  - 把 LRU 链表分为 young 区（热数据，约占 5/8）和 old 区（冷数据，约占 3/8）。
  - 新读入的页先放到 old 区的头部，而不是整个链表的头部。
  - 在 old 区中停留超过 innodb_old_blocks_time（默认 1 秒）之后再次被访问，才移到 young 区。全表扫描读入的页在短时间内被连续访问，不会进入 young 区，也就不会污染热数据。
  - young 区前四分之一的页被访问时不移动位置，减少链表操作的开销。
- 相关的结构：free 链表（空闲页）、flush 链表（待刷盘的脏页）。

### 26. Change Buffer 是什么？
**答案：**
- 作用：更新非唯一二级索引时，如果目标页不在 Buffer Pool 中，不立即从磁盘读入这个页，而是把修改操作记录在 Change Buffer 中；等以后这个页被读入内存时，再合并（merge）这些修改。也会在后台定期合并。
- 好处：减少写操作带来的随机读 IO，提升写多读少场景下的性能。
- 限制：
  - 只适用于非唯一的二级索引。唯一索引在更新时必须读取页来判断是否冲突，既然已经读入了页，就没有必要缓冲。
  - 写入后马上就读取的场景收益很小（马上就要合并）。
- Change Buffer 本身也会持久化到系统表空间，并受 redo log 保护，宕机不会丢失。
- 配置：innodb_change_buffer_max_size（占 Buffer Pool 的比例）。

### 27. 【高频】为什么删除大量数据后表文件没有变小？表空间怎么回收？
**答案：**
- 原因：DELETE 只是把记录标记为删除，被删除的空间留在数据页中，以后插入数据时可以复用，但不会还给操作系统。删除整页的数据后，这个页也只是被标记为可以复用。所以表文件（.ibd 文件）的大小不会变小，还会产生大量的空洞（碎片）。
- 回收方法：
  - 重建表：`ALTER TABLE t ENGINE=InnoDB`，或者 `OPTIMIZE TABLE t`（InnoDB 中实际执行的就是重建表加更新统计信息）。会新建一个临时表，把数据重新紧凑地写入，然后替换原表。
  - 使用 gh-ost 或 pt-online-schema-change 在线重建，影响更可控。
  - 整张表都不需要时：TRUNCATE 或 DROP（会直接释放文件，前提是开启了独立表空间 innodb_file_per_table）。
  - 分区表：直接 DROP PARTITION。
- 注意：
  - 重建时需要额外的磁盘空间（约等于表的大小），要提前确认空间足够。
  - 重建会消耗大量 IO，导致主从延迟，要在低峰期执行。
- 可举例：智能体对话数据分批删除后，在 20260507 单独做了表空间释放。

### 28. 【专家】OPTIMIZE TABLE、ALTER TABLE ENGINE=InnoDB 回收空间的原理是什么？对线上有什么影响？
**答案：**
- 原理（MySQL 5.6 之后支持 Online DDL）：
  1. 新建一个临时的表空间文件。
  2. 按主键顺序扫描原表，把数据紧凑地写入新表（重建聚簇索引和所有二级索引）。
  3. 拷贝期间，其他事务对原表的增删改记录在 row log 中。
  4. 拷贝完成后回放 row log 中的增量修改。
  5. 用新文件替换原表文件。
  - 整个过程大部分时间允许读写（ALGORITHM=INPLACE，LOCK=NONE），只在开始和结束时短暂持有元数据锁（MDL）。
- 对线上的影响：
  - IO 和 CPU 的消耗很大，会影响其他查询的性能。
  - 需要额外的、约等于原表大小的磁盘空间。
  - 执行时间和表的大小成正比，大表可能要几个小时。
  - 主从延迟：主库执行完后，DDL 才通过 binlog 发送到从库，从库再执行同样长的时间，期间从库的复制会被阻塞。
  - MDL 的风险：开始或结束阶段需要获取 MDL 写锁，如果此时有长事务或慢查询持有 MDL 读锁，DDL 就会等待；而后续所有对这张表的查询都会排在 DDL 后面等待，可能造成整张表不可用。
- 做法：
  - 在低峰期执行；执行前确认没有长事务；设置 lock_wait_timeout，拿不到锁就快速放弃。
  - 对大表使用 gh-ost（可以限速、暂停）。
  - 通过 DBA 平台（DMS）执行。

## 主从与高可用

### 29. 【高频】主从复制的原理是什么？
**答案：**
- 三个线程：
  1. 主库的 dump 线程：从库连接后，主库把 binlog 的内容发送给从库。
  2. 从库的 IO 线程：接收 binlog，写入本地的中继日志（relay log）。
  3. 从库的 SQL 线程（或多个 worker 线程）：读取中继日志并回放，把修改应用到从库的数据上。
- 复制模式：
  - 异步复制（默认）：主库写完 binlog 就返回成功，不等待从库。性能最好，但主库宕机时可能丢失还没传到从库的数据。
  - 半同步复制：至少一个从库确认收到 binlog 后，主库才返回成功。
  - 组复制（MGR）：基于 Paxos 协议达成多数派一致。
- GTID：每个事务有全局唯一的 ID，切换主库和搭建从库时，不需要再手动寻找 binlog 的文件名和位置，更方便可靠。
- 并行复制：从库按组提交或按 writeset 判断哪些事务可以并行回放，降低复制延迟。

### 30. 【高频】主从延迟的原因有哪些？怎么解决？
**答案：**
- 原因：
  - 大事务：一次删除或更新大量数据，从库回放需要同样长的时间。
  - 从库回放的并发度不够（主库并发写入，从库单线程或并行度不足）。
  - 从库的配置比主库差，或者从库还承担了大量的读查询，资源被抢占。
  - 主库上的 DDL 操作（大表执行 DDL 时，从库要执行同样长的时间）。
  - 没有主键的表：row 格式的 binlog 在从库回放时，每一行都要全表扫描来定位。
  - 网络延迟。
- 解决：
  - 拆分大事务，分批执行（如分批删除数据）。
  - 开启并行复制（slave_parallel_workers 加 writeset）。
  - 从库的配置不低于主库。
  - 每张表都要有主键。
  - DDL 在低峰期执行，或者使用 gh-ost。
  - 业务层：对一致性要求高的读请求走主库。
  - 监控延迟（Seconds_Behind_Master，或者更准确的心跳表），延迟过大的从库摘除出读流量。

### 31. 半同步复制、组复制（MGR）是什么？
**答案：**
- 半同步复制：
  - 主库提交事务时，至少等待一个从库确认已经把 binlog 写入中继日志，才返回成功。
  - MySQL 5.7 的 after_sync（无损半同步）模式：在提交到存储引擎之前等待从库的确认，避免主库宕机时客户端已经看到了提交的数据，但从库上没有。
  - 等待超时（rpl_semi_sync_master_timeout）后，退化为异步复制，以保证可用性，但这时就存在丢数据的风险。
  - 代价是多了一次网络往返的延迟。
- 组复制（MGR）：
  - 多个节点组成一个复制组，基于 Paxos 的变种协议，事务要在多数节点上达成一致后才能提交。
  - 内置冲突检测、自动故障检测和成员管理。
  - 支持单主模式（推荐）和多主模式。
  - 配合 MySQL Router 可以实现自动故障切换（InnoDB Cluster）。
  - 写入延迟较高，对网络质量要求高，对大事务不友好。
- 选择：普通业务使用"半同步加高可用切换组件"；对数据一致性要求很高、希望自动切换的，使用 MGR 或云数据库的高可用方案。

### 32. 【专家】主库宕机后，怎么切换并保证数据不丢？
**答案：**
- 故障检测：由高可用组件（MHA、Orchestrator、云数据库的高可用服务）检测到主库不可用，需要多点探测，防止误判。
- 选出新主库：选择数据最新的从库（比较 GTID 的执行进度）；如果其他从库有比它更多的中继日志，先把差异部分补齐。
- 补齐数据：如果原主库的机器还能访问（只是 MySQL 进程挂了），可以把它的 binlog 中还没有同步到从库的部分补到新主库上。
- 切换：
  - 把新主库设为可写（关闭 read_only），其他从库改为从新主库复制（GTID 模式下自动定位位置）。
  - 修改流量入口（VIP、DNS、代理的配置）。
  - 防止旧主库恢复后继续写入导致脑裂：通过 STONITH（强制隔离旧节点）或者设置 read_only 来隔离它。
- 保证不丢数据：
  - 使用无损半同步复制（after_sync）：已经提交的事务至少在一个从库上存在。
  - 切换时优先选择收到了全部 binlog 的那个从库。
  - 异步复制下无法保证不丢数据，只能尽量从旧主库补齐 binlog。
- 演练：定期进行故障切换演练，确认 RTO 和 RPO 符合预期。

## SQL 优化

### 33. 【高频】慢 SQL 怎么排查？EXPLAIN 的关键字段（type、key、rows、Extra）分别看什么？
**答案：**
- 发现慢 SQL：
  - 开启慢查询日志（long_query_time），用 pt-query-digest 汇总分析。
  - 使用 DBA 平台的慢 SQL 分析功能。
  - 查看 performance_schema 中的语句统计。
  - 结合 APM 和 trace 定位到具体的接口。
- EXPLAIN 的关键字段：
  - type（访问类型，从好到差）：system、const（主键或唯一索引的等值查询）、eq_ref、ref（普通索引的等值查询）、range（范围扫描）、index（全索引扫描）、ALL（全表扫描）。一般至少要达到 range，最好是 ref 及以上。
  - key：实际使用的索引；possible_keys 是可能使用的索引。key 为 NULL 表示没有使用索引。
  - key_len：使用的索引长度，可以判断联合索引用到了哪几列。
  - rows：估算需要扫描的行数（越小越好）；filtered 是按条件过滤后剩余行的比例。
  - Extra：
    - `Using index`：使用了覆盖索引，好。
    - `Using where`：在 Server 层做过滤。
    - `Using index condition`：使用了索引下推。
    - `Using filesort`：需要额外排序，要注意。
    - `Using temporary`：使用了临时表，要注意。
- 进一步分析：`EXPLAIN ANALYZE`（MySQL 8.0.18 及以上）会实际执行查询，给出每一步的真实耗时和行数；optimizer_trace 可以查看优化器的选择过程。

### 34. 【高频】深分页（`LIMIT 1000000, 10`）为什么慢？怎么优化？
**答案：**
- 原因：MySQL 要先扫描并丢弃前 100 万行，才能取出后面的 10 行。如果没有覆盖索引，前面这 100 万行每一行都要回表，代价极大。
- 优化方法：
  - 游标分页（推荐）：记住上一页最后一条记录的排序值，`WHERE id > 上一页最后的 id ORDER BY id LIMIT 10`，每次都直接从索引中定位，耗时和翻页的深度无关。缺点是不能直接跳到任意一页，只能"上一页、下一页"。适合信息流、"加载更多"这类场景。
  - 延迟关联：先在覆盖索引上查出这一页的主键，`SELECT id FROM t WHERE ... ORDER BY ... LIMIT 1000000, 10`，再用这些 ID 关联原表取出完整的行，减少回表次数。
  - 业务限制：限制最大页码（如只允许查看前 100 页），超过的部分引导用户使用搜索。
  - 大数据量的检索交给 ES（ES 中也要用 search_after）。
- 可举例："最近使用"接口使用 nextCursor 游标分页。

### 35. COUNT(*)、COUNT(1)、COUNT(字段) 有什么区别？大表计数怎么做？
**答案：**
- 区别：
  - COUNT(*) 和 COUNT(1)：统计行数，包括值为 NULL 的行。InnoDB 对两者的处理方式相同，性能没有差别，优化器会选择最小的二级索引来扫描。
  - COUNT(字段)：只统计这个字段不为 NULL 的行，需要读取字段值并判断，如果字段可以为 NULL，就没法优化。
  - 推荐使用 COUNT(*)。
- InnoDB 没有保存总行数：因为有 MVCC，不同事务看到的行数可能不同，所以每次都要扫描（MyISAM 保存了总行数）。
- 大表计数的方法：
  - 维护一张计数表（在同一个事务中更新，或者异步更新），或者用 Redis 计数（需要处理一致性问题）。
  - 只需要大致数量时，使用 EXPLAIN 的估算值，或者 information_schema 中的 table_rows（误差较大）。
  - 按条件计数时，确保条件列有索引；定时统计后缓存结果。
  - 列表接口不必每次都返回精确的总数（改为"是否还有更多"，配合游标分页）。

### 36. JOIN 的执行算法有哪些？小表驱动大表是什么意思？
**答案：**
- 算法：
  - Index Nested-Loop Join（NLJ）：遍历驱动表的每一行，用关联字段到被驱动表的索引上查找。被驱动表的关联字段有索引时使用，效率高。
  - Block Nested-Loop Join（BNL，8.0.20 之前）：被驱动表没有可用的索引时，把驱动表的数据分块读入 join buffer，再全表扫描被驱动表，逐行和 buffer 中的数据比对，代价高。
  - Hash Join（8.0.18 开始，8.0.20 之后取代了 BNL）：用驱动表（较小的那张表）构建哈希表，再扫描另一张表进行探测。适合没有索引的等值关联，效果比 BNL 好得多。
- 小表驱动大表：
  - 这里的"小表"指的是经过 WHERE 条件过滤后参与关联的数据量较小的那张表，而不是物理上的表大小。
  - 在 NLJ 中，驱动表的每一行都要到被驱动表的索引上查找一次，代价约为"驱动表行数 × 被驱动表索引的查找代价"。驱动表越小，查找次数越少。
  - 优化器一般会自动选择驱动表，必要时可以用 STRAIGHT_JOIN 指定。
- 实践：被驱动表的关联字段一定要有索引；关联字段的类型和字符集要一致（否则发生隐式转换，索引失效）；高并发的业务中，尽量避免多表 JOIN，改为应用层分两次查询加批量 IN 查询。

### 37. 【高频】ORDER BY 和 GROUP BY 怎么优化？filesort 是什么？
**答案：**
- filesort：无法利用索引的顺序时，MySQL 要对结果额外排序。数据量小时在内存中排序（sort_buffer_size），超过时使用磁盘上的临时文件做归并排序。EXPLAIN 的 Extra 列显示 `Using filesort`。
- ORDER BY 的优化：
  - 让排序利用索引的有序性：WHERE 中的等值条件列加上排序列组成联合索引，如 `WHERE uid = ? ORDER BY create_time DESC` 对应索引 (uid, create_time)。
  - 多个排序字段的方向要和索引一致（MySQL 8.0 支持降序索引）。
  - 尽量使用覆盖索引，避免回表。
  - 加 LIMIT，减少排序的数据量（优化器会对 LIMIT 使用堆排序）。
- GROUP BY 的优化：
  - 对分组字段建立索引，利用索引的有序性分组，避免创建临时表（`Using temporary`）。
  - MySQL 8.0 中 GROUP BY 不再隐式排序，不需要再写 ORDER BY NULL。
  - 能在 WHERE 中过滤的条件，不要放到 HAVING 中。
- 调参：适当调大 sort_buffer_size（不要设得过大，它是按连接分配的）。

### 38. 子查询和 JOIN 怎么选？
**答案：**
- 早期版本（MySQL 5.5 及以前）：`IN (子查询)` 常被改写为相关子查询，对外层的每一行都执行一次子查询，性能很差，所以习惯上改写为 JOIN。
- MySQL 5.6 及以后：优化器支持对子查询做半连接（semi-join）优化、物化等，很多 IN 和 EXISTS 子查询会被自动转换为 JOIN 执行，性能差距已经不大。
- 选择原则：
  - 以 EXPLAIN 的结果为准，看最终的执行计划。
  - 语义上是"判断是否存在"时，用 EXISTS 或 IN 子查询更清晰；需要同时取出两张表的字段时，用 JOIN。
  - 相关子查询在外层行数很多时仍然可能很慢，要特别注意。
  - 复杂的子查询可以拆成多次简单的查询，在应用层处理（同时也便于做缓存和分库分表）。

### 39. 【高频】N+1 查询问题是什么？怎么避免？
**答案：**
- 定义：先执行 1 次查询得到 N 条记录，再对每条记录各执行 1 次查询去获取关联的数据，共执行 N+1 次查询。数据量大时，大量的网络往返和查询开销会让接口变得非常慢，并且对数据库造成很大压力。常见于 ORM 的懒加载，或者在循环中调用 DAO。
- 避免方法：
  - 批量查询：先收集所有关联的 ID，用 `WHERE id IN (...)` 一次查出，在内存中用 map 组装。
  - JOIN 一次查出（注意 JOIN 的成本）。
  - ORM 的预加载功能（如 GORM 的 Preload，它内部也是使用 IN 查询）。
  - 对关联数据做缓存。
  - 冗余字段：把常用的关联字段直接存到主表中。
- 并发查询不能替代批量查询：每个关联项开一个协程并发查询，虽然看起来变快了，但查询次数和连接占用并没有减少，还会带来协程和连接池的压力。
- 可举例：
  - agent-mount 把"每个挂载项起一个协程查库"改成 WHERE IN 批量查询，平均耗时从 3.124s 降到 98ms。
  - 删除衔接视频需求的列表接口中，对 qc_task 和 customer 使用批量 IN 查询，再在内存中聚合，避免了 JOIN 和 N+1 查询。

### 40. JSON 字段适合存什么？JSON 字段上的查询怎么优化？
**答案：**
- 适合存放：
  - 结构不固定、经常扩展的属性（扩展字段、配置项、第三方返回的原始数据）。
  - 整体读写、很少按其中某个字段查询的数据（如 ui_data、打点日志的扩展信息、机器质检的 meta_info）。
- 不适合：经常需要过滤、排序、关联、聚合的字段（应该拆成普通的列）；需要约束和强类型的核心业务数据。
- 查询：使用 `col->'$.key'` 或 `col->>'$.key'`（取出不带引号的值）、JSON_EXTRACT、JSON_CONTAINS 等函数。
- 优化：
  - 对经常查询的 JSON 路径建立虚拟生成列（`GENERATED ALWAYS AS (col->>'$.key')`），再在这个列上建索引。
  - MySQL 8.0.13 及以上可以直接建立函数索引；8.0.17 及以上支持对 JSON 数组建立多值索引（MEMBER OF）。
  - 更新时使用 JSON_SET 局部修改（8.0 支持部分更新，减少日志量）。
  - 控制 JSON 的大小，大的 JSON 会影响行的存储和查询性能。
- 可举例：PaaS 公共资源池建设中，用 `package_result ->> '$.package_url'` 从 JSON 字段中查出形象包的地址。

## 运维与大表

### 41. 【高频】大表加字段、加索引怎么做才不锁表？Online DDL 的原理是什么？
**答案：**
- MySQL 5.6 之后的 Online DDL：大部分 DDL 在执行期间允许并发的读写。
  - 原理：先短暂获取 MDL 写锁做准备，然后降级为 MDL 读锁，允许 DML 操作；执行期间的 DML 变更记录到 row log 中；数据重建或索引构建完成后，回放 row log；最后再短暂获取 MDL 写锁，完成切换。
- 语法：`ALTER TABLE t ADD COLUMN c INT, ALGORITHM=INPLACE, LOCK=NONE;` 明确指定算法和锁级别；如果不支持，语句会直接报错，而不是悄悄地锁表执行，更安全。
- MySQL 8.0 的 INSTANT：在表的最后添加列（8.0.29 之后支持在任意位置添加）时，只修改元数据，瞬间完成。
- 注意：
  - 即使是 Online DDL，开始和结束时也需要 MDL 写锁。如果有长事务持有 MDL 读锁，DDL 会被阻塞，后续所有的查询都会排队，导致表不可用。执行前要检查长事务，设置 lock_wait_timeout。
  - 重建表的操作消耗大量 IO，会导致主从延迟。
  - 大表使用 gh-ost 或 pt-osc，可以控制速度。
- 可举例：多次给 figure、e2e_eval_task 等表加字段，都使用了 `ALGORITHM=INPLACE, LOCK=NONE`；新增字段设置默认值，兼容存量数据，不需要回刷。

### 42. 【专家】`ALGORITHM=INPLACE` 和 `ALGORITHM=COPY`、`INSTANT` 有什么区别？哪些变更只能用 COPY？
**答案：**
- INSTANT（MySQL 8.0）：只修改数据字典中的元数据，不触碰数据文件，瞬间完成。支持的操作有：添加列（8.0.12 起支持在末尾添加，8.0.29 起支持任意位置）、删除列（8.0.29 起）、修改列的默认值、修改 ENUM 和 SET 的定义（在末尾追加值）、修改索引类型等。
- INPLACE：在存储引擎内部完成，不经过 Server 层创建临时表拷贝数据，期间一般允许并发的 DML（配合 LOCK=NONE）。分两种情况：
  - 需要重建表：如添加主键、修改列的顺序、在 8.0.29 之前添加列、OPTIMIZE。
  - 不需要重建表：如添加二级索引、修改列名、修改 varchar 的长度（不跨越 255 字节的边界时）。
- COPY：创建一张新表，逐行拷贝数据，期间阻塞写入（只允许读），最慢、影响最大。
- 只能使用 COPY 的变更（典型情况）：
  - 修改列的数据类型（如 INT 改为 BIGINT、VARCHAR 改为 TEXT）。
  - 修改字符集（转换数据）。
  - 删除主键但不同时添加新的主键。
  - varchar 的长度从 255 字节以内扩展到 255 字节以上（长度前缀从 1 字节变为 2 字节）。
- 大表上需要 COPY 的变更，改用 gh-ost 或 pt-osc 在线执行，避免长时间阻塞写入。
- 可举例：数字人主表的人设 prompt 字段改为 TEXT（支持的字数从 1500 扩到 3000）时使用了 ALGORITHM=COPY；新增 voice_info 字段时使用了 INPLACE。

### 43. gh-ost、pt-online-schema-change 的原理是什么？
**答案：**
- 两者的共同思路：新建一张结构已经修改好的影子表，把原表的数据分批拷贝过去，同时同步拷贝期间的增量变更，最后原子地重命名，用影子表替换原表。
- pt-online-schema-change（Percona）：
  - 在原表上创建 INSERT、UPDATE、DELETE 三个触发器，把增量的变更同步写入影子表。
  - 分块拷贝存量数据。
  - 缺点：触发器和业务写入在同一个事务中执行，会增加写入的开销和锁竞争；表上已经有触发器时无法使用。
- gh-ost（GitHub）：
  - 不使用触发器，而是伪装成从库，读取 binlog（需要 row 格式）来获取增量变更，异步应用到影子表。
  - 对业务写入没有额外开销。
  - 可以动态限速、暂停（根据负载和主从延迟自动节流），可以在从库上测试，切换的时机也可以控制。
- 风险点：
  - 切换时的重命名需要短暂的锁。
  - 需要约等于原表大小的额外磁盘空间。
  - 执行时间长，期间要监控延迟和负载。
  - 外键会让流程变得复杂。

### 44. 【高频】大表历史数据怎么安全删除？一次删几百万行有什么问题？
**答案：**
- 一次删除几百万行的问题：
  - 大事务长时间持有大量的行锁和间隙锁，阻塞业务的写入。
  - 产生大量的 undo log 和 binlog，主从延迟剧增。
  - 中途失败时回滚的时间更长。
  - IO 被打满，影响线上查询。
  - 删除后表空间并不会释放。
- 安全的做法：
  1. 先备份或归档：导出到冷存储，校验行数和内容。
  2. 分批删除：按主键范围分批，`DELETE FROM t WHERE id BETWEEN ? AND ? AND create_time < ?`，或者 `DELETE ... WHERE create_time < ? ORDER BY id LIMIT 5000`，每批之后休眠一段时间。
  3. 在低峰期执行，监控主从延迟和负载，超过阈值就暂停。
  4. 使用 DBA 平台（DMS）提交变更，经过审批，保留执行记录。
  5. 删除完成后释放表空间（重建表）。
- 更好的设计：按时间分区或分表，过期的数据直接 DROP PARTITION 或 DROP TABLE，几乎没有开销。
- 可举例：对话数据冷备到 AFS 后，按 0-1023、1024-2047 两段分表生成删除 SQL，通过 DMS 的数据库原生变更方式分批执行，执行前和 DBA 确认过。

### 45. 【专家】千万级、亿级大表怎么做分库分表？分片键和分片数量怎么定？
**答案：**
- 先评估是否真的需要：归档历史数据、冷热分离、优化索引、读写分离能不能解决问题。
- 分片键：选择最核心的查询维度（如 uid），让大多数查询只落在一个分片上；分布要均匀；值不会改变。按 uid 分片时，同一个用户的数据会在同一个分片中，便于用户维度的查询和事务。
- 分片数量：
  - 按数据量和增长预期估算：如果预计 3 到 5 年后的数据量是 X，单表控制在千万行左右，那么表的数量约为 X 除以一千万，取 2 的幂（如 512、1024、2048）。
  - 一次性规划得足够多，避免频繁扩容：分表的数量可以多，分库的数量按当前的容量需求设置，以后通过迁移整张表来扩展库的数量。
  - 取 2 的幂，便于以后成倍扩容（采用一致性哈希或成倍分裂时，只需要迁移一半的数据）。
- 实现方式：中间件（ShardingSphere、Vitess、云数据库的分布式版本，如 GaiaDB、DRDS），或者在应用层自己路由。
- 配套：全局唯一 ID；非分片键的查询（映射表或同步到 ES）；分布式事务；数据迁移方案（全量加增量、校验、切流）。
- 可举例：lgzx_app_chat_record 和 lgzx_app_third_chat_record 按 uid 对 2048 取模分表；646 init 表的方案是迁移到 GaiaDB，暂定按 uid 分成 512 张表。

### 46. 分表后（如按 uid 取模 2048 张表），按非分片键查询怎么办？
**答案：**
- 映射表（索引表）：建立"非分片键到分片键"的映射，如 session_id 到 uid、订单号到 uid。先查映射表得到 uid，再定位到具体的分片。映射表本身也可能需要分片。
- 基因法：在非分片键中嵌入分片键的信息，如生成订单号时把 uid 的后几位编码进去，从订单号就能直接算出分片，不需要再查映射表。
- 同步到异构存储：把数据通过 binlog 同步到 ES 或数仓，复杂的查询、运营查询、统计分析都在异构存储中完成，在线库只服务分片键维度的查询。
- 广播查询：并发查询所有分片后合并结果。只适合低频的后台查询，并且要控制并发数和超时。
- 冗余存储：按另外一个维度再存一份数据（如同时按卖家和买家分片），写入时双写，用空间换取查询效率。
- 可举例：对话数据导出和统计都走数仓表（search_dwd_pv_and_chat_log_hf），不直接查询 2048 张分表。

### 47. 【高频】线上批量改数据前要做哪些准备（备份、回滚 SQL、分批、DBA 确认）？
**答案：**
- 评估影响：统计影响的行数（先用 SELECT COUNT 确认），确认 WHERE 条件准确、使用了索引；评估对线上业务的影响和执行时长。
- 备份：把要修改或删除的数据先导出备份（按任务 ID 等条件拉取相关的几张表的数据）；或者复制整张表作为备份。
- 准备回滚：提前写好回滚 SQL 或回滚脚本，或者确认可以从备份中恢复，并验证回滚方案确实可行。
- 写变更 SOP：执行的顺序、每一步的验证方法、出现问题时的回滚顺序（按相反的顺序回滚）。
- 分批执行：大批量的变更分批提交，每批之后检查结果和数据库的负载、主从延迟。
- 审批和执行：通过 DMS 等平台提交，由 DBA 审核；在低峰期执行；先在测试环境演练。
- 执行后验证：抽样检查数据是否正确，观察业务指标是否正常，记录执行情况。
- 可举例：清理 20b 衔接视频数据时，制定了 SOP（按顺序执行，回滚时也按顺序回滚）；上线前分别备份了 qc_task、qc_assignment、qc_evaluation_record 三张表的对应数据；用脚本生成变更 SQL，在 DMS 上分批提交。

### 48. 字段类型怎么选（varchar 长度、text、datetime 和 timestamp）？
**答案：**
- 整数：按取值范围选择最小的合适类型；ID 统一使用 BIGINT（UNSIGNED）；状态和枚举使用 TINYINT。
- 字符串：
  - varchar(n) 中 n 是字符数，按实际需要设置，不要一律设置成 255 或更大：排序和临时表会按最大长度分配内存，索引也有长度上限（utf8mb4 下单列最多 768 个字符）。
  - 超长的内容使用 TEXT 或 JSON：不能有默认值，索引只能建前缀索引，查询时尽量不要 SELECT *，可以把大字段拆到单独的扩展表中。
  - 字符集统一使用 utf8mb4（支持 emoji）。
- 金额：使用 DECIMAL，或者以分为单位用 BIGINT 存储，不要用 FLOAT 或 DOUBLE（有精度问题）。
- 时间：
  - DATETIME：8 字节（5.6.4 之后为 5 字节，加上小数秒的额外字节），范围是 1000 年到 9999 年，和时区无关，存进去是什么就是什么。
  - TIMESTAMP：4 字节，范围是 1970 年到 2038 年，存储时转换为 UTC，读取时按会话的时区转换。有 2038 年问题。
  - 推荐使用 DATETIME，在应用层统一时区；也可以用 BIGINT 存储时间戳。
- 字段尽量设置为 NOT NULL 并给出默认值（NULL 会让索引和统计变复杂）；新增字段的默认值要能兼容存量数据。

### 49. 【专家】GaiaDB、PolarDB 这类云原生数据库和传统 MySQL 架构有什么区别？
**答案：**
- 传统 MySQL：每个实例有自己的本地存储；主从之间通过 binlog 复制完整的数据。每增加一个从库就多一份完整的数据，扩容时需要拷贝全量数据，速度很慢；存储容量受单机磁盘的限制。
- 云原生数据库（计算和存储分离）：
  - 计算节点（兼容 MySQL 协议）无状态，底层共享一个分布式存储（多副本、自动扩容，容量可以达到上百 TB）。
  - 写节点把 redo log 发送给存储层，由存储层负责把日志应用到数据页（日志即数据），减少网络传输的数据量。
  - 只读节点共享同一份存储，通过同步 redo 或者 LSN 来更新自己的缓存，增加只读节点时不需要拷贝数据，可以秒级扩容，主从延迟很低（毫秒级）。
  - 备份基于存储快照，速度快；故障切换速度快。
- 分布式版本（GaiaDB 的分布式形态、DRDS、PolarDB-X）：在此基础上增加了分库分表的能力，可以水平扩展写入能力。
- 注意：
  - 兼容 MySQL 协议，但部分特性（存储引擎、某些参数、DDL 的行为）会有差异，要参考对应产品的文档。
  - 存储按使用量计费：删除数据后要释放表空间，才能真正降低成本。
- 可举例：对话数据存储在 GaiaDB 集群中，单个集群的存储容量为 32159GB，治理时既要删除数据，也要释放表空间。

### 50. 【专家】数据库存储占用到 80%，你会怎么治理？
**答案：**
- 先止血：
  - 确认增长速度和预计写满的时间。
  - 如果马上就要满，先扩容存储（云数据库可以在线扩容）。
  - 暂停非必要的大批量写入。
  - 清理明显无用的数据（临时表、备份表、过期的日志表）。
- 分析构成：
  - 按库和表统计数据大小和索引大小（information_schema.TABLES 中的 data_length、index_length、data_free），找出占用空间最大的表。
  - 分析每张大表的数据：按时间的分布、无效数据的比例（如 uid=0 的数据）、是否有冗余的索引、碎片率（data_free）。
- 治理措施：
  - 删除无效数据：业务上不需要的数据，确认后清理（要先备份）。
  - 冷热分离：历史数据冷备到低成本存储（AFS、对象存储），校验后从在线库删除。
  - 释放空间：删除数据后重建表，回收碎片。
  - 优化结构：删除冗余和无用的索引；大字段压缩或移到对象存储中；选择更合适的字段类型。
  - 从源头治理：不再写入无效数据（如 uid=0 的请求不再入库）；定期清理的任务常态化（数据生命周期管理）。
- 执行规范：备份、分批、和 DBA 确认、低峰期执行、监控主从延迟、可以回滚。
- 长期：建立存储容量的监控和告警（如 70% 预警、80% 告警），做容量规划，定期复盘增长趋势。
- 可举例：shendeng 库的存储占用约为 80%，清理 lgzx_app_thread_record 表的数据后降到约 61%。对话数据（约 20T）采用"冷备到 AFS、抽样校验、DBA 确认后分批删除、释放表空间"的流程完成治理。
