# 13 Redis（45 题）（题目与答案）

以下默认基于 Redis 7.x。

## 数据结构

### 1. 【高频】Redis 有哪些数据类型？各自的典型使用场景是什么？
**答案：**
- String：缓存对象（序列化后的 JSON）、计数器（INCR）、分布式锁（SET NX）、限流计数、Session。
- Hash：存储对象的多个字段（用户信息、配置），可以单独读写某个字段。
- List：消息队列（LPUSH 加 BRPOP）、最新消息列表、时间线（LRANGE 分页）。
- Set：去重、标签、共同好友（求交集 SINTER）、抽奖（SRANDMEMBER、SPOP）。
- ZSet（有序集合）：排行榜、按时间排序的列表（如最近使用、延迟队列）、滑动窗口限流。
- 特殊类型：
  - Bitmap：签到、在线状态、布隆过滤器的底层。
  - HyperLogLog：大规模的基数统计（UV），误差约 0.81%，每个 key 最多占 12KB。
  - GEO：附近的人、按距离计算。
  - Stream：可持久化的消息队列，支持消费者组和 ACK。

### 2. 【高频】String、List、Hash、Set、ZSet 的底层编码分别是什么？
**答案：**
- String：
  - int：整数值。
  - embstr：长度不超过 44 字节的短字符串，对象头和 SDS 在一块连续的内存中。
  - raw：较长的字符串，使用 SDS。
- List：quicklist，即由多个 listpack 组成的双向链表（Redis 7 之前每个节点是 ziplist）。
- Hash：
  - 元素少、值短时使用 listpack（hash-max-listpack-entries 默认 128，hash-max-listpack-value 默认 64 字节）。
  - 超过阈值后转为 hashtable。
- Set：
  - 全部是整数且数量少时使用 intset（set-max-intset-entries 默认 512）。
  - Redis 7.2 起，元素少且不全是整数时使用 listpack。
  - 否则使用 hashtable。
- ZSet：
  - 元素少时使用 listpack（zset-max-listpack-entries 默认 128，值长度默认 64 字节）。
  - 否则使用跳表（skiplist）加 dict：dict 用于按 member 以 O(1) 查找分数，跳表用于按分数排序和范围查询。
- 编码转换是单向的（从紧凑编码转为普通编码后不会再转回来）；可以用 `OBJECT ENCODING key` 查看编码。

### 3. 【高频】ZSet 为什么用跳表而不用红黑树？跳表的查询复杂度是多少？
**答案：**
- 跳表：在有序链表的基础上，增加多层"快速通道"索引。每个节点按概率（Redis 中为 1/4）随机决定层数，最高 32 层。查询时从最高层开始，向右前进，到达下一个节点比目标大的位置时下降一层，平均复杂度是 O(log N)。
- 不用红黑树的原因（作者 antirez 的解释）：
  - 范围查询更简单高效：找到起点后，沿着底层的链表顺序遍历即可，对应 ZRANGEBYSCORE、ZRANGE 等常用的操作；红黑树做范围查询需要中序遍历，实现更复杂。
  - 实现简单，容易调试和修改：插入和删除只需要修改相邻节点的指针，不需要旋转。
  - 可以灵活调整概率参数，在内存占用和性能之间权衡；平均每个节点的指针数比红黑树少。
  - 支持按排名查询：每层的指针都记录了跨度（span），可以以 O(log N) 的复杂度计算出排名（ZRANK）。
- 复杂度：查找、插入、删除平均都是 O(log N)，最坏情况是 O(N)（概率极低）。

### 4. listpack 和 ziplist 有什么区别？ziplist 的连锁更新是什么？
**答案：**
- ziplist：一块连续的内存，每个元素记录前一个元素的长度（prevlen）用于从后往前遍历。prevlen 小于 254 字节时占 1 个字节，否则占 5 个字节。
- 连锁更新：在 ziplist 中插入或修改一个元素，使它的长度从小于 254 字节变成大于等于 254 字节时，下一个元素的 prevlen 要从 1 字节扩展为 5 字节；如果下一个元素的长度也因此跨越了 254 字节的边界，就会继续影响再下一个元素……最坏情况下要重新分配 N 次内存，复杂度是 O(N²)。
- listpack（Redis 5 引入，Redis 7 中全面替代了 ziplist）：
  - 每个元素只记录自己的长度（编码加数据加本元素的总长度 backlen），不再记录前一个元素的长度。
  - 从后往前遍历时，读取当前元素末尾的 backlen 就能知道这个元素的起始位置。
  - 修改一个元素不会影响其他元素，彻底消除了连锁更新。
- 共同点：都是为了节省内存而采用的紧凑结构，适合元素少、元素小的场景；元素多时，查找是 O(N)，所以超过阈值后会转换为其他编码。

### 5. SDS 相比 C 字符串有什么优势？
**答案：**
- SDS（Simple Dynamic String）的结构：len（已使用的长度）、alloc（分配的总长度）、flags（类型）、buf（实际数据）。
- 优势：
  - O(1) 获取长度：直接读取 len 字段，C 字符串需要遍历到 '\0'。
  - 二进制安全：根据 len 判断结束位置，而不是 '\0'，所以可以存储图片、序列化数据等任意的二进制内容。
  - 防止缓冲区溢出：修改前检查空间是否足够，不够就自动扩容。
  - 减少内存重新分配的次数：空间预分配（扩容时多分配一些空间：小于 1MB 时翻倍，大于 1MB 时每次多分配 1MB）；惰性释放（缩短字符串时不立即释放多余的空间）。
  - 兼容部分 C 字符串函数（buf 末尾仍然保留 '\0'）。
- 根据字符串长度使用不同的头部类型（sdshdr8、16、32、64），节省头部占用的内存。

### 6. 【高频】用 ZSET 实现"最近使用列表"，member 和 score 怎么设计？怎么只保留最近 N 条？
**答案：**
- 设计：
  - key：`user:recent:{uid}`，每个用户一个 ZSet。
  - member：对象 ID（如 app_id），同一个对象再次被使用时，用 ZADD 更新它的分数，天然去重。
  - score：最近使用的时间戳（毫秒或秒）。
  - 详情（最近一条 query、会话 ID 等）存放在单独的 key 中（String 或 Hash，如 `app:recent:data:{uid}:{appId}`），ZSet 中只存 ID，保持 ZSet 轻量。
- 写入（用 Pipeline 或 Lua 合并成一次请求）：
  - `ZADD key ts appId`。
  - `ZREMRANGEBYRANK key 0 -(N+1)`：按分数从低到高删除，只保留分数最高的 N 条。
  - `EXPIRE key 过期时间`：设置过期时间，不活跃的用户自动清理。
  - 被删除的成员对应的详情 key 也要设置过期时间或者删除。
- 读取：`ZREVRANGE key 0 N-1 WITHSCORES` 按时间倒序获取，再批量获取详情（MGET 或 Pipeline）。
- 乱序写入：可以用 `ZADD key GT ts appId`（Redis 6.2 起支持），只有新的时间戳比原来的大才更新，防止旧消息覆盖新数据。
- 可举例：数字人"最近使用"的 ZSET `user:digital_human_recent_agents:{uid}`，member 为 appId，score 为时间戳，只缓存 16 条，过期时间 12 个月；详情存在 `app:digital_human_recent_agents:data:{uid}:{appId}` 中；Redis 未命中时回源 MySQL。

### 7. Bitmap、HyperLogLog、GEO、Stream 分别适合什么场景？
**答案：**
- Bitmap：本质是 String，按位操作（SETBIT、GETBIT、BITCOUNT、BITOP）。适合"大量 ID 的二值状态"：用户签到（每天一位）、在线状态、活跃用户统计。ID 是连续整数时最省内存（1 亿个用户约占 12MB）；ID 稀疏时会浪费空间。
- HyperLogLog：基数统计（去重计数），PFADD、PFCOUNT、PFMERGE。每个 key 固定最多占 12KB，标准误差约 0.81%。适合 UV 统计、搜索词去重计数这类大规模、允许一定误差、不需要知道具体有哪些元素的场景。
- GEO：底层是 ZSet（用 geohash 编码作为 score），GEOADD、GEOSEARCH。适合附近的人、附近的门店、按距离排序。
- Stream：可持久化的消息队列，支持消费者组（XGROUP、XREADGROUP）、ACK（XACK）、待处理消息列表（PEL）、消息回溯。适合轻量级的消息队列、事件流。

### 8. 【专家】用 Redis 实现排行榜，分数相同时怎么按时间排序？
**答案：**
- 问题：ZSet 中分数相同的成员按 member 的字典序排序，不能满足"分数相同时，先达到的排在前面"的需求。
- 方案一，复合分数：`score = 分数 × 10^k + (MAX_TS - 达成时间)`。
  - 分数作为高位，时间作为低位；用一个很大的常数减去时间戳，使先达成的时间值更大，在倒序排序中排在前面。
  - 注意：ZSet 的 score 是 double 类型，精确表示的整数范围只到 2^53（约 9×10^15）。分数的取值范围乘以 10^k 不能超过这个上限，否则会丢失精度。时间可以用相对于活动开始的秒数，以减少占用的位数。
- 方案二，小数部分表示时间：`score = 分数 + (1 - ts / 10^n)`，同样要注意精度。
- 方案三：分数相同的成员数量不多时，取出这些成员后，再在应用层按时间（存在另一个 Hash 中）做二次排序。
- 更新分数时，要重新计算整个复合分数（不能直接用 ZINCRBY 增加分数）。可以用 Lua 脚本原子地读取原分数、计算后写回。

## 线程模型与性能

### 9. 【高频】Redis 为什么快？单线程为什么还能支撑高 QPS？
**答案：**
- 纯内存操作，数据结构高效（为不同场景设计了专门的编码，如 listpack、跳表、渐进式 rehash 的哈希表）。
- 单线程执行命令：
  - 没有锁竞争，没有线程切换的开销，实现简单。
  - Redis 的瓶颈通常在网络和内存，而不是 CPU。
  - 每个命令都是原子的。
- I/O 多路复用（epoll）：一个线程同时处理成千上万个连接，只处理已经就绪的连接。
- 高效的协议（RESP，简单、易解析）；支持 Pipeline，批量发送命令，减少网络往返。
- 量级：单个实例在普通命令下可以达到 10 万级的 QPS。
- 前提：避免慢命令。一个耗时的命令会阻塞所有的请求（这就是单线程的代价）。

### 10. 【高频】Redis 6.0 引入的多线程是做什么的？
**答案：**
- 作用：用多个 I/O 线程并行处理网络读写（读取客户端请求、解析协议、把结果写回 socket）。在高并发、网络 I/O 成为瓶颈时，可以提升吞吐。
- 命令的执行仍然是单线程的：所以不需要担心并发安全问题，命令的原子性不变。
- 配置：io-threads（如 4，建议小于 CPU 核数）；io-threads-do-reads yes（是否也用多线程处理读，默认只处理写）。
- 适用：大量的小请求、网络带宽和 CPU 有余量、单个实例的 QPS 已经达到瓶颈。
- 补充：
  - 在 6.0 之前，Redis 就已经用后台线程处理一些耗时操作（异步删除大 key 的 lazyfree、AOF 刷盘、关闭文件）。
  - 持久化（RDB、AOF 重写）由 fork 出的子进程完成。

### 11. 【高频】哪些命令会阻塞 Redis（KEYS、大 key 删除、HGETALL）？怎么避免？
**答案：**
- 会阻塞的命令（复杂度为 O(N)，N 很大时尤其明显）：
  - `KEYS *`：遍历所有的 key。改用 SCAN 渐进式遍历。
  - 对大集合执行全量操作：HGETALL、SMEMBERS、LRANGE 0 -1、ZRANGE 0 -1。改用 HSCAN、SSCAN、ZSCAN，或者分页获取。
  - 删除大 key：DEL 一个包含几百万元素的 Hash，会同步释放内存。改用 UNLINK（异步删除），或者开启 lazyfree-lazy-* 系列配置。
  - FLUSHALL 和 FLUSHDB：使用 ASYNC 参数。
  - 集合运算：SUNION、SINTER、SDIFF 作用于大集合时。
  - SORT。
  - 执行时间长的 Lua 脚本或 MULTI 事务。
  - 持久化相关：fork 大内存的实例时会阻塞主线程（时长和内存大小成正比）；AOF 使用 always 刷盘策略。
- 避免：
  - 在配置中禁用或重命名危险命令（rename-command KEYS ""）。
  - 用慢查询日志（slowlog）监控。
  - 拆分大 key。
  - 批量操作控制每批的数量。

### 12. 【高频】大 key 有什么危害？怎么发现和拆分？
**答案：**
- 标准（经验值）：String 类型的值超过 10KB；集合类型的元素个数超过 5000，或者总大小超过 10MB。
- 危害：
  - 读写大 key 耗时长，阻塞其他请求。
  - 占用网络带宽。
  - 删除时阻塞（同步释放大量内存）。
  - 集群模式下，所在的分片内存和负载不均衡（数据倾斜）。
  - 迁移（集群扩容）和主从同步时，传输缓慢或超时。
  - 过期时如果是同步删除，也会阻塞。
- 发现：
  - `redis-cli --bigkeys`（抽样，只显示每种类型最大的 key）、`--memkeys`。
  - `MEMORY USAGE key`。
  - 离线分析 RDB 文件（redis-rdb-tools）。
  - 云 Redis 的大 key 分析功能。
- 拆分：
  - String：按业务拆成多个 key，或者压缩；不需要整体读取时，拆成 Hash 的多个字段。
  - 集合类型：按 ID 取模或哈希分成多个子 key（如 `key:{0..N}`），读取时只访问对应的子 key。
  - 只保留需要的数据（如最近使用列表只保留 16 条）。
  - 删除大 key 时用 UNLINK，或者分批删除（HSCAN 加 HDEL）。

### 13. 【高频】热 key 有什么危害？怎么发现和处理？
**答案：**
- 危害：大量请求集中访问同一个 key，所在的实例或分片的 CPU 和网络被打满，成为瓶颈，影响这个分片上的其他 key；严重时这个实例宕机，流量转移到其他节点后继续打垮，引发雪崩。增加实例数量也无法解决（一个 key 只在一个分片上）。
- 发现：
  - `redis-cli --hotkeys`（需要设置 LFU 淘汰策略）。
  - MONITOR 采样（对性能有影响，要短时间使用）。
  - 在客户端或代理层统计 key 的访问频率（滑动窗口加 TopK）。
  - 云 Redis 的热 key 分析功能。
  - 业务上可以预知的热点（活动、热门内容）。
- 处理：
  - 本地缓存（最有效）：热 key 缓存在应用实例的本地，设置短的过期时间，大部分读请求不再访问 Redis。
  - 拆分为多个副本：`key_1` 到 `key_N` 分散在不同的分片上，读取时随机选一个，写入时更新所有副本。
  - 读写分离：增加只读副本。
  - 限流：对热 key 单独限流。
  - 热点写（计数器）：在本地合并后批量写入，或者拆分成多个子计数器。

### 14. Pipeline、事务（MULTI）、Lua 脚本有什么区别？
**答案：**
- Pipeline：客户端把多个命令一次性发送出去，再一次性接收结果，减少网络往返的次数（RTT）。
  - 不保证原子性：命令之间可能穿插执行其他客户端的命令。
  - 后面的命令不能依赖前面命令的结果。
  - 适合批量写入、批量读取。
- 事务（MULTI 和 EXEC）：
  - MULTI 之后的命令进入队列，EXEC 时依次执行，执行过程中不会被其他客户端的命令打断（具有隔离性）。
  - 但没有回滚：某个命令执行失败（如类型错误），其他命令照样执行。
  - 可以用 WATCH 实现乐观锁：被监视的 key 在 EXEC 之前被修改，事务就会放弃执行。
  - 后面的命令不能基于前面命令的结果做判断。
- Lua 脚本（EVAL，或者 Redis 7 的 FUNCTION）：
  - 整个脚本原子地执行，可以在脚本中读取数据、做逻辑判断，然后再写入（如"检查库存后扣减"、"判断锁的值后再删除"）。
  - 也减少了网络往返。
  - 注意：脚本执行期间会阻塞 Redis，必须短小；有 lua-time-limit 的超时保护。
- 选择：批量处理用 Pipeline；需要原子性加条件判断时用 Lua；事务很少使用。

### 15. 【专家】Lua 脚本在集群模式下有什么限制？
**答案：**
- 一个脚本访问的所有 key 必须在同一个 slot（哈希槽）中，否则会报 CROSSSLOT 错误。原因是脚本在一个节点上原子执行，无法跨节点操作数据。
- 解决方法：使用哈希标签（hash tag），把需要一起操作的 key 中参与计算 slot 的部分用大括号括起来，如 `{user:123}:cart`、`{user:123}:stock`，只有大括号中的内容参与 slot 计算，这样它们会落在同一个 slot。
  - 注意：哈希标签设计不当（如所有 key 都使用同一个标签）会导致数据和流量集中到一个分片，形成热点。
- 所有用到的 key 必须通过 KEYS 参数传入，不要在脚本内部动态拼接 key 名（代理和集群需要根据 KEYS 参数来路由；动态生成的 key 可能落在别的节点上）。
- 脚本的缓存：使用 EVALSHA 时，每个节点都要加载过脚本；节点上没有时会返回 NOSCRIPT 错误，客户端要降级为 EVAL 重新加载。
- 执行时间：长时间运行的脚本会阻塞整个节点；脚本中执行了写操作之后，就不能再被 SCRIPT KILL 中止，只能 SHUTDOWN NOSAVE。

## 持久化

### 16. 【高频】RDB 和 AOF 的原理和优缺点是什么？
**答案：**
- RDB（快照）：
  - 在某个时刻把内存中的全部数据写成一个压缩的二进制文件。
  - 触发方式：BGSAVE（fork 子进程，在后台生成）、按配置的规则自动触发（save 900 1 表示 900 秒内至少有 1 次修改就触发）、主从全量同步时。
  - 优点：文件紧凑，适合备份和全量复制；恢复速度快。
  - 缺点：两次快照之间的数据可能丢失（分钟级）；fork 大内存的实例时有短暂的阻塞，写时复制还会带来额外的内存占用。
- AOF（追加日志）：
  - 把每个写命令以追加的方式记录到日志文件，重启时重新执行这些命令来恢复数据。
  - 刷盘策略（appendfsync）：always（每个命令都刷盘，最安全但最慢）、everysec（每秒刷盘一次，最多丢失 1 秒的数据，推荐使用）、no（由操作系统决定）。
  - 优点：数据更完整；文件是可以阅读的命令，误操作后可以手动修复（如删掉误执行的 FLUSHALL）。
  - 缺点：文件大、恢复慢，需要定期重写来压缩。
- Redis 7 的 Multi-Part AOF：拆分为基础文件加增量文件，由 manifest 文件管理。

### 17. AOF 重写的过程是什么？
**答案：**
- 目的：AOF 文件会不断变大（对同一个 key 修改多次会产生多条记录）。重写时根据当前内存中的数据，为每个 key 生成最少的命令，得到一个新的、更小的 AOF 文件。不需要读取旧的 AOF 文件。
- 过程（BGREWRITEAOF，或者按 auto-aof-rewrite-percentage 和 auto-aof-rewrite-min-size 自动触发）：
  1. 主进程 fork 出子进程，子进程根据内存快照（写时复制）把数据写入新的文件。
  2. 重写期间，主进程继续处理写命令，并把新的写命令同时写入旧的 AOF 和重写缓冲区。在 Redis 7 中，改为写入一个新的增量 AOF 文件，不再需要重写缓冲区。
  3. 子进程完成后，主进程把增量部分追加到新文件（Redis 7 中更新 manifest 文件），然后原子地替换旧文件。
- 注意：fork 和写时复制带来的内存与阻塞问题；重写期间磁盘 IO 增大。

### 18. 【高频】fork 子进程做 RDB 时，写时复制（COW）对内存有什么影响？
**答案：**
- fork：创建子进程时，复制父进程的页表（不复制实际的内存数据），父子进程共享同一份物理内存页。复制页表的过程会阻塞主线程，内存越大页表越大，阻塞时间越长（每 GB 内存大约需要十几毫秒）。
- 写时复制：子进程在写快照期间，如果主进程修改了某个内存页，内核会把这个页复制一份给主进程修改，子进程继续读取原来的页。
- 对内存的影响：
  - 写入越频繁，被复制的页就越多，内存占用最多可能接近翻倍。
  - 所以 Redis 机器要预留足够的内存（如最大内存只设置为物理内存的 50% 到 70%），否则可能因为内存不足触发 OOM 被杀掉，或者使用 swap 导致性能急剧下降。
- 透明大页（THP）：开启后，内存页的大小变为 2MB，修改一个字节也要复制 2MB，写时复制的开销会大幅增加，还会导致延迟升高。官方建议关闭 THP。
- 其他建议：单个实例的内存不要太大（如控制在 10 到 20GB 以内）；在低峰期执行持久化；从库负责持久化，主库不做持久化（需要权衡数据安全）。

### 19. 混合持久化是什么？
**答案：**
- 配置：`aof-use-rdb-preamble yes`（Redis 4.0 引入，5.0 之后默认开启）。
- 原理：AOF 重写时，先把当前的全量数据以 RDB 格式写入新 AOF 文件的开头，之后重写期间产生的增量命令再以 AOF 格式追加在后面。
- 优点：
  - 恢复速度快：大部分数据是 RDB 格式，直接加载，不需要逐条执行命令。
  - 数据完整：增量部分是 AOF 格式，最多只丢失约 1 秒的数据（everysec 策略下）。
  - 兼具 RDB 和 AOF 的优点。
- 缺点：AOF 文件中的 RDB 部分不可阅读，不能手动编辑；和很老的 Redis 版本不兼容。
- 生产推荐：开启 AOF（everysec），加上混合持久化，再定期把 RDB 备份到远程存储。

## 过期与淘汰

### 20. 【高频】Redis 的过期删除策略是什么（惰性删除、定期删除）？
**答案：**
- 过期时间保存在一个单独的过期字典中。
- 惰性删除：访问某个 key 时，先检查它是否过期，过期了就删除并返回空。对 CPU 友好；但没有被访问的过期 key 会一直占用内存。
- 定期删除：后台的定时任务（每秒执行 hz 次，默认 10 次）每次从过期字典中随机抽取一部分 key，删除其中已经过期的；如果过期的比例超过 25%，就继续抽取，同时限制每次执行的最长时间，避免阻塞。
- 两者结合：在 CPU 消耗和内存回收之间取得平衡。
- 仍然可能有大量过期的 key 没有被及时删除，这时依靠内存淘汰策略兜底。
- 主从：从库不会主动删除过期的 key，而是等待主库同步过来的 DEL 命令（Redis 3.2 之后，从库读取过期的 key 时会返回空）。
- 注意：大量 key 在同一时间过期，会让定期删除的任务占用较多的 CPU。

### 21. 【高频】内存淘汰策略有哪些？LRU 和 LFU 在 Redis 中怎么近似实现？
**答案：**
- 在内存达到 maxmemory 时触发：
  - noeviction（默认）：不淘汰，写命令返回错误。
  - allkeys-lru：在所有 key 中淘汰最近最少使用的。
  - allkeys-lfu：在所有 key 中淘汰访问频率最低的（Redis 4.0 引入）。
  - allkeys-random：随机淘汰。
  - volatile-lru、volatile-lfu、volatile-random：只在设置了过期时间的 key 中淘汰。
  - volatile-ttl：淘汰剩余过期时间最短的。
- 选择：用作缓存时一般选择 allkeys-lru 或 allkeys-lfu（有明显的热点数据时选 LFU）；既有缓存又有不能丢失的数据时，选择 volatile-* 系列（不能丢的数据不设置过期时间）。
- 近似 LRU：
  - 每个对象记录最后访问的时间（24 位的时钟）。
  - 淘汰时随机抽取 maxmemory-samples 个 key（默认 5 个），淘汰其中最久没有被访问的。
  - Redis 3.0 之后维护一个候选池（大小为 16），提高近似的效果。
  - 不使用精确的 LRU 链表，是为了节省内存和开销。
- 近似 LFU：
  - 复用同一个 24 位字段：16 位记录上次的递减时间，8 位记录对数计数器（访问次数越多，计数器增长得越慢，最大为 255）。
  - 计数器随时间衰减（lfu-decay-time），防止很久以前的热点一直占用内存。
  - 用 lfu-log-factor 控制计数器的增长速度。

### 22. 大量 key 同时过期会有什么问题？
**答案：**
- 缓存雪崩：大量缓存同时失效，请求全部打到数据库，可能把数据库打垮。
- Redis 自身：定期删除时，如果过期 key 的比例超过 25% 就会持续循环删除，占用主线程的 CPU，导致请求延迟出现毛刺（虽然每次执行有时间上限，但会频繁触发）。
- 删除大 key 时：如果过期的是大 key，同步删除会阻塞（可以开启 lazyfree-lazy-expire 改为异步删除）。
- 解决：
  - 过期时间加随机值（如基础 TTL 再加上 0 到 300 秒的随机数），把过期时间打散。
  - 热点数据设置为不过期，或者使用逻辑过期，后台主动刷新。
  - 开启 lazyfree 相关的配置。
  - 应对缓存雪崩的其他手段：多级缓存、限流和降级、互斥地回源。

## 缓存问题

### 23. 【高频】缓存穿透、缓存击穿、缓存雪崩分别是什么？怎么解决？
**答案：**
- 缓存穿透：查询的数据在缓存和数据库中都不存在（恶意请求不存在的 ID），每次请求都会穿过缓存打到数据库。
  - 缓存空值：把不存在的结果也缓存起来，设置较短的过期时间。
  - 布隆过滤器：预先存入所有合法的 ID，不在过滤器中的请求直接拒绝。
  - 参数校验：拦截格式不合法的 ID。
- 缓存击穿：某一个热点 key 过期的瞬间，大量并发请求同时回源数据库。
  - 互斥锁或 singleflight：只允许一个请求回源，其他请求等待或者返回旧值。
  - 逻辑过期：不设置真实的过期时间，在值中记录逻辑过期时间，过期后由一个线程异步刷新，其他请求继续返回旧值。
  - 热点 key 永不过期，由后台主动更新。
- 缓存雪崩：大量 key 在同一时间过期，或者 Redis 宕机，导致大量请求同时打到数据库。
  - 过期时间加随机值。
  - Redis 高可用（哨兵或集群）。
  - 多级缓存（本地缓存加 Redis）。
  - 限流、降级、熔断，保护数据库。
  - 提前预热缓存。

### 24. 【高频】布隆过滤器的原理是什么？有什么缺点？
**答案：**
- 原理：
  - 一个长度为 m 的位数组，加上 k 个哈希函数。
  - 添加元素时，用 k 个哈希函数分别计算出 k 个位置，把这些位置设置为 1。
  - 查询时，检查这 k 个位置：只要有一个是 0，元素就一定不存在；全部是 1，元素可能存在。
- 特点：空间效率极高（1 亿个元素、1% 的误判率，大约只需要 114MB）；查询是 O(k)。
- 缺点：
  - 存在误判：会把不存在的元素判断为可能存在（假阳性）；但不会把存在的元素判断为不存在。误判率由 m、n（元素个数）、k 决定，可以根据期望的误判率计算出需要的大小。
  - 不支持删除：一个位可能被多个元素共享。需要删除时，可以使用计数布隆过滤器或布谷鸟过滤器（Cuckoo Filter）。
  - 需要预估元素的数量：元素数量超过预估值时，误判率会急剧上升，只能重建。
  - 需要先把全部数据加载进去，新增数据时也要同步添加。
- 实现：RedisBloom 模块（BF.ADD、BF.EXISTS），或者用 Bitmap 自己实现，或者使用本地的布隆过滤器。

### 25. 【高频】缓存击穿时用互斥锁还是逻辑过期？
**答案：**
- 互斥锁（或 singleflight）：
  - 缓存未命中时，获取锁成功的那个请求负责回源并重建缓存，其他请求等待一段时间后重试读取缓存，或者通过 singleflight 共享同一次回源的结果。
  - 优点：数据一致性好，总是返回最新的数据；实现简单。
  - 缺点：等待期间请求的延迟增加；如果回源很慢，大量请求会被阻塞；需要处理锁超时的问题。
- 逻辑过期：
  - 缓存永不真正过期，值中带有逻辑过期时间。
  - 读取时发现逻辑上已经过期，就尝试获取锁，由一个线程异步回源更新，当前请求以及其他请求直接返回旧值。
  - 优点：不阻塞，性能好，延迟稳定。
  - 缺点：在刷新完成之前会返回旧数据；需要提前预热（缓存中没有数据时无法使用）；占用的内存不会被自动回收。
- 选择：对一致性要求高的数据（如价格、库存）用互斥锁；对性能和可用性要求高、可以接受短暂旧数据的热点数据（配置、热门内容）用逻辑过期。

### 26. 【高频】缓存未命中时回源数据库并回填，怎么防止并发回源？singleflight 是什么？
**答案：**
- 问题：一个 key 未命中时，如果有大量并发请求同时到达，每个请求都会去查数据库，数据库瞬间承受多倍的压力（属于缓存击穿的一种）。
- singleflight（Go 的 golang.org/x/sync/singleflight）：在同一个进程内，对同一个 key 的并发调用，只有第一个调用真正执行函数，其他调用等待这次执行的结果并共享它。
```go
v, err, _ := sf.Do("conf:"+appID, func() (any, error) {
    c, err := loadFromDB(appID)
    if err == nil { cache.Set(appID, c, ttl) }
    return c, err
})
```
- 注意：
  - singleflight 只在单个进程内合并请求；多实例部署时，每个实例仍然会各自回源一次，对数据库的压力从"并发数"量级降为"实例数"量级。需要全局只回源一次的，使用分布式锁。
  - 回源函数如果卡住，所有等待的请求都会被阻塞，要设置超时（可以使用 DoChan 配合 select 超时）。
  - 出错时所有等待的请求都会收到同一个错误，可以考虑用 Forget 让后续请求重新尝试。
- 再配合空值缓存，防止缓存穿透。

### 27. 缓存的过期时间怎么设置？要不要加随机值？
**答案：**
- 按数据的特点设置：
  - 变化频繁、对一致性要求高的数据：设置短的过期时间（秒级到分钟级），或者在数据变更时主动删除缓存。
  - 很少变化的数据（配置、字典）：设置较长的过期时间（小时级），加上主动删除缓存。
  - 业务上有明确保留期限的数据，按期限设置（如"最近使用"列表保留 12 个月）。
- 必须加随机值：批量写入的 key（如缓存预热、批量导入）如果设置了相同的过期时间，会在同一时刻集中失效，造成缓存雪崩，并让 Redis 在定期删除时消耗大量 CPU。做法是过期时间等于基础 TTL 加上一个随机数（如基础 TTL 的 10% 以内）。
- 空值缓存：过期时间要短（如 30 秒到几分钟），防止数据已经写入数据库后，缓存中还长期保留着空值。
- 不建议把缓存设置为永不过期（除非由后台主动维护），过期时间是保证最终一致的兜底手段。

### 28. 【专家】Redis 和 MySQL 双写时，一边失败怎么办？
**答案：**
- 先明确以谁为准：一般以 MySQL 为准，Redis 是派生数据，可以从 MySQL 重建。
- 先写 MySQL：
  - MySQL 写入失败：直接返回失败（或者重试），不写 Redis，两边保持一致。
  - MySQL 成功、Redis 失败：不要回滚 MySQL。删除 Redis 中对应的 key（下次读取时回源加载）；删除也失败时，把重试任务放进消息队列，或者依靠 binlog 订阅来补偿；最后由过期时间兜底。
- 异步双写（通过 MQ 消费写入两边）：只有两边都成功后才提交 offset；失败的消息重试，超过次数进入死信队列；写入操作必须幂等。
- Redis 作为主要存储、MySQL 作为持久化备份的场景（如计数）：先写 Redis，再异步批量写入 MySQL；Redis 数据丢失后，用 MySQL 中的数据恢复，接受少量的误差，并定期校准。
- 读取兜底：Redis 未命中或数据异常时回源 MySQL，所以即使 Redis 写失败，最终也能恢复正确的数据。
- 对账：定期抽样对比两边的数据并修复。
- 可举例："最近使用"接口由 697 订阅 pipe 后双写 Redis 和 MySQL；读取时 Redis 未命中就查 MySQL 并回写 Redis。

## 高可用与集群

### 29. 【高频】主从复制的流程是什么？全量同步和增量同步有什么区别？
**答案：**
- 建立连接：从库执行 REPLICAOF，向主库发送 PSYNC 命令，带上自己记录的 replication ID 和复制偏移量（offset）。
- 全量同步（第一次同步，或者无法进行增量同步时）：
  1. 主库执行 BGSAVE 生成 RDB 文件（也可以使用无盘复制，直接通过网络发送）。
  2. 生成 RDB 期间的新写命令，主库记录到这个从库的复制缓冲区中。
  3. 把 RDB 发送给从库，从库清空自己的数据后加载 RDB。
  4. 主库再把缓冲区中的命令发送给从库。
  - 代价高：fork、磁盘 IO、网络传输、从库加载期间不可用。
- 增量同步（断线重连后）：
  - 主库有一个环形的复制积压缓冲区（repl-backlog-buffer，默认 1MB）。
  - 从库重连后发送自己的 offset，如果这个 offset 之后的数据仍然在积压缓冲区中，主库只发送缺失的那部分命令。
  - 如果数据已经被覆盖了（断线时间太长，或者缓冲区太小），就退化为全量同步。
  - 建议根据写入速度和可能的断线时长，调大 repl-backlog-size。
- 之后，主库持续把写命令异步发送给从库，属于异步复制，主库宕机时可能丢失少量数据。

### 30. 【高频】哨兵（Sentinel）的工作原理是什么？怎么选主？
**答案：**
- 作用：监控主从节点、主库故障时自动切换、通知客户端新的主库地址（客户端连接哨兵来获取主库地址）。
- 部署：至少 3 个哨兵节点（取奇数），部署在不同的机器上。
- 故障判定：
  - 主观下线：某一个哨兵在 down-after-milliseconds 时间内都没有收到主库的有效回复，就认为主库下线了。
  - 客观下线：认为主库下线的哨兵数量达到 quorum 配置的值，才判定为客观下线。
- 选举领头哨兵：用类似 Raft 的投票机制，获得多数票的哨兵负责执行故障切换。
- 选出新主库（按以下顺序筛选）：
  1. 排除不健康的从库（已下线、和主库断开连接太久）。
  2. 按 replica-priority 的优先级（值越小越优先，为 0 表示不参与选举）。
  3. 复制偏移量最大的（数据最新）。
  4. 运行 ID 最小的。
- 切换：让新主库执行 REPLICAOF NO ONE，其他从库改为复制新主库，旧主库恢复后变为从库；通过发布订阅通知客户端。
- 防止脑裂导致的数据丢失：配置 min-replicas-to-write 和 min-replicas-max-lag，主库连接的健康从库数量不足时，拒绝写入。

### 31. 【高频】Redis Cluster 的数据分片原理是什么？为什么是 16384 个槽？
**答案：**
- 分片：
  - 一共有 16384 个哈希槽（slot），`slot = CRC16(key) % 16384`。
  - 每个主节点负责一部分槽，每个主节点可以有自己的从节点。
  - 客户端缓存"槽到节点"的映射，直接把请求发给对应的节点；如果映射过期了，节点返回 MOVED 重定向。
- 去中心化：节点之间通过 Gossip 协议交换状态和槽的信息；节点故障后，由它的从节点自动提升为主节点（由其他主节点投票）。
- 为什么是 16384 个槽（作者的解释）：
  - 节点之间的心跳包中要携带一个槽位图，16384 个槽占 2KB；如果是 65536 个槽就要 8KB，心跳的开销太大。
  - 集群的主节点数量一般不会超过 1000 个，16384 个槽足够分配，每个节点也能分到足够多的槽，保证分布均匀。
  - 槽位图在节点数量少时可以被压缩，槽太多时压缩率会变低。
- 限制：
  - 多个 key 的操作（MGET、事务、Lua 脚本）要求这些 key 在同一个槽，需要使用哈希标签 `{}`。
  - 只能使用 0 号数据库。

### 32. Cluster 模式下 MOVED 和 ASK 重定向有什么区别？
**答案：**
- MOVED：表示这个槽已经永久迁移到了另一个节点（或者客户端的映射本来就是错的）。客户端除了把这次请求转发到新节点之外，还要更新本地的"槽到节点"映射，之后的请求都直接发给新节点。
- ASK：发生在槽的迁移过程中（这个槽正在从节点 A 迁移到节点 B，处于 MIGRATING 或 IMPORTING 状态）。客户端请求节点 A 时，如果这个 key 已经被迁移到了 B，A 会返回 ASK。客户端要先向 B 发送 ASKING 命令，然后在 B 上执行这一次请求，但不更新本地的映射（因为迁移还没有完成，这个槽的其他 key 可能还在 A 上）。
- 总结：MOVED 是永久的、需要更新映射；ASK 是临时的，只对这一次请求有效。
- 智能客户端（如 go-redis 的 ClusterClient）会自动处理这两种重定向。

### 33. 【专家】Redis 集群扩容时数据怎么迁移？对业务有什么影响？
**答案：**
- 流程：
  1. 加入新节点（CLUSTER MEET），此时它还没有分配到槽。
  2. 规划要迁移的槽（如从每个旧节点各迁移一部分），逐个迁移。
  3. 对每个槽：把目标节点设置为 IMPORTING 状态，源节点设置为 MIGRATING 状态；循环执行 CLUSTER GETKEYSINSLOT 获取一批 key，用 MIGRATE 命令迁移到目标节点；全部迁移完后，在所有节点上执行 CLUSTER SETSLOT NODE，宣布这个槽的新归属。
  4. 可以使用 redis-cli --cluster reshard 或 rebalance 自动完成。
- 对业务的影响：
  - MIGRATE 命令对每个 key 是同步阻塞的（序列化、发送、在目标节点写入、再从源节点删除）。迁移大 key 时会长时间阻塞源节点和目标节点，可能导致超时，甚至被判定为节点故障，引发主从切换。
  - 迁移期间会出现 ASK 重定向，延迟略有增加。
  - 网络和 CPU 的消耗增加。
- 建议：
  - 先清理和拆分大 key。
  - 在低峰期迁移，控制每批的 key 数量和迁移速度。
  - 监控延迟。
  - 提前扩容，不要等到内存快满时才扩容。
  - 云 Redis 通常提供在线扩容的能力（基于代理，或者先复制再切换），对业务的影响更小。

### 34. 主从切换时会丢数据吗？怎么减少丢失？
**答案：**
- 会丢失：
  - 异步复制：主库已经向客户端返回成功的写入，还没来得及同步到从库，主库就宕机了。从库被提升为新主库后，这部分数据就丢失了。
  - 脑裂：主库和哨兵、从库之间发生网络分区，但客户端仍然能连接到旧主库并继续写入；哨兵选出了新的主库，网络恢复后旧主库降级为从库，会清空自己的数据，重新从新主库同步，分区期间写入旧主库的数据全部丢失。
- 减少丢失：
  - `min-replicas-to-write 1` 加 `min-replicas-max-lag 10`：主库在与它保持同步的从库数量少于 1 个，或者复制延迟超过 10 秒时，拒绝写入。以牺牲部分可用性为代价，限制了丢失数据的时间窗口，也能缓解脑裂的问题。
  - WAIT 命令：等待指定数量的从库确认收到了数据（半同步效果），用于关键的写入。
  - 业务层：Redis 不作为唯一的数据源，重要的数据以数据库为准，Redis 中的数据可以重建。
- 结论：Redis 的高可用方案无法保证完全不丢数据，对强一致的数据不应该只存在 Redis 中。

### 35. 【专家】Codis、Twemproxy 这类代理方案和 Redis Cluster 有什么区别？
**答案：**
- 代理方案的架构：客户端连接代理，代理按 key 计算分片后，转发到后端普通的 Redis 实例。
  - Twemproxy（Twitter）：轻量的代理，用一致性哈希分片；不支持在线扩容（增减节点需要重启或者数据会重新分布），已经基本停止维护。
  - Codis（豌豆荚）：代理加 1024 个槽，由 Dashboard 管理，用 ZooKeeper 或 etcd 存储元数据；支持在线迁移槽和扩容（使用修改过的 Redis，codis-server）；Redis 的版本跟进较慢，目前也很少维护。
- Redis Cluster：官方方案，没有代理，去中心化，由客户端直接连接各个节点（需要使用支持集群的客户端）。
- 对比：
  - 客户端：代理方案对客户端透明，任何客户端都可以使用，就像连接一个单机 Redis；Cluster 需要智能客户端，并且对多 key 操作有限制。
  - 性能：代理方案多了一跳网络，延迟略高，代理本身也要做高可用；Cluster 直接连接节点，性能更好。
  - 运维：代理方案有中心化的管理界面，运维直观；Cluster 依赖 Gossip，大集群中有一定的元数据同步开销，排查问题相对复杂。
  - 功能：代理层可以统一实现读写分离、热 key 缓存、命令过滤、多租户等能力（很多云 Redis 和公司内部的方案都采用"代理加集群"的架构）。

### 36. 【高频】Redis 分布式锁怎么实现？SET NX PX 加 Lua 解锁为什么是必要的？
**答案：**
- 加锁：`SET lock:{resource} {唯一值} NX PX 30000`。
  - NX：key 不存在时才设置成功，保证互斥。
  - PX：设置过期时间，防止持有锁的进程崩溃后锁永远不释放（死锁）。
  - 一条命令同时完成"设置值"和"设置过期时间"，保证原子性。早期的写法是 SETNX 加 EXPIRE 两条命令，如果在两条命令之间进程崩溃，锁就永远不会过期。
  - 唯一值（UUID 或请求 ID）用来标识锁的持有者。
- 解锁必须用 Lua 脚本：
  - 如果直接执行 DEL，可能删掉别人的锁。例如：A 的锁已经过期了，B 获得了锁；A 执行完业务后执行 DEL，删掉的是 B 的锁。
  - 如果先 GET 判断是不是自己的值，再 DEL，这两步之间锁可能刚好过期并被别人获取，仍然会误删。
  - 所以"判断是不是自己的值，是才删除"必须原子执行，用 Lua 脚本实现：
```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("DEL", KEYS[1]) end
return 0
```
- 其他问题：锁的续期（看门狗）、可重入（用 Hash 记录重入次数）、主从切换时锁丢失（使用 Redlock 有争议，对正确性要求高时使用 fencing token 或 etcd）。

### 37. 看门狗（Redisson watchdog）机制是什么？
**答案：**
- 问题：锁的过期时间很难设置得刚好。设置短了，业务还没执行完锁就过期了；设置长了，持有锁的进程崩溃后，锁要很久才能释放。
- 看门狗：
  - 加锁时如果没有指定过期时间，Redisson 默认设置 30 秒的过期时间，并启动一个后台定时任务。
  - 每隔过期时间的三分之一（10 秒），检查当前线程是否仍然持有锁，持有就把过期时间重置为 30 秒。
  - 业务执行完毕，主动解锁后，停止续期。
  - 进程崩溃时，续期任务也随之停止，锁在最多 30 秒后自动过期，不会永远锁住。
- 在 Go 中实现：加锁成功后，启动一个 goroutine 定期执行续期（用 Lua 脚本，判断值是自己的才执行 PEXPIRE），通过 context 控制它在解锁时退出。
- 注意：
  - 续期失败（网络问题、锁已经被别人获取）时，要通知业务方停止操作。
  - 业务代码卡住（死循环）时，看门狗会一直续期，锁永远不会释放，所以仍然需要设置一个业务层面的最长持有时间。
  - 长时间的 GC 停顿仍然可能导致锁过期，对正确性要求高时需要 fencing token。

### 38. 【高频】用 Redis 实现滑动窗口限流、令牌桶限流。
**答案：**
- 滑动窗口（ZSET，用 Lua 保证原子性）：
```lua
-- KEYS[1]=限流key ARGV: now(ms) window(ms) limit member(唯一请求id)
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1] - ARGV[2])
if redis.call('ZCARD', KEYS[1]) < tonumber(ARGV[3]) then
  redis.call('ZADD', KEYS[1], ARGV[1], ARGV[4])
  redis.call('PEXPIRE', KEYS[1], ARGV[2])
  return 1
end
return 0
```
  - 精确，但每个请求都要在 ZSET 中保存一条记录，请求量大时内存开销大。
  - 可以改为"分格计数"：把窗口切成若干个小格，每个小格用一个 INCR 计数，统计时把最近几个小格的计数加起来，更节省内存。
- 令牌桶（Hash 中存储 tokens 和 last_ts，用 Lua 实现）：
  1. 读取当前的令牌数和上次补充令牌的时间。
  2. 计算这段时间内应该补充的令牌：`新令牌数 = min(桶容量, tokens + (now - last_ts) × 每毫秒生成的令牌数)`。
  3. 令牌数大于等于 1 就扣减一个并允许通过，否则拒绝。
  4. 写回令牌数和当前时间，并设置过期时间。
  - 时间最好由服务端统一传入（多台机器的时钟可能不一致），或者在 Lua 中用 `redis.call('TIME')` 获取 Redis 服务器的时间（Redis 5 起支持脚本效果复制，可以在脚本中使用 TIME）。
- 现成的库：go-redis/redis_rate（基于 GCRA 算法，效果类似令牌桶）。

### 39. 用 Redis 实现延迟队列。
**答案：**
- ZSET 方案：
  - 添加任务：`ZADD delay_queue {执行时间戳} {任务ID或任务内容}`。
  - 消费：Worker 定期（如每 100 毫秒）用 Lua 原子地取出到期的任务并从 ZSET 中删除，防止多个 Worker 取到同一个任务：
```lua
local items = redis.call('ZRANGEBYSCORE', KEYS[1], 0, ARGV[1], 'LIMIT', 0, ARGV[2])
if #items > 0 then redis.call('ZREM', KEYS[1], unpack(items)) end
return items
```
  - 取出的任务放入一个"处理中"的列表（或者再推送到普通队列，如 List 或 Stream），处理成功后再删除；处理失败或超时没有确认的任务要重新放回，防止任务丢失。
  - 任务内容较大时，ZSET 中只存任务 ID，内容存在 Hash 中。
- 局限：
  - 轮询会带来延迟和空转的开销。
  - 任务量巨大时，ZSET 会成为大 key（可以按时间分片成多个 ZSET）。
  - 数据的可靠性依赖 Redis 的持久化。
  - 对可靠性要求高的场景，使用 MQ 的延迟消息，或者数据库加定时扫描。
- Redisson 提供了现成的 RDelayedQueue。

### 40. 【高频】用 Redis 做轮询分配（round-robin），怎么保证并发下分配均匀？
**答案：**
- 用 INCR 原子计数：`n = INCR rr:{池名}`，再用 `idx = (n - 1) % 人员数量` 选出被分配的人。INCR 是原子操作，多个实例并发调用时，每次得到的值都不同，分配结果天然均匀，不会重复。
- 人员列表的变化：
  - 人员列表存放在 Redis 的 List 或数据库中，读取后取模。
  - 人员数量变化时，分配的顺序会改变，但仍然是均匀的；如果要求严格按顺序轮询，可以使用"List 加 RPOPLPUSH"实现循环队列：`RPOPLPUSH rr_list rr_list`，每次把队尾的人员移到队头并返回，是原子操作。
- 交叉分配（一个任务分给两个人）：`idx = (n / 2) % 人员数量`，分配给 idx 和 idx+1 这两个人，保证是两个不同的人。
- 考虑负载：如果每个人的处理能力不同，可以使用加权轮询，或者选择"当前未完成任务最少的人"（用 ZSET 记录每个人的任务数，取分数最小的，并用 Lua 原子地加一）。
- 可举例：质检员的轮询分配，单人模式下 `idx = 已分配总数 % 人数`，交叉模式下 `idx = (已分配总数 / 2) % 人数`；抽检员通过 Redis 轮询分配（assignQCUserRoundRobin）。

### 41. Redis Stream 能替代 Kafka 吗？
**答案：**
- Stream 的能力：
  - 只能追加的消息日志，每条消息有唯一的 ID（时间戳加序号）。
  - 支持消费者组（XREADGROUP）：组内的多个消费者分担消息。
  - 支持 ACK（XACK）和待处理消息列表（PEL）：没有确认的消息可以被重新获取或转移给其他消费者（XCLAIM、XAUTOCLAIM）。
  - 支持阻塞读取、按 ID 回溯消费、用 MAXLEN 限制长度。
- 和 Kafka 相比：
  - 存储：Stream 的数据在内存中，容量受内存限制，成本高；不适合保存海量消息或长时间保留。Kafka 存在磁盘上，可以保存 TB 级的数据，保留数天甚至更久。
  - 可靠性：Stream 依赖 Redis 的持久化（AOF everysec 可能丢失约 1 秒的数据）和异步复制（主从切换时可能丢失数据）。Kafka 有多副本和 ISR 的保证。
  - 扩展：一个 Stream 就是一个 key，只能在一个分片上，无法像 Kafka 的分区那样水平扩展，吞吐上限就是单个节点的能力。
  - 生态：Kafka 和流处理（Flink、Connect）的生态成熟。
- 结论：消息量不大、对延迟要求低、可以接受少量丢失、已经在使用 Redis 的轻量场景（内部的异步任务、通知），可以使用 Stream；大规模、高可靠的数据管道和日志收集，仍然使用 Kafka。

### 42. Session 共享用 Redis 怎么做？
**答案：**
- 问题：多个实例部署时，Session 存在某一台机器的内存中，用户的请求被转发到其他实例后就找不到登录状态。
- 方案：
  - 把 Session 集中存储到 Redis 中：key 为 `session:{sessionId}`，值用 Hash 或序列化后的 String，设置过期时间（如 30 分钟），用户每次访问时刷新过期时间（滑动过期）。
  - sessionId 通过 Cookie（设置 HttpOnly、Secure、SameSite 属性）或请求头传递。
  - 各个实例都从 Redis 读取，服务就变成了无状态的，可以水平扩展。
- 注意：
  - 安全：sessionId 要足够随机（不可预测）；登录后重新生成 sessionId，防止会话固定攻击；退出登录时主动删除。
  - 高可用：Redis 故障会导致所有用户的登录状态失效，要部署哨兵或集群。
  - 性能：每个请求都要访问一次 Redis，可以在网关层统一处理；Session 中只存放必要的信息。
- 另一种方案：使用 JWT 这类无状态的 token，服务端不存储 Session；但 token 难以主动注销（需要维护黑名单），而且 token 体积较大。

### 43. 【专家】Redis 内存容量怎么预估？一个 key 的实际内存开销是多少？
**答案：**
- 单个 key 的开销远大于数据本身：
  - 全局哈希表中的条目 dictEntry（约 24 字节，加上内存分配器 jemalloc 的对齐，实际约 32 字节）。
  - key 本身的 SDS（有头部的开销）。
  - 值的 redisObject（16 字节）加上数据部分（SDS 或具体的数据结构）。
  - 设置了过期时间的 key，在过期字典中还有一个条目。
  - jemalloc 按固定的规格（8、16、32、48、64……字节）分配内存，会产生内部碎片。
  - 粗略估计：一个很小的 String 类型的 key-value，实际占用约 50 到 100 字节。
- 估算方法：
  - 不要只按"数据大小乘以数量"计算，最好的方法是实测：写入一批（如 10 万个）真实格式的数据，用 INFO memory 中 used_memory 的变化量计算出每条的平均开销，再乘以数量。
  - 也可以用 `MEMORY USAGE key` 查看单个 key 的大小。
- 再乘以系数：
  - 内存碎片率（mem_fragmentation_ratio，一般在 1.0 到 1.5 之间）。
  - fork 时写时复制需要的预留（maxmemory 建议设置为物理内存的 50% 到 70%）。
  - 复制缓冲区、客户端缓冲区。
  - 未来的增长余量。
- 节省内存：使用紧凑编码（把小对象放进 Hash，利用 listpack，例如 Instagram 用 Hash 存储海量的小 key）；缩短 key 名；控制集合的大小（如只保留最近 16 条）；压缩值；设置合理的过期时间。
- 可举例：数字人"最近使用"按每条 0.2KB、每个用户最多 16 条估算，单日峰值 30 万 PV 时，Redis 约需要 0.9GB。

### 44. 【专家】Redis 在线上出现延迟毛刺，你会怎么排查？
**答案：**
- 先区分是 Redis 本身慢，还是网络或客户端的问题：
  - 用 `redis-cli --latency` 或 `--intrinsic-latency` 测试基础延迟。
  - 对比客户端看到的耗时和 Redis 慢查询日志中的耗时。
- Redis 侧常见的原因：
  - 慢命令：`SLOWLOG GET` 查看慢查询（KEYS、HGETALL 大 key、大集合运算、耗时的 Lua 脚本）。
  - 大 key 的读写和删除：`--bigkeys`；改用 UNLINK。
  - fork 导致的阻塞：查看 INFO stats 中的 latest_fork_usec，看是否和 RDB 或 AOF 重写的时间点吻合；关闭透明大页（THP）。
  - AOF 刷盘阻塞：磁盘 IO 繁忙时，fsync 会阻塞写入（INFO persistence 中的 aof_delayed_fsync）。
  - 内存使用达到上限，频繁淘汰数据；或者发生了 swap（检查进程的 swap 使用量）。
  - 大量 key 同时过期，导致定期删除的任务占用 CPU。
  - CPU 争用：和其他进程抢占 CPU、绑核的问题。
  - 用 `LATENCY DOCTOR` 和 `LATENCY HISTORY` 查看延迟事件。
- 网络和客户端侧的原因：
  - 连接池不足，请求在客户端排队。
  - 网络抖动、带宽被打满（大 value）。
  - 客户端的 GC 停顿。
  - 连接数过多。
- 处理：根据原因优化（拆分大 key、禁用危险命令、调整持久化策略、扩容或增加分片、使用本地缓存承接热 key）。

### 45. 【专家】什么场景不应该用 Redis？
**答案：**
- 需要强一致、不能丢失的核心数据（资金、订单状态）只存放在 Redis 中：Redis 是异步复制，持久化也可能丢失数据，应该以数据库为准，Redis 只作为缓存或辅助。
- 数据量远超内存、访问频率低的冷数据：存放在内存中成本太高，应该使用数据库或对象存储。
- 需要复杂查询的场景（多条件组合筛选、关联查询、聚合统计）：Redis 只能按 key 访问，不适合，应该使用数据库、ES 或数仓。
- 需要事务回滚、跨多个 key 的强事务：Redis 的事务没有回滚。
- 大规模、高可靠的消息队列：使用 Kafka 等专业的 MQ。
- 存储大的值（文件、大段 JSON 达到 MB 级）：会阻塞 Redis、占用网络带宽，应该使用对象存储，Redis 中只存放引用。
- 对正确性要求极高的分布式锁：使用 etcd 或 ZooKeeper 加 fencing token。
- 结论：Redis 适合作为高性能的缓存、计数、排行、限流、临时状态的存储，不应该作为唯一的、权威的数据源。
