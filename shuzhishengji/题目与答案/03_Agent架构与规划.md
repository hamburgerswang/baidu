# 03 Agent 架构与规划（50 题）（题目与答案）

### 1. 【高频】什么是 Agent？和普通的 LLM 应用、Workflow 有什么区别？
**答案：**
- Agent 由大模型、工具、记忆和循环决策组成：模型在运行时自己决定下一步做什么，观察结果后继续决策，直到完成目标。
- 普通 LLM 应用：单次或固定几次调用（问答、摘要），没有"观察-决策-行动"的循环。
- Workflow：执行路径由开发者预先编排，模型只是其中的节点，分支可预测。
- Agent：路径由模型动态决定，灵活性高，但成本、延迟和不确定性也更高。
- 实际是一个连续的光谱：单次调用 → 链式调用 → 路由 → Workflow → 自主 Agent，按任务的开放程度选择。

### 2. 【高频】Agent 的核心组成部分有哪些（规划、记忆、工具、行动）？
**答案：**
- 规划：任务分解、决定下一步、反思修正，如 ReAct、Plan-and-Execute。
- 记忆：短期记忆是上下文中的对话和中间结果；长期记忆存在向量库、KV 存储或用户画像中，按需检索。
- 工具：通过 Function Calling 或 MCP 调用 API、搜索、代码执行，扩展模型能力。
- 行动：执行工具调用，把结果作为 Observation 写回上下文，驱动下一轮推理。
- 工程上还需要：执行引擎（循环、状态、超时）、护栏（权限、内容审核）、可观测（trace、日志、评估）。

### 3. 【高频】ReAct 的原理是什么？有什么缺点？
**答案：**
- 原理：模型交替输出 Thought（推理）、Action（工具调用）、Observation（工具结果），循环直到给出最终答案。
- 优点：推理和行动交织，能根据外部反馈修正，比纯 CoT 幻觉少。
- 缺点：
  - 逐步串行决策，步数多时延迟高、token 消耗大（每步都要带上完整历史）。
  - 缺少全局规划，容易在局部打转、重复调用同一工具。
  - 上下文随步数增长，长任务容易超出窗口；前面的错误会累积。
- 现在多用原生 Function Calling 实现 ReAct 循环，不再依赖文本格式解析。

### 4. Plan-and-Execute 和 ReAct 有什么区别？各适合什么任务？
**答案：**
- Plan-and-Execute：先由规划器一次性生成完整的步骤列表，再由执行器逐步执行，出现偏差时重新规划。
- ReAct：边想边做，每步根据上一步结果决定下一步。
- Plan-and-Execute 适合步骤明确、可以提前拆解的任务（调研报告、数据处理流水线）；规划用强模型，执行可用便宜模型，步骤之间还能并行。
- ReAct 适合需要根据中间结果不断调整的探索型任务（排查问题、交互式查询）。
- 实践中常混合使用：先粗规划，每步内部用 ReAct 执行。

### 5. 【专家】Reflexion、Self-Refine 这类自我反思机制怎么实现？怎么避免无限反思？
**答案：**
- Self-Refine：同一个模型先生成结果，再按标准自我评价、给出修改意见，然后根据意见改写，循环迭代。
- Reflexion：任务失败后，让模型总结失败原因，生成"反思记忆"存起来，下次尝试时带上这段反思。
- 关键是评价信号要可靠：优先使用外部客观反馈（单测结果、工具报错、规则校验），只靠模型自评容易"自我感觉良好"。
- 避免无限反思：
  - 设置最大反思轮数（通常 2 到 3 轮）。
  - 评分达到阈值就停止；连续两轮没有改进也停止。
  - 设置 token 和时间预算。
- 注意收益递减：多数提升出现在第一轮修改。

### 6. 【高频】Workflow（固定编排）和自主 Agent 怎么选？什么时候该用哪种？
**答案：**
- 优先使用 Workflow：流程固定、需要稳定可控、对成本和延迟敏感、需要审计（如客服办理业务、线上生产任务）。
- 使用自主 Agent：任务开放、步骤无法提前确定、能容忍一定不确定性（如调研、编程、复杂排查）。
- 原则：能用简单方案解决就不用复杂方案；先用 Workflow 跑通，再在确实需要灵活性的节点引入 Agent。
- 常见形态：整体是 Workflow，个别节点是 Agent（如数字人对话 flow 中的检索、挂载节点固定，回复生成节点由模型决定）。

### 7. 【专家】如何设计一个"可控的自主性"：哪些步骤让模型决定，哪些步骤写死？
**答案：**
- 写死：涉及安全、权限、计费、合规的步骤；有明确业务规则的分支；必须执行的前置和后置步骤（鉴权、内容审核、打点）。
- 交给模型：自然语言理解、开放式生成、工具选择、参数抽取、多种策略之间的选择。
- 设计手段：
  - 限定动作空间：只暴露当前场景允许的工具。
  - 结构化输出：模型只输出决策，由程序执行。
  - 关键节点设置护栏和人工确认。
  - 设置步数、时间、成本上限。
- 逐步放权：先用规则控制，通过评估数据证明模型决策可靠后，再扩大模型的决策范围。

### 8. Agent 的任务分解（Task Decomposition）有哪些方法？
**答案：**
- 用 Prompt 让模型直接列出子任务（最常用）。
- 层次分解：大目标拆成子目标，子目标再拆成可执行的动作（HTN 思想）。
- 依赖图分解：输出带依赖关系的 DAG，没有依赖的子任务可以并行执行。
- 基于模板：对常见任务类型预置分解模板，模型只负责填参数，稳定性高。
- 交给子 Agent：主 Agent 只做分解和汇总，子任务分派给专门的子 Agent。
- 要点：子任务粒度要适中，每个子任务要有明确的完成标准。

### 9. 【高频】Agent 陷入死循环或反复调用同一工具怎么处理？
**答案：**
- 检测：记录每次调用的工具名和参数哈希；同一工具加相同参数连续出现 N 次即判定为循环；也可以检测相邻几轮的输出是否几乎相同。
- 干预：
  - 在上下文中提示模型"你已经调用过这个工具且结果相同，请换一种方法或直接给出结论"。
  - 临时屏蔽该工具。
  - 强制进入总结阶段。
- 预防：工具返回明确的错误信息和建议（而不是空结果）；限制最大步数；Prompt 中写明终止条件。
- 兜底：超过阈值后结束循环，返回已有的部分结果和说明，同时记录 trace 用于分析。

### 10. 【高频】Agent 最大步数怎么设置？超过后怎么收尾？
**答案：**
- 设置依据：统计线上正常任务的步数分布，取 P99 再留一些余量；简单问答类 Agent 一般 3 到 5 步，复杂任务 10 到 30 步。同时设置 token 预算和总耗时上限。
- 收尾方式：
  - 不直接报错，而是再调用一次模型，让它基于已有信息给出当前最好的答案，并说明哪些部分没完成。
  - 长任务可以保存当前状态，提示用户是否继续。
- 记录超限的 case，分析是任务本身太复杂还是 Agent 策略有问题。

### 11. Agent 执行到一半失败，如何做断点恢复？
**答案：**
- 每一步执行完就持久化状态：当前步骤、已完成步骤的结果、上下文、待执行计划（如 LangGraph 的 checkpoint）。
- 每一步要设计成幂等的，或者记录已执行的有副作用的操作，恢复时跳过已完成的部分，避免重复下单、重复发消息。
- 恢复时从最近的检查点加载状态，继续执行；外部依赖失败可以按策略重试。
- 对外部异步任务（如视频生成），记录任务 ID，恢复后查询状态，不重新提交。

### 12. 【专家】Agent 状态机怎么设计？run、step、tool_call 等状态如何流转？
**答案：**
- 层级：一次 run 包含多个 step，每个 step 可以是"消息生成"或"工具调用"，一个工具调用 step 可以包含多个 tool_call。
- run 状态：queued → in_progress → requires_action（等待客户端提交外部工具结果）→ in_progress → completed / failed / cancelled / expired。
- 流式事件：run_begin → tool_step_begin → tool_call_info / message 增量 → tool_step_end，循环多轮后 run_end。
- 设计要点：
  - 状态转移只能在少数明确的地方触发，并做合法性校验。
  - 取消（cancelling）要能在任意 step 中途生效。
  - 每个状态变化都推送事件并落库，方便前端渲染和问题排查。
  - 设置超时，防止长期卡在 requires_action。

### 13. OpenAI Assistants API 中 Assistant、Thread、Run、Step 分别是什么？
**答案：**
- Assistant：Agent 的配置，包括模型、指令、工具、知识库文件。
- Thread：一次会话，保存消息历史，由服务端管理上下文的截断。
- Run：在某个 Thread 上执行一次 Assistant，是一次异步任务，有自己的状态机。
- Step：Run 内部的执行步骤，分为消息生成和工具调用两类，可用于展示过程和排查问题。
- 价值：把会话管理、工具调用循环、知识检索托管到服务端，开发者不用自己写 Agent 循环。OpenAI 后来推出 Responses API 作为它的演进方向。

### 14. 【高频】LangChain 的核心抽象有哪些？你怎么评价它？
**答案：**
- 核心抽象：模型封装（LLM、ChatModel）、Prompt 模板、输出解析器、Chain（LCEL 管道）、Tool、Agent、Retriever、Memory、回调（Callback）。
- 优点：生态丰富，集成了大量模型、向量库和工具；适合快速做原型。
- 缺点：抽象层次多，调试和定制困难；版本迭代快，接口变化频繁；封装隐藏了实际发给模型的 Prompt，线上排查不便。
- 实践：原型阶段可以用；生产环境核心链路倾向于自己写薄封装，或者用 LangGraph 这类更底层、更可控的编排框架。

### 15. 【高频】LangGraph 和 LangChain 的区别是什么？StateGraph、节点、边、条件边怎么用？
**答案：**
- LangChain 偏向线性的链式组合；LangGraph 把 Agent 表示成有状态的图，支持循环、分支、持久化，更适合复杂 Agent。
- StateGraph：定义共享状态（State），每个节点读取状态并返回更新，用 reducer 规定怎么合并（如消息列表追加）。
- 节点：一个函数，如调用模型、执行工具。
- 边：固定的流转关系。条件边：根据状态决定下一个节点，如"模型返回了工具调用就去 tools 节点，否则结束"。
- 典型 ReAct 图：agent 节点 → 条件边 → tools 节点 → 回到 agent 节点。

### 16. 【专家】LangGraph 的 checkpoint 机制是什么？怎么实现人机协同（human-in-the-loop）中断和恢复？
**答案：**
- checkpoint：每个节点执行后，把整个图的状态按 thread_id 保存到 checkpointer（内存、SQLite、Postgres、Redis），支持断点恢复、查看历史状态、回到某个状态重新执行。
- 人机协同：
  - 在指定节点前后设置中断（interrupt_before / interrupt_after），或在节点内部调用 interrupt()。
  - 图执行到中断点时暂停并保存状态，把待确认的内容返回给前端。
  - 用户确认或修改后，带着同一个 thread_id 继续执行（如传入 Command(resume=...)）。
- 典型用途：调用高风险工具前人工审批、让用户修改 Agent 生成的计划。
- 生产注意：checkpointer 选持久化存储；状态里不要放过大的对象；设置过期清理。

### 17. AutoGPT、BabyAGI 这类早期 Agent 为什么在生产中很难用？
**答案：**
- 完全自主：没有约束，目标容易发散，经常陷入循环。
- 错误累积：长链路中每一步都有失败概率，整体成功率很低。
- 成本和延迟不可控：一个任务可能调用模型上百次。
- 难以评估和调试：行为不可预测，问题难以复现。
- 当时的模型规划能力和工具调用能力不足。
- 启示：生产中的 Agent 要限定场景、限定工具、限定步数，并结合 Workflow 增强可控性。

### 18. 【高频】你会自研 Agent 框架还是用开源框架？依据是什么？
**答案：**
- 考虑因素：
  - 定制化程度：业务需要深度控制执行流程、协议、打点时倾向自研。
  - 性能和语言栈：团队主力是 Go，而主流框架多是 Python。
  - 运维和稳定性：开源框架版本变动快，升级成本高。
  - 团队能力和交付时间。
- 常见做法：核心执行引擎、协议、状态管理自研（用 Go 实现算子化 flow）；Prompt 实验、离线评估、原型验证用开源框架（LangChain、LangGraph）。
- 自研也要借鉴开源框架的设计（状态图、checkpoint、工具抽象），不要重复造轮子。

### 19. 【专家】如何设计一个算子化（DAG/flow）的 Agent 执行引擎？算子之间怎么传递上下文？
**答案：**
- 算子：统一接口，如 `Run(ctx, state) error`，每个算子只做一件事（意图识别、检索、选择模型、组装 Prompt、调用模型、获取挂载组件、后处理）。
- 编排：用配置文件描述 DAG（节点、依赖、条件分支），引擎负责拓扑排序；没有依赖的节点并行执行；每个算子有独立的超时和降级策略。
- 上下文传递：使用共享的请求级状态对象（如 State 结构体或 map），算子读写约定好的字段；对并发写入加锁，或者让每个算子只写自己的命名空间。
- 可观测：每个算子自动打 span，记录耗时、输入输出摘要、错误；可以把 flow 配置自动生成流程图辅助排查。
- 扩展：新增能力只需注册新算子、修改配置，不改引擎代码。
- 可举例：数字人 flow 中新增 op_retrieve_script（获取视频脚本）和 op_mount（获取挂载组件）两个算子；后来去掉问一问商品卡时，只需在执行图中删掉 op_mount 节点。

### 20. Agent 的执行图用配置驱动还是代码驱动？各有什么优劣？
**答案：**
- 配置驱动：
  - 优点：修改流程不用发版，可以按场景复用算子，便于可视化，非开发人员也能调整。
  - 缺点：复杂逻辑表达困难，调试不直观，配置错误只能在运行时发现。
- 代码驱动：
  - 优点：表达能力强，有类型检查，便于测试和调试。
  - 缺点：每次修改都要发版，灵活性差。
- 实践：算子用代码实现，编排用配置；复杂分支逻辑封装成算子内部的代码；配置上线前做校验并支持灰度。

### 21. 【高频】Coding Agent（如 Claude Code、Cursor）的核心设计是什么？
**答案：**
- 工具集：读文件、搜索（grep、glob）、编辑（精确的字符串替换）、执行命令、运行测试，粒度小且可组合。
- 主循环：本质是带工具的 ReAct 循环，由模型自主决定读哪些文件、改哪里、怎么验证。
- 上下文管理：按需读取代码，不一次性加载整个仓库；用项目说明文件（如 CLAUDE.md）提供约定；上下文过长时自动压缩。
- 验证闭环：修改后运行测试或编译，根据报错继续修改。
- 安全：危险命令需要确认、权限分级、沙箱。
- 交互：计划模式、待办列表、子 Agent 处理独立的子任务。

### 22. 【专家】Claude Code 这类 Agent 的工具设计、上下文管理、子 Agent 机制有什么值得借鉴的地方？
**答案：**
- 工具设计：
  - 工具描述写得非常详细，包括什么时候用、什么时候不用、常见错误。
  - 编辑工具要求精确匹配原文，避免误改。
  - 工具返回结果有截断和分页，控制上下文膨胀。
- 上下文管理：
  - 大量使用搜索工具按需检索，而不是预先塞入全部内容。
  - 长对话自动压缩（compaction）。
  - 用待办列表维持长任务的目标，防止目标漂移。
- 子 Agent：
  - 把调研类、可并行的任务交给子 Agent，子 Agent 有独立的上下文，只把结论返回给主 Agent，避免中间过程污染主上下文。
  - 可以为子 Agent 限定工具集。
- 权限：按工具和命令前缀做授权，高风险操作需要确认。
- 借鉴到业务 Agent：工具描述要像写给新同事的文档；控制好上下文；隔离子任务。

### 23. Agent 中"路由（Router）"模式是什么？怎么实现意图路由？
**答案：**
- 路由模式：先对输入分类，再分发到不同的专门处理链路（不同的 Prompt、工具集、子 Agent 或模型）。
- 实现方式：
  - 规则（关键词、正则、指令前缀，如 cmd 快捷指令直接走确定的链路）。
  - 分类模型（快且便宜）。
  - 大模型分类（理解能力强，可以输出结构化路由结果）。
  - 向量相似度匹配到意图示例。
- 设计要点：设置"其他"类和兜底链路；低置信度时追问或走通用链路；监控各路由的分布和准确率。
- 收益：每条链路的 Prompt 更短、更专注，效果更好，成本更低。

### 24. 【高频】意图识别用大模型还是分类模型？怎么做混合方案？
**答案：**
- 大模型：冷启动快、能处理长尾和复杂语义、意图变化时只需改 Prompt；缺点是延迟高、成本高。
- 分类模型：几十毫秒、成本低、稳定；缺点是需要标注数据，新增意图要重新训练。
- 混合方案：
  - 第一层用规则处理确定性请求。
  - 第二层用分类模型处理高频意图，高置信度时直接使用结果。
  - 低置信度或长尾请求交给大模型。
  - 大模型的结果作为标注数据回流，定期重新训练分类模型。
- 用评测集分别评估各层的准确率和覆盖率，调整置信度阈值。

### 25. Agent 如何处理用户中途改变需求或打断？
**答案：**
- 每轮都根据最新输入重新判断意图，不要死守之前的计划。
- 新需求与当前任务冲突时，以最新指令为准；必要时向用户确认"是否放弃之前的任务"。
- 执行中的长任务要支持取消：收到打断信号后停止后续步骤；已执行的有副作用操作要告知用户。
- 流式输出场景：用户发送新消息时，取消正在进行的生成（通过 context 取消下游调用），节省成本。
- 状态管理：保留被中断任务的状态，用户想继续时可以恢复。

### 26. 【专家】实时语音/数字人 Agent 的对话打断（barge-in）怎么实现？
**答案：**
- 检测：用 VAD（语音活动检测）实时判断用户是否开口说话；为了区分有效打断和"嗯""对"这类附和或环境噪音，可以加时长阈值、能量阈值或语义判断。
- 执行：确认打断后立即停止 TTS 播放和数字人口型驱动，取消正在进行的 LLM 和 TTS 请求，清空待播放队列。
- 上下文：记录被打断时已经播放出去的那部分内容，只把已播放部分写入对话历史，避免模型以为用户听到了完整回复。
- 回声消除（AEC）：防止数字人自己的声音被识别为用户输入，误触发打断。
- 延迟：整条链路的打断响应要控制在几百毫秒以内，需要端侧和服务端配合。

### 27. Agent 回复中如何插入结构化组件（卡片、表单、按钮）？
**答案：**
- 协议设计：流式响应中除了文本事件，还定义组件事件，带上组件类型、组件数据（ui_data）和渲染位置，由前端按类型渲染。
- 生成方式：
  - 模型通过工具调用返回结构化数据，由服务端组装成组件。
  - 服务端根据意图、配置等规则在特定时机插入组件（如商业化挂载）。
  - 模型在文本中输出占位标记，服务端替换成组件。
- 要点：组件数据要做 schema 校验；前端无法识别的组件类型要有降级展示；组件交互（点击、提交）要能回传给 Agent 继续对话。

### 28. 【高频】Agent 如何在对话中挂载商业化组件（线索表单、商品卡）？召回时机怎么控制？
**答案：**
- 架构：对话服务在合适的节点调用挂载服务（如 agent-mount），根据 Agent 配置、组件类型、用户 query、会话状态返回要展示的组件数据，由前端渲染。
- 召回时机：
  - 规则触发：配置强干预规则，如指定 query 或指定轮次。
  - 模型判断：用大模型判断用户是否有商业意图（咨询价格、预约服务），可以通过提示词实验调优。
  - 快捷指令：用户点击按钮时走确定的 cmd 链路，直接返回组件。
- 体验控制：按 session 做频控，避免每轮都弹出表单；用户已提交表单后不再召回；对会员和非会员使用不同策略。
- 归因：组件数据中带上 sessionId、logId、messageId、contentId 等字段，用于衡量转化效果。
- 可举例：B 端线索工具分流为表单（system_leads）、电话加到店（system_order_service）、报价计算器和报价单（system_quotation），并做了关闭线索表单的提示词 AB 实验。

### 29. 多轮对话中，Agent 怎么判断任务是否已完成？
**答案：**
- 任务型：定义完成标准，如所有必填槽位已填写、工具执行成功、用户确认。
- 让模型判断：每轮输出结构化的任务状态（进行中、已完成、需要用户补充信息）。
- 用户信号：用户明确表示满意、结束对话，或者开始了新话题。
- 程序校验：对可验证的任务（如订单已创建）用外部状态确认，而不是只依赖模型的说法。
- 完成后：给出总结，提供后续选项（追问建议）。

### 30. Agent 的"追问澄清"策略怎么设计？
**答案：**
- 什么时候追问：缺少关键参数、存在歧义（多个可能的解释）、高风险操作需要确认。
- 什么时候不追问：可以合理推断的、用户画像或历史中已有的信息，直接使用默认值并告诉用户。
- 追问方式：一次只问最关键的问题；提供选项（按钮）降低用户输入成本；问题要具体。
- 控制：限制最大追问次数，超过后用最佳猜测执行，并说明所做的假设。
- 评估：对比追问后的任务成功率和用户流失率，找到平衡点。

### 31. 【专家】如何让 Agent 的行为可预测、可解释？
**答案：**
- 降低随机性：关键决策使用低温度、结构化输出；固定 Prompt 版本和模型版本。
- 限制行为空间：Workflow 加有限的工具集；明确规则写在代码中，不依赖模型判断。
- 可解释：
  - 让模型输出决策理由（reasoning 字段）。
  - 完整记录 trace：每步的输入、输出、工具调用、耗时。
  - 能够回放任意一次请求的执行过程。
- 回归测试：固定评测集，每次变更都运行回归，检测行为是否发生意外变化。
- 对用户：展示 Agent 正在做什么（"正在搜索……""正在查询订单……"），并在回答中标注依据和引用。

### 32. 什么是 Agentic RAG？和传统 RAG 有什么区别？
**答案：**
- 传统 RAG：固定流程，即检索一次、拼接上下文、生成答案，不管问题是否需要检索。
- Agentic RAG：由 Agent 决定是否检索、检索什么、去哪个知识源检索、检索结果是否足够；可以多轮检索、改写 query、调用多个工具交叉验证。
- 优点：能处理多跳问题、复杂问题，减少不必要的检索。
- 缺点：延迟和成本更高，行为不如传统 RAG 稳定。
- 选择：简单 FAQ 用传统 RAG；需要综合多个来源、多步推理的问题用 Agentic RAG。

### 33. Agent 中的"思考"内容要不要展示给用户？流式展示怎么做？
**答案：**
- 是否展示：
  - 展示的好处：减少等待焦虑，增加可信度，用户能看到推理依据。
  - 不展示的情况：思考内容可能包含不准确的中间推测、暴露内部策略，或者对普通用户来说过于冗长。
- 常见做法：默认折叠展示（"已思考 x 秒"，可以展开）；或者只展示过程状态（"正在搜索""正在分析"），不展示原文。
- 流式实现：定义不同的事件类型，如 reasoning 增量事件、tool 状态事件、answer 增量事件，前端分区渲染；思考结束时发送一个分隔事件。
- 安全：思考内容同样需要内容审核。

### 34. Deep Research 类 Agent 的架构是什么样的？
**答案：**
- 需求澄清：先确认研究范围、深度和输出形式。
- 规划：把研究问题拆成若干子问题，生成研究大纲。
- 迭代检索：针对每个子问题多轮搜索、阅读网页和文档、提取要点；根据发现补充新问题。可以由多个子 Agent 并行处理。
- 汇总：对信息去重、交叉验证，按大纲组织成报告，每个结论附上引用来源。
- 质检：检查覆盖度、引用是否真实、有无矛盾。
- 工程要点：运行时间长（几分钟到几十分钟），需要异步任务、进度推送和断点续跑。

### 35. 【专家】Deep Research 类 Agent 如何控制搜索轮次、去重和结果汇总？
**答案：**
- 轮次控制：
  - 设置总预算（搜索次数、token、时间）和每个子问题的上限。
  - 每轮结束让模型评估"信息是否足够回答该子问题"，足够就停止；连续几轮没有新信息也停止。
- 去重：
  - query 去重：新的搜索词和已搜索过的做语义相似度比较，太相似就跳过。
  - 结果去重：按 URL 归一化去重，再对内容做相似度去重。
- 汇总：
  - 每个子问题先单独总结成结构化笔记（结论加来源），避免把原文全部塞进最终上下文。
  - 最终报告基于笔记生成；不同来源结论冲突时，明确列出分歧。
  - 引用要和来源对应，并做抽样校验。

### 36. Browser/Computer Use Agent 的实现思路是什么？难点在哪？
**答案：**
- 实现：
  - 感知：截图（视觉模型理解）或 DOM、无障碍树（文本化，更省 token、定位更准）。
  - 动作：点击、输入、滚动、跳转，用 Playwright 等工具执行。
  - 循环：观察页面 → 决定动作 → 执行 → 再观察。
- 难点：
  - 页面元素定位不准、页面动态加载。
  - 弹窗、验证码、登录态。
  - 步骤多、耗时长，成功率低。
  - 安全风险：网页中可能藏有注入指令，误操作可能造成损失。
- 工程：在沙箱浏览器中运行；关键操作需要用户确认；能调用 API 的尽量调用 API，不操作界面。

### 37. Code Interpreter 的实现原理是什么？沙箱怎么做？
**答案：**
- 原理：模型生成代码（通常是 Python），由服务端在沙箱中执行，把标准输出、报错、生成的文件（图表、CSV）作为结果返回给模型；模型根据结果继续修改代码或给出答案。
- 会话保持：同一个会话复用同一个执行环境（如 Jupyter kernel），变量和文件在多次执行之间保留。
- 沙箱：
  - 容器或微虚拟机隔离。
  - 限制 CPU、内存、执行时间。
  - 禁止或限制网络访问。
  - 只读的基础镜像，加临时工作目录。
  - 会话结束后销毁环境。
- 文件：用户上传的文件挂载到工作目录（如 /mnt/data），生成的文件通过下载链接返回给用户。

### 38. 【高频】Agent 中的代码执行沙箱有哪些隔离方案（容器、gVisor、Firecracker、WASM）？
**答案：**
- 普通容器（Docker）：启动快、生态成熟，但和宿主机共享内核，隔离性最弱，运行不可信代码需要额外加固（seccomp、只读文件系统、非 root 用户、资源限制）。
- gVisor：在用户态实现一个内核，拦截系统调用，隔离性比普通容器强，有一定性能开销，部分系统调用不支持。
- Firecracker 微虚拟机：每个沙箱有独立内核，隔离性接近虚拟机，启动时间在百毫秒级，被 AWS Lambda 和很多代码执行服务采用。
- WASM：轻量、启动极快、默认没有系统访问权限，但对 Python 生态和原生扩展的支持有限。
- 选型：执行不可信代码时选择 Firecracker 或 gVisor；内部可信的场景可以用加固后的容器。

### 39. Agent 如何处理文件上传、文件解析（pdf、docx、pptx）？
**答案：**
- 上传：先校验类型和大小（白名单 MIME 类型加大小限制），存到对象存储（如 BOS），只把文件引用传给 Agent。
- 解析：
  - pdf：文本层直接提取，扫描件走 OCR，复杂版面需要版面分析。
  - docx：解析 XML 结构，保留标题层级和表格。
  - pptx：提取每页文字，或者转成图片后让多模态模型理解。
- 解析结果转成 markdown，长文档切块后走 RAG，短文档直接放入上下文。
- 工程：文件转换服务（如用 LibreOffice 转换格式）要部署在隔离的容器中，注意运行用户的权限、超时和并发控制。
- 可举例：agent-tools-pandoc 服务中 LibreOffice 在容器内执行失败，根因是运行用户权限和环境变量，重写 Dockerfile 后修复，之后新增了 pptx 转图片能力。

### 40. 【专家】Agent 的多模型策略怎么设计：哪些步骤用大模型，哪些用小模型？
**答案：**
- 小模型或规则：意图分类、路由、query 改写、参数抽取、追问生成、内容审核、格式转换这类窄任务、高频任务。
- 大模型：复杂规划、多步推理、最终答案生成、对质量要求高的场景。
- 推理模型：难度高的规划和决策环节，不用于实时对话。
- 动态路由：按问题难度、用户等级、成本预算选择模型；大模型不可用时降级到备用模型。
- 评估：每次替换都要在评测集上对比效果，计算成本和延迟收益。
- 配置化：模型选择放在配置中心集中管理，按场景配置（如数字人默认模型、引导话术模型统一在配置中管理）。

### 41. 模型调用失败时怎么做降级（换模型、换策略、返回兜底文案）？
**答案：**
- 区分错误类型：
  - 超时、限流（429）、5xx：可以重试（带退避），或切换到备用模型或供应商。
  - 参数错误、内容审核拦截：不能重试，要修正请求或返回提示。
- 降级层级：
  1. 同模型重试。
  2. 切换同等能力的备用模型。
  3. 切换更小、更快的模型。
  4. 简化策略（不再检索、不调用工具，直接回答）。
  5. 返回兜底文案或缓存的答案。
- 熔断：某个模型连续失败时短期内不再调用它，避免拖慢所有请求。
- 流式请求：已经输出了部分内容时，不要无感知地切换模型重新生成，要明确提示用户或从头生成。

### 42. 【高频】GPTs / 智能体平台（如文心智能体、Coze）的整体架构是什么样的？
**答案：**
- 创作端（B 端）：开发者通过表单或对话方式配置智能体，包括人设 Prompt、开场白、知识库、插件和工作流、模型选择、商业化组件；有预览调试和发布审核流程。
- 配置存储：智能体配置存入数据库，按版本管理，区分草稿、预览、线上。
- 运行时（C 端）：
  - 对话服务读取配置，组装 Prompt，执行 Agent 循环（检索、调用插件、生成）。
  - 记录对话历史，流式返回结果。
  - 挂载服务按配置返回卡片和组件。
- 分发：搜索、首页推荐、智能体广场、"最近使用"入口。
- 支撑能力：内容审核、打点日志和数据分析、评估平台、计费。

### 43. 低代码智能体平台中，用户配置（人设、知识库、插件）如何转成运行时的 Agent？
**答案：**
- 配置编译：发布时把配置转成运行时结构，包括渲染后的 System Prompt、工具定义列表、知识库 ID 列表、模型参数、挂载组件配置。
- 运行时加载：按 app_id 读取配置（使用缓存）；根据配置决定 flow 中启用哪些算子，例如挂载了知识库才执行检索算子，配置了插件才把插件注册为工具。
- 版本隔离：预览环境读草稿配置，线上读已发布版本，互不影响。
- 一致性：配置还会同步到下游系统（如千帆 Assistant），要处理同步失败和数据不一致。
- 可举例：智能体更新时千帆侧返回"Assistant 不存在"（错误码 5002），在保存接口中识别该错误码，自动重建 Assistant，修复了约 240 个智能体跳转下线页的问题。

### 44. 【专家】智能体平台如何同时支持上万个不同配置的 Agent？配置怎么加载和缓存？
**答案：**
- 无状态运行时：Agent 不是常驻进程，而是"配置加通用执行引擎"，每个请求按 app_id 加载配置后执行，所以 Agent 的数量不影响服务实例数。
- 多级缓存：
  - 进程内本地缓存（LRU 加短 TTL）缓存热门 Agent 的配置。
  - Redis 作为第二级缓存。
  - 数据库作为数据源。
  - 配置变更时通过消息通知各实例主动失效缓存。
- 批量加载：一个 Agent 的配置可能分散在多张表中（基础信息、挂载组件、插件），要批量查询，避免 N+1，也避免一个挂载项起一个协程查库。
- 热点和长尾：热门 Agent 常驻缓存；长尾 Agent 按需加载；缓存未命中时用 singleflight 防止并发回源打爆数据库。
- 可举例：agent-mount 前置数据获取改成 WHERE IN 批量查询后，平均耗时从 3.124s 降到 98ms，协程数减少 30%。

### 45. Agent 的"人设"一致性怎么保证？
**答案：**
- Prompt：人设描述具体化，包括身份、性格、说话风格、口头禅、知识边界、禁忌；给出示例对话。
- 上下文：长对话中人设容易被稀释，可以在每轮或定期重申关键人设；对话历史压缩时保留人设相关信息。
- 防越狱：用户诱导 Agent 脱离人设时，按人设的方式拒绝。
- 评估：构造人设一致性评测集，用 LLM-as-a-Judge 打分。
- 数字人场景：人设还需要和形象、声音、动作表情保持一致。

### 46. 【高频】Agent 和传统规则对话系统（任务型对话、槽位填充）怎么结合？
**答案：**
- 任务型对话的优点是流程可控、结果准确；缺点是开发成本高、难以处理意外的输入。
- 结合方式：
  - 大模型负责自然语言理解（意图识别、槽位抽取），由状态机管理流程和槽位状态，确定性的业务逻辑（下单、查询）用代码执行。
  - 大模型负责回复生成，让话术更自然。
  - 遇到流程外的问题（闲聊、未知问题）交给大模型兜底，回答后引导回主流程。
- 适用场景：订票、预约、表单收集，这类必须保证结果正确的业务流程。

### 47. Agent 如何根据用户画像做个性化回复？
**答案：**
- 数据来源：用户主动设置的偏好、历史对话中抽取的事实、行为数据（最近使用过的 Agent、点击记录）。
- 注入方式：把与当前问题相关的画像片段放入上下文，而不是全部塞入；画像放在动态部分，不影响前缀缓存。
- 个性化的方向：回复风格、推荐内容、默认参数（如城市、语言）。
- 隐私：画像的使用要符合授权范围；用户可以查看和删除；敏感属性不用于个性化。
- 评估：通过 AB 实验验证个性化带来的收益。

### 48. 【专家】Agent 的定时任务、主动触达（proactive agent）怎么设计？
**答案：**
- 触发源：定时（cron）、事件（数据变化、外部 webhook）、条件满足（价格降到阈值）。
- 架构：
  - 任务注册表：保存用户创建的任务，包括触发条件、执行内容、通知渠道。
  - 调度器：分布式定时调度，用分布式锁或分片保证不重复执行。
  - 执行器：以异步任务方式运行 Agent。
  - 通知服务：推送到 App、消息、邮件。
- 关键问题：
  - 幂等，防止重复触达。
  - 频控和免打扰时段，避免骚扰用户。
  - 失败重试和告警。
  - 成本控制，限制每个用户的任务数量。
  - 用户可以随时暂停和取消。
- 用户在对话中设置提醒时，Agent 只负责解析成结构化的任务，执行交给调度系统。

### 49. 你认为当前 Agent 落地最大的瓶颈是什么？
**答案：**
- 可靠性：多步任务中每一步都有出错概率，端到端成功率难以达到生产要求；行为不稳定，难以保证效果。
- 评估难：开放式任务缺少客观指标，难以量化"效果是否变好了"，迭代缺少依据。
- 成本和延迟：多轮模型调用带来高成本和高延迟，实时交互场景（语音、数字人）尤其明显。
- 安全和权限：Agent 拥有工具权限后，注入、越权、误操作的风险增大。
- 业务集成：现有系统的接口、数据权限、流程改造成本高。
- 应对：限定场景、Workflow 与 Agent 结合、建设评测体系、分步放权。

### 50. 【专家】如果让你从零设计公司级的 Agent 平台，你会怎么分层？核心模块有哪些？
**答案：**
- 接入层：API 网关、鉴权（AK/SK、用户态）、限流、多渠道接入（App、Web、API、SDK、语音）、流式协议（SSE、WebSocket）。
- 编排运行时：Agent 执行引擎（算子化 DAG 加 ReAct 循环）、状态管理和 checkpoint、会话管理、上下文管理（历史压缩、记忆检索）。
- 能力层：
  - 模型网关：多模型路由、降级、计费、缓存。
  - 工具和插件中心：注册、鉴权、MCP 接入。
  - 知识库：RAG 的解析、索引和检索。
  - 记忆服务。
  - 挂载和组件服务（商业化）。
- 配置层：Agent 配置、Prompt 模板版本管理、灰度和 AB 实验平台。
- 数据和评估层：打点日志、trace、数仓、评测集管理、自动评估、人工质检、badcase 闭环。
- 治理层：内容安全、权限、审计、配额和成本管理、数据生命周期（冷备、归档、删除）。
- 设计原则：运行时无状态、可水平扩展；配置与代码分离；每层都可观测；按租户隔离；核心链路有降级预案。
