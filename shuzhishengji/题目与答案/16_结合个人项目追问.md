## 智能体平台

### 1. agent-mount 优化从 3s 降到 98ms，瓶颈到底在哪？只是查库次数多吗？
**答案：**
- 瓶颈主要在前置获取 mount data 的方式：原来按每个挂载项起一个协程，分别查 MySQL 的 uimeta 和 uidata。挂载项一多，查库次数、协程数量和内存分配都随之线性增长。
- 不只是查库次数多，还连带了三个问题：
  - 协程数多：优化前 229 个，优化后 160 个，减少 30.1%。
  - 内存分配多：allocs 和 heap 对象都从 359 降到 185，减少 48.5%，GC 压力随之下降。
  - 并发查库在数据库连接池上排队，长尾延迟被放大。
- 改法：收集 ID 后用 `WHERE IN` 一次批量查询，再在内存中组装。
- 结果：AgentMount 平均耗时从 3.124s 降到 98.43ms。hey 压测（`-n 100 -c 10`）的平均耗时从 3.23s 降到 0.197s，Requests/sec 从 3.09 提到 50.6。
- 测试条件：用一个手动挂载了 100 个商品的智能体压测。线上手动挂载商品的智能体有 238,645 个，其中挂载数 ≥20 的有 3,331 个。

### 2. 改成 `WHERE IN` 批量查询后，挂载项特别多（上千个）时会不会有新问题？
**答案：**
- 会有，主要是三个风险：
  - SQL 过长，解析开销增加，还可能触碰 max_allowed_packet 的限制。
  - IN 列表超过 eq_range_index_dive_limit（默认 200）后，优化器改用统计信息估算行数，可能选错执行计划。
  - 一次返回的数据量大，单次查询耗时和内存占用都会上升。
- 现状：线上挂载数 ≥20 的智能体有 3,331 个，上千个挂载项属于极少数。
- 【文档未记录，需本人确认】当前代码有没有对 IN 列表做分批上限。
- 【可补充的改进思路】
  - IN 列表按固定大小分批（如每批 500 个），批次之间可以有限并发。
  - 对挂载数据做缓存（Agent 维度的本地缓存加 Redis），配置变更时主动失效。
  - 运营侧限制单个 Agent 的最大挂载数量。
  - 压测极端用例（如 1000 个挂载项），用数据确认上限。

### 3. 优化后协程数只降了 30%，剩下的协程是什么？还能再降吗？

- 判断：剩余的协程是正常开销，不随挂载数增长，所以不是瓶颈，继续压缩的收益不大。

### 4. 为什么用双接口加提前 return 灰度，而不是用配置开关？
**答案：**
- 文档中的做法：
  - 接口分 v1 和 v2，新逻辑默认走 v1，老逻辑保留在 v2。
  - 在获取 mountdata 的位置先提前 return，代码分两半上线；验证通过后再去掉 return，正式生效。
- 这么做的考虑：
  - 新老两套逻辑同时存在于线上，可以用同一批请求分别调用 v1 和 v2，逐一对比返回数据，覆盖了全部 10 类挂载组件。
  - 代码先上线、逻辑后生效，降低了一次发布的变更量。
  - 发现问题可以直接切回老接口。
- 和配置开关的比较：配置开关能做到不发版就切换，回滚更快，粒度也可以更细（按 Agent 或流量比例）。

### 10. 704 必须先上线，如果 704 上线后出问题回滚，其他服务会怎样？

## 数字人

### 13. 「最近使用」接口为什么选 Redis ZSET 加 MySQL 双写？只用 MySQL 行不行？
**答案：**
- 方案回顾：
  - 646 在 `/bot/conversation` 记录 QA 对时，通过 bigpipe（ai-agent-last-use）写出。
  - 697 ai-agent-cserver 订阅后双写 Redis 和 MySQL。
  - Redis 使用 ZSET `user:digital_human_recent_agents:{uid}`（member 为 appId，score 为时间戳），详情放在单独的 String 中。
  - MySQL 表为 `digital_human_recent_agents`。
- 为什么用 ZSET：天然按时间排序和去重，同一个数字人再次使用时只需更新分数；取最近 N 条是 O(log N)，首屏读取非常快。
- 为什么还要 MySQL：
  - Redis 只缓存 16 条，翻页需要更多的历史数据。
  - 需要持久化保存 12 个月，Redis 中的数据丢失后可以恢复。
- 只用 MySQL 行不行：从容量上看可以。预估 QPS 峰值约 5、耗时 150ms，按 uid 加时间建索引完全能支撑。
- 用 Redis 的理由：这个接口用于 CNY 活动的精选 Tab 和广场页"我聊过的"，首屏的访问量和延迟要求更高，用 Redis 承接首屏可以降低数据库压力。
- 【文档未记录，需本人确认】当时有没有评估过只用 MySQL 的方案，以及最终选择 Redis 的理由。如果被追问，可以坦诚地说按当时的 QPS，单用 MySQL 也能满足，Redis 主要是为活动的流量峰值和首屏延迟留出余量。

- 【文档未记录，需本人确认】
  - 双写的顺序是先写 Redis 还是先写 MySQL。
  - 写失败时消息是否会重新投递，是否有重试和告警。

  - 定期抽样对比两边的数据并修复。
  - Redis 写入使用 `ZADD GT`，防止乱序时旧消息覆盖新数据。

### 15. 为什么只缓存最近 16 条？这个数是怎么定的？
**答案：**
- 文档中的依据：缓存只存 16 条，当前的分页大小是每页 15 条。16 条可以完整覆盖首屏的 15 条，多出的 1 条用来判断是否还有下一页（hasMore）。
- 容量：一条 ZSET 数据约 0.2KB，每个 uid 最多 0.2 × 16 = 3.2KB。按单日峰值 30 万 PV 估算，Redis 约 0.9GB，可以接受。
- 首屏之后的数据走 MySQL 查询，所以 Redis 不需要保存更多。

### 18. 交叉质检分数按分档合并，为什么不直接取平均？
**答案：**
- 规则：分数划分为四个档位，[0,0.8)、[0.8,1.5)、[1.5,2.5)、[2.5,3]。两个质检员的分数在同一档时取均值，不在同一档时取较低分。
- 为什么不直接取平均：
  - 两个人分歧很大时（如一个给 0.5 分、一个给 2.8 分），平均值落在中间的"合格"区间，会掩盖其中一个人发现的严重问题。
  - 质检的目的是不放过问题，所以采取保守策略：分歧大时以较低的分数为准，宁可误判为不合格，再由人工复核。
  - 分数接近时，取均值能平滑个人打分的误差。
- 合格判定：final_score 是 6 个维度均分的算术平均。final_score 或多模态均分低于 0.8、声音均分低于 0.75，或者形象、表情、动作、背景任一维度均分低于 1.0，就判定为不合格。
- 管理员抽检可以覆盖 final_score，作为最终的兜底。
- 【可补充的改进思路】统计两个质检员之间的一致率；分歧特别大的 case 自动交给第三人复核；用这些数据培训质检员。

### 25. 15GB 文件上传，为什么并发 18 比并发 12 还慢？

### 28. 删除后为什么还要单独做表空间释放？释放时对线上有什么影响？
**答案：**
- 原因：InnoDB 删除数据只是把记录标记为删除，空间留在数据页中供以后复用，不会还给操作系统，表文件不会变小。云数据库（GaiaDB）的存储按使用量计费，不释放表空间，存储占用和成本都不会下降。
- 做法：2026-05-07 做了表空间释放，并再次清理了厂内的对话历史。
- 对线上的影响（通用原理）：
  - 释放空间要重建表（OPTIMIZE TABLE，或 ALTER TABLE ... ENGINE=InnoDB），需要拷贝全表数据，IO 和 CPU 的消耗很大，会影响其他查询。
  - 需要额外的磁盘空间。
  - 开始和结束时需要获取 MDL 锁，如果有长事务，可能会阻塞。
  - 会导致主从延迟。
- 应对：在低峰期执行，分表逐个执行，执行前检查有没有长事务，通过 DMS 执行并和 DBA 确认，同时监控延迟和业务指标。
- 【文档未记录，需本人确认】具体使用的释放方式、执行时长，以及释放了多少空间。文档没有记录最终释放的容量，被问到时要以实际数据为准。

### 30. 如果让你重新设计你负责过的某个系统，你会改什么？
**答案：**
- 建议选一个系统，诚实地讲出问题和改进，这能体现你的反思能力。参考：
- 以端到端评估和形象包生产平台为例：
  - 问题一，任务状态的健壮性：Worker 先改状态再处理，进程崩溃后任务可能卡在"生产中"。重新设计时，会统一采用"带心跳或超时的任务领取，加上 reconcile 巡检"的模式，并把 case 维度的状态做到幂等，可以断点续跑。
  - 问题二，业务规则分散：比如云渲染大类的映射有三处需要同步修改。会把这类规则收敛成一处，并用表驱动的测试兜底。
  - 问题三，状态复用的可读性：长底板复用了 status 枚举，读取时必须先判断类型。会把展示映射集中管理，或者在设计初期就把"类型"和"阶段"拆成正交的两个维度。
- 以 agent-mount 为例：一开始就会按批量查询加缓存来设计数据获取，并对 IN 列表设置分批上限，而不是按挂载项起协程。
- 回答的结构：当时的约束（工期、需求不确定）→ 现在看到的问题和证据 → 改进方案 → 预期收益。不要否定当时的决策，而是说明随着认识加深，会怎么做得更好。
