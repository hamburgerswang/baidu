# 15 场景设计与综合（35 题）（题目与答案）

## Agent 场景设计

### 1. 【高频】设计一个支持千万日活的智能客服 Agent 系统。
**答案：**
- 需求和量级：千万日活，人均 3 次对话，每天约 3000 万次对话；峰值 QPS 按平均值的 5 到 10 倍估算，大约是几千。目标是首 token 延迟 1 秒以内、问题自助解决率高、能够转人工、成本可控。
- 架构：
  - 接入层：多渠道（App、Web、小程序、电话），网关负责鉴权、限流，SSE 流式输出。
  - 对话服务（无状态，可以水平扩展）：会话管理、意图路由。
  - 处理链路：FAQ 精确匹配 → RAG 知识库问答 → 任务型流程（查订单、退款，通过工具调用业务系统）→ 转人工。
  - 支撑：模型网关（多模型、降级）、知识库平台、工单和人工坐席系统、评估平台。
- 关键难点和方案：
  - 成本：大部分高频问题用 FAQ 和缓存解决，路由和改写用小模型，只有复杂问题才使用大模型；用好 Prompt 缓存。
  - 准确性：业务数据一律通过工具实时查询；回答带引用；低置信度时追问或转人工。
  - 业务办理的安全：涉及操作的工具使用用户的身份和权限；高风险操作需要确认；幂等。
  - 多轮对话：会话状态存储在外部（Redis），槽位填充的状态结构化保存。
  - 稳定性：模型故障时降级为 FAQ 加转人工；限流排队；有完整的降级预案。
- 运营闭环：满意度和转人工率的监控，badcase 收集，知识库缺口分析，AB 实验。

### 2. 【高频】设计一个企业内部知识问答助手（支持权限、引用、更新）。
**答案：**
- 需求：接入 Wiki、文档、工单等多种数据源；回答准确并且带出处；员工只能看到自己有权限的内容；文档更新后能及时生效。
- 架构：
  - 数据接入：各数据源的连接器，按事件驱动增量同步，同时定期全量校对；同步文档的权限信息（ACL）。
  - 处理流水线：解析（不同格式分别处理，包括 OCR 和表格）→ 结构化切分（父子 chunk，附带标题路径）→ embedding → 写入向量库和全文索引，每个 chunk 带上权限元数据和版本号。
  - 问答链路：query 改写 → 混合检索（服务端根据员工身份强制注入权限过滤条件）→ rerank → 生成答案并标注引用 → 校验引用。
- 难点和方案：
  - 权限：在检索阶段就按权限前过滤，不能依赖 Prompt；权限变化时及时同步。
  - 引用的真实性：chunk 编号和原文链接一一对应，可以跳转定位到原文段落；做引用校验。
  - 更新：基于内容哈希做增量更新；删除的文档同步删除对应的 chunk；查询时只检索最新版本。
  - 效果：建立评测集，按环节排查 badcase（召回、排序、生成），持续优化。
- 可扩展：Agentic RAG（多轮检索、跨数据源）、结构化数据查询（Text2SQL）、对话中直接创建工单。

### 3. 【专家】设计一个 Coding Agent，能读代码库、改代码、跑测试。
**答案：**
- 核心循环：基于工具的 ReAct 循环，由模型自主决定读取哪些文件、修改哪里、怎么验证。
- 工具设计（粒度小、可以组合、描述详细）：
  - 搜索：glob 按文件名查找、grep 按内容查找、符号或语义检索。
  - 读取文件：支持按行范围读取。
  - 编辑：精确的字符串替换，要求原文唯一匹配，避免误改。
  - 执行命令：编译、测试、lint。
  - 版本控制：查看 git diff、状态。
- 上下文管理：
  - 不一次性加载整个代码库，按需检索读取。
  - 用项目说明文件提供约定（构建方式、目录结构、代码规范）。
  - 长任务自动压缩上下文；用待办列表维持目标。
  - 调研类的子任务交给子 Agent，只回传结论。
- 验证闭环：修改代码后运行测试或编译，失败就把报错信息返回给模型继续修改；设置最大轮数。
- 安全：
  - 在沙箱或容器中执行命令。
  - 危险命令（删除、强制推送、修改权限）需要用户确认。
  - 网络访问受限，密钥隔离。
  - 所有修改可以回滚（基于 git）。
- 评估：用 SWE-bench 风格的评测集（真实的问题加上隐藏的测试），统计通过率、步数、成本。
- 可引用：用 LangGraph 实现 Claude Code 核心设计的调研。

### 4. 设计一个能自动写周报的 Agent（数据来源：代码提交、文档、日程）。
**答案：**
- 数据采集（通过工具或 MCP 接入）：
  - 代码平台：本周的 commit、CR、合入记录、代码变更行数。
  - 文档平台：新建和编辑过的文档（如知识库中的迭代文档）。
  - 项目管理：卡片的状态变化（完成了哪些需求和 bug）。
  - 日程：参加的评审和会议。
- 处理流程：
  1. 按时间范围拉取数据，去重。
  2. 按项目或需求聚类（用卡片号、仓库、文档目录关联）。
  3. 让模型针对每个项目总结出"做了什么、进度、结果"。
  4. 按周报模板生成（本周完成、进行中、下周计划、风险）。
- 要点：
  - 只写有数据依据的内容，不编造进展；指标和链接直接引用原始数据。
  - 生成后由用户确认和修改再发布，不自动发送。
  - 权限：只读取本人有权限的数据。
- 扩展：每周定时触发，生成草稿后通知用户；用历史周报学习用户的写作风格。
- 可引用：这次整理迭代目录生成工作总结，就是同样的思路。

### 5. 【专家】设计一个 Deep Research Agent，输出带引用的研究报告。
**答案：**
- 流程：
  1. 需求澄清：确认研究的范围、深度、读者、输出格式。
  2. 规划：生成研究大纲，拆分成若干子问题。
  3. 并行调研：多个子 Agent 分别负责子问题，循环执行"搜索 → 筛选 → 阅读 → 提取要点 → 发现新的问题"。
  4. 汇总：交叉验证信息，处理不同来源之间的冲突。
  5. 撰写：按大纲写报告，每个结论都附上引用。
  6. 质检：检查引用的真实性、内容的覆盖度、是否有矛盾。
- 关键设计：
  - 预算控制：总的搜索次数、token 数和时间上限；每个子问题判断"信息是否足够"，足够就停止，连续几轮没有新信息也停止。
  - 去重：query 语义去重、URL 归一化、内容去重。
  - 笔记机制：每个来源先提炼成结构化的笔记（结论、原文摘录、链接），最终报告基于笔记撰写，避免把所有原文都塞进上下文。
  - 引用：引用编号和来源列表对应；抽样校验引用的内容是否真的支持结论。
  - 来源质量：优先选择权威来源，标注信息的时效性。
- 工程：作为异步长任务运行（几分钟到几十分钟），推送进度，支持断点续跑，结果可以导出。
- 评估：报告的质量（人工或 LLM 按维度打分）、引用的准确率、成本和耗时。

### 6. 设计一个电商导购 Agent，能推荐商品并挂载商品卡片。
**答案：**
- 能力：理解购物需求（预算、用途、偏好）、追问澄清、检索和推荐商品、比较商品、在对话中挂载商品卡片（价格、图片、购买链接）、引导下单。
- 架构：
  - 意图和槽位：品类、预算、品牌偏好、场景，多轮对话中逐步收集。
  - 商品检索工具：结构化过滤（品类、价格区间、库存）加语义检索（描述、评价），再结合推荐模型排序。
  - 模型：根据检索到的结果组织推荐理由和比较，不编造参数和价格（价格和库存实时查询）。
  - 挂载服务：根据推荐出的商品 ID 生成商品卡片的 ui_data，以组件事件的形式流式插入到回复中。
- 关键点：
  - 商业化的平衡：相关性优先，不能为了商业化强行推荐。
  - 卡片的频率控制，避免每轮都出现。
  - 归因：卡片的曝光、点击、转化，都要带上 session_id、message_id、商品 ID，用于计算效果。
  - 实时性：价格和库存以接口返回为准，缓存的时间要短。
- 可引用：智能体挂载商品卡、问一问商品卡（component_id=4）、agent-mount 的商品自动挂载等组件。

### 7. 【高频】设计一个实时语音交互的数字人 Agent，端到端延迟控制在 1 秒内。
**答案：**
- 链路：客户端采集音频 → RTC 或 WebSocket 上行 → VAD 和流式 ASR → 对话 Agent（大模型）→ 流式 TTS → 数字人驱动（口型、表情、动作）→ 渲染（云端渲染推流，或者在端上渲染）→ 播放。
- 延迟预算（目标是用户说完话后约 1 秒内开始响应）：
  - 端点检测：一两百到几百毫秒。
  - ASR 最终结果：一两百毫秒。
  - LLM 生成首句：两三百到几百毫秒。
  - TTS 首包：一两百毫秒。
  - 驱动渲染和网络传输：一两百毫秒。
- 关键手段：
  - 全链路流式，各环节重叠执行：ASR 的中间结果稳定时就提前启动 LLM 推理；LLM 输出首个短句后立即开始 TTS；TTS 的首包一出来就开始驱动和播放。
  - 模型侧：精简 Prompt，命中前缀缓存，选择低延迟的模型，减少前置的串行步骤（检索可以并行或者省略）。
  - 打断：VAD 检测到用户开始说话时，立即停止播放和生成，只把已经播放的内容写入对话历史。
  - 部署：服务就近部署，连接预热，数字人实例提前预热好资源池。
- 监控：分段统计各环节的耗时（P50、P99），定位瓶颈。
- 可引用：实时互动数字人平台、agent-proxy 互动超低延迟的调研、数字人首 token 慢的排查（修复了消息序列错误）。

### 8. 【专家】设计一个支持上万个第三方开发者的智能体开放平台。
**答案：**
- 开发者侧：
  - 智能体创建：人设、开场白、知识库、插件和工作流、模型选择、商业化组件。
  - 预览调试、发布审核、版本管理、数据分析看板。
  - API 或 SDK 接入（AK/SK 鉴权、配额）。
- 运行时：
  - 无状态的通用执行引擎，按 app_id 加载配置（多级缓存，配置变更时主动失效）。
  - 插件和工具网关：第三方接口的限流、超时、熔断、域名白名单。
  - 知识库服务：多租户隔离。
- 分发：搜索、广场、推荐、"最近使用"。分发前要校验智能体的状态（已下线、私有的不能分发）。
- 治理：
  - 内容安全：智能体配置审核、输入输出审核、违规时下线。
  - 多租户：配额、隔离、按开发者计费。
  - 质量：成功率、满意度的监控，低质量的智能体降低权重。
- 数据：对话打点（配置维度和运行时维度），提供给开发者和运营使用；对话数据要有生命周期管理（冷备、删除）。
- 难点：配置同步到下游系统时的一致性（如千帆 Assistant 不存在时的自愈）；大量长尾智能体的冷启动和缓存；第三方插件的稳定性和安全。
- 可引用：文心智能体平台相关的工作，如 240 个智能体跳转下线页的修复、数据捞取能力的升级、对话数据冷备。

### 9. 设计一个 Agent 评测平台，支持数据集管理、自动评测、人工质检。
**答案：**
- 数据集：上传（Excel 或文件，存到 BOS）、通过输入 query 构建、从线上日志抽样、版本管理、分类标签。
- 评测任务：选择数据集和被测对象（Agent 版本、Prompt、模型、形象包），创建异步任务。由 Worker 轮询执行：防止重复处理、单条失败自动重试、记录重试信息、统计失败数。
- 评估方式：
  - 规则评估：格式、关键词、工具调用是否正确。
  - LLM-as-a-Judge：按维度打分并给出理由，交换顺序以消除位置偏差。
  - 人工质检：轮询或交叉分配任务、多维度打分表单、分档合并分数、管理员抽检并覆盖分数。
  - 机器质检回调。
- 结果：按指标和维度汇总，版本之间对比，查看 badcase 明细，导出；达标后标记为可交付或可上线。
- 权限：外部质检员（众测）、PM、超级管理员，各自能看到和操作的内容不同。
- 通知：任务完成或失败时发送群通知。
- 可引用：端到端视频评估平台（Pipeline 二期），包括 4 张表、17 个指标、6 个维度、交叉质检、管理员抽检和 VideoProduceWorker。

### 10. 设计一个数据分析 Agent（自然语言查数据库、出图表）。
**答案：**
- 流程：
  1. 理解问题（指标、维度、时间范围、过滤条件）。
  2. 选择数据源：优先使用语义层或指标层，其次才是直接查表。
  3. 生成 SQL：基于裁剪后的 schema 和相似问题的示例。
  4. 校验并执行：只读账号，只允许 SELECT，强制加 LIMIT，设置超时。
  5. 检查结果是否合理。
  6. 生成结论和图表：模型生成图表配置（如 ECharts 的 JSON），或者在沙箱中执行 Python 代码画图。
  7. 回答中给出使用的口径和 SQL，方便用户核对。
- 关键点：
  - 口径一致：常用的指标（如 DAU、转化率）由语义层预先定义好，模型只负责选择指标和维度，避免每次都现场写复杂的口径。
  - 权限：行级和列级的权限控制，敏感字段脱敏。
  - 准确性：执行出错时自动修正；结果为空或异常时追问用户；用评测集统计 SQL 的准确率。
  - 性能：大表查询要走数仓（如 Spark 或 Doris），异步执行，缓存结果。
- 可引用：为运营提供的自助捞数 SQL 模板（基于数仓的宽表和 get_json_object），可以作为 Agent 的示例库。

### 11. 【专家】设计一个 Agent 任务调度平台，支持长任务、断点续跑、人工审批。
**答案：**
- 数据模型：
  - 任务表：类型、参数、状态、当前步骤、优先级、所有者。
  - 步骤和检查点表：每一步的输入、输出、状态、重试次数、外部任务 ID。
  - 审批表：待审批的操作、审批人、审批结果。
  - 事件和日志表。
- 执行：
  - 调度器按优先级和配额分发任务；Worker 抢占任务时用条件更新，防止重复执行。
  - 每完成一步就持久化检查点（参考 LangGraph 的 checkpoint 机制）。
  - 有副作用的步骤要幂等（使用幂等键）。
- 断点续跑：Worker 崩溃或任务超时后，其他 Worker 从最近的检查点继续执行；外部的异步步骤通过任务 ID 查询状态，而不是重新提交。
- 人工审批：执行到需要审批的节点时，任务进入"等待审批"状态并通知审批人；审批通过后继续执行，驳回则终止或回退；设置审批的超时时间。
- 状态推进：事件驱动（回调、审批结果），加上定时巡检兜底（reconcile），修复卡住的任务。
- 可观测：任务的时间线、各步骤的耗时和成功率、积压量、告警。
- 控制：取消、暂停、恢复、重试某一步、按租户设置配额和成本上限。

### 12. 设计一个多模态内容生产流水线（文案 → 配音 → 视频）。
**答案：**
- 流程（DAG）：
  1. 文案生成（LLM）。
  2. 人工或机器审核。
  3. TTS 配音（选择音色、调整语速，支持克隆的声音）。
  4. 视频生成（数字人口型驱动，或者文生视频、图生视频）。
  5. 合成（音轨、字幕、背景）。
  6. 质检。
  7. 发布。
- 架构：
  - 工作流引擎：节点之间的依赖解析，上游完成后自动触发下游，审核通过后再进入下一步。
  - 异步任务队列（如 Celery、MQ），把 GPU 密集型的节点调度到专门的资源池。
  - 每个节点的产物存储到对象存储，只传递引用。
- 关键点：
  - 节点失败时自动重试，或者人工重试；支持批量任务（如单批 100 个任务）、并发轮询、在夜间低峰期执行。
  - 素材的规范校验（格式、编码、码率、帧率、分辨率、时长）。
  - 成本：GPU 资源池的排队和优先级。
  - 合规：AIGC 水印，素材的授权。
  - 结果通知（群消息）和回写（Excel 或数据库）。
- 可引用：维护的 Flask 工作流服务（基于 Celery 的 DAG、PM 审核后自动触发下游、批量重试、如流通知），以及背景素材的上传校验规则。

### 13. 【高频】设计一个大模型 API 网关，支持多供应商、限流、计费、降级。
**答案：**
- 统一接入：
  - 兼容 OpenAI 格式的统一 API，覆盖流式和非流式、工具调用、多模态。
  - 调用方使用网关签发的密钥，供应商的密钥统一托管在网关，调用方接触不到。
- 路由：
  - 按模型别名或场景配置首选和备选模型。
  - 按延迟、错误率、剩余配额、成本动态选择。
  - 前缀感知路由，提高 KV Cache 的命中率。
- 流量治理：
  - 按调用方、模型、用户多个维度限流（QPS、TPM、并发）。
  - 排队和优先级（在线请求优先于离线批量任务）。
  - 超时；可重试的错误带退避重试。
  - 熔断，并切换到备用供应商。
  - 流式请求只能在开始输出前切换供应商。
- 计费：从响应中统计输入、输出、缓存命中的 token，按单价计算费用；实时累计并检查配额，超出预算时告警或拒绝；明细异步落库，用于对账。
- 缓存：支持供应商的 Prompt 缓存；精确缓存和语义缓存（可以选择开启）。
- 安全：内容审核、日志脱敏、审计。
- 可观测：每个模型的首 token 延迟、TPOT、错误率、成本大盘。

### 14. 设计一个对话数据的埋点、存储和分析系统。
**答案：**
- 埋点设计：
  - 一条对话日志包含基础维度（时间、uid、app_id、session_id、logid、渠道、环境、Agent 模式）、内容（query、answer）、Agent 配置维度（是否挂载了知识库、插件）、运行时维度（触发了哪个知识库或工具、使用的模型、耗时、是否出错、多模态检索结果）。
  - 扩展字段统一放在 JSON 字段中。
- 采集和传输：服务端异步写日志，或者发送到 MQ，不阻塞主链路；保证不丢失（至少一次投递）。
- 存储：
  - 实时链路：发送到 Kafka，再由 Flink 写入 OLAP（如 Doris、ClickHouse），用于实时看板。
  - 离线链路：进入数仓的宽表（按小时分区），用于深度分析。
  - 原始对话的在线存储要和分析存储分开，并且做冷热分层。
- 分析：
  - 预置报表（Sugar 等 BI 工具）：调用量、满意度、工具触发率、调度命中率。
  - 自助查询的 SQL 模板。
  - badcase 抽样。
- 治理：统一字段口径并维护文档；敏感信息脱敏；按数据保留期限清理。
- 可引用：agent_content 打点字段的升级（is_dataset_set、rag_triggered_plugin 等）、数仓表 search_dwd_pv_and_chat_log_hf、多人调度的 Sugar 报表、对话历史导出。

### 15. 【专家】设计一个商业化归因系统：衡量一个 query 通过什么内容给哪个 Agent 带来了多少商业价值。
**答案：**
- 归因链路：搜索 query → 展示的内容（content_id）→ 进入的 Agent（app_id）→ 会话（session_id）→ 消息（message_id）→ 商业化组件的曝光和点击（线索表单、电话、报价）→ 转化（提交线索、后续成单）。
- 关键是全链路的 ID 透传：
  - 从入口处开始，每一跳都携带 searchWord、logid（lid）、content_id、session_id、message_id。
  - 在挂载服务返回的组件数据（如 ui_data 的 chatInfo）中写入这些 ID，前端在用户点击或提交时原样带回。
  - 线索数据入库时也带上这些 ID。
- 难点：
  - 通路多：q2a、q2c、Agent 房间页、快捷指令、电话加线索，每种通路的字段来源都不同（如只有 q2c 有 content_id），要逐一梳理调用点。
  - 跨多个服务：需要按依赖顺序上线（被依赖方先上线），新字段都是可选的、向后兼容。
  - 归因模型：可以先用末次触点归因，再逐步引入多触点归因；明确时间窗口（如 7 天内的转化都算）。
- 数据层：曝光、点击、转化事件进入数仓，按 query、content、Agent 维度聚合出转化率和商业价值，形成"生产-分发-商业化"的数据飞轮，反哺内容的生产和分发。
- 可引用：线索 RFQ 的 query 获取能力升级和飞轮数据链路打通，涉及 704、676、646、722、714 五个服务和五种通路，上线顺序为 704 → 676 → 722 → 646，并修复了 searchid 的取值问题。

## 线上问题处理

### 16. 【高频】Agent 服务突然大量超时，你的排查步骤是什么？
**答案：**
- 止损：
  - 先看影响面（全部请求还是部分 Agent、部分接口）。
  - 如果刚有变更，立即回滚。
  - 降级非核心环节（追问、挂载组件、检索），切换到备用模型，扩容、限流。
- 定位：
  - 时间线：超时开始的时间点和变更、流量、依赖告警是否吻合。
  - trace：超时的请求卡在哪个环节。
    - 模型：排队、限流（429）、供应商故障。
    - 检索服务、工具调用、数据库和 Redis。
    - 前置数据加载变慢。
    - 服务自身：CPU、GC、协程数暴涨、连接池打满。
  - 流量：是否有突发流量，是否有异常的大请求（超长上下文）。
- 修复：针对根因处理（切换供应商、修复慢查询、扩大连接池、修复 bug），然后逐步恢复被降级的功能。
- 复盘：时间线、根因、影响范围、改进措施（超时配置、熔断、监控告警、预案演练），并跟踪改进措施的落实。

### 17. 模型供应商故障，整个 Agent 不可用，怎么快速止损？
**答案：**
- 快速确认：模型网关的错误率和延迟监控、供应商的状态页、直接调用测试，确认是供应商的问题。
- 止损措施（按事先准备好的预案执行）：
  1. 切换到备用供应商或备用模型（通过配置开关，秒级生效）。
  2. 如果没有同等能力的备用模型，降级到小模型或自建模型，回答质量可能下降，但服务可用。
  3. 功能降级：只保留 FAQ 和缓存的答案；返回友好的提示和兜底文案；客服场景转人工。
  4. 熔断，防止请求堆积拖垮整个服务。
- 沟通：同步给相关方，必要时在产品中发布公告。
- 恢复：供应商恢复后，逐步切回流量，观察指标。
- 改进：多供应商的主备架构常态化；定期做切换演练；为不同模型维护对应的 Prompt，并且在评测集上验证过备用模型的效果。

### 18. 【高频】某个 Agent 被用户诱导输出了违规内容，怎么处理？
**答案：**
- 立即止损：
  - 根据严重程度，下线这个 Agent，或者关闭相关的功能。
  - 撤回或删除已经产生的违规内容（包括分享出去的内容）。
  - 封禁恶意用户。
- 定位：
  - 通过日志和 trace 还原完整的对话：用户用了什么手法（越狱、角色扮演、编码绕过、多轮诱导）。
  - 审核为什么没有拦截：输入审核、输出审核是否生效，流式输出时的审核策略是否有漏洞。
- 修复：
  - 把这次的攻击手法加入审核规则和模型的训练样本。
  - 加固 Prompt 中的拒答策略。
  - 对流式输出采用更严格的审核（边生成边审核）。
  - 用类似的攻击用例做红队测试，验证修复效果。
- 复盘和上报：按公司的安全事件流程上报和复盘。
- 预防：把攻击用例纳入回归测试集；监控违规率；新上线的 Agent 先经过安全评测。

### 19. 线上数据库 CPU 打满，怎么快速定位和止损？
**答案：**
- 快速定位：
  - `SHOW PROCESSLIST` 或 performance_schema：查看当前正在执行的 SQL，找出执行时间长、数量多的语句。
  - 慢查询日志，以及 DBA 平台的 TOP SQL（按 CPU、扫描行数排序）。
  - 和时间点对比：是否有新上线的功能、是否有批量任务（数据清理、导出、统计）、流量是否突增、是否有缓存失效导致大量请求回源到数据库。
- 止损：
  - KILL 掉异常的慢查询，暂停批量任务。
  - 如果是新功能导致的，立即回滚，或者关闭对应的开关。
  - 限流：在应用层对相关接口限流、降级，或者在数据库代理层做 SQL 限流。
  - 缓存失效引起的：恢复缓存（预热），用 singleflight 防止并发回源。
  - 临时扩容：增加只读实例，分担读流量。
- 根因修复：
  - 添加或修复索引（全表扫描、索引失效）。
  - 改写 SQL（深分页、N+1 查询、大 IN 列表）。
  - 大事务分批执行。
  - 加缓存。
- 复盘：SQL 上线前的审核流程（EXPLAIN）、慢查询告警、批量任务的执行规范（低峰期、限速）。

### 20. Redis 突然大量超时，可能有哪些原因？
**答案：**
- Redis 侧的原因：
  - 慢命令阻塞（KEYS、对大 key 执行 HGETALL、DEL 大 key、耗时的 Lua 脚本），可以查看 SLOWLOG。
  - 热 key：单个分片的 CPU 打满。
  - 持久化：fork 阻塞（latest_fork_usec）、AOF 刷盘阻塞、开启了透明大页（THP）。
  - 内存达到上限，频繁淘汰数据；或者发生了 swap。
  - 大量 key 同时过期。
  - 主从切换或集群迁移（出现 ASK、MOVED 重定向，或者迁移大 key 时阻塞）。
  - 连接数达到上限。
- 客户端侧的原因：
  - 连接池太小，请求在客户端排队（连接池等待超时）。
  - 客户端的 GC 停顿、CPU 打满。
  - 读写大 value 导致的网络传输慢。
- 网络：带宽打满、丢包、跨机房访问。
- 排查顺序：看 Redis 监控（CPU、内存、连接数、QPS、慢查询）→ 看客户端连接池的指标 → 看网络。
- 止损：限流降级、启用本地缓存、迁移或拆分热 key、停止危险的操作、扩容或增加分片。

### 21. 发布后错误率上升，怎么判断是否回滚？
**答案：**
- 原则：如果怀疑问题和这次发布有关，并且影响到了用户，就优先回滚，再定位问题，而不是在线上边排查边修复。止损比找到根因更重要。
- 判断依据：
  - 时间相关性：错误率是不是在发布（或灰度批次）之后开始上升。
  - 灰度对比：新版本实例的错误率明显高于老版本的实例。
  - 错误类型：报错的位置是否在这次修改的代码中。
  - 影响程度：是否突破了 SLO 的阈值（错误预算消耗得很快）。
- 回滚的前提：
  - 每次发布都提前准备好回滚方案。
  - 如果数据库结构变更或数据格式发生了不兼容的变化，回滚代码可能会有问题，所以变更要设计成向前兼容。
  - 多个服务联合发布时，按相反的顺序回滚。
- 回滚之后：确认指标恢复；保留现场（日志、问题实例）用于分析；修复后重新走灰度发布流程。
- 预防：分批灰度发布，每一批都观察指标；把自动化的指标检查作为发布的卡点。

### 22. 【专家】上线后发现一批数据被写错了，怎么修复且不影响线上？
**答案：**
- 先止血：找到写错数据的根因（代码 bug、配置错误、脚本错误），先修复，或者关闭对应的功能，防止继续产生错误的数据。
- 评估范围：根据时间窗口、业务条件、日志、binlog，统计受影响的数据（行数、用户、业务影响）。
- 确定正确的数据：
  - 从备份、binlog 中恢复修改前的值（可以使用闪回工具，基于 row 格式的 binlog 生成反向 SQL）。
  - 从上游的数据源或日志中重新计算出正确的值。
- 修复方案：
  - 写修复脚本或 SQL，先在测试环境用线上数据的副本验证。
  - 执行前备份当前的数据，准备好回滚 SQL。
  - 分批执行（控制每批的大小、批次之间休眠），在低峰期执行，监控主从延迟和业务指标。
  - 通过 DMS 提交，经过 DBA 审核。
- 下游：错误的数据可能已经同步到了缓存、ES、数仓或者其他系统，要一并修复，或者重新同步；必要时通知受影响的用户或业务方。
- 验证和复盘：抽样核对修复的结果；复盘为什么测试和灰度阶段没有发现这个问题，补充校验和监控。
- 可引用：清理 20b 衔接视频数据时，制定了修复 SOP：备份三张质检表、按顺序变更、按相反的顺序回滚、在 DMS 上分批提交。

## 技术决策与管理

### 23. 【高频】在两个技术方案之间做选择时，你会考虑哪些因素？
**答案：**
- 是否满足需求：功能、性能指标（延迟、QPS）、一致性的要求、可扩展性。
- 复杂度和成本：开发的人力和工期、运维成本、机器成本、团队的学习成本。
- 风险：技术是否成熟、对现有系统的影响面、能否灰度和回滚、出现故障时的影响范围。
- 长期：可维护性、职责是否清晰、和整体架构是否一致、是否会引入技术债。
- 团队：团队的技术栈和经验、上下游团队的配合成本。
- 方法：
  - 列出评估维度，把各方案逐项对比（必要时打分）。
  - 用数据说话：做一个原型或压测验证关键假设。
  - 写进技术评审文档，让相关方一起评审。
  - 没有完美的方案，要明确取舍了什么、为什么可以接受。
- 可引用：数字人"最近使用"的读取方案，对比了两种方案后选择了"分发 server 调用 agent server"，因为职责更清晰；TTS 迁入爱速搭时，对比了"申请爱速搭组织"（1 到 2 人日，但审批时间不可控）和"用 Go 重写后部署到 appengine"（2 到 3 人日）两种方案。

### 24. 【高频】怎么评估一个技术方案的风险？
**答案：**
- 识别风险：
  - 技术风险：新技术是否成熟、性能能否达标、是否有未经验证的假设。
  - 依赖风险：上下游团队的排期、第三方服务的稳定性和配额。
  - 数据风险：数据迁移、一致性、数据丢失。
  - 上线风险：影响面、能否回滚、发布的顺序依赖。
  - 安全和合规风险。
  - 进度风险：工期估算是否乐观、关键人员是否只有一个人。
- 评估：对每个风险按发生的概率和影响程度分级。
- 应对：
  - 高风险的点先做原型或压测验证。
  - 设计降级和回滚方案；用功能开关和灰度控制影响面。
  - 关键依赖提前对齐，留出缓冲时间。
  - 写进评审文档，明确每个风险的负责人。
- 持续跟踪：在里程碑节点复查风险，有变化及时同步。
- 可引用：长底板组件评审中明确了一个风险，三处筛选映射必须同步修改，漏改一处长底板形象就"查不到"；PaaS 上线评审明确了 pipeline 后端必须先于 paas 上线。

### 25. 业务需求紧急，但技术方案有隐患，你怎么处理？
**答案：**
- 先把隐患说清楚：具体的风险是什么、发生的概率、发生后的影响（数据、资金、用户体验），用业务方能理解的语言描述，不只是说"技术上不好"。
- 给出可选的方案，而不是只是拒绝：
  - 方案 A：按期上线一个最小可用版本，同时用兜底措施控制风险（开关、限流、监控、人工兜底），之后再排期偿还技术债。
  - 方案 B：延期 N 天，做正确的方案。
  - 说明每个方案的代价。
- 让决策人基于信息做决策，并把结论记录下来（风险由谁承担、技术债什么时候偿还）。
- 底线：涉及安全、数据丢失、资金正确性的问题不妥协，必须解决之后才能上线。
- 跟进：上线后加强监控；按照约定的时间完成技术债的偿还，不要让临时方案变成永久方案。

### 26. 【专家】多个团队联合开发一个需求，你怎么推进和协调？
**答案：**
- 对齐目标和范围：组织需求评审和技术评审，明确每个团队负责的部分、接口的边界、验收标准。
- 接口先行：先定好接口文档（字段、错误码、调用时序、上线顺序），各团队基于接口文档并行开发，用 mock 联调。
- 计划：拆分出里程碑（开发、联调、提测、上线），识别关键路径和依赖，每个任务都要有负责人和截止时间。
- 过程管理：
  - 定期同步进度（站会或周会），提前暴露风险，阻塞的问题及时升级。
  - 整理疑问清单，逐条关闭。
  - 联调时使用统一的环境和测试数据。
- 上线：统一的上线文档（发布顺序、负责人、验证方法、回滚方案）；上线当天大家同时在线，按 checklist 执行。
- 复盘：沉淀协作中暴露的问题和经验。
- 可引用：
  - 对客 PaaS 平台：打通了 PaaS、MIS、Pipeline、架构四方，输出了 PaaS 对客接口文档、疑问点整理、提测文档、上线文档，上线顺序为架构后端 → pipeline 后端 → pipeline 前端 → paas。
  - 商业化线索工具：对接 B 端和 C 端的前端、服务端以及 QA。

### 27. 技术债怎么识别和偿还？
**答案：**
- 识别：
  - 代码层面：重复代码、没有测试、复杂度高、过时的依赖。
  - 架构层面：耦合过紧、性能瓶颈、单点。
  - 运维层面：手工操作、没有监控、临时脚本。
  - 信号：同类 bug 反复出现、修改一个功能需要动很多地方、新人很难上手、频繁发生线上问题。
- 记录：建立技术债清单，记录影响、偿还的成本、优先级，不要只停留在口头上。
- 偿还策略：
  - 按"影响程度除以偿还成本"排序，优先处理影响稳定性和效率的问题。
  - 结合业务需求顺带偿还（修改到某个模块时顺便重构这个模块）。
  - 固定比例：每个迭代预留一部分时间（如 10% 到 20%）用于偿还技术债。
  - 大的重构要有灰度方案和对比验证，保证行为不变。
- 预防：代码评审、技术评审中控制新增的技术债；临时方案要写明偿还计划。
- 可引用：每月的 O 端平台技术优化；mount 服务前置数据获取的重构；646 拒绝老协议流量；对话数据冷备和存量数据治理。

### 28. 你怎么做代码评审？关注哪些点？
**答案：**
- 正确性：逻辑是否正确、边界条件、错误处理（是否吞掉了错误）、空指针、并发安全（数据竞争、锁、goroutine 泄漏）。
- 稳定性：超时、重试、幂等、资源释放（Body、Rows、文件）、panic 的兜底、对下游的保护（限流、批量操作的大小）。
- 性能：N+1 查询、循环中的 IO、不必要的内存分配、索引是否使用正确（附上 EXPLAIN 的结果）、缓存的使用。
- 兼容性：接口和数据结构是否向后兼容、DDL 是否在线执行、上线顺序是否有依赖、新功能是否有开关。
- 安全：输入校验、SQL 注入、越权（资源归属的校验）、敏感信息是否打到了日志中、密钥是否写在了代码里。
- 可维护性：命名、函数的职责、和现有代码风格的一致性、必要的注释、测试的覆盖。
- 方式：
  - 先看改动的意图和设计，再看细节；大的改动要求拆成小的提交。
  - 评论区分"必须修改"和"建议"，就事论事。
  - 借助工具：lint、静态检查、`-race`、AI 辅助评审。

### 29. 【高频】怎么写一份好的技术评审文档？
**答案：**
- 结构：
  1. 背景和目标：要解决什么问题，衡量成功的指标。
  2. 需求范围：包含什么、不包含什么。
  3. 现状分析：现有的链路和问题，最好有数据。
  4. 方案设计：
     - 整体架构和流程图（时序图、状态机）。
     - 数据模型（表结构和 DDL、索引）。
     - 接口定义（字段、错误码、示例）。
     - 关键的算法和规则。
  5. 方案对比和取舍：备选方案和选择的理由。
  6. 非功能设计：性能和容量估算、一致性、安全、监控告警、降级预案。
  7. 兼容性和上线：存量数据的处理、发布顺序、灰度、回滚方案。
  8. 风险和待确认的问题。
  9. 排期和分工、测试要点。
- 要点：
  - 读者是评审人，结论先行，图表优于大段的文字。
  - 关键的设计决策要写清楚"为什么"。
  - 数字要有依据（压测结果、容量估算）。
  - 评审后补充评审意见和结论，并持续更新。
- 可引用：长底板方案的 PPL 技术评审、删除衔接视频的技术评审（6 个接口、可用率算法、DDL 和刷新脚本）、对客 PaaS 的技术评审。

### 30. 怎么带新人？怎么做技术分享和沉淀？

### 31. 【专家】AI 编程工具（Copilot、Cursor、Claude Code）对团队研发流程有什么影响？你怎么用？
**答案：**
- 影响：
  - 编码：样板代码、单元测试、接口对接、脚本、SQL 等工作的效率明显提升；开发者的重心从"写代码"转向"描述需求、评审和验证"。
  - 学习和排查：快速理解陌生的代码库、阅读日志、定位问题。
  - 文档：自动生成技术文档、接口文档、周报和总结。
  - 新的风险：生成的代码看起来正确，但存在隐藏的 bug；安全问题（注入、越权）；代码风格不一致；敏感代码和数据的外泄。
- 我的用法：
  - 明确的任务交给 AI：写单元测试、写数据处理脚本、生成 CRUD 和接口代码、整理文档、批量修改。
  - 设计和关键逻辑由自己把握：AI 生成的代码必须经过评审和测试，再合入代码库。
  - 给足上下文：项目规范文件、现有代码的风格、接口定义，让它遵循现有的约定。
  - 验证闭环：让 AI 修改后运行测试或编译，用结果来校验。
- 团队层面：
  - 制定使用规范：哪些代码和数据不能发送给外部模型、代码评审的要求不降低。
  - 沉淀团队的提示词和项目说明文件（如 CLAUDE.md），共享常用的工作流。
  - 衡量效果：交付周期、缺陷率。
- 可引用：使用 AI 编写单元测试的实践文档。

### 32. 【专家】你怎么看 Agent 技术未来 1 到 2 年的发展方向？
**答案：**
- 模型：

### 33. 如果业务方案效果不及预期，你怎么用数据说服产品调整方向？
**答案：**
- 先确认数据可信：统计口径正确、样本量足够、排除了实验设计的问题（分流是否均匀、实验周期是否足够长）。
- 拆解问题：漏斗分析（曝光 → 点击 → 使用 → 转化）找出流失最多的环节；分人群和场景对比；结合 badcase 和用户反馈，分析"为什么"。
- 呈现方式：
  - 结论先行：核心指标的变化，和预期之间的差距。
  - 证据：关键数据、对比图表、具体的案例。
  - 原因分析。
  - 建议：调整的方向，以及每个方向的预期收益和成本，甚至可以提前做一个小实验来验证。
- 态度：站在共同的业务目标上讨论，不是否定产品的判断，而是基于数据共同决策。尊重产品的最终决策，但要把风险和数据记录下来。
- 可引用：资源型智能体追问优化，用 150 条样本的评估数据（badcase 率从 20% 降到 4.67%）和产品对齐效果与后续目标；多人调度统计中和产品确定口径（使用 query 维度）。

### 34. 【专家】专家和高级工程师的区别是什么？你认为自己已经具备了哪些专家能力？
**答案：**
- 区别：
  - 高级工程师：能独立、高质量地完成复杂模块的设计和开发，解决疑难问题。
  - 专家：
    - 影响范围更大：从负责一个模块，到负责一个领域或平台的技术方向。
    - 系统性：能把一类问题抽象成平台能力或方法论，而不只是解决单个问题。
    - 前瞻性：判断技术趋势，提前规划。
    - 带动团队：通过技术评审、规范、分享提升团队的整体能力。
    - 跨团队：主导跨团队的复杂项目，对业务结果负责。
- 我已经具备的（结合实际项目举例）：
  - 平台从 0 到 1 的建设：数字人形象制作、质检、端到端评估、对客 PaaS 交付平台的 server 端设计（数据模型、状态机、一致性方案）。
  - 跨团队主导：RFQ 归因链路（5 个服务、5 种通路）、PaaS 四方打通（明确上线顺序和依赖）。
  - 用数据驱动的性能和质量优化：mount 服务耗时降低约 30 倍；追问 badcase 率降到 4.67%。
  - 大规模的数据治理：约 20T 对话数据的冷备和删除；存储占用从 80% 降到 61%。
  - 风险控制的方法：灰度双接口、在线 DDL、先备份后变更的 SOP、新能力只命中新的枚举值。
- 还需要加强的（诚实地说）：
  - Agent 核心技术的深度（上下文工程、记忆、评估体系的方法论）。
  - 技术规划和对外的技术影响力（分享、规范的沉淀）。
  - 下一步的计划。

### 35. 你下一年的技术规划是什么？
**答案：**
- 框架：业务目标 → 技术挑战 → 规划的方向 → 衡量指标 → 里程碑。
- 示例（结合数字人 PaaS 和 Agent 方向，按实际情况调整）：
  1. 平台稳定性和效率：PaaS 交付链路的 SLA 体系（可用性、交付时长）；生产调度平台化（统一的任务状态机、自动重试、巡检兜底）；把交付周期从天级缩短到小时级（推广长底板、生成式底板等方案）。
  2. 质量体系：端到端评估从人工为主转向机器质检加人工抽检；建立评估指标和数据闭环，用数据驱动形象和对话策略的迭代。
  3. Agent 能力：实时互动 Agent 的低延迟优化（全链路流式、打断）；记忆和个性化；用 MCP 和工具网关统一管理能力。
  4. 工程效能：沉淀通用组件（状态机、异步任务框架、批量查询和缓存的规范）；把 AI 编程工具引入团队的研发流程。
  5. 团队和影响力：输出技术分享、规范和 SOP；带新人。
- 每项规划都要有可以衡量的目标（如延迟降低 X%、自动化质检的覆盖率达到 Y%、交付时长缩短到 Z），并说明如何支撑业务目标。
