# 09 Agent 服务工程化（40 题）（题目与答案）

## 流式与协议

### 1. 【高频】大模型流式输出为什么用 SSE？SSE 和 WebSocket 怎么选？
**答案：**
- 用 SSE 的原因：大模型输出是"服务端到客户端"的单向推送，SSE 正好满足：基于普通 HTTP，网关、负载均衡、鉴权都能直接复用；浏览器原生支持（EventSource），自带断线重连；实现简单。
- WebSocket：全双工、双向通信，适合客户端也需要持续发送数据的场景，如实时语音（持续上传音频）、协同编辑、游戏、需要随时打断的实时交互。代价是要自己处理心跳、重连、鉴权，并且需要网关支持长连接。
- 选择：文本对话、Agent 流式回复用 SSE；实时语音和数字人交互用 WebSocket 或 WebRTC。

### 2. 【高频】SSE 的协议格式是什么？断线重连、Last-Event-ID 怎么用？
**答案：**
- 格式：
  - 响应头为 `Content-Type: text/event-stream`，保持连接不关闭。
  - 每个事件由若干行组成：`event: 事件类型`、`data: 内容`（可以多行）、`id: 事件ID`、`retry: 重连间隔（毫秒）`，事件之间用空行分隔。
  - 以冒号开头的行是注释，常用来发送心跳，防止连接因空闲被断开。
- 断线重连：浏览器的 EventSource 断开后会自动重连，并在请求头中带上 `Last-Event-ID`（最后收到的事件 ID）；服务端据此从断点之后继续发送。
- 前提：服务端要缓存最近的事件（如按 message_id 存在 Redis 中），才能支持续传。
- 注意：EventSource 只支持 GET，而且不能自定义请求头，所以大模型场景常用 fetch 加流式读取的方式手动解析 SSE。

### 3. SSE 经过 Nginx、网关时会被缓冲，怎么解决？
**答案：**
- 现象：服务端是逐 token 发送的，但客户端隔很久才一次性收到一大段，流式效果消失。
- 原因：Nginx 默认开启 proxy_buffering，会缓冲上游的响应；gzip 压缩也会缓冲；部分 CDN 和网关也有缓冲。
- 解决：
  - Nginx：对流式接口配置 `proxy_buffering off`，或者由服务端返回 `X-Accel-Buffering: no` 响应头。
  - 关闭该接口的 gzip。
  - 调大 `proxy_read_timeout`，防止长连接被中途断开。
  - 服务端每写一个事件都要 Flush。
  - 定期发送心跳（注释行），防止空闲连接被中间设备断开。
- 验证：用 `curl -N` 直接请求，观察是否逐条输出。

### 4. 【专家】Go 中如何实现 SSE 服务端？怎么感知客户端断开并取消下游模型调用？
**答案：**
- 实现：
  - 设置响应头 `Content-Type: text/event-stream`、`Cache-Control: no-cache`、`Connection: keep-alive`。
  - 把 ResponseWriter 断言为 `http.Flusher`，每写一个事件就调用一次 Flush。
- 感知断开：客户端断开后，`r.Context()` 会被取消（`ctx.Done()` 关闭）；写入时也会返回错误。
- 取消下游：把请求的 ctx 传给模型调用和工具调用（`http.NewRequestWithContext`），客户端一断开，下游请求自动取消，节省 token 和资源。
```go
for {
    select {
    case <-ctx.Done():
        return // 客户端断开，下游 ctx 同时被取消
    case chunk, ok := <-stream:
        if !ok { return }
        fmt.Fprintf(w, "event: message\ndata: %s\n\n", chunk)
        flusher.Flush()
    }
}
```
- 注意：
  - 如果断开后还需要把已生成的内容保存到对话历史，保存逻辑要使用独立的 ctx（如 `context.WithoutCancel`）。
  - 设置写超时；用心跳检测半开连接。

### 5. 流式输出中同时返回文本、工具状态、卡片组件，事件类型怎么设计？
**答案：**
- 用 SSE 的 event 字段区分类型，data 是 JSON：
  - 生命周期：run_begin、run_end（带最终状态、用量）、error。
  - 文本：message_delta（增量文本）、message_completed（完整消息，带 message_id）。
  - 思考：reasoning_delta。
  - 工具：tool_call_begin（工具名、参数）、tool_call_end（状态、结果摘要），用于展示"正在搜索……"。
  - 组件：component 事件（组件类型、ui_data、插入位置），如线索表单、商品卡、追问建议。
- 每个事件都带上 session_id、message_id、序号（seq），用于排序、去重和断点续传。
- 向后兼容：前端遇到不认识的事件类型时忽略，新增类型不影响旧版本客户端。

### 6. 流式消息的状态（in_progress、completed）怎么设计？前端怎么渲染？
**答案：**
- 每条消息有自己的状态：in_progress（生成中）、completed（完成）、failed（失败）、cancelled（被用户中止）、incomplete（因长度限制等原因被截断）。
- 增量事件带 status=in_progress，最后发送一条 status=completed 的完整消息（包含全文），作为最终版本。前端以最终版本为准，修正增量拼接中可能出现的问题。
- 前端渲染：
  - 收到增量就追加到对应 message_id 的消息气泡中，显示打字效果和"生成中"的状态。
  - 收到 completed 后替换为完整内容，渲染 markdown，显示操作按钮（复制、点赞、重新生成）。
  - 失败或取消时显示提示和重试按钮。
- 服务端：只有 completed（或用户确认保留的部分内容）才写入对话历史。

### 7. 实时语音数字人用 WebSocket 还是 WebRTC？延迟预算怎么分配？
**答案：**
- WebSocket：基于 TCP，实现简单，服务端友好；适合传输音频片段和控制消息；但在弱网下 TCP 重传会导致延迟抖动。
- WebRTC：基于 UDP，专门为实时音视频设计，内置回声消除、降噪、抖动缓冲、带宽自适应；延迟低、弱网表现好；但实现和部署复杂（需要信令服务、STUN/TURN、媒体服务器）。
- 常见选择：音视频媒体流走 WebRTC（或 RTC SDK），控制信令和文本走 WebSocket；对延迟要求不高的简单场景，可以全部用 WebSocket。
- 延迟预算（目标是用户说完话后约 1 秒内开始听到回复）：
  - VAD 判断用户说完话：一两百毫秒到几百毫秒。
  - ASR 最终结果：一两百毫秒（流式识别可以更早拿到结果）。
  - LLM 首 token 到首句完成：几百毫秒。
  - TTS 首包：一两百毫秒。
  - 网络和播放缓冲：一百毫秒左右。
- 各环节必须流式衔接，不能等上一个环节全部完成再开始下一个。

### 8. 【专家】ASR → LLM → TTS 的语音链路怎么做到端到端低延迟（流式、分句、预测）？
**答案：**
- 全链路流式：
  - ASR 流式识别，边说边出中间结果。
  - LLM 流式输出。
  - TTS 流式合成，按句合成，首句合成完立即播放，不等全文。
- 分句：LLM 输出累积到一个完整的短句（遇到句号、问号、逗号且长度足够时）就送去 TTS；首句可以更短，以尽快出声。
- 预测和提前启动：
  - 在 ASR 中间结果稳定时，提前启动 LLM 推理（投机执行）；如果最终识别结果不同，就丢弃重来。
  - 更快的端点检测（语义 VAD，判断用户的话是否已经说完）。
- 减少 LLM 首 token 延迟：精简 Prompt、命中前缀缓存、用低延迟的模型、减少前置的串行步骤（检索可以并行或省略）。
- 部署：各服务就近部署，减少网络跳数；连接复用和预热。
- 端到端模型（语音直接到语音）可以进一步降低延迟，但可控性较差。

### 9. TTS 分句合成时，句子怎么切分才自然？
**答案：**
- 优先在强标点处切分：句号、问号、感叹号、换行。
- 句子太长时，在逗号、分号等弱标点处切分，避免单句合成太慢、首包延迟太高。
- 句子太短时（如"好的。"），和下一句合并，避免频繁停顿，语调更连贯。
- 不在数字、英文单词、专有名词、markdown 符号中间切开；送去 TTS 前去掉 markdown 格式（星号、井号、列表符号），把数字、单位、符号规范化（如"3.5%"读作"百分之三点五"）。
- 首句可以短一些以尽快出声，后续句子长度适中，保证合成效率和韵律自然。
- 维护一个文本缓冲区，LLM 的增量 token 不断追加，满足切分条件就送出一句。

## 性能与成本

### 10. 【高频】Agent 服务的延迟由哪些部分组成？怎么逐段优化？
**答案：**
- 组成：
  - 网络和网关。
  - 前置处理：鉴权、读取 Agent 配置、加载挂载数据、读取对话历史。
  - 理解：意图识别、query 改写。
  - 检索和工具调用。
  - 模型：排队、prefill（首 token）、decode（生成）。
  - 后处理：内容审核、挂载组件、保存记录。
- 优化：
  - 先用 trace 量化每一段的耗时，找到最大的瓶颈。
  - 前置数据：缓存、批量查询、并行加载。
  - 理解：用小模型或规则；简单请求跳过。
  - 检索和工具：并行、缓存、设置超时。
  - 模型：精简 Prompt、前缀缓存、选择合适的模型、流式输出。
  - 后处理：异步执行（落库、打点不阻塞响应）。
- 可举例：agent-mount 前置数据获取改成批量查询后，平均耗时从 3.124s 降到 98ms。

### 11. 【高频】模型调用的 QPS 和 TPM 限额不够时怎么办？
**答案：**
- 短期：
  - 申请提升配额。
  - 在多个账号、多个区域、多个供应商之间分摊流量。
  - 客户端做排队和平滑（令牌桶），避免突发流量触发 429 错误。
  - 遇到 429 时带退避重试。
- 减少消耗：
  - 缓存（语义缓存、结果缓存）。
  - 缩短 Prompt（降低 TPM）。
  - 把非核心的调用（追问、改写）换成小模型或自建模型。
  - 合并多次调用。
- 分级：核心业务优先使用配额；非核心功能在配额紧张时降级或关闭。
- 长期：自建推理服务承接高频、窄任务的流量；做容量规划，提前申请配额。

### 12. 【专家】多模型供应商路由怎么设计（按成本、延迟、可用性切换）？
**答案：**
- 统一接口：在模型网关层统一请求和响应格式（如兼容 OpenAI 格式），业务方只指定模型能力或模型别名，不关心具体的供应商。
- 路由策略：
  - 按场景和能力：每个场景配置首选模型和备选模型列表。
  - 按成本：简单请求路由到便宜的模型。
  - 按延迟：实时监控各供应商的 P99 首 token 延迟，优先选择快的。
  - 按可用性：错误率高时自动熔断，切换到备选模型；恢复后逐步放回流量。
  - 按配额：根据剩余配额分配流量。
- 一致性：不同模型的效果有差异，切换前要在评测集上验证；每个模型维护一套适配的 Prompt。
- 流式请求：已经开始输出后不能无感知地切换模型，只能在开始前切换，或者从头重试。
- 可观测：记录每次请求实际使用的模型，按供应商统计成本、延迟和错误率。

### 13. 模型网关需要哪些能力（统一协议、限流、计费、重试、熔断）？
**答案：**
- 协议：统一的 API 格式，屏蔽各供应商的差异；支持流式和非流式；支持工具调用、多模态、结构化输出。
- 流量治理：按业务方、用户、模型限流；排队；超时；可重试错误自动重试（带退避）；熔断和降级；多供应商路由。
- 计费和配额：按调用方统计 token 用量和费用，设置预算和配额，超额告警或拒绝。
- 缓存：精确缓存、语义缓存，支持供应商的 Prompt Caching。
- 安全：统一管理各供应商的密钥（业务方不接触）；内容审核；日志脱敏。
- 可观测：请求日志、trace、各模型的延迟和错误率大盘。
- 管理：模型的上下线、灰度、按场景配置默认模型。

### 14. 【高频】token 成本怎么优化（缓存、压缩、小模型、减少调用）？
**答案：**
- 缓存：
  - 用好 Prompt Caching：稳定的前缀放在前面，可以大幅降低输入 token 的费用。
  - 结果缓存和语义缓存：重复的问题直接返回。
- 压缩：精简 System Prompt；工具定义按需加载；对话历史做摘要；检索结果精简（减少 top-k、去重）；工具结果只保留需要的字段。
- 用小模型：意图识别、改写、追问、分类、格式转换这些步骤使用小模型或自建模型。
- 减少调用：合并多个步骤为一次调用；简单请求跳过不必要的环节（如不需要检索就不检索）；限制 Agent 的最大步数。
- 控制输出：限制 max_tokens，要求回答简洁。
- 度量：按功能拆分 token 消耗，从占比最大的部分开始优化；每次优化都要在评测集上确认效果没有下降。

### 15. 语义缓存在 Agent 场景能用吗？哪些请求适合缓存？
**答案：**
- 能用，但场景有限：Agent 的回答往往和上下文、用户、实时数据有关，命中率不高，误命中的风险也大。
- 适合缓存：
  - 独立的、和上下文无关的知识问答（FAQ、产品介绍、政策说明）。
  - 首轮问题（没有对话历史）。
  - 开场白、常见的引导回复。
  - 中间步骤的结果（query 改写、检索结果、工具结果）。
- 不适合缓存：
  - 多轮对话中依赖上下文的问题。
  - 个性化回答。
  - 实时数据（价格、库存、天气）。
  - 有副作用的操作。
  - 创意类内容（用户希望每次不同）。
- 实施：缓存 key 中包含 Agent ID、知识库版本、权限范围；设置较高的相似度阈值，并做实体校验；监控缓存命中后的差评率。

### 16. 【专家】一次 Agent 请求要调多次模型，怎么做并行化？
**答案：**
- 画出依赖图：找出哪些调用相互独立。例如安全审核、意图识别、query 改写可以同时进行；多路检索可以并行；多个子问题可以并行回答；主回答和追问生成可以部分并行。
- 并行方式：用 errgroup 加 context 并发调用，每个调用设置独立的超时；一个可选的调用失败不影响其他调用。
- 投机执行：在意图识别结果出来之前，先按最可能的意图启动检索；如果猜错就丢弃。用少量额外成本换取延迟降低。
- 流水线：主回答流式输出的同时，用已生成的内容开始准备追问和挂载组件。
- 注意：并发调用会增加瞬时 QPS，要控制并发上限，防止触发限流；用 trace 验证并行化后关键路径的耗时确实缩短了。

### 17. 前置数据（挂载配置、知识库配置）加载慢，怎么优化？
**答案：**
- 定位：用 pprof 和 trace 看时间花在哪里（查库次数、单次查询耗时、协程调度、序列化）。
- 批量查询：把"每个挂载项查一次库"改成 `WHERE id IN (...)` 一次查出，消除 N+1 查询；IN 列表太长时分批查询。
- 缓存：Agent 配置这类读多写少的数据，使用本地缓存加 Redis，配置变更时主动失效缓存。
- 并行：相互独立的数据源并行加载。
- 按需加载：只加载本次请求会用到的配置。
- 数据结构：预先计算并冗余存储常用的组合结果。
- 上线方式：新老逻辑并存（v1 和 v2 两个接口），先灰度，对比数据一致后再切换。
- 可举例：agent-mount 原来对每个挂载项起一个协程查 MySQL，改为 WHERE IN 批量查询。用 hey 压测（100 个请求、并发 10）和 pprof 分析，平均耗时从 3.124s 降到 98.43ms，QPS 从 3.09 提升到 50.6，协程数从 229 降到 160，内存分配次数从 359 降到 185；回归了 10 类挂载组件，数据一致。

### 18. 【高频】Go 服务中，一个请求内并发查多个下游，用 errgroup 怎么写？超时怎么控制？
**答案：**
```go
ctx, cancel := context.WithTimeout(r.Context(), 800*time.Millisecond)
defer cancel()
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(8) // 限制最大并发数
var user *User
var conf *Conf
g.Go(func() (err error) { user, err = getUser(ctx, uid); return })
g.Go(func() (err error) { conf, err = getConf(ctx, appID); return })
if err := g.Wait(); err != nil { /* 任何一个出错，ctx 被取消，其他调用也会尽快返回 */ }
```
- 每个 goroutine 写入各自的变量，不需要加锁；写入同一个切片时，按下标写入。
- 超时：整体超时用 WithTimeout；单个下游的超时可以在内部再套一层更短的 WithTimeout。
- 可选的下游：失败不应影响整体时，在函数内部吞掉错误并记录日志、返回 nil，使用默认值降级。
- 下游调用必须使用传入的 ctx，取消才能生效。

### 19. 【高频】每个挂载项起一个协程查库，有什么问题？怎么改？
**答案：**
- 问题：
  - 查库次数随挂载项数量线性增长（N+1 问题），挂载项多的 Agent 一个请求就要查上百次。
  - 协程和数据库连接数暴涨，连接池容易被打满，导致排队，其他请求也变慢。
  - 每个协程和每次查询都有内存分配，GC 压力大。
  - 并发查询看似快，但受连接池和数据库的限制，长尾延迟反而更高。
- 改法：
  - 收集所有需要查询的 ID，用 `WHERE id IN (...)` 一次批量查出，再在内存中按 ID 组装（用 map 索引）。
  - ID 很多时分批查询（如每批 500 个），控制单条 SQL 的大小。
  - 结合缓存减少查库。
- 可举例：改造后 agent-mount 的平均耗时下降了约 30 倍。影响面是 238,645 个手动挂载了商品的智能体，其中挂载数在 20 个以上的有 3,331 个。

## 稳定性

### 20. 【高频】模型接口不稳定时，重试策略怎么设计？哪些错误不能重试？
**答案：**
- 可以重试：网络错误、超时、429（限流）、5xx（服务端错误）、模型过载。
- 不能重试：400（参数错误、上下文超长）、401/403（鉴权失败）、内容审核拦截、业务逻辑错误。重试这些错误只会浪费资源。
- 策略：
  - 指数退避加随机抖动（如 200ms、400ms、800ms），防止大量请求同时重试。
  - 遇到 429 时，按 Retry-After 头指定的时间等待。
  - 限制最大重试次数（2 到 3 次）和总耗时预算。
  - 只在一个层级重试，避免多层叠加导致重试次数指数级放大。
  - 重试时可以切换到备用模型或供应商。
- 对有副作用的调用，确保幂等后再重试。

### 21. 流式请求中途失败，能重试吗？用户看到一半的内容怎么办？
**答案：**
- 难点：用户已经看到了部分内容，再重新生成，新内容和已展示的内容可能不一致。
- 处理方式：
  - 首 token 之前失败：可以透明重试，用户无感知。
  - 生成到一半失败：
    - 方案一：通知前端，显示"生成中断"，保留已生成的部分，提供"重新生成"按钮由用户触发。这是最常用的做法。
    - 方案二：把已生成的内容作为前缀，让模型续写（部分模型支持 assistant 消息预填充），可以基本保持连贯。
    - 方案三：清空已展示的内容，从头重新生成（体验较差）。
- 对话历史：中断的消息标记为不完整，不要作为正常回复写入历史，避免后续出现消息序列问题。
- 支持断点续传的协议（Last-Event-ID）可以应对网络断开，但无法解决模型侧的失败。

### 22. 【专家】Agent 服务的熔断、降级预案有哪些？
**答案：**
- 熔断：对每个下游（模型、检索、工具、挂载服务）设置熔断器；错误率或延迟超过阈值时打开熔断，快速失败；一段时间后半开，放少量请求试探，成功就恢复。
- 降级预案（按下游分别准备）：
  - 主模型不可用：切换到备用模型，再不行切换到小模型，最后返回兜底文案。
  - 检索不可用：不使用知识库直接回答（标注"可能不准确"），或者只用 FAQ。
  - 工具不可用：告诉用户该功能暂时不可用，其他功能照常。
  - 挂载、追问等非核心功能：直接跳过，不影响主回答。
  - 流量过载：限流、排队，优先保证核心用户和核心场景。
- 开关：所有降级都做成可以动态切换的配置开关，支持手动和自动触发。
- 演练：定期做故障演练，验证预案确实有效。

### 23. 下游配置服务（如千帆 Assistant）数据不一致时，怎么做自愈？
**答案：**
- 识别：调用下游时识别明确表示"数据不存在或不一致"的错误码，与临时错误区分开。
- 自愈：
  - 根据本地的权威数据（自己的数据库）重新同步到下游，例如更新失败且返回"不存在"时，改为重新创建。
  - 重建后更新本地保存的关联 ID。
- 兜底：
  - 自愈也失败时，记录日志并告警，进入待修复队列。
  - 定期对账任务：扫描本地数据和下游数据的差异，批量修复。
- 风险控制：重建要幂等，防止重复创建；记录自愈的次数，异常增多时告警，说明可能存在系统性问题。
- 可举例：约 240 个智能体上线后点击提问会跳转到"已下线"页面。定位到 shendeng 调用千帆 `/v2/assistants/update` 时返回 5002（Assistant 不存在），原因是这些智能体的 Assistant 是在线下环境创建的。在 pipe_app_save 中识别 5002 后改为调用 CreateAssistant 重建；在线下把 assistant_id 改成错误值复现了问题，并验证了修复。

### 24. 老协议、老版本客户端的请求导致 panic，怎么处理？
**答案：**
- 止损：
  - 定位到是老协议的请求后，在入口识别老协议，直接返回明确的错误码（拒绝），不再进入会 panic 的逻辑。
  - 在出问题的函数入口对可能为空的字段做校验，返回错误而不是 panic。
- 兜底：HTTP 处理链路有 recover 中间件，单个请求的 panic 不会导致进程崩溃，并把堆栈写入日志、触发告警。
- 根因：老协议缺少新逻辑依赖的字段（如 EventWriter 为空）。新代码要对协议版本做兼容判断。
- 长期：统计老协议流量，推动调用方升级；设定下线时间；用协议版本号区分处理逻辑。
- 可举例：646 的 `/bot/conversation` 在处理老协议请求时，在 BuildAgentFile 中 panic 返回 500。根据 panic_trace 和请求日志复现后，直接拒绝老协议流量，并在函数入口对 EventWriter 做空值判断。

### 25. 【高频】Go 服务中 panic 怎么兜底？goroutine 里的 panic 能被外层 recover 吗？
**答案：**
- HTTP 和 RPC 入口：使用 recover 中间件（如 gin.Recovery），捕获 panic 后返回 500，打印堆栈并告警，进程不会退出。
- goroutine 里的 panic 不能被外层 recover：recover 只对当前 goroutine 有效，子 goroutine 中未捕获的 panic 会导致整个进程崩溃。
- 所以，每个新启动的 goroutine 都要自己加 recover，最好封装一个统一的启动函数：
```go
func SafeGo(fn func()) {
    go func() {
        defer func() {
            if r := recover(); r != nil {
                log.Errorf("panic: %v\n%s", r, debug.Stack())
            }
        }()
        fn()
    }()
}
```
- 注意：
  - recover 必须在 defer 函数中直接调用才有效。
  - 有些错误无法 recover，如并发读写 map 导致的 fatal error、栈溢出。
  - panic 只用于不可恢复的程序错误，业务错误要用 error 返回。

### 26. 长耗时任务（视频生成、批量评估）怎么设计异步任务和状态轮询？
**答案：**
- 提交：接口只负责创建任务记录（状态为待处理），立即返回 task_id，不同步等待结果。
- 执行：后台 Worker 处理任务：
  - 从数据库轮询待处理的任务，或者消费消息队列。
  - 调用下游的异步服务，记录下游任务 ID。
  - 下游完成后通过回调或轮询获取结果，更新任务状态。
- 状态：待处理、处理中、成功、失败（带原因）、部分成功；记录进度，如已完成的 case 数和总数。
- 获取结果：客户端轮询状态接口，或者服务端推送（webhook、消息通知、群通知）。
- 可靠性：失败重试、超时检测（处理中状态卡太久就判定为失败或重新调度）、防止重复处理、记录失败原因。
- 可举例：端到端评估的视频生产由 VideoProduceWorker 轮询待生产的任务，先把状态改为生产中，再解析 BOS 上的 Excel 数据集，逐条调用视频生产，单个 case 失败自动重试一次，最后发送通知；视频生产完成后通过回调接口推进状态。

### 27. 【专家】异步任务 Worker 怎么防止重复处理？任务失败怎么重试和告警？
**答案：**
- 防止重复处理（多个 Worker 实例同时运行时）：
  - 抢占式更新：`UPDATE task SET status=处理中, worker=x WHERE id=? AND status=待处理`，影响行数为 1 才算抢到任务，利用数据库行锁实现互斥。
  - 或者用 `SELECT ... FOR UPDATE SKIP LOCKED` 批量领取任务。
  - 或者用 Redis 分布式锁，或者消息队列按分区让每条消息只被一个消费者处理。
  - 处理逻辑本身要幂等（重复执行也不会有副作用）。
- 卡死的任务：记录开始时间和心跳，处理中状态超时未更新的，判定 Worker 已挂掉，重置为待处理或失败。
- 重试：
  - 区分可重试的错误和不可重试的错误。
  - 记录重试次数，设置上限，使用退避间隔。
  - 超过上限后进入失败状态（死信）。
  - 保留每次重试的失败信息（如原始的下游任务 ID 和失败原因），方便追溯。
- 告警：失败率、积压量、处理时长超过阈值时告警；失败的任务发送通知（如群消息）。

### 28. 回调（callback）接口怎么保证可靠（幂等、重试、签名校验）？
**答案：**
- 安全：
  - 签名校验：调用方用约定的密钥对请求体加时间戳签名，接收方校验，防止伪造。
  - 校验时间戳，防止重放攻击。
  - 可以配合 IP 白名单。
- 幂等：同一个事件可能被重复回调，用事件 ID 或业务唯一键（如 task_id 加事件类型）去重；状态更新使用条件更新（只能从特定状态转移，不能倒退）。
- 快速响应：回调接口收到后先记录、校验，然后立即返回成功；耗时的处理异步进行，避免调用方超时后重试。
- 调用方的重试：失败时按退避策略重试，有最大次数限制；接收方返回明确的成功或失败。
- 兜底：回调可能丢失，接收方要有主动轮询查询状态的机制（定时对账）。

### 29. 大文件（十几 GB）上传怎么做？分片大小、并发数怎么调？
**答案：**
- 分片上传：
  - 客户端把文件切成固定大小的分片，先调用初始化接口获取 upload_id。
  - 并发上传各个分片（可以直接传到对象存储，如 BOS 的分片上传接口，不经过业务服务器）。
  - 全部完成后调用合并接口。
  - 用 MD5 或 CRC 校验完整性。
- 断点续传：记录已上传成功的分片，失败或中断后只重传缺失的部分。
- 调优：
  - 分片太小：请求数量多，每个请求的固定开销占比大。
  - 分片太大：单个分片失败后重传的代价大，内存占用高。
  - 并发不是越高越好：受客户端带宽、服务端和网关的限制，并发过高会造成拥塞、重传，反而变慢。
  - 需要在实际网络环境下压测几组参数，找到最优值。
- 可举例：爱速搭平台上传 15GB 文件的压测结果：分片 5MB、并发 12 用时 33 分钟；50MB、并发 12 用时 25 分钟（最优）；90MB、并发 12 超过 40 分钟；50MB、并发 18 用时 32 分钟。

## 平台化

### 30. 【高频】智能体平台的配置数据（人设、插件、知识库）存在哪？怎么缓存？
**答案：**
- 存储：MySQL 作为权威数据源，按功能分表（智能体主表、Prompt 模板表、插件挂载表、知识库关联表、挂载组件表），按版本管理草稿和线上版本。
- 缓存：
  - 第一级是进程内本地缓存（热门 Agent，TTL 较短）。
  - 第二级是 Redis（序列化后的完整运行时配置）。
  - 未命中时回源数据库并回填，用 singleflight 防止并发回源。
- 失效：Agent 发布或修改时，主动删除 Redis 中的缓存，并通过消息通知各实例清理本地缓存；同时设置 TTL 兜底。
- 一致性：配置的更新频率很低，可以接受秒级的不一致；但下线、删除这类关键状态要及时生效。
- 下游同步：配置还需要同步到依赖的系统（如千帆 Assistant），要处理同步失败的情况。

### 31. 智能体上线、下线、预览、正式环境怎么隔离？
**答案：**
- 配置版本：区分草稿（编辑中）、预览（创作者调试使用）、线上（已发布）。预览读草稿配置，线上只读已发布的版本，互不影响。
- 请求标识：通过参数区分环境（如 env=1 表示预览、env=0 表示线上），服务端据此读取对应的配置，并在打点中区分，统计时排除预览流量。
- 状态控制：Agent 有上线、下线、审核中、私有等状态；分发入口和对话接口都要校验状态，已下线的 Agent 不能被分发和对话。私有的、非本人创作的 Agent 要从"最近使用"等列表中过滤掉。
- 数据隔离：预览产生的对话、线索数据和线上数据分开存储或打上标记。
- 发布流程：草稿 → 审核 → 发布（生成线上版本快照）→ 刷新缓存 → 同步下游系统。

### 32. 预览环境和线上环境，组件能力为什么要有差异？怎么控制？
**答案：**
- 差异的原因：
  - 有些组件涉及真实的交易、线索、计费，预览时不能产生真实的业务数据（如提交线索、下单）。
  - 有些组件依赖线上才有的数据（商品库存、投放数据）。
  - 预览环境要防止被滥用（绕过审核直接对外使用）。
- 控制：
  - 挂载服务根据环境标识过滤组件：预览环境只返回允许预览的组件类型，或者返回 mock 数据。
  - 维护组件和环境的白名单配置。
  - 在前端提示"预览模式下部分功能不可用"。
- 可举例：在 agent-mount 中补充了预览环境下限制部分组件的逻辑，涉及 `/agent/mount/info/get` 接口，按上线 checklist 发布。

### 33. 【专家】Agent 平台的多租户隔离怎么做（数据、配额、模型资源）？
**答案：**
- 数据隔离：
  - 所有业务数据带 tenant_id，查询时由服务端强制注入过滤条件。
  - 大租户可以使用独立的库、表、collection；知识库和记忆按租户分区。
  - 缓存 key 带租户前缀；日志和导出数据按租户隔离权限。
- 配额：按租户设置 QPS、并发、每日 token、存储空间、Agent 数量上限；超额时限流或降级，并告警。
- 模型资源：
  - 共享资源池：用公平调度和优先级防止某个租户占满资源（每个租户有并发上限）。
  - 大客户使用独享的推理资源或独立的 API 配额，保证 SLA。
- 鉴权：每个租户有独立的 AK/SK，按租户授权可以使用的能力和模型。
- 计费：按租户统计用量。
- 故障隔离：某个租户的异常流量不能影响其他租户（限流、熔断按租户维度设置）。

### 34. 对客售卖的 Agent PaaS，AK/SK 鉴权怎么设计？
**答案：**
- 签发：客户开通时，平台生成 AK（Access Key ID，公开标识）和 SK（Secret Key，只在创建时展示一次）；服务端加密存储 SK。
- 请求签名：
  - 客户端用 SK 对请求的关键部分（方法、路径、参数、请求体哈希、时间戳、随机数）计算 HMAC-SHA256 签名，和 AK、时间戳一起放在请求头中。
  - 服务端根据 AK 查出 SK，重新计算签名并比对；校验时间戳在允许的窗口内，随机数没有用过（防重放）。
  - SK 本身不在网络上传输。
- 也可以用 SK 换取短期 token，后续请求带 token（如数字人 SDK 的场景）。
- 权限：AK 关联客户、可用的能力和资源（Agent、形象），按权限范围和场景授权。
- 管理：支持多组 AK/SK 并存，方便轮换；可以禁用和删除；调用按 AK 计费、限流、审计。
- 可举例：PaaS 客户同步时调用架构服务的 `/dh/agent/ak_profile/create` 生成 AK，平台保存 sk 和 token；评审后的补充项包括给 AK 增加场景字段。

### 35. 【高频】PaaS 交付订单的状态机怎么设计？状态由谁推进？
**答案：**
- 状态：待交付 → 审核中（素材审核）→ 制作中（形象底板视频制作、声音克隆）→ 待部署 → 部署中 → 已交付；异常分支包括审核驳回、部署失败、已终止、已缩容。
- 原则：
  - 每个状态转移都有明确的触发事件和前置条件，在代码中集中定义允许的转移，不允许随意跳转。
  - 状态只在少数几个地方推进，便于保证一致性和排查问题。
- 推进者：
  - 用户和客户的操作：提交素材、触发部署、缩容。
  - 审核人员：审核通过或驳回。
  - 外部系统的回调：制作完成、部署完成。
  - 定时任务：巡检兜底，修复卡住的状态。
- 记录：每次状态变化记录日志（操作人、时间、前后状态、原因），对外提供状态查询接口。
- 可举例：对客 PaaS 中，delivery 表的 stage 只在三处显式推进：status_query（客户在开播前调用，按需触发部署）、bind_cmeta 回调、缩容；另有 RecomputeDelivery 定时任务做兜底巡检。

### 36. 【专家】多个子系统（审核、制作、部署）各有自己的状态，总状态怎么保证一致？
**答案：**
- 唯一数据源：每个子状态以各自的源表为准（形象表、声音表、审核记录表），总状态不重复保存子状态的副本，或者只把它当作缓存。
- 聚合计算：需要展示时实时聚合，如审核状态不单独落表，按（交付单 ID，素材 key）取最新的一条审核记录，计算出待提交、审核中、驳回或通过。
- 显式推进加兜底巡检：
  - 总状态只在少数明确的事件点推进。
  - 定时任务定期按子状态重新计算总状态，修复因回调丢失、异常中断导致的不一致（reconcile 思想）。
- 幂等和条件更新：状态更新带前置状态条件，防止并发时回退或覆盖。
- 外部依赖确认：部署是否完成以外部系统的实际状态为准（如 agent 信息中 warmup_num 大于 0）。
- 可举例：对客 PaaS 中，审核状态实时聚合，形象和声音状态由各自的源表负责；有 RecomputeDelivery 定时巡检；部署状态通过 agent/info 的 warmup_num 确认。

### 37. 资源池（预热实例、路数）怎么管理？扩缩容怎么触发？
**答案：**
- 资源池：数字人、Agent 实例需要预热（加载形象、模型）才能低延迟地响应，因此要维护一批已经预热好的实例，按"路数"（同时可服务的会话数）分配给客户。
- 管理：
  - 记录每个实例或 Agent 的状态（待部署、部署中、可用、已缩容）、所属客户、有效期、使用量。
  - 区分公共资源池（共享、按需分配）和客户专属资源。
  - 定期清理 QA 测试账号占用、已过期的资源。
- 扩缩容触发：
  - 客户购买或续费时扩容，到期或退订时缩容（把路数设为 0）。
  - 按使用率自动扩缩：并发使用率高时扩容，长期空闲时回收。
  - 活动前提前预热扩容。
- 确认：扩缩容是异步的，要轮询确认部署结果（如 warmup_num 大于 0 才算部署成功），失败时重试并告警。
- 可举例：对客 PaaS 中，缩容接口调用 bind_cmeta 把路数设为 0；做过 PaaS 资源池梳理，统计每个 agent 的状态和有效时长、QA 账号占用、待预热的数字人清单。

### 38. 低代码平台（amis、爱速搭）快速搭后台有什么优缺点？
**答案：**
- 优点：
  - 用 JSON 配置描述页面，CRUD 列表、表单、详情、向导等常见后台页面能很快搭好。
  - 后端只需提供标准的接口，前端人力投入少。
  - 修改方便，适合快速迭代的运营后台（O 端）。
- 缺点：
  - 复杂交互受限于组件能力（如自定义播放器、快捷键、拖拽时画面跟帧），需要用 custom 组件写原生代码来绕过。
  - 复杂的表单联动和嵌套字段映射比较繁琐。
  - 调试不如普通前端方便；平台的权限、环境配置（如只支持域名和 IP）有约束。
  - 大文件上传等性能问题需要调优。
- 适用：内部运营和管理后台；对外的产品界面建议正常开发。
- 可举例：数字人 O 端平台（形象制作、质检、声音克隆、端到端评估）基于爱速搭搭建；质检播放器的优化需求用 custom 渲染器加原生 video 元素实现了全部 P0 功能，因为自带的 video 组件不支持空格键控制和拖拽时画面跟帧。

### 39. Agent 平台的灰度发布和配置回滚怎么做？
**答案：**
- 代码灰度：按实例或集群逐步发布（先分级环境、小流量集群，再全量）；观察错误率、延迟、核心指标；有问题立即回滚。
- 功能灰度：
  - 用开关和配置控制新功能，按用户、Agent、流量比例逐步放量。
  - 新老逻辑并存（如 v1 和 v2 两个接口），对比两者的结果一致后再切换。
  - 也可以先上线代码但不生效（提前 return），确认无误后再打开。
- 配置和 Prompt 灰度：配置中心支持版本管理和分批生效，可以一键回滚到上一个版本。
- 跨服务的发布：确定发布顺序（被依赖的服务先发），每一步都可以单独回滚，新字段要兼容旧版本。
- 每次发布都有上线 checklist：变更内容、验证方法、回滚方案、观察指标。
- 可举例：RFQ 链路改动涉及 5 个服务，按 704 → 676 → 722 → 646 的顺序发布；对客 PaaS 按架构后端 → pipeline 后端 → pipeline 前端 → paas 的顺序上线。

### 40. 【专家】如何建设 Agent 平台的 SLA 体系（可用性、延迟、成功率）？
**答案：**
- 定义 SLI（衡量指标）：
  - 可用性：成功请求数除以总请求数（排除用户自身的错误）。
  - 延迟：首 token 的 P50、P95、P99，总耗时。
  - 质量：任务成功率、回答合规率。
  - 按接口、场景、租户分别计算。
- 设定 SLO（目标）：如可用性 99.9%、首 token P95 小于某个值；按业务重要性分级设置。
- 错误预算：1 减去 SLO，就是允许出错的额度。预算用完时冻结高风险的变更，优先做稳定性工作。
- 依赖治理：梳理所有依赖（模型、检索、数据库、缓存、工具），每个依赖的 SLA 都要能支撑整体目标；没有达标的依赖要做冗余、降级或熔断。
- 监控和告警：基于 SLI 的实时大盘；按错误预算的消耗速度告警；有值班和应急响应流程。
- 复盘：每次故障都要复盘，跟踪改进项；定期做容量规划和故障演练。
- 对外 SLA：对客的 PaaS 要在合同中约定 SLA 和赔偿条款，对内的 SLO 要比对外的 SLA 更严格。
